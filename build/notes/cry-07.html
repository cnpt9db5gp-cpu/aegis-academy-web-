TLS and Secure Channels

Summary

TLS is where everything in this course gets used at once: certificates to authenticate, DH for
forward secrecy, AEAD for confidentiality and integrity, and careful protocol design to avoid the
classic downgrades.

The lecture's framing: TLS is not "encryption". It is an authenticated key exchange that
happens to use encryption. Get the authentication wrong and the rest is worthless — cry-05's
man in the middle is the failure mode TLS exists to prevent.

What TLS actually provides

  AUTHENTICATION     of the server, via a certificate chain
  CONFIDENTIALITY    via an AEAD cipher
  INTEGRITY          via the AEAD tag (not a separate MAC)
  FORWARD SECRECY    via ephemeral (EC)DHE, in TLS 1.3 always
  CA-CHANNEL ENCRYPTION  0-RTT is NOT forward secret. See below.

  WHAT IT DOES NOT PROVIDE:
    - that the server is honest (it could serve a phishing page)
    - that the CONTENT is correct (a signed malicious update is valid TLS)
    - privacy from traffic analysis (IP, SNI, timing, size)
    - protection against an endpoint that has been compromised
    - anything at all before the certificate is validated

The TLS 1.3 handshake

  Client                                              Server
    |                                                    |
    |--- ClientHello ---------------------------------->|
    |    key_share (X25519)                             |
    |    supported_versions: 1.3                        |
    |    cipher_suites: TLS_AES_128_GCM_SHA256          |
    |    signature_algorithms: rsa_pss, ed25519         |
    |                                                    |
    |<-- ServerHello ------------------------------------|
    |     key_share (X25519)                            |
    |     cipher: TLS_AES_128_GCM_SHA256                |
    |                                                    |
    |<-- {EncryptedExtensions} --------------------------|
    |<-- {Certificate} ----------------------------------|
    |     the server's certificate chain                 |
    |<-- {CertificateVerify} ----------------------------|
    |     signature over the transcript                 |
    |<-- {Finished} -------------------------------------|
    |                                                    |
    |    both sides compute:                             |
    |      handshake_secret = HKDF(ECDHE_shared)        |
    |      traffic keys   = HKDF(handshake_secret)     |
    |      session keys   = HKDF(handshake_secret)      |
    |      -> traffic is now encrypted, from here       |
    |                                                    |
    |--- {Finished} ----------------------------------->|
    |                                                    |
    |    application data (encrypted)                   |

Note what is missing: there is no ServerKeyExchange in TLS 1.3
(unlike 1.2), because the server's key share is already in the
ServerHello. The whole thing is two round trips, then encryption.

Note also what makes it safe: the CertificateVerify signature is
over the transcript hash of the entire handshake so far. That binds
the key exchange to the certificate, so an attacker cannot substitute
the server's key_share without invalidating the signature.

The 0-RTT problem

  TLS 1.3 lets the client send application data in its FIRST flight
  (0-RTT), for things like a page reload.

  0-RTT DATA IS NOT FORWARD SECRET.
    The early data is encrypted to the server's long-term key and
    recorded. If that key is compromised later, the recorded 0-RTT is
    decrypted.

  AND 0-RTT IS REPLAYABLE.
    There is no way to know it has been seen. An attacker can replay it.

  THEREFORE:
    0-RTT is acceptable for GET and other idempotent requests.
    0-RTT for a POST /transfer is a critical finding.

  How to check: does the client use 0-RTT, and what does it send early?
  WireGuard, iCloud, and some CDNs use it aggressively; some of those
  uses are inappropriate.

Certificates

  A CERTIFICATE BINDS a public key to a name.

    subject:      CN=example.com
    issuer:       CN=Example CA, O=Example Inc, C=US
    validity:     notBefore .. notAfter
    subjectAltName:  DNS:example.com, DNS:*.example.com, IP:1.2.3.4
    basicConstraints: CA:FALSE
    keyUsage:      digitalSignature, keyEncipherment
    extendedKeyUsage: serverAuth
    publicKey:     the key itself
    signature:     the issuer's signature over the TBSCertificate

  VALIDATION, all of it:
    1. parse strictly (DER, no trailing bytes, no malformed extensions)
    2. chain to a trusted root in the app's trust store
    3. each issuer's CA:TRUE and keyCertSign
    4. notBefore/notAfter, at the current time
    5. hostname against subjectAltName (NEVER against CN, never against
       a suffix match)
    6. keyUsage and extendedKeyUsage fit the purpose
    7. path length constraints
    8. revocation: CRL or OCSP, and a REVOCATION FAILURE IS A FAILURE
    9. verify the signature
   10. check the signature is valid and the transcript matches

The hostname check, which is where people cut corners

  WRONG:  endswith(".example.com")    -> evil-example.com passes
  WRONG:  endswith("example.com")     -> notexample.com passes
  WRONG:  == the CN field             -> CN is deprecated, and CA:B? 
                                          CERTs carry no SAN
  WRONG:  a wildcard anywhere         -> *.com is never valid
  RIGHT:  exact match, or a wildcard
          as the LEFTMOST label only:
            *.example.com   matches  a.example.com
            *.example.com   matches  www.example.com
            *.example.com   does NOT match example.com
            *.example.com   does NOT match a.b.example.com
            (*.com is invalid by RFC 6125)

Downgrade and version negotiation

  THE ATTACK: convince one side that the other cannot do TLS 1.3.
  Then the 1.2 rules (weaker, more cipher suites, sometimes no PFS)
  apply.

  DEFENCES BUILT INTO THE PROTOCOL:
    - TLS 1.3 puts a marker in the ServerHello random bytes
      (DOWNGRD\x01) so the CLIENT can detect that the server was told
      to downgrade
    - TLS 1.3 has no separate version negotiation field; it uses
      supported_versions in an extension
    - all signatures cover the transcript, so a downgrade changes the
      hash and invalidates the signature

  WHAT TO CHECK IN YOUR OWN DEPLOYMENT:
    - is version pinned, or is it "the best the client offers"?
    - is a weak suite still in the list? (one entry is enough)
    - is there a fallback to plaintext for the initial request?
      (HSTS is the answer, and `includeSubDomains` and preload matter)

# check what a real endpoint will negotiate, and with what
for v in -tls1 -tls1_1 -tls1_2 -tls1_3; do
  r=$(echo | timeout 5 openssl s_client $v -connect example.com:443 -servername example.com 2>&1 \
      | grep -E "^ *(New|.*Protocol|.*Cipher) *:" | tr -s ' ' | tr '\n' ' ')
  printf "  %-10s %s\n" "$v" "${r:-refused}"
done

Session resumption and 0-RTT

  SESSION RESUMPTION (TLS 1.3, PSK)
    the server issues a session ticket (an encrypted blob containing
    the resumption PSK and a timestamp)
    the client stores it and presents it on the next connection
    the handshake is shortened

  THE FORWARD SECRECY QUESTION:
    does the ticket contain the actual traffic keys, or just an
    identifier?
      - if it contains the keys, then resuming after a key compromise
        restores access to that session. Old tickets should be
        short-lived and rotated.
      - "anti-replay" requires single-use tickets, which costs state

  THE PRACTICAL POSTURE:
    - short ticket lifetimes (hours, not weeks)
    - rotate the ticket key
    - 0-RTT only for idempotent operations
    - never 0-RTT for anything that changes state

What TLS does not do, and what you have to add

  CERTIFICATE PINNING
    Pros: resists a compromised CA (the 2018 events), resists many
          interception proxies
    Cons: rotation is painful, a mistake bricks the client, and an
          attacker with one app update can bypass it
    Only pin in a context you control (an app you ship), never in a
    browser.

  HSTS + preload
    Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
    eliminates the "first request over HTTP" downgrade entirely.
    The preload list is the hard part, and it is what you want.

  SUBRESOURCE INTEGRITY
    an integrity attribute on <script> and <link> pins a specific
    hash. Works today, in every browser, with no key management.

  OPAQUE / ECH
    hides the server name from a passive observer. Coming, and it
    changes the threat model for SSRF-to-metadata (see ps-05).

Terminology

Term Meaning
TLS An authenticated key exchange that carries encrypted data
Certificate chain Leaf → intermediate(s) → root
Trust anchor The root in the verifier's trust store
SNI Server Name Indication; sent in cleartext, pre-ECH
CertificateVerify Signature over the handshake transcript
Transcript hash Running hash of every handshake message
0-RTT / early data Client data before the server is authenticated
Session ticket / PSK Resumption credential; may contain traffic keys
Downgrade attack Forcing a weaker version
HSTS Header forcing HTTPS, and preloading it
Certificate pinning Pinning a key or SPKI in a client you control
SRI Subresource Integrity; a hash in the markup
ECH Encrypted Client Hello; hides SNI
AEAD in TLS AES-GCM or ChaCha20-Poly1305; no separate MAC
OCSP stapling Server-supplied revocation status
ALPN Application-Layer Protocol Negotiation

# --- 1. read a real handshake ---
{
  echo "=== a live handshake, annotated ==="
  echo | timeout 8 openssl s_client -connect example.com:443 -servername example.com \
    -showcerts 2>/dev/null | grep -E "^(New|Server public key|Negotiated TLS1.3 group|Verify return code)" \
    | sed 's/^/  /'
  echo
  echo "  'Server Temp Key: X25519' or 'Negotiated TLS1.3 group: X25519'"
  echo "  ^ an ephemeral group. That is forward secrecy."
  echo "  'Verify return code: 0 (ok)' is the only acceptable answer."
} 2>&1 | tee 01-handshake.txt

# --- 2. the version matrix ---
{
  echo "=== what will it negotiate, at each forced version? ==="
  for v in "-tls1" "-tls1_1" "-tls1_2" "-tls1_3"; do
    out=$(echo | timeout 6 openssl s_client $v -connect example.com:443 -servername example.com 2>&1)
    proto=$(echo "$out" | grep -E "^New," | awk -F, '{print $2}')
    cipher=$(echo "$out" | grep -E "^Cipher *:" | head -1 | awk '{print $2}')
    if [ -z "$proto" ]; then
      printf "  %-9s REFUSED\n" "$v"
    else
      printf "  %-9s %-10s %s\n" "$v" "$proto" "$cipher"
    fi
  done
  echo
  echo "  TLS 1.0 and 1.1 being accepted is a finding: both are deprecated"
  echo "  (RFC 8996) and both lack modern cipher suites and AEAD."
  echo
  echo "=== cipher suite inventory from the server's own advertisement ==="
  echo | timeout 6 openssl s_client -connect example.com:443 -servername example.com \
    -cipher 'ALL:@SECLEVEL=0' 2>/dev/null | grep -A2 "Cipher list" | head -3 | sed 's/^/  /'
} 2>&1 | tee 02-versions.txt

# --- 3. the certificate, examined properly ---
python3 - <<'PY' 2>&1 | tee 03-cert.txt
import ssl, socket, subprocess, datetime

def grab(host, port=443):
    ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
    ctx.check_hostname = False
    ctx.verify_mode = ssl.CERT_NONE          # we are READING the cert, not trusting it
    with socket.create_connection((host, port), timeout=8) as s:
        with ctx.wrap_socket(s, server_hostname=host) as ss:
            pem = ss.getpeercert(binary_form=True)
            return pem, ss.version(), ss.cipher()

import subprocess, tempfile, os
for host in ("example.com", "github.com"):
    try:
        der, ver, cip = grab(host)
        f = tempfile.NamedTemporaryFile(delete=False, suffix=".der"); f.write(der); f.close()
        txt = subprocess.run(["openssl","x509","-inform","DER","-in",f.name,
                              "-noout","-text"], capture_output=True, text=True).stdout
        os.unlink(f.name)
        print(f"  === {host} ===")
        print(f"  negotiated  : {ver}  {cip[0]}")
        for line in txt.splitlines():
            s = line.strip()
            if s.startswith(("Issuer:","Not Before","Not After","Signature Algorithm","Public-Key","DNS:","CA:")):
                print(f"    {s[:90]}")
        print()
    except Exception as e:
        print(f"  {host}: {type(e).__name__}: {e}")
        print()
print("  WHAT TO READ:")
print("    Public-Key            2048+ (or EC). 1024 is a finding.")
print("    Signature Algorithm   sha1WithRSA = a finding (expired 2017)")
print("    DNS:                  the SAN. The CN alone is not enough.")
print("    Not After             days until expiry. < 30 = a finding.")
print("    CA:TRUE               on a LEAF certificate is a finding")
print("                            (it lets anyone issue for your name)")
PY

# --- 4. the hostname check, demonstrated ---
python3 - <<'PY' 2>&1 | tee 04-hostname.txt
def wildcard_match(host: str, pattern: str) -> bool:
    """RFC 6125 rules, correctly."""
    if not pattern.startswith("*."):
        return host.lower() == pattern.lower()
    suffix = pattern[1:]                 # ".example.com"
    if host.lower().endswith(suffix):
        left = host[: -len(suffix)]
        return left != "" and "." not in left      # exactly ONE label
    return False

cases = [
    ("a.example.com",      "*.example.com",  True,  "one label matches"),
    ("www.example.com",    "*.example.com",  True,  "one label matches"),
    ("example.com",        "*.example.com",  False, "the bare domain does NOT match"),
    ("a.b.example.com",    "*.example.com",  False, "two labels do NOT match"),
    ("evil-example.com",   "*.example.com",  False, "suffix trick rejected"),
    ("notexample.com",     "example.com",    False, "prefix trick rejected"),
    ("evil.com",           "*.com",          False, "wildcard TLD is invalid"),
    ("example.com.evil.tld","example.com",   False, "suffix trick rejected"),
    ("EXAMPLE.com",        "example.com",    True,  "case-insensitive"),
]
print(f"  {'host':<24} {'pattern':<18} {'match':<7} why")
print("  " + "-"*74)
for h, p, expect, why in cases:
    got = wildcard_match(h, p)
    flag = "ok " if got == expect else "***"
    print(f"  {h:<24} {p:<18} {str(got):<7} {why}")
print()
print("  THE TWO THAT MATTER MOST:")
print("    example.com vs *.example.com  -> False. Most libraries get this right;")
print("                                    many hand-rolled checks get it wrong.")
print("    a.b.example.com vs *.example.com -> False. A wildcard matches exactly")
print("                                    ONE label. '.*' style rules are wrong.")
PY
cat 04-hostname.txt

# --- 6. the posture, as a one-pager ---
cat > 07-posture.md <<'EOF'
# A defensible TLS posture

## Server
- [ ] TLS 1.3 only. If 1.2 is required, AEAD suites only.
- [ ] TLS 1.0/1.1 disabled (RFC 8996, deprecated since 2021)
- [ ] AEAD everywhere: TLS_AES_128_GCM_SHA256, TLS_AES_256_GCM_SHA384,
      TLS_CHACHA20_POLY1305_SHA256
- [ ] no CBC, no RC4, no 3DES, no export, no NULL
- [ ] forward cipher suite (ECDHE) only
- [ ] OCSP stapling on
- [ ] certificates: 2048+ RSA or ECDSA P-256/Ed25519, SHA-256+, SAN
      present, CA:FALSE, appropriate keyUsage, <= 90-day validity
- [ ] HSTS with max-age >= 31536000, includeSubDomains, preload
- [ ] session tickets: short-lived, rotated keys
- [ ] 0-RTT disabled, or restricted to idempotent operations

## Client
- [ ] verify the chain to a trust anchor you control
- [ ] verify the hostname against the SAN, with RFC 6125 rules
- [ ] enforce expiry and revocation; revocation FAILURE = REJECT
- [ ] no certificate warning overrides
- [ ] no `curl -k`, no `verify=False`, no `CERT_NONE`

## Application
- [ ] sensitive endpoints marked `Cache-Control: no-store`
- [ ] secrets never in URLs (they land in logs via Referer)
- [ ] subresource integrity on third-party scripts
- [ ] certificate pinning only in a client you ship, with a backup pin

## The three things that are findings on sight
1. TLS 1.0 or 1.1 accepted
2. certificate verification disabled anywhere
3. an RSA key exchange (no PFS) still enabled
EOF
cat 07-posture.md
