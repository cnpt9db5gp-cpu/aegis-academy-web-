Installing Kali: Live, Virtual Machine, or Dual Boot

Summary

Three ways to put Kali on a machine, in increasing order of commitment and decreasing order of
safety. Choose the virtual machine. The rest of this curriculum assumes a Kali VM you can
throw away and rebuild, because you will break it — probably in the very first privilege
escalation lab, by rm -rf-ing something you meant to rm.

Mode Survives reboot Risk to your main OS Right for
Live USB No None Trying Kali for the first time, or a machine you do not own
VM (recommended) Yes, as a file None Everything in this curriculum
Dual boot Yes Bootloader conflicts If you genuinely want Kali as a primary OS

The single decision that matters

Your Kali machine is the attacker and your lab VMs are the targets. Do not run intentionally
vulnerable services on Kali itself.

This is not superstition. The moment your practice target has a working shell as root, you have
a root shell on the box that also holds your SSH keys, your browser session, your API tokens and
your progress history. Learners have genuinely compromised their own attacker machine by
pivoting out of a lab exercise. Keep them separate. See docs/LAB-SETUP.md.

VirtualBox on Kali

Kali ships VirtualBox by default. If it is missing:

sudo apt update && sudo apt install virtualbox

A Kali VM you will actually want to use needs:

Resource Minimum Recommended
RAM 2048 MB 4096 MB
vCPU 2 4
Disk 40 GB 80 GB SSD
Video 128 MB, 3D off 256 MB
Network 2 adapters 2 adapters

Two network adapters, always. Adapter 1: NAT (for updates and package installs).
Adapter 2: Host-only (for your lab range — this is the isolated network your targets live on
and it is what makes scanning them legal and invisible to your real network).

Installer notes

  • Choose Graphical installer unless you want a typing exercise.
  • Pick your keyboard layout properly; a wrong layout makes ~ and backtick unreachable, and you
    will need those constantly in shell scripting.
  • Do not install a bootloader. You are a guest, not a dual-boot user.
  • Enable Shared clipboard and Shared folder — shared clipboard makes copying commands
    out of these notes into the VM trivial.
  • Consider a snapshot immediately after install.

Dual boot, honestly

Dual boot means Kali can write to the partition table. Kali's rolling nature means you will
occasionally have a kernel that will not boot, or a broken graphics driver, and the fix requires
booting something else. The recovery options are:

  • A live USB (you would need one)
  • A separate USB with chroot/grub-install tooling
  • Windows putting itself back in charge

That is a real cost, and it is why dual boot is last on the list. If you already run Linux and
understand partition management, it is a legitimate choice — just make a backup of anything you
cannot replace.

Live USB

Worth twenty minutes to see the environment before committing:

# from a Linux box, or use balenaEtcher on Windows/Mac
lsblk                                   # find the USB device - double check the size
sudo dd if=kali-linux-*.iso of=/dev/sdX bs=4M status=progress conv=fdatasync sync

Boot it and choose "Try Kali" (not "Install"). Live is ephemeral: nothing persists between boots
unless you create a persistence partition. Useful for a quick look, useless for this curriculum.

Terminology

Term Meaning
VM / guest The virtual machine; from Kali's perspective it thinks it is real hardware
Host The physical machine running the hypervisor
Hypervisor / VirtualBox The layer that presents fake hardware to the guest
NAT adapter Guest traffic appears to come from the host; outbound works, inbound does not
Host-only adapter A private network between host and guests, no internet, no route to your LAN
Bridged adapter Guest appears on your physical network — do not use this for lab targets
Snapshot A frozen copy of VM state; the cheapest undo in computing
vCPU / vRAM Virtual processor cores and virtual RAM
Shared folder A host directory exposed inside the guest (VirtualBox feature, needs Guest Additions)

Kali commands

# Is this a VM, and which hypervisor? (works on the guest)
sudo dmidecode -s system-manufacturer
systemd-detect-virt
hostnamectl | grep -i virtualization

# What network interfaces do I have, and which is which?
ip -br addr
ip route
nmcli device status 2>/dev/null | head

# Confirm the host-only interface exists (vboxnet0 typically)
ip -br addr | grep -E 'vboxnet|virbr'

# CPU / memory / disk reality check
lscpu | grep -E 'Model name|^CPU\(s\)'
free -h
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT
df -h /

# Disk usage of Kali's tool data - useful before you fill the disk with captures
du -sh /usr/share/* 2>/dev/null | sort -h | tail -15

Field lab

Objective: build the VM this curriculum assumes, and prove the two-adapter isolation works.

# On the HOST (your Kali laptop)
VBoxManage list vms
VBoxManage list hostonlyifs

# Create the isolated lab network if it does not exist
VBoxManage hostonlyif create
VBoxManage hostonlyif ipaddr vboxnet0 192.168.56.1

# Configure your Kali VM
VM=YourVMName
VBoxManage modifyvm $VM --memory 4096 --cpus 4
VBoxManage modifyvm $VM --nic1 nat --nic2 hostonly --hostonlyif2 vboxnet0
VBoxManage modifyvm $VM --clipboard-mode bidirectional
VBoxManage sharedfolder add $VM labshare --hostpath ~/aegis --name labshare

# Snapshot immediately
VBoxManage snapshot $VM take "pristine" --description "fresh install"

# INSIDE the guest, prove you are isolated from your real LAN
ip -br addr
ip route
# You should see vboxnet0 (192.168.56.x) and NOT your home router's subnet

The check that matters: inside the guest, ip route must show 192.168.56.0/24 via the
host-only adapter and nothing resembling your real home LAN (192.168.1.0/24 in my case). If
you see your home LAN, you have bridged something by accident — fix it before scanning anything.

Self-test

  1. Why must a lab VM have two network adapters rather than one?
  2. What is the specific danger of running intentionally vulnerable services on your Kali host?
  3. Your VM will not boot after a Kali update. Name two recovery options.
  4. Why does systemd-detect-virt matter during an engagement?
  5. When would host-only be wrong, and what would you use instead?
