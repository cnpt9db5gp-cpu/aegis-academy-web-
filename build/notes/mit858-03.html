User Authentication

Summary

Lecture 3 asks how you know who is talking. The answer has three independent parts, and most
systems get the third one wrong.

The lecture's own reading is telling: Your password doesn't matter.

Key ideas

  • Authentication (who) is separate from authorisation (what)
  • Three factors: something you know, something you have, something you are
  • Passwords fail because of reuse, phishing, and poor storage, not because they are weak math
  • Offline attackability is the property that matters: can the verifier be attacked at leisure?
    Password hashes: yes. Biometrics: yes. Online-attempt-limited factors: harder
  • Session handling is where authentication actually breaks
  • Second factors work when the second factor is not also phishable or replayable
  • Trust recovery and account recovery are security functions, not UX details

Why passwords fail

  1. Users reuse them across sites → one breach unlocks many
  2. They are phishable → a look-alike login page captures them
  3. They are typed on compromised machines → keyloggers
  4. They are stored poorly by services → offline cracking
  5. They are transmitted in the clear by legacy protocols → sniffing

Fixing the math (longer, random) helps far less than fixing 1-4.

Storage

Scheme Storage Offline attackable?
plaintext nothing trivially
salted fast hash (MD5/SHA1) one hash per user yes, extremely fast
unsalted fast hash one hash for all users yes, and rainbow tables work
bcrypt / scrypt / Argon2 slow hash + salt yes, but expensive
FIDO2 / passkey nothing to steal server-side no
client-side (age, PGP) nothing server-side no, until the client is compromised

The pivot: FIDO2 binds the credential to the origin, so a phishing site gets nothing.

Sessions are the real attack surface

Even with perfect authentication, session handling fails:

  • session IDs must be unguessable (128 bits of entropy, at minimum)
  • must be rotated on privilege change (session fixation)
  • must be tied to TLS and marked HttpOnly, Secure, SameSite
  • logout must invalidate server-side, not just clear a cookie
  • expiry must be absolute as well as idle
  • Watch for session IDs in URLs (they end up in logs and Referer headers)

Terminology

Term Meaning
Authentication Proving identity
Authorisation Deciding permissions
MFA / 2FA Multiple independent factors
Something you know/have/are The three factor categories
Offline attackable Verifier can be attacked without rate limits
Salt / pepper Per-user randomness preventing precomputation
bcrypt / Argon2 Deliberately slow password hashes
FIDO2 / passkey Public-key credential bound to the origin
Session fixation Attacker sets the session ID before login
Replay attack Reusing a captured authentication exchange

python3 - <<'PY'
import hashlib, time
pw = b"correct horse battery staple"
for algo in ("md5", "sha1", "sha256"):
    t = time.perf_counter()
    for _ in range(200_000):
        h = getattr(hashlib, algo)(pw).hexdigest()
    dt = (time.perf_counter() - t) / 200_000 * 1e6
    print(f"  {algo:<8} {h[:24]}...  {dt:.2f} us/hash -> ~{1/dt*1e6:,.0f} guesses/sec/core")
print()
print("  A GPU does ~1e10/sec. A 25-character random passphrase does not care.")
print("  A reused 8-character password is found in seconds. Length beats complexity.")

Field lab

Objective: measure offline attack rates against different hash schemes, and audit your own
session hygiene.

mkdir -p ~/aegis/labs/mit858-03 && cd ~/aegis/labs/mit858-03

# --- 1. how fast is a hash, really? ---
python3 - <<'PY' | tee 01-hash-speed.txt
import hashlib, time
pw = b"password123"
N = 300_000
print(f"  {'algorithm':<10}{'us/hash':>10}{'guesses/sec/core':>20}")
print("  " + "-"*40)
for algo in ("md5", "sha1", "sha256", "sha512"):
    fn = getattr(hashlib, algo)
    t = time.perf_counter()
    for i in range(N):
        fn(pw + str(i).encode()).hexdigest()
    dt = (time.perf_counter() - t) / N * 1e6
    print(f"  {algo:<10}{dt:>10.2f}{1/dt*1e6:>20,.0f}")
print()
print("  Fast hashes are designed for speed. Password storage must be the opposite.")
PY
cat 01-hash-speed.txt

# --- 2. a slow hash, compared ---
cat > slow.py <<'PY'
import time, os, hashlib, hmac
def argon_like(n=5000):
    """Stand-in for a deliberately slow KDF: iterated hashing."""
    t = time.perf_counter()
    for i in range(n):
        hashlib.sha256(b"pw" + str(i).encode()).hexdigest()
    return (time.perf_counter() - t) / n * 1e6
def bcrypt_like(n=5000):
    """Stand-in for scrypt/argon2: memory-hard iteration."""
    t = time.perf_counter()
    for i in range(n):
        p = hashlib.pbkdf2_hmac("sha256", b"pw" + str(i).encode(), b"salt", 10000)
    return (time.perf_counter() - t) / n * 1e6
print("  (real bcrypt/argon2 are slower still, and deliberately so)")
PY
python3 slow.py

# --- 3. salt: why it matters, demonstrated ---
python3 - <<'PY' | tee 02-salt.txt
import hashlib
pw = b"password123"
print("  NO SALT - every user with this password has the same hash:")
for user in ("alice", "bob", "carol"):
    print(f"    {user:<8} {hashlib.md5(pw).hexdigest()}")
print("  -> precompute once, look up all three. Rainbow tables exploit this.")
print()
print("  WITH SALT - one hash per user, all different:")
for user in ("alice", "bob", "carol"):
    salt = user.encode()               # stand-in; real salts are random
    print(f"    {user:<8} {hashlib.md5(salt + pw).hexdigest()}")
print("  -> the precomputation no longer applies. Crack each separately.")
PY
cat 02-salt.txt

# --- 4. session hygiene, on your own machine ---
{
  echo "=== cookie flags in your browser profile ==="
  for db in ~/.mozilla/firefox/*/cookies.sqlite ~/.config/google-chrome/*/Cookies; do
    [ -f "$db" ] || continue
    echo "  profile: $db"
    sqlite3 "$db" "SELECT name, host, isSecure, isHttpOnly FROM cookies LIMIT 10;" 2>/dev/null | sed 's/^/    /'
  done
  echo
  echo "=== what a session cookie SHOULD look like ==="
  cat <<'EOF'
    Set-Cookie: sessionid=<128 bits of entropy>; Secure; HttpOnly; SameSite=Lax; Path=/
    - Secure     : only over TLS
    - HttpOnly   : JavaScript cannot read it (kills XSS cookie theft)
    - SameSite   : limits CSRF
    - rotated    : a new value at login, and at every privilege change
    - absolute expiry as well as idle timeout
EOF
} 2>&1 | tee 03-sessions.txt

# --- 5. the design question, written out ---
cat > 04-design.md <<'EOF'
# Designing authentication for something real

## If you can use passkeys: use them
- Nothing phishable: the credential is bound to the origin
- Nothing to steal server-side: only a public key is stored
- No database breach gives a usable credential

## If you must use passwords
1. length over complexity (NIST guidance: allow at least 64 characters)
2. no composition rules (no "one uppercase, one symbol") - they push users to
   predictable substitutions, and do not meaningfully raise resistance
3. no forced rotation (it produces `Password1!`, `Password2!`)
4. check against a breach corpus at the service, not in the client's head
5. store with a memory-hard KDF: Argon2id, scrypt, or bcrypt with a high cost
6. rate-limit per account and per source, without account lockout
   (lockout is a denial-of-service against the user)
7. support a password manager by allowing paste and long input

## Second factor
- TOTP codes: phishable, replayable within the window
- push approval: bound to the request, safer
- FIDO2: the only factor that resists phishing by design

## Sessions
- 128+ bits of entropy, from a CSPRNG
- rotate on login and on every privilege change (fixes session fixation)
- invalidate server-side on logout
- absolute and idle expiry

## Recovery
Account recovery is an authentication path and must be as strong as login.
A "security question" whose answer is on your public social media is not a factor.
EOF
cat 04-design.md

Step 1 is the argument for length over complexity: a fast hash does millions of guesses per
second per core, so the only defence is either a slow KDF or a password long enough that guessing
is hopeless.
