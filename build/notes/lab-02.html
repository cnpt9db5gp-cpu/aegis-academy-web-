Deploying Metasploitable and Other Intentionally Vulnerable Hosts

Summary

Intentionally vulnerable targets are the only way to practise at a repeatable difficulty. This
note covers what to deploy, what each is for, and the rule that matters most: a vulnerable
host on a host-only network is the entire safety case for running it.

The framing: the deploy is not the lesson. The lesson is a
specific exercise against a specific target. A target you cannot name
the purpose of is a toy.

Companion to lab-01 (the platform) and lab-04 (the traffic and
the write-up).

The catalogue, by purpose

  TARGET                  WHAT IT IS FOR             BRIDGE TO
  ------------------------------------------------------------------------
  Metasploitable2 (VulnHub)
      Several VMs in one, or build your own from the download.
      Famous for: many hosts, a rich pivot story, aged software.
      Use for: the capstone (cap-01..cap-06)
      Watch: it is UNPATCHED by design and 20+ years of CVEs old.

  Metasploitable3
      Ubuntu, more modern, fewer services, still deliberately weak.
      Use for: "am I actually using current tools?"

  DVWA
      PHP + MySQL, levels 1-5 of the same web app.
      THE BEST TARGET FOR Tier 4. Level 1-5 walks up the whole web
      track: injection, XSS, CSRF, weak session, file upload.
      Use for: ps-02, ps-03, cs161-07

  OWASP Juice Shop
      A modern, intentionally vulnerable SPA. The best target for
      PortSwigger-class material because it has access control,
      business logic, and IDOR built in.
      Use for: ps-04, ps-09, psw-02

  WebGoat
      Lesson-based, one vulnerability per lesson.
      Use for: reading the explanation first, then practising

  AD Miner (an analyser, not a target)
      Runs against YOUR OWN lab AD and produces the reporting
      equivalent of BloodHound's path analysis.
      Use for: after lab-03, to see what a defender would see.

  Hack The Box / PG Practice / tryhack.me
      Real, harder, and NOT a lab you can break freely.
      PG Practice is the honest one - machines designed to be
      solvable, with a writeup culture.

cat > 01-preflight.sh <<'EOF'
#!/usr/bin/env bash
# BEFORE deploying anything vulnerable. Every line is a gate.
echo "=============================================================="
echo " PRE-DEPLOY SAFETY CHECK"
echo "=============================================================="
f=0
gate() { if [ "$1" = "y" ]; then printf "  [ok]   %s\n" "$2"
         else printf "  [STOP] %s\n" "$2"; f=1; fi; }

echo
echo "--- network ---"
gate "${ISOLATED:-n}" "the target's network is HOST-ONLY, not bridged"
gate "${NO_EGRESS:-n}" "the target CANNOT reach the internet"
gate "${NOT_MY_LAN:-n}" "the target is NOT on my real LAN"
echo
echo "--- the specific address ---"
echo -n "  the target's IP: "
TARGET_IP=""
read -r TARGET_IP
case "$TARGET_IP" in
  192.168.56.*|10.10.10.*)
    printf "  [ok]   %s is inside the lab ranges\n" "$TARGET_IP" ;;
  *)
    printf "  [STOP] %s is NOT in a lab range. Do not deploy a vulnerable\n" "$TARGET_IP"
    printf "         host on that address.\n"; f=1 ;;
esac
echo
echo "--- evidence that isolation is real ---"
echo "  From INSIDE the target VM, run these. If ANY succeeds, stop."
echo "    ping -c1 8.8.8.8          expect FAIL"
echo "    ping -c1 192.168.1.1      expect FAIL (your real router)"
echo "    ping -c1 $(ip route | awk '/default/{print $3; exit}')  expect FAIL (your gateway)"
echo
echo "  Record the results in notes/isolation-<date>.txt."
echo
if [ "$f" -eq 0 ]; then
  echo "  Gates passed. Deploy."
else
  echo "  A gate failed. DO NOT DEPLOY."
  echo "  A deliberately vulnerable host with egress is an attack tool"
  echo "  aimed at everything you can reach, including your real network."
fi
exit $f
EOF
chmod +x 01-preflight.sh

cat > 02-dvwa.sh <<'EOF'
#!/usr/bin/env bash
# DVWA on loopback or the host-only range. The best Tier 4 target.
#
# The vulnerability here is intentional and documented. That is what
# makes it safe to run: it is a lab, not a breach.
set -euo pipefail
ROOT="$HOME/aegis/labs/lab-02/deploy/dvwa"
BIND="${1:-127.0.0.1:8081}"     # loopback by default. Change deliberately.
mkdir -p "$ROOT"; cd "$ROOT"

echo "=== 1. Is PHP available? ==="
command -v php >/dev/null || { echo "  sudo apt install php-cli php-sqlite3 php-mbstring"; exit 1; }
php --version | head -1 | sed 's/^/  /'

echo "=== 2. Pull DVWA ==="
if [ ! -d DVWA ]; then
  git clone --depth 1 https://github.com/digininja/DVWA.git
  echo "  cloned"
else
  echo "  already present"
fi

echo "=== 3. Configure for SQLite (no MySQL service needed) ==="
# DVWA ships with a MySQL default. SQLite is far simpler on a lab and
# has one fewer thing to break.
cp config/config.inc.php.dist config/config.inc.php
python3 - <<'PY'
import re, pathlib
p = pathlib.Path("config/config.inc.php")
s = p.read_text()
s = s.replace("$_DVWA = array();", "$_DVWA = array();")
# switch the DB definition block to sqlite3
s = re.sub(r"\$_DB\s*=\s*array\((?:[^;]|\n)*?\);",
           "$_DB = array('dbtype' => 'sqlite3', 'database' => 'dvwa.sqlite');",
           s, count=1)
# loopback only, and no database creator account needed
s = s.replace("define('ALLOW_EMPTY_PASSWORD', true);",
              "define('ALLOW_EMPTY_PASSWORD', true);")
p.write_text(s)
print("  config written for sqlite3")
PY

echo "=== 4. Start on $BIND ==="
echo "  php -S $BIND -t $ROOT"
nohup php -S "$BIND" -t "$ROOT" > "$ROOT/server.log" 2>&1 &
sleep 1
curl -s -o /dev/null -w "  HTTP %{http_code} on $BIND\n" "http://$BIND/login.php"

echo
echo "=== 5. THE TARGET'S PURPOSE, which is the point of deploying it ==="
cat <<'PURPOSE'
  DVWA has five security levels. Walk them in order:

    Level 1 (Low)        brute-forceable login; SQL injection with no
                         protection at all; XSS reflected; CSRF with a
                         token that is checked but trivial
    Level 2 (Medium)      adds a modest filter that is bypassable with
                         a different technique (a different encoding, a
                         different injection point)
    Level 3 (High)        parameterised queries (no injection at all);
                         CSRF tokens with a session requirement
    Level 4 (Medium+)     blind SQLi; DOM-based XSS instead of server-side
                         reflection; a second-order injection
    Level 5 (Impossible)  the correct implementation of everything

  THE LESSON, and it is the one people miss:
    Levels 1 to 4 are not four versions of the same app. They are four
    DIFFERENT attacks requiring different techniques. The filter in
    level 2 does not stop you - it changes which technique works. A
    pentester who can only do reflected XSS cannot solve level 4.

  This is why Tier 4's theory notes exist. DVWA Level 4 is DOM XSS and
  it is genuinely hard if you have only learned to inject payloads
  into form fields.
PURPOSE
EOF
chmod +x 02-dvwa.sh
./02-dvwa.sh 2>&1 | tail -20 | tee 03-dvwa.txt

cat > 04-metasploitable.sh <<'EOF'
#!/usr/bin/env bash
# Metasploitable: the pivot lab.
#
# Metasploitable2 comes as seven VMs. You do not need all of them.
# The useful set for the capstone is three:
#
#   msf2-dc     a Windows 2000 domain controller. Deliberately ancient:
#               NTLM only, no ASLR, weak services, and a known path to
#               SYSTEM. This is where the capstone's AD phase runs.
#   msf2-meterpreter  a Windows XP host with writable services, and
#               AV, which is the point of it
#   msf2-ubuntu   a Linux host with weak NFS and web services, for the
#               Unix half
#
# METASPLOITABLE3 is one Ubuntu box, current-ish, for "am I using
# modern tooling".
#
# SAFETY: Metasploitable2 runs Windows 2000 with no patches and known
# RCE. It MUST be on a host-only network. It is the single highest
# risk target in this catalog, and the preflight in 01-preflight.sh
# is not optional for it.
echo "=== deploy order, and why ==="
cat <<'ORDER'
  1. msf2-ubuntu       first. Linux is quick, it validates your
                       tooling, and it is the least risky.
  2. msf2-dc           second. This is the capstone's centrepiece.
  3. msf2-meterpreter  third. The AV-evasion phase.
  4. Juice Shop        fourth. The web tier, on the same host.
  5. DVWA              fifth. Loopback is fine for this.

  Each one gets its own snapshot at 04-PRE-EXERCISE.
ORDER
cat <<'SETTING'
  THE VBOXSETTINGS THAT MATTER
    --nic1 hostonly                       NEVER bridged
    --nictype1 82540EM                    the most compatible NIC
    --memory 512                          msf2 machines are old
    --cpus 1
    --snapshot on                         power-on snapshot

  AND THE SNAPSHOT DISC: store it outside the VM folder, on a disk
  with room. A snapshot chain that fills the disk corrupts the VM.
SETTING
EOF
chmod +x 04-metasploitable.sh
