Memory Forensics with Volatility 3

Summary

Memory is where the running state lives: injected code, network connections, credentials in the
LSASS, and processes that never touched disk. It is also the most perishable evidence there is.

The framing: Volatility answers questions about a running system that
you cannot answer from disk. The technique is not "run Volatility" —
it is knowing which question each plugin answers and running them in
order.

Volatility 3 is not installed on this machine. Every command below
carries an install check, and the analytical content works regardless.

The plugins, grouped by the question they answer

  WHAT IS RUNNING?
    windows.pslist         processes: pid, ppid, threads, start time
    windows.pstree         the parent/child tree (what launched what)
    windows.cmdline        the command line of every process
    windows.handles        open file and registry handles per process
    windows.dlllist        loaded modules per process
    windows.malfind        private RWX regions: INJECTION

  WHAT IS IT CONNECTED TO?
    windows.netscan        TCP connections, owning pid, remote address
    windows.netstat        listening and established sockets
    windows.getsids        pid -> session mapping (who is at the keyboard)

  WHAT CREDENTIALS EXIST?
    windows.credential_dump   lsadump + mimikatz + SAM + DPAPI
    windows.hashdump          the NT hashes of every account
    windows.lsadump           the LSASS secrets

  WHAT IS THE MACHINE?
    windows.info         OS, build, system time, processor count
    windows.pstree       the boot parent (smss -> wininit)
    windows.cmdline      the boot command line
    windows.verinfo      the OS version
    windows.envars       environment variables of each process
    windows.getsids      sessions

  WHAT CHANGED?
    windows.registry.printkey    a specific key
    windows.registry.hivelist    which hives are loaded
    windows.registry.hivelist    WHICH USER was logged on
    windows.registry.userassist  what the USER typed into Explorer
    windows.registry.runkeys     persistence
    windows.shimcachemem     what executables have ever run
    windows.shimcachemem-timeline  the same, with timestamps
    windows.mftscan       files in memory
    windows.dumpfiles     carve a file out of memory

  LINUX HOSTS
    linux.pslist, linux.pstree, linux.bash (history from memory),
    linux.proc.Maps, linux.lsof

The order to run them

# --- 2. the sequence, with the reasoning ---
cat > 02-workflow.sh <<'EOF'
#!/usr/bin/env bash
# Volatility 3 against a memory image from YOUR OWN system.
# Volatility is not installed here; these are the commands and the
# order. The ORDER is the content; the binary path is incidental.
#
# vol.py [PLUGIN] -f <image> [--pid X] [--name Y]
set -uo pipefail
VOL="${VOL:-vol.py}"
IMG="${1:?usage: ./02-workflow.sh <memory.image> [pid]}"
PID="${2:-}"
[ -f "$IMG" ] || { echo "no image at $IMG"; exit 1; }
if ! command -v "$VOL" >/dev/null 2>&1; then
  echo "vol.py not installed. pipx install volatility3"
  echo "The commands below are correct; they will work once it is."
  echo
fi

echo "=== 1. WHAT IS THIS? (always first) ==="
# windows.info gives you the OS build and the system time.
# The SYSTEM TIME IS YOUR CLOCK REFERENCE. Record it.
echo "  $VOL windows.info -f '$IMG'"

echo
echo "=== 2. WHAT IS RUNNING? ==="
echo "  $VOL windows.pstree -f '$IMG'"
echo "    ^ the tree tells you what launched what. An explorer.exe"
echo "      with a child that is not explorer, or a svchost.exe"
echo "      running cmd.exe, is the shape of an intrusion."
echo "  $VOL windows.pslist -f '$IMG'"

echo
echo "=== 3. WHAT WAS EXECUTED? ==="
echo "  $VOL windows.cmdline -f '$IMG'"
echo "    ^ every command line, with the full path. Compare against"
echo "      where Windows binaries actually live."
echo "  $VOL windows.shimcachemem-timeline -f '$IMG'"
echo "    ^ what ran, oldest first, with the path it ran from."

echo
echo "=== 4. WHAT IS INJECTED? ==="
echo "  $VOL windows.malfind -f '$IMG'"
echo "    ^ private read-write-execute memory with no file behind it."
echo "      This is the single highest-signal plugin in the toolkit:"
echo "      it finds shellcode that never touched disk."
if [ -n "$PID" ]; then
  echo "  $VOL windows.malfind -f '$IMG' --pid $PID"
  echo "  $VOL windows.dlllist -f '$IMG' --pid $PID"
  echo "  $VOL windows.malfind.Dump --pid $PID -f '$IMG' --dump-dir ./dumps"
fi

echo
echo "=== 5. WHO IS ON THE KEYBOARD? ==="
echo "  $VOL windows.getsids -f '$IMG'"
echo "  $VOL windows.sessions -f '$IMG'"
echo "    ^ a headless server with one interactive session is unusual."
echo "      This is how you notice someone is RDP'd into a box that"
echo "      nobody uses interactively."

echo
echo "=== 6. WHAT IS IT TALKING TO? ==="
echo "  $VOL windows.netscan -f '$IMG'"
echo "  $VOL windows.netstat -f '$IMG'"
echo "    ^ the pid that owns an outbound connection is the process."
echo "      Map it back to pslist. An outbound connection from a"
echo "      signed Microsoft binary, to a new address, at 03:00, is"
echo "      the finding."

echo
echo "=== 7. WHAT CREDENTIALS EXIST? ==="
echo "  $VOL windows.credential_dump -f '$IMG' > creds.txt"
echo "  $VOL windows.hashdump -f '$IMG' > hashes.txt"
echo "  $VOL windows.lsadump -f '$IMG' > lsadump.txt"
echo "    ^ WAIT FOR AUTHORISATION. These print every credential on"
echo "      the host, including the logged-on user's. Handle the"
echo "      output as evidence, not as a convenience."

echo
echo "=== 8. WHAT DID THE USER DO? ==="
echo "  $VOL windows.registry.userassist -f '$IMG'"
echo "    ^ UserAssist records what was launched from EXPLORER, with"
echo "      timestamps. It is the best 'what did this person do'"
echo "      source in a memory image."

echo
echo "=== THE SEQUENCE, IN ONE LINE ==="
echo "  info -> pstree/cmdline -> malfind -> netscan -> sessions -> creds"
echo "  (establish what, then what is wrong with it, then who, then"
echo "   what it reached, then what it stole)"
EOF
chmod +x 02-workflow.sh
./02-workflow.sh ~/aegis/labs/for-03/nonexistent.raw 2>&1 | head -30 | tee 03-workflow.txt

# --- 3. offline: the malfind shape, which is the concept ---
python3 - <<'PY' 2>&1 | tee 04-malfind.txt
print("  === what windows.malfind actually finds ===\n")
print("  A PROCESS is a set of virtual memory regions. Legitimate ones:")
print()
print("    IMAGE   MAPPED   the .text section of a DLL  - not private")
print("    IMAGE   MAPPED   the .data section            - not private")
print("    MAPPED  PRIVATE  the heap, the stack          - RW, no exec")
print()
print("  MALLOC  PRIVATE  RWX  <- THIS. There is no reason for a")
print("                           process to have memory that is")
print("                           simultaneously writable AND")
print("                           executable AND private (no file")
print("                           behind it).")
print()
print("  WHAT THE FOUR CAVEATS ARE, and why they matter:")
print()
print("    1. JIT. Java, .NET, WPF, Chrome, Firefox, and any runtime")
print("       JIT-compiles code into RWX pages. A JIT process will")
print("       produce findings. Correlate before you report.")
print("    2. UNLINKED PEB. An unlinked PEB means the process removed")
print("       itself from the process list while running. There is")
print("       NO benign reason for this.")
print("    3. .NET. CLR processes have RWX regions with MZ/PE headers")
print("       or with a 'This program cannot be run in DOS mode'")
print("       string that is NOT MZ at offset 0 - the classic")
print("       'not really a PE' shellcode signature.")
print("    4. HOOKED. A VMT-removed process, or a hooked ntdll, means")
print("       something is intercepting the API calls that a userland")
print("       tool relies on to see the process list.")
print()
print("  THE RANKING OF FINDINGS:")
print("    RWX + unlinked PEB           -> almost certainly malicious")
print("    RWX + a MZ/PE at a non-zero offset -> almost certainly malicious")
print("    RWX + a .NET/Chrome/JVM PID  -> probably JIT, verify elsewhere")
print()
print("  THE DUMP: windows.malfind.Dump writes the region out so you can")
print("  do static analysis on it (for-05). That is the handoff:")
print("      memory forensics finds the code, static analysis explains it.")
PY
cat 04-malfind.txt

# --- 5. acquisition, which is where memory is actually won ---
cat > 05-acquire.md <<'MD'
# Acquiring memory

```text
  ON WINDOWS (WinPmem, or Magnet RAM Capture):
    load the driver, read physical memory to a file
    it suspends threads briefly - the system is briefly unresponsive
    this is a LIVE acquisition and is subject to everything for-01
    says about live acquisition

  ON LINUX (LiME):
    ./lime lime.ko "path=out.lime format=lime compress=0"
    the output is a LiME-formatted image, which Volatility reads
    (format=lime means Volatility detects it)

  FROM A DUMP FILE:
    Windows crash dumps, hibernation files, pagefile.sys
    a hibernation file is MEMORY, and Volatility reads it
    a pagefile is partial and unreliable but occasionally enough

  THE PRACTICAL PROBLEM: memory is 8-128 GB. You need:
    - storage for it (you have 400 GB free)
    - the time to transfer it
    - RAM to analyse it: Volatility loads a large index into memory.
      Analysing a 64 GB image wants 64 GB+ of RAM.
```

## The authority limit

```text
  WHAT YOU CAN PROVE FROM MEMORY, AND WHAT YOU CANNOT:

  PROVABLE
    a process existed, with these threads, at this time
    this process had these modules loaded
    this process had these open handles
    these sockets were open, owned by these pids
    these credentials were in the LSASS at acquisition time
    this user was logged on, in this session
    this memory region was RWX and private

  NOT PROVABLE FROM MEMORY ALONE
    that the executable on disk is the one that was running
      (the on-disk file may have been replaced since)
    who created the process
      (parentage is a strong hint, not proof - PEB unlinking breaks it)
    what happened before the image was taken
      (memory is a snapshot, not a recording)
    the content of an encrypted volume
      (unless the keys were resident - which is why BitLocker keys
       in memory are worth a finding on their own)

  THE RULE: corroborate with disk and with logs. A memory finding
  alone is a hypothesis; a memory finding plus an event log entry
  plus a file on disk is a conclusion.
```
MD
cat 05-acquire.md

Step 4 is the deliverable: 04-malfind.txt explains why an RWX private region is the
highest-signal artefact in memory, and then gives you the four caveats that stop you reporting a
JVM as malware. RWX + unlinked PEB is almost certainly malicious; RWX + Chrome is
probably JIT.

02-workflow.sh is the order — info → pstree/cmdline → malfind → netscan → sessions →
creds — with the reasoning next to each plugin, and it stops before credential_dump to note that
those plugins print every credential on the host and must be handled as evidence.

05-acquire.md sizes it against this machine: 30 GiB of RAM means a full-RAM image from a
large target is at the edge of practical, which is a real constraint worth knowing before you plan.

Record: 04-malfind.txt and 05-acquire.md.
