Kerberos Deep Dive: TGTs, Service Tickets and Delegation

Summary

Kerberos is three ideas: a ticket that lets you prove who you are without sending a password,
a referral that tells you where to get one, and delegation that lets a service act on
your behalf. Every AD attack in this course is one of those three being abused.

The lecture's framing: a ticket is a bearer credential. Whoever holds it
can use it. That single property explains Kerberoasting, delegation,
ticket theft, and why the ticket lifetime is the security parameter.

The three objects

  KEY TABULATION KEY (KTAB)
    the long-term secret, derived from the account PASSWORD and the REALM
    AES: PBKDF2(password, salt=REALM_UPPER, iterations)
    the KDC has it; the user could compute it; a DC can decrypt with it
    >>> This is why roasting a ticket is cracking a password. <<<

  TICKET-GRANTING TICKET (TGT)
    issued by the Authentication Service to a user
    encrypted with the KDC's own long-term key
    contains: identity, groups, session key, validity
    THIS IS THE CROWN JEWEL. One TGT = the user. Everything after it
    needs no password.

  SERVICE TICKET (TGS / TGS-REP)
    issued by the Ticket Granting Service for ONE service
    encrypted with that SERVICE's long-term key
    contains: the client identity and a session key for THAT service
    the service decrypts it and therefore knows who you are
    forwardable or delegable flags live here

The flow

  1. AS-REQ   client -> KDC (the Authentication Service)
             "I am alice, prove it"
             includes a timestamp encrypted with the password-derived KTAB

  2. AS-REP   KDC -> client
             "here is a TGT, encrypted with MY key so only I could
              have made it, and containing a session key"
             the client now has a TGT without ever sending the password

  3. TGS-REQ  client -> KDC
             "I want a service ticket for cifs/dc01.lab.internal"
             presented with the TGT

  4. TGS-REP  KDC -> client
             "here is a service ticket, encrypted with the CIFS
              SERVICE's key so only that service can read it"
             the service decrypts it with its own long-term key

  5. AP-REQ   client -> service, presenting the service ticket
  6. AP-REP   service -> client, proving IT is not fake

  MUTUAL AUTHENTICATION: the service cannot be impersonated, because it
  proved possession of its own long-term key in step 6. That is the
  point of the last exchange.

  THE TICKET CONTENTS:
    realm              the domain
    client principal   alice
    client addresses   the source IPs it may be used from
    validity window    notbefore / notafter
    session key        a fresh symmetric key for THIS session
    cname/sname        who / which service
    flags              forwardable, renewable, renewable-ok, delegable
    PAC                the privilege attributes: groups and rights
                        (see "the PAC" below)
    (KDC cannot read the service ticket's session key, and the service
     cannot read the TGT's. That is the whole point.)

The PAC: why an enterprise AD ticket is a business card

  The PRIVILEGE ATTRIBUTE CERTIFICATE is a Microsoft extension inside
  the ticket, signed by the KDC with its own key.

  IT CONTAINS:
    - the user's SID and every group SID they are in
    - the user's domain
    - a LOGON TIME and LOGOFF TIME   <- for the KERBEROS TICKET
      EXPIRATION, an extension used by protected users and by admin
      S4U2Self delegation
    - extra SIDs from token filtering and from groups
    - the "extra SIDs" that carry cross-realm authorisation

  WHY IT MATTERS TO AN ATTACKER:
    1. TICKET LIFETIME: a normal user ticket is 10 hours. The PAC's
       logoff time is how a user is logged off everywhere at once.
    2. IT IS A COMPLETE AUTHORISATION SNAPSHOT. Seizing it with
       DPAPI, Rubeus or a LSASS dump gives you every group membership
       the user had, without enumerating anything.
    3. IT IS THE TARGET of delegation attacks: forge or steal a TGT
       and you do not need any further credentials.

Delegation: the third idea, and the big one

  THE PROBLEM:
    user -> web server -> file server
    The web server cannot get a service ticket for the file server on
    the user's behalf, because that would require the web server to
    have the user's password.

  THE SOLUTION (delegation):
    the user's TGT is FORWARDABLE. The web server presents it to the
    KDC, which issues a service ticket FOR THE USER, which the web
    server then presents downstream. The file server sees the user, not
    the web server.

  THE THREE SETTINGS, and they are all wrong somewhere:

  1. NO DELEGATION - safe. The service cannot get downstream tickets.

  2. CONSTRAINED DELEGATION ("protocol transition" for kerberos-only)
     the service may get a ticket for ONE named SPN.
     cifs/sqlsvc/web01 -> allowed for SPNs of that account only
     SAFE, and the recommended setting.

  3. UNCONSTRAINED DELEGATION  (msDS-AllowedToDelegateTo = all)
     the service may get a ticket for ANY service, as ANY user.
     -> if the service is compromised, the attacker gets TICKETS FOR
        ANY USER WHO LOGS IN TO IT, for the next 10 hours.
     -> if the service runs as SYSTEM, the attacker gets SYSTEM TGTs.
     -> THE FINDING. It has been a Critical finding in every
        assessment of every large Windows estate since 2010.

Why delegation is the whole ball game

  A user browses to a web server that has unconstrained delegation.
  The web server captures the user's forwarded TGT.
  The attacker now holds that user's TGT.
  The attacker can get a service ticket for ANYTHING as that user,
  for up to 10 hours, with no password, no hash, and no further access.

  The user never does anything unusual. They open a browser tab.

  IF the web server runs as SYSTEM (which IIS application pools do by
  default), the captured ticket is a SYSTEM TGT, and SYSTEM is usually
  local admin on that host - and often a privileged domain principal.
Setting Risk Mitigation
Unconstrained delegation Critical: any downstream ticket for any user Migrate to constrained; enforce with a DC audit policy
Legacy msDS-SecurityHistory Critical: same, via a different attribute Remove; audit for it too
Constrained delegation Low, if correctly scoped Regularly review the SPN list
Protocol transition Medium: allows a service to request a TGT for a user without preauth Only where required
RBC (Resource-Based Constrained) Safer: trust is on the target service, not the DC Migrate to RBC

Attacking the tickets

  THE TICKET IS A BEARER CREDENTIAL.
    whoever holds it can use it, for its validity period, from a
    permitted address, for its service.

  WHICH MEANS:

    STEALING   - LSASS dump, DPAPI, keylogger, or the delegation capture
                 above. One ticket = full impersonation.

    ROASTING   - a ticket encrypted with the ACCOUNT's key can be
                 decrypted by anyone who GUESSES the password. Take many
                 tickets, guess offline. (ad-04.)

    PASS-THE-TICKET - take the TGT out of the LSASS cache and inject it
                 into your own session. No password, no network traffic
                 to the domain controller, nothing in the DC logs.

    GOLDEN TICKETS - forge a TGT using the KRBTGT account's password.
                 Survives a password reset, because the KDC signs with
                 its own key. Requires KRBTGT hash.
    SILVER TICKETS - forge a service ticket using the SERVICE's key.
                 Does not touch the KDC at all. Invisible in domain logs.
                 Requires the service account's hash.

    DIAMOND TICKETS - recover the KRBTGT long-term key from a DC's
                 memory, then do golden tickets without ever touching
                 the domain again.

Kerberoasting and the KTAB

  THE KTAB DERIVATION, and why roasting works:

    AES (Windows 2008+):
      ktab = PBKDF2-HMAC-SHA1(password,
                             salt = REALM_UPPERCASE (e.g. "LAB.INTERNAL"),
                             iterations = 4096)
      NTLM (older domains, still common):
      ktab = MD5(UTF16LE(REALM_UPPERCASE) + password)

  THE ASYMMETRY:
    the KDC can decrypt ANY user's ticket because it can compute any
    user's KTAB (it does this at logon).
    an ATTACKER can do the same IF they can guess the password.

  AND THE TICKET TELLS YOU THE ITERATIONS:
    the ticket contains an encrypted PA-DATA blob whose size reveals the
    RC4 or AES iteration count. So the attacker does not have to guess
    the domain configuration - the ticket hands it to them.

  THE ATTACK:
    1. request a service ticket for every account with an SPN
    2. take the ticket's session key
    3. decrypt it offline with password guesses, using the ktab derived
       from each guess
    4. one successful guess gives the service account's NT hash too
       (because AES ktab decryption requires the plaintext password)

  THE MITIGATION THAT ACTUALLY WORKS:
    a long random service account password. "Long" is not enough -
    "SQLServiceAccount2019" is long and roasts in seconds. Length plus
    unpredictability plus rotation.
    gMSA (group managed service accounts) give a 120-character random
    password managed by the DC, rotated automatically.

The clock

  Kerberos tolerates a 5-minute clock skew by default
  (MaxClockSkew). Beyond that, tickets are invalid.

  So clock synchronisation is a security control, not just an
  operational nuisance. A host 10 minutes out cannot authenticate.

  A host you control, deliberately desynchronised, can cause a denial
  of authentication - which is why time-based attacks exist and why
  NTP authentication is a real control.

Terminology

Term Meaning

python3 - <<'PY' 2>&1 | tee 01-flow.txt
import hashlib, hmac, os, base64, secrets

REALM = "LAB.INTERNAL"          # the domain name, uppercase. It is NOT secret.
print("  === Kerberos, the mechanics, without a KDC ===")
print()
print(f"  REALM = {REALM!r}   <- public. Everyone knows it.")
print()

# --- the KTAB: the long-term key derived from the password ---
def ktab_aes(password, realm=REALM):
    return hashlib.pbkdf2_hmac("sha1", password.encode("utf-16-le"),
                               realm.upper().encode("utf-16-le"), 4096, 32)
def ktab_ntlm(password, realm=REALM):
    return hashlib.md5(realm.upper().encode("utf-16-le") + password.encode("utf-16-le")).digest()

pw = "S3rv1ceAcc0unt!2026"
print("  THE KTAB - derived from the password and the realm:")
print(f"    AES 4096 iterations : {ktab_aes(pw).hex()[:48]}...")
print(f"    NTLM (MD4-ish)      : {ktab_ntlm(pw).hex()}")
print()
print("  THE ASYMMETRY THAT MAKES ROASTING WORK:")
print("    - the KDC can compute ANY user's KTAB (it must, to log them in)")
print("    - the ticket is ENCRYPTED with that KTAB")
print("    - so anyone who GUESSES the password can DECRYPT the ticket")
print("    - the ticket does not contain the password, it contains")
print("      material encrypted with a key derived from it")
print()
print("  Hence: take tickets, guess offline, recover passwords AND")
print("  (via AES ktab) the accounts NT hashes.")

# --- demonstrate: encrypt and decrypt a service ticket ---
session_key = os.urandom(16)
service_ticket = b"SERVICE-TICKET-PAYLOAD-alice@lab.internal"
enc_ticket = bytes(a ^ b for a, b in zip(service_ticket, session_key))

print()
print("  === the ASYMMETRY, demonstrated ===")
print(f"  service ticket (ciphertext) : {enc_ticket.hex()[:48]}...")
print(f"  the session key             : {session_key.hex()}")
print()

print("  ATTACKER'S POSITION 1: they have the ciphertext (roasted from")
print("  an SPN enumeration) and want the plaintext. They try passwords:")
for guess in ["Summer2026", "S3rv1ceAcc0unt!2026"]:
    if guess == pw:
        print(f"    guess {guess!r:<28} CORRECT -> key = {session_key.hex()}")
        print(f"    decrypt                  -> {service_ticket.decode()}")
print()
print("  ATTACKER'S POSITION 2: they have the NT hash (from a dump) and")
print("  want a TGT. Overpass-the-hash does this:")
nt = hashlib.new("md4", pw.encode("utf-16-le")).digest() if "md4" in hashlib.algorithms_available else os.urandom(16)
print(f"    NT hash : {nt.hex()}")
print("    a DC will issue a TGT for a principal presented as that hash,")
print("    provided network-level protections do not block it")
print("    (which is what 'Full NTLM: Enable additional channel-level")
print("     security to prevent man-in-the-middle attacks' prevents)")
print("     for outbound SMB. It is NOT on for Kerberos, deliberately,")
print("     because it would break domain logons.)")
PY

# The PAC: what it is and why it is the target

```text
  A Microsoft extension inside the Kerberos ticket. Signed by the KDC.
  Not encrypted - READABLE by anyone holding the ticket.

  CONTENTS
    - User SID
    - Group SIDs (the complete group membership snapshot)
    - Domain name
    - Logon time / Logoff time (Kerberos ticket expiration extension)
    - Extra SIDs (token filtering, cross-realm authorisation)
    - Flags: name, upn, cname, sid, group ids

  WHY IT MATTERS FOR AN ATTACK

  1. TICKET LIFETIME IS A REAL ATTACK PARAMETER
     Default user ticket: 10 hours.
     Default service ticket: 1 hour.
     The shorter the ticket lifetime, the smaller the window a stolen
     ticket is useful for. Most hardening guides recommend reducing
     both, and few organisations do.

  2. IT IS AN AUTHORISATION SNAPSHOT
     A captured PAC tells an attacker every group the user belongs to,
     without any enumeration. Capture alice's PAC and you know that
     alice is in "Backup Operators" - no queries needed.

  3. DELEGATION ATTACKS TARGET THE TGT SPECIFICALLY
     Unconstrained delegation means a service can forward a user's TGT.
     That TGT is the whole session.

  4. THE KERBEROS TICKET EXPIRATION EXTENSION
     Protected users and S4U2Self add a per-ticket logoff time so that
     "log off everywhere" actually logs off everywhere. It also means
     a captured ticket has a hard, checkable expiry - which is exactly
     what a defender wants for detection.
```

## The ticket types table

| Ticket | Validity (default) | Encrypted with | If stolen you can |
|---|---|---|---|
| TGT | 10 h | KRBTGT account key | Request any service ticket, as that user |
| CIFS/HTTP service ticket | 1 h | service account key | Use that service, as that user |
| Delegated TGT | 10 h | KRBTGT | Everything, for the whole user session |
| Golden ticket | until KRBTGT key rotates | KRBTGT (forged) | Everything. Survives password reset |
| Silver ticket | until service key rotates | service key (forged) | That one service. Never touches the KDC |
| Diamond ticket | until the DC reboots or the key rotates | recovered KRBTGT | Everything, without touching the domain again |

**The last column is the whole point of AD ticket attacks: the recovery
path is completely different for each one, and two of them are
invisible to the domain controller's logs.**

# Delegation: the third idea

THE PROBLEM
user -> IIS server -> SQL server
The IIS server cannot get a service ticket for the SQL server on
the user's behalf. It would need the user's password.

THE SOLUTION
Forwardable tickets. The IIS server presents the user's TGT to the
KDC and gets a ticket FOR THE USER, which it presents downstream.
The SQL server sees the user, not the IIS server.

THE THREE SETTINGS

  1. NO DELEGATION
    Safe. Default. The service cannot get downstream tickets.

  2. CONSTRAINED DELEGATION
    The service may get a ticket for NAMED SPNs only.
    Trust this service for cifs/sqlsvc/web01
    SAFE. The recommended setting. Regularly review the list.

  3. UNCONSTRAINED DELEGATION
    msDS-AllowedToDelegateTo = KEY USE FOR ALL TRUSTED AUTHENTICATION
    The service may get a ticket for ANY service, as ANY user.
    -> compromised service = tickets for every user who logs in to it
    -> if it runs as SYSTEM, tickets for SYSTEM
    -> THE FINDING

THE LEGACY PATH, STILL FOUND
msDS-SecurityHistory = KEY USE FOR ALL TRUSTED AUTHENTICATION
Same exposure, a different attribute, and it is far more commonly
missed by audits that only check msDS-AllowedToDelegateTo.


| Setting | Exposure | Control |
|---|---|---|
| Unconstrained delegation | Critical | remove; migrate to constrained |
| `msDS-SecurityHistory` | Critical | remove; audit for both |
| Constrained delegation | Low if scoped | review SPNs quarterly |
| RBC delegation | Low | trust lives on the target, not the DC |
| Protocol transition (S4U2Self) | Medium | only where a protocol change is real |

  Risk
    An attacker who obtains code execution on any of these three hosts
    can request Kerberos service tickets for ANY user who subsequently
    authenticates to it, capturing their TGT. The host running as
    SYSTEM (IIS01) yields SYSTEM TGTs, and SYSTEM is a local

any user's KTAB to log them in, which is exactly the capability an attacker borrows.
