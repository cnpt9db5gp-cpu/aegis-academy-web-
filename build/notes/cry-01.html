Course Overview and Stream Ciphers

Summary

Dan Boneh's online course opens with the framing that makes cryptography learnable rather than a
grab-bag of algorithms: cryptography is about problems, not about ciphers. Encryption is a
tool for solving the one-way function problem; hashing is a tool for the collision
resistance problem; signatures are for non-repudiation; MACs are for authentication.

Start from the problem, and the primitive is determined. Start from the
primitive, and you have to memorise.

Companion to cs161-02's IND-CPA definition and the mit858-13
secure-channel note. This is the conceptual layer; those are the
applied layers.

The three problems

  PROBLEM                          WHAT YOU NEED        PRIMITIVE
  -------------------------------   ------------------   ----------------
  hide the contents of a message    forward secrecy,     one-way permutation
                                    authenticity         + randomness
  prove two messages are equal     integrity             collision resistance
  prove who sent a message         non-repudiation       signature scheme
  prove a message is untampered    authentication       MAC

The single most important sentence in the course: you cannot get
all of these from one primitive. Every real protocol uses several,
because each one only buys part of the requirement.

Three requirements, three separate jobs

  CONFIDENTIALITY   only the intended party can read it
                    -> encryption with a key the attacker does not have

  INTEGRITY         nobody can change it without detection
                    -> MAC, or a signature. ENCRYPTION ALONE GIVES YOU
                      NEITHER. AES-CBC without a MAC is not secure.

  AUTHENTICATION    the receiver knows the sender
                    -> a MAC shared with that sender, or a signature

  These are independent. A scheme can have any subset. Any design that
  claims otherwise has a bug.

Encodings are not encryption

  BASE64 IS NOT ENCRYPTION. It is a transport encoding.
    'hello' -> aGVsbG8=     which anyone can reverse in one command.

  The confusion matters operationally: a "secret" in a config file that
  is base64 is a plaintext secret with extra steps. You will see it.

    $ echo aGVsbG8= | base64 -d
    hello

What makes a function one-way

  A function f is ONE-WAY if computing y = f(x) is easy, and computing
  x from y is hard.

  EnCRYPTION needs a one-way PERMUTATION (a bijection) so decryption
  works: the inverse is computable with the key.

  HASHING needs a one-way FUNCTION (not necessarily a permutation) plus
  collision resistance.

  KEY DERIVATION needs one-wayness plus an OUTPUT LENGTH property:
    the function must map a short password to a fixed-size key, and it
    must be SLOW, because the input space is small.

The last point is the one that distinguishes the three uses. A fast
one-way function is right for encryption (you want to encrypt a lot) and
wrong for passwords (you want each guess to cost a lot).

Stream ciphers

  A stream cipher encrypts one symbol at a time:

    c_i = m_i XOR S_i

  where S is a pseudo-random keystream. Decryption is identical:
    m_i = c_i XOR S_i

  REQUIREMENTS ON THE KEYSTREAM:
    - unpredictable (an attacker must not be able to predict S)
    - never reused under the same key (see below - this is the big one)
    - not itself secret (it is derived from the key)

  THE ONE-TIME PAD:
    if S is truly random, as long as the message, and never reused,
    then it is PERFECTLY SECURE. Shannon proved it. No computational
    assumption at all.
    Every real stream cipher is "an OTP with a bad keystream".

The keystream generator

  A PRG takes a short seed (the key) and stretches it into a long
  keystream. It must be indistinguishable from random to anyone who
  has not seen the seed.

  Real generators are built from a PRF plus a statistical correction:

    state = key
    loop:
      output one keystream byte
      state = state * a + b   (mod 2^n)

  That is a linear congruential generator. It is TERRIFYINGLY weak:
    - low bits have short periods
    - only the low ~log2(n) bits are usable
    - with four consecutive outputs you can solve for a and b exactly
    - Lagged Fibonacci generators fall to a much harder lattice attack

  THIS IS NOT A PEDANTIC POINT. It is why "I generated the nonce with
  a seeded RNG" is a real finding rather than a style comment.

# Demonstrate that an LCG is trivially broken. Four outputs, two unknowns.
A, C, M = 1664525, 1013904223, 2**32
# s1 = (A*s0 + C) % M ;  s2 = (A*s1 + C) % M
# s2 - s1 = A*(s1 - s0)  (mod M)  ->  A = (s2-s1) * inverse(s1-s0) mod M
def recover_from_four(outs, modulus=2**32):
    import math
    (s0,s1,s2,s3) = outs
    d1 = (s1 - s0) % modulus
    d2 = (s2 - s1) % modulus
    a = (d2 * pow(d1, -1, modulus)) % modulus
    c = (s1 - a * s0) % modulus
    # now PREDICT FORWARD
    nxt = s3
    for _ in range(5):
        nxt = (a * nxt + c) % modulus
        print(f"    predicted next keystream byte: {nxt & 0xff:02x}")
    return a, c

s = 12345
outs = []
for _ in range(4):
    s = (A * s + C) % M
    outs.append(s)
print("  four observed keystream bytes (4 x 32 bits):")
for o in outs: print(f"    {o:08x}")
print("  from those, the generator's parameters are:")
a, c = recover_from_four(outs)
print(f"    a = {a}  c = {c}  (recovered from the seed, which the attacker never had)")

Keystream reuse: the single most common real failure

  c1 = m1 XOR S
  c2 = m2 XOR S

  c1 XOR c2 = m1 XOR m2

  So one message plus the ciphertexts recovers the other message.
  Every message under that keystream is compromised.

  WHERE IT HAPPENS:
    - a fixed IV with CBC/CFB/OFB/CTR
    - a random nonce that repeats (birthday: 2^32 messages for 32 bits)
    - a seeded PRG, so the keystream is the same every run
    - a fixed keystream in a hand-rolled implementation

  This is `cs161-02`'s nonce-reuse note in its purest form, and it is
  what makes Kerberoasting work.

Encrypt-then-MAC

  Encrypt-then-MAC:  E(M) then MAC(E(M)), verify MAC first
  MAC-then-encrypt:  MAC(M) then E(...), verify after decrypting

  Encrypt-then-MAC is the correct order, because:
    - you can reject a tampered ciphertext WITHOUT decrypting it
      (so a padding oracle, or any decryption error, is unreachable)
    - you decrypt only data an attacker cannot have modified

  MAC-then-encrypt leaves you decrypting attacker-controlled data
  before you know whether it is authentic. That gap is a padding
  oracle (see cry-d4).

Terminology

Term Meaning
Confidentiality Only the intended party can read it
Integrity Unauthorised modification is detectable
Authenticity The sender is known
One-way function Easy forward, hard backward
Permutation A bijection; decryption possible
Stream cipher XOR with a keystream
Keystream The pseudo-random sequence being XORed
PRG / PRF Pseudo-random generator / function
LCG Linear congruential generator; badly broken
One-time pad Random keystream as long as the message, never reused
Perfect secrecy Ciphertext gives no information at all
Encrypt-then-MAC The correct composition order
Base64 An encoding, emphatically not encryption
Nonce Unique per message; transmitted, not secret

# --- 1. base64 is not encryption ---
{
  echo "=== base64 reversed in one command ==="
  printf 'c3VwZXItc2VjcmV0OnBhc3N3b3JkMTIz' | base64 -d; echo
  echo
  echo "=== find base64-shaped 'secrets' in a repo ==="
  grep -rnE '[A-Za-z0-9+/]{24,}={0,2}' --include="*.env" --include="*.yml" --include="*.json" \
       --include="*.conf" . 2>/dev/null | head -5 | while read -r line; do
    tok=$(echo "$line" | grep -oE '[A-Za-z0-9+/]{24,}={0,2}' | head -1)
    dec=$(echo "$tok" | base64 -d 2>/dev/null | head -c 40)
    if [ $? -eq 0 ] && echo "$dec" | grep -qP '[\x20-\x7e]{8,}'; then
      printf "  POSSIBLE PLAINTEXT: %s\n" "$(echo "$line" | cut -c1-70)"
    fi
  done
  echo "  ^ a base64 value that decodes to readable text is a plaintext secret"
} 2>&1 | tee 01-base64.txt

# --- 2. the LCG, broken in public ---
python3 - <<'PY' 2>&1 | tee 02-lcg.txt
import math
A, C, M = 1664525, 1013904223, 2**32
s = 12345
outs = []
for _ in range(4):
    s = (A * s + C) % M
    outs.append(s)
print("  the 'keystream', from seed 12345 (the attacker never sees this)")
for i, o in enumerate(outs):
    print(f"    out[{i}] = {o:08x}")
d1 = (outs[1] - outs[0]) % M
d2 = (outs[2] - outs[1]) % M
a = (d2 * pow(d1, -1, M)) % M
c = (outs[1] - a * outs[0]) % M
print(f"\n  recovered from four outputs:  a = {a}, c = {c}")
print("  (the parameters are the PUBLIC constants; the seed is what we solved)")
print("\n  and now predict forward, which is what breaks a real cipher:")
nxt = outs[3]
for i in range(5):
    nxt = (a * nxt + c) % M
    print(f"    predicted keystream byte {i}: {nxt & 0xff:02x}")
print()
print("  Four 32-bit keystream words and the entire generator is yours.")
print("  This is why seeded PRNGs are 'fine for a test fixture and")
print("  catastrophic for a nonce'.")

# --- 3. keystream reuse, the real failure ---
python3 - <<'PY' 2>&1 | tee 03-reuse.txt
import os
def xor(a, b): return bytes(x ^ y for x, y in zip(a, b))

print("  === keystream reuse recovers plaintext pairs ===\n")
k = bytes(range(32))                      # a "keystream"
m1 = b"transfer 0100 to alice"
m2 = b"transfer 9900 to mallory"
c1, c2 = xor(m1, k), xor(m2, k)
xored = xor(c1, c2)
print(f"  m1            : {m1.decode()}")
print(f"  m2            : {m2.decode()}")
print(f"  c1            : {c1[:24].hex()}")
print(f"  c2            : {c2[:24].hex()}")
print(f"  c1 XOR c2     : {xored[:24].hex()}")
print(f"  m1 XOR m2     : {xor(m1,m2)[:24].hex()}")
print()
print("  IDENTICAL:", xored == xor(m1, m2))
print()
print("  Given c1, c2 and m1, the attacker recovers m2 exactly.")
print("  No key, no cryptanalysis, no search. This is arithmetic.")
print()
print("  It is also, precisely, why Kerberoasting works:")
print("    a service key, N tickets, the SAME keystream on the first")
print("    two -> the ticket's plaintext is recoverable -> crack offline.")
print()
print("  === the one-time pad, done correctly, for contrast ===")
key = os.urandom(len(m1))
c = xor(m1, key)
print(f"  plaintext     : {m1.decode()}")
print(f"  ciphertext    : {c.hex()}")
print(f"  recovered     : {xor(c, key).decode()}   (only because WE have the key)")
print()
print("  Shannon proved: with a random key as long as the message, the")
print("  ciphertext is independent of the plaintext. Not 'hard to")
print("  break' - zero information, unconditionally.")

# --- 4. a real stream cipher, and its states ---
{
  echo "=== ChaCha20 as an actual keystream generator ==="
  echo "  chacha20 is in OpenSSL. 256-bit key, 96-bit nonce, 32-bit counter."
  echo
  echo "  keystream, zero key, zero nonce (the standard test vector prefix):"
  printf '\x00%.0s' $(seq 1 32) > k.bin
  head -c 64 /dev/zero > n.bin
  openssl enc -chacha20 -K "$(xxd -p -c 64 k.bin)" -iv "$(xxd -p -c 64 n.bin)" \
    -in /dev/zero -out ks.bin 2>/dev/null \
    && xxd ks.bin | head -4 | sed 's/^/  /'
  echo
  echo "  Same key, nonce incremented by one:"
  printf '\x00%.0s' $(seq 1 31) '\x01' > n2.bin
  openssl enc -chacha20 -K "$(xxd -p -c 64 k.bin)" -iv "$(xxd -p -c 64 n2.bin)" \
    -in /dev/zero -out ks2.bin 2>/dev/null && xxd ks2.bin | head -2 | sed 's/^/  /'
  echo
  echo "  Completely different. Nonce uniqueness is the entire security."
  rm -f k.bin n.bin n2.bin ks.bin ks2.bin
  echo
  echo "=== how to check a token's randomness yourself ==="
  python3 -c "
import os, collections, math
b = open('ks.bin','rb').read() if __import__('os').path.exists('ks.bin') else os.urandom(4096)
c = collections.Counter(b)
H = -sum((v/len(b))*math.log2(v/len(b)) for v in c.values())
print(f'  {len(b)} bytes, {len(c)} distinct values, entropy {H:.3f}/8.0 bits per byte')
print(f'  a seeded LCG would show ~{len(b)*0.0:.0f}-8.0 but with a visible short period in low bits')
print(f'  chi-square-ish check: max count {max(c.values())} (expected {len(b)/256:.1f})')
"
} 2>&1 | tee 04-chacha.txt

# --- 5. encrypt-then-MAC, versus the wrong order ---
cat > 05-etm.md <<'EOF'
# Encrypt-then-MAC, and why the order matters

## The two compositions

```
  ENCRYPT-THEN-MAC            MAC-THEN-ENCRYPT
  c  = E(kE, m)               e  = E(kE, MAC(kM, m))
  t  = MAC(kM, c)             d  = Dec(kE, e)
                             verify MAC(kM, d)

  VERIFY MAC FIRST            DECRYPT, THEN VERIFY
```

## Why MAC-then-encrypt is wrong

You decrypt **attacker-supplied data before knowing whether it is
authentic**. Everything an attacker can reach during that decryption is
a gadget:

- padding errors (the padding oracle, cry-d4)
- decompression bombs before the MAC is checked
- length fields that cause huge allocations before the MAC is checked
- any error path that differs between "bad MAC" and "bad plaintext"

## The rule

```
  NEVER process a received ciphertext or a decrypted value in any way
  that an attacker can observe, before the integrity check has passed.

  In practice:
    1. read the MAC
    2. verify it, in constant time
    3. ONLY THEN decrypt
    4. any error afterwards is a bug
```

## Where this shows up in real systems

- early CBC constructions without a MAC (the POODLE-era problem)
- JSON web tokens: the payload is decoded BEFORE the signature is checked
- encrypted cookies with no integrity tag
- archives ("decrypt then untar") - Zip Slip and zip bombs are this bug
EOF
cat 05-etm.md

# --- 6. the problem-to-primitive table, as a worksheet ---
cat > 06-worksheet.md <<'EOF'
# Problems → primitives

| Requirement | Primitive | Construction |
|---|---|---|
| confidentiality (with a shared key) | one-way permutation | stream cipher / block cipher in a secure mode |
| confidentiality (with a public key) | trapdoor permutation | RSA, ECIES |
| integrity from a shared key | PRF | HMAC, or encrypt-then-MAC |
| integrity + authenticity from a public key | one-way function + trapdoor | signature scheme |
| collision resistance | one-way function | hash function |
| password storage | slow one-way function | Argon2id, scrypt, bcrypt |
| key agreement | DDH-hard group | Diffie-Hellman, ECDH |
| forward secrecy | ephemeral DDH keys | (EC)DHE in every handshake |
| randomness | CSPRNG | /dev/urandom, not math.random, not rand() |

## The question to ask about any crypto you read

1. What requirement is this satisfying?
2. Which assumption does it rest on? (computational hardness, information
   theoretic, physical, or "the key stayed secret")
3. What is the KEY LENGTH in bits, for every key in the system?
4. What is the lifetime of the data being protected?
5. If the assumption breaks, what fails, and how long does it take?

If you cannot answer 2 and 3 for a system you are asked to assess, you
cannot assess it.
EOF
cat 06-worksheet.md
