Digital Signatures and Randomness

Summary

A signature gives you two things a MAC cannot: non-repudiation (the signer cannot credibly
deny it) and transferability (a third party can verify without a shared secret). The price is
a signature scheme is a randomised construction, and that fact causes most of its bugs.

The lecture's framing: the signing algorithm itself is easy; the
surrounding sign/verify protocol is where everything goes wrong.

What a signature is for

  MAC   integrity + authentication, needs a SHARED SECRET
        -> both parties can forge it -> no repudiation

  SIGNATURE  integrity + authenticity + non-repudiation
        -> the public key verifies, the private key signs
        -> only the holder could have produced it
        -> a third party can verify with no prior relationship

  THE PRICE:
    - slower (asymmetric)
    - larger (256 bytes vs 32)
    - it needs a certificate to bind a public key to an identity
      (cry-07), because a bare public key proves nothing about WHO
    - and it introduces randomness, which is where the bugs live

Schnorr signatures

  THE SIMPLEST CORRECT CONSTRUCTION, and the clearest:

  SETUP
    private key  x  (a random scalar)
    public key   y = g^x mod p

  SIGN(m, x)
    k = random nonce                       <- THE CRITICAL LINE
    R = g^k mod p
    e = H(R || y || m)      a hash into the challenge
    s = k - e*x mod (p-1)
    signature = (R, s)

  VERIFY(m, (R,s), y)
    e = H(R || y || m)
    check:  g^s == R * y^e  mod p

  WHY IT WORKS:
    e binds R and m. s encodes k - e*x. Substituting g^s:
      g^s = g^(k-e*x) = g^k * (g^x)^(-e) = R * y^(-e)
    so g^s == R * y^e iff s = k - e*x for SOME k, i.e. iff the
    signer knew x and the discrete log of R. Extractable.

  THIS IS BIP340 / EdDSA / Ed25519. The security is a random oracle
  model argument: forking lemma says an adversary who forges
  efficiently can extract x.

# Schnorr from scratch, with the nonce made deliberately WRONG, then fixed
import hashlib, secrets

p = 2**255 - 19
g = 5

def H(*parts):
    h = hashlib.sha256()
    for x in parts: h.update(x.to_bytes(32, "little"))
    return int.from_bytes(h.digest(), "little") % (p - 1) + 1

def keygen():
    x = secrets.randbelow(p - 1) + 1
    return x, pow(g, x, p)

def sign_fixed(m, x, y):
    k = secrets.randbelow(p - 1) + 1        # RANDOM nonce, every time
    R = pow(g, k, p)
    e = H(R, y, m)
    s = (k - e * x) % (p - 1)
    return (R, s)

def verify(m, sig, y):
    R, s = sig
    e = H(R, y, m)
    return pow(g, s, p) == (R * pow(y, e, p)) % p

def sign_bad_nonce_reuse(m, x, y, k):
    """THE BUG: reusing the nonce leaks the private key in two queries."""
    R = pow(g, k, p)
    e = H(R, y, m)
    s = (k - e * x) % (p - 1)
    return (R, s)

x, y = keygen()
m = b"AEGIS-Schnorr-demo"
sig = sign_fixed(m, x, y)
print(f"  verify(m)        : {verify(m, sig, y)}")
print(f"  verify(tampered) : {verify(b'tampered', sig, y)}")
print()

print("  === now the bug: a REUSED nonce ===")
k = secrets.randbelow(p - 1) + 1
s1 = sign_bad_nonce_reuse(b"message one", x, y, k)
s2 = sign_bad_nonce_reuse(b"message two", x, y, k)
R1 = s1[0]; e1 = H(R1, y, b"message one")
R2 = s2[0]; e2 = H(R2, y, b"message two")
print(f"  same R in both signatures: {R1 == R2}")
# s1 = k - e1*x, s2 = k - e2*x   ->   s1 - s2 = (e2 - e1)*x
leaked = ((s1[1] - s2[1]) * pow(e2 - e1, -1, p - 1)) % (p - 1)
print(f"  private key extracted from the public signatures: {leaked == x}")
print(f"  recovered x = {leaked}")
print()
print("  TWO signatures. That is the entire cost of the bug.")
print("  And it is the bug behind the PS3 ECDSA nonce failure (2010),")
print("  the Android Bitcoin wallet thefts (2013), and still the most")
print("  common implementation bug in signature schemes ever made.")

ECDSA, and its nonce

  ECDSA:
    sign:  k random, R = k*G, r = R.x mod n, s = k^-1 (H(m) + r*x) mod n
    verify with the standardisation from BIP 62 / RFC 6979

  THE NUMERICAL PROBLEM:
    if k < n and r*s and r are all in range, everything is fine.
    if k or s wraps to 0, the signature is invalid.
    if k or s is out of range [1, n-1], you have leaked information.

    k = 0 -> signing fails
    s = 0 -> signing fails
    s > n/2 -> MALLEABLE: (r, n-s) is also a valid signature
    k leaked -> x = (s*k - H(m)) * r^-1 mod n

  TWO MITIGATIONS, BOTH MANDATORY:
    1. RFC 6979: DETERMINISTIC k = HMAC-SHA256(x || m).
       No RNG at all in the nonce path. This ELIMINATES the entire
       class of bug rather than mitigating it.
    2. Low-S normalisation: reject s > n/2.
       Removes malleability. Also required by BIP 62.

  AND THE MALLEABILITY CONSEQUENCE, which is a real DoS and a real
  signature-forgery in the wrong context:
    if a server accepts (r,s) and also (r, n-s), then any observer
    who sees ONE valid signature can produce a SECOND valid signature
    for the same message. That breaks systems that assume "this
    signature is unique" - nonce-based dedup, transparent logging,
    and some blockchain designs.

What the random number generator must do

  A SIGNATURE NONCE NEEDS:
    - unpredictable (an attacker who knows k recovers x)
    - UNIQUE (reuse leaks, as shown)
    - uniformly distributed
    - secret, until used

  BECAUSE IT IS ONE SECRET VALUE PER OPERATION, a compromised or
  biased RNG IS A PRIVATE KEY COMPROMISE. Not a degradation. Total loss.

  THE FAILURE MODES, all of which have happened:
    - the same seed reused (VMs cloned from a template image)
    - a weak PRNG (early Bitcoin wallets: the Android SecureRandom bug)
    - concurrent signers sharing a PRNG state and producing the same k
    - fork() inheriting the same PRNG state across processes
    - entropy starvation at boot -> a low-entropy early nonce

# The concurrency bug, which is subtle and has caused real key theft
import os, threading
# A global PRNG shared between threads, with no locking:
_counter = 0
def weak_nonce():
    global _counter
    _counter += 1
    return _counter          # never repeats... but two threads can race

results = []
def worker(m):
    for _ in range(1000):
        n = weak_nonce()
        results.append(n)
ts = [threading.Thread(target=worker, args=(i,)) for i in range(8)]
[t.start() for t in ts]; [t.join() for t in ts]
dupes = [n for n, c in __import__("collections").Counter(results).items() if c > 1]
print(f"  {len(results)} nonces generated across 8 threads")
print(f"  duplicated nonces: {len(dupes)}")
print("  ^ a COUNTER is safe from reuse and UNSAFE from prediction.")
print("    A PRNG is the opposite. You need both properties:")
print("      unpredictable AND never repeated.")
print("    The only way to get both is a real CSPRNG with atomic")
print("    state updates (getrandom(2), /dev/urandom, or a kernel")
print("    syscall) - not a userspace counter, and not rand().")

Sign-then-verify, and the protocol around it

  WHAT ACTUALLY NEEDS SIGNING (not just hashing):
    - software updates and release artifacts
    - configuration that changes authorisation
    - firmware
    - document signatures (PDF, code signing, package managers)
    - anything where a MITM's edit must be detectable by a third party

  WHERE PEOPLE USE A PLAIN HASH AND ARE FINE:
    - an internal integrity check where all parties already share a secret
    - a checksum for corruption detection
    - a commitment inside a protocol that already authenticates

  THE ANTI-PATTERN:
    - "we sign the SHA-256 of the file" where the real fix is
      verifying the signature at all. Never signed = never verified.
    - verifying the hash AFTER using the data. Same bug as cry-02's
      tag ordering.

Deterministic signatures: the elegant middle

  Ed25519 signs deterministically: the nonce is derived from the
  private key AND the message (RFC 8032).

    k = SHA-512(private_key || message) mod L

  Consequences:
    + no RNG in the signing path at all
    + signatures are reproducible, which makes them testable
    + the nonce-reuse class is structurally impossible
    - a deterministic signature on the same message is identical,
      so it is not a unique identifier (Schnorr/BIP340 adds a
      separate nonce for that reason)

  BIP340 (Schnorr) adds an explicit nonce parameter for exactly this
  privacy reason, while keeping the signature maths Schnorr's.

Terminology

Term Meaning
Digital signature Integrity, authenticity, non-repudiation
Non-repudiation The signer cannot credibly deny signing
Schnorr signature g^s == R·y^e; the basis of EdDSA
Forking lemma Efficient forgery implies key extraction
ECDSA The other widespread scheme; nonce-sensitive
RFC 6979 Deterministic ECDSA nonces; eliminates the bug class
Low-S normalisation Reject s > n/2; removes malleability
Signature malleability (r,s) and (r,n-s) both valid
Nonce reuse Two signatures, one nonce, private key recovered
PS3 / Android failures Real key thefts from this exact bug
Deterministic signature No RNG; reproducible; Ed25519, BIP340
Code signing The main real-world use
Signing hash vs signing data Always hash first; never sign raw

#!/usr/bin/env python3
"""Schnorr signature nonce reuse: private key recovery.

Two signatures, one nonce. The private key falls out with elementary
arithmetic. This is the exact bug class behind the PS3 (2010) and
Android Bitcoin wallet (2013) failures.
"""
import hashlib, secrets

p  = 2**255 - 19
n  = p - 1
g  = 5

def H(*parts) -> int:
    h = hashlib.sha256()
    for x in parts: h.update(x.to_bytes(32, "little"))
    return int.from_bytes(h.digest(), "little") % n + 1

x = secrets.randbelow(n) + 1
y = pow(g, x, p)
k = secrets.randbelow(n) + 1          # one nonce, used twice
R = pow(g, k, p)

def sign(m):
    e = H(R, y, m)
    return (k - e * x) % n             # s = k - e*x

m1, m2 = b"transfer 0100 to alice", b"transfer 9900 to mallory"
s1, s2 = sign(m1), sign(m2)
e1, e2 = H(R, y, m1), H(R, y, m2)

print("  two signatures over different messages, same nonce:")
print(f"    (R, s1) for {m1.decode()}")
print(f"    (R, s2) for {m2.decode()}")
print()
print("    s1 = k - e1*x        (1)")
print("    s2 = k - e2*x        (2)")
print("    s1 - s2 = (e2-e1)*x  subtract (1)-(2)")
print()
recovered = ((s1 - s2) * pow(e2 - e1, -1, n)) % n
print(f"    recovered private key: {recovered}")
print(f"    matches the real one : {recovered == x}")
print()
print("    TWO SIGNATURES. That is the cost of the bug.")
print()
print("    ps3:      2010, Sony's ECDSA implementation returned the same")
print("               k for every signature. Private keys extracted at will.")
print("    android:  2013, Bitcoin wallets on a flawed SecureRandom.")
print("    ed25519:  no nonce RNG at all - k = SHA512(privkey || msg).")
print("    rfc6979:  same for ECDSA. The class is eliminated, not mitigated.")

_counter = 0; results2 = []
def worker2():
    global _counter

cat > 05-protocol.md <<'EOF'
# The signing protocol, not just the algorithm

The maths is the easy part. Almost every real signature failure is a
protocol failure.

```text
  WHAT MUST HAPPEN, IN ORDER:
    1. hash the content                     (never sign the raw bytes)
    2. sign the hash with a DETERMINISTIC nonce  (RFC 6979 / Ed25519)
    3. normalise s to low-S
    4. attach the signature AND the certificate chain
    5. the verifier:
         a. parse strictly                (length-prefixed, not delimited)
         b. validate the certificate chain to a trusted root
         c. check validity dates AND the hostname
         d. check key usage and constraints
         e. verify the signature
         f. check revocation status
         g. ONLY NOW use the content
```

## The orderings that produce real bugs

| Bug | Consequence |
|---|---|
| verify the signature, then use the data | forging is still a forgery, but the bug is a verification-ordering bug and you will be asked about it in the report |
| check the chain but not the hostname | a certificate for `example.com.evil.tld` validates |
| ignore expiry | a compromised 2018 key still works |
| ignore revocation | CRL/OCSP checked but a failure is treated as "valid" |
| accept any key the user supplies | no trust anchor at all; TOFU without the TOFU |
| cache a verification result by URL alone | ignores the cert entirely on a hit |
| compare a signature with `==` | timing oracle on the signature |

## Verification checklist to run against any deployment

```bash
# what is actually trusted here
openssl s_client -connect TARGET:443 -servername TARGET -showcerts </dev/null 2>/dev/null \
  | openssl x509 -noout -text | grep -E "Issuer|Subject|Not|Key Usage|Extended" | sed 's/^/  /'

# is the chain actually checked, or is -verify_return_error used?
echo | openssl s_client -connect TARGET:443 2>&1 | grep -E "Verify return code|verify error" | sed 's/^/  /'
#  "Verify return code: 0 (ok)"  is the only good answer
#  "Verify return code: 10 (certificate has expired)" is a finding
```

- [ ] hostname verified against the certificate, not the URL's suffix
- [ ] expiry enforced
- [ ] revocation checked (CRL or OCSP), and a failure is a FAILURE
- [ ] the chain terminates at a trust anchor the app controls
- [ ] signature compared with a constant-time function
- [ ] the hash is verified BEFORE any use of the content
- [ ] low-S enforced where the format allows malleability
EOF

     --include="*.py" --include="*.js" . | grep -B3 -A1 -iE "exec|eval|write|open\(|render|query" \

        | openssl x509 -noout -enddate 2>/dev/null)

     --include="*.py" --include="*.js" --include="*.php" --include="*.go" . | sed 's/^/  /'

the private key recovered with (s1 - s2) / (e2 - e1) mod n. Four lines of arithmetic. That is
the entire PS3 failure, the entire Android Bitcoin wallet theft, and the entire reason RFC 6979
exists.

Step 3 is the one people miss — a counter is safe from reuse and unsafe from prediction;
a PRNG is the reverse. You need both properties, and only a kernel CSPRNG gives you both.
