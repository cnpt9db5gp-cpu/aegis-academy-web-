Binary, Hex and the CPU Fetch-Execute Cycle

Summary

Everything a computer does is a number being moved and transformed. Before any of the higher
level work — reverse engineering, exploitation, protocol analysis — you need the fetch-execute
cycle to be automatic rather than something you have to think about.

The content here is the foundation: how a number is represented, how the CPU reads bytes, and
why that makes hex the native language of the field.

Everything is bits; we group them

  1 bit   0 or 1
  8 bits  1 byte    -> 0x00 .. 0xFF    256 values
  16 bits 2 bytes   -> uint16           65,536 values
  32 bits 4 bytes   -> uint32           4,294,967,296 values
  64 bits 8 bytes   -> uint64, pointer  1.8 x 10^19 values

  hex digit = 4 bits   ->  one hex digit is exactly half a byte
  hex byte  = 2 digits ->  0x41 is 0100 0001

Hex exists because binary grouping is unreadable and base 16 maps exactly onto nibbles. There
is no arithmetic in hex; it is a display convenience. 0x41 is the same as 65, which is the
same as 'A'.

Signed numbers, and why it matters for overflow

  int8:   0x7F = 127        0x80 = -128      (two's complement)
  int32:  0x7FFFFFFF = 2147483647
          0xFFFFFFFF = -1

  Two's complement:
    to invert:     flip every bit
    to negate:     invert, then add 1
    MIN_INT has no positive counterpart -> negation overflows

  Consequences:
    -1     as int32 = 0xFFFFFFFF
    -1     as uint32 = 4294967295
    ABS(INT_MIN) overflows to INT_MIN
    0x7FFFFFFF + 1 wraps to 0x80000000 (= INT_MIN)

This is exactly why cs161-03's integer overflow is a memory-safety bug:
the wraparound produces a small allocation size and a large write.

Endianness

  BIG ENDIAN ("network byte order")   0xDEADBEEF
    memory:  DE AD BE EF     (most significant byte first)

  LITTLE ENDIAN (x86)                 0xDEADBEEF
    memory:  EF BE AD DE     (least significant byte first)

  Why you care: the SAME 4 bytes are a different integer on each machine.
  Anything that crosses a machine boundary must convert. Raw shellcode,
  raw packet structures, and exploit payloads are all machine-specific.

  Network protocols are big-endian. x86 is little-endian. Protocol
  parsers are therefore a conversion exercise, and a place bugs live.

python3 -c "
import struct, sys
print('  sys.byteorder =', sys.byteorder)
b = b'\xef\xbe\xad\xde'
print('  bytes on the wire :', b.hex())
print('  as little-endian  : 0x%08x' % struct.unpack('<I', b)[0])
print('  as big-endian     : 0x%08x' % struct.unpack('>I', b)[0])
"

The fetch-execute cycle

  CPU STATE:
    PC     program counter - address of the NEXT instruction
    IR     instruction register - the instruction being executed
    FLAGS  condition codes from the last operation
    GPRs   general purpose registers (rax, rbx, rcx, rdx, rsi, rdi, ...)

  LOOP, forever:
    1. FETCH     IR <- memory[PC];  PC <- PC + length(instruction)
    2. DECODE    what operation, which operands, which encoding length
    3. EXECUTE   perform the operation; update FLAGS
    4. (repeat)

  Two things follow from this loop and nothing else:

    a) THE CPU ONLY READS BYTES. It has no concept of "a string" or
       "an integer". Every data structure is your interpretation layered
       on a byte stream. Every type confusion bug is this fact exploited.

    b) IT IS DETERMINISTIC. Given the same initial state and the same
       bytes, it does the same thing. Which is why programs are
       reproducible, debuggable, and fully reverse-engineerable.

Point (a) is the load-bearing insight. A buffer overflow, a type
confusion, and a string being "null-terminated" are all the same fact seen
from different angles: the CPU has no type system.

Why this makes reverse engineering possible

  A binary is a file of bytes.
    - the .text section is a sequence of instruction bytes
    - the .rodata section is a sequence of constants
    - the .data/.bss sections are a sequence of variables

  If instruction encodings are regular (and on x86-64 they are, once you
  know the prefixes), a disassembler can recover the instructions from
  bytes alone. There is no source. There is no metadata. The bytes are
  the program.

  That is why x86 disassembles well and Python bytecode does not: Python
  has a data-driven opcode table, x86 has a mostly fixed-width structure.

python3 - <<'PY' | tee 01-conversions.txt
print("  === hex <-> decimal <-> binary ===")
for h in (0x00, 0x41, 0xFF, 0xDEADBEEF):
    print(f"  0x{h:08X} = {h:<12} = {h:032b}")
print()
print("  === signed vs unsigned, same bytes ===")
import struct
for v in (-1, 0, 127, -128, 2147483647):
    b = struct.pack("<i", v)
    print(f"  {v:>12} -> 0x{int.from_bytes(b,'little'):08X}  bytes {b.hex()}")
print()
print("  === endianness ===")
b = struct.pack("<I", 0xDEADBEEF)
print(f"  pack 0xDEADBEEF little-endian -> {b.hex()}")
print(f"  read those bytes as big-endian   -> 0x{int.from_bytes(b,'big'):08X}")
print("  the SAME bytes, two different numbers. That is endianness.")
PY

# --- 2. the fetch-execute cycle, runnable ---
cat > 02-fetch-execute.sh <<'EOF'
#!/usr/bin/env bash
# Show a CPU actually reading bytes and executing them.
cat > /tmp/loop.asm <<'ASM'
global _start
section .text
_start:
    mov     rax, 10            ; SYS_exit
    mov     rbx, 0             ; exit status
    mov     rcx, 5             ; a counter
.loop:
    dec     rcx                ; the instruction
    jnz     .loop              ; branch on FLAGS (ZF set when rcx == 0)
    mov     rax, 60            ; SYS_exit (overwritten: see note)
    mov     rbx, 0
    inc     rbx                ; exit code 1, so we can see it worked
    syscall
    mov     rax, 60
    mov     rbx, 0
    syscall
ASM
if ! command -v nasm >/dev/null; then echo "  nasm not installed (apt install nasm)"; exit 0; fi
nasm -f elf64 /tmp/loop.asm -o /tmp/loop.o && ld -o /tmp/loop /tmp/loop.o
echo "  === the machine code the CPU will execute ==="
xxd /tmp/loop | sed 's/^/  /'
echo
echo "  === run it ==="
/tmp/loop; echo "  exit code: $?  (1 = the loop ran and the syscall worked)"
rm -f /tmp/loop.asm /tmp/loop.o /tmp/loop
EOF
chmod +x 02-fetch-execute.sh
./02-fetch-execute.sh

# --- 3. the byte stream is the program ---
{
  echo "=== a binary is bytes; here is where they live ==="
  printf '  int main(void){return 0;}\n' > /tmp/tiny.c
  gcc -O0 -no-pie /tmp/tiny.c -o /tmp/tiny
  readelf -SW /tmp/tiny | awk 'NR<=5 || /\.text|\.rodata|\.data|\.bss|\.got/' | sed 's/^/  /'
  echo
  echo "=== the actual instruction bytes of main ==="
  objdump -d /tmp/tiny | sed -n '/<main>:/,/^$/p' | sed 's/^/  /'
  echo
  echo "=== those are the bytes the CPU fetches, one after another ==="
  echo "    change one byte and the behaviour changes. There is nothing else."
  rm -f /tmp/tiny.c /tmp/tiny
} 2>&1 | tee 03-bytes.txt

# --- 4. types do not exist at the machine level ---
python3 - <<'PY' | tee 04-no-types.txt
import struct
raw = struct.pack("<I", 0x41414141) + struct.pack("<d", 1.5)
print("  12 bytes of memory, no type information whatsoever:")
print("   ", raw.hex())
print()
print("  read as: uint32 + double ->", struct.unpack("<Id", raw))
print("  read as: double + uint32 ->", struct.unpack("<dI", raw))
print("  read as: four uint8s     ->", struct.unpack("<BBBB", raw))
print()
print("  Three different, equally valid interpretations of the same 12 bytes.")
print("  The CPU does not know which one the programmer intended.")
print("  Type confusion is simply 'use the wrong interpretation on purpose'.")
print()
print("  What DOES survive: structure at a known offset, alignment rules,")
print("  and length prefixes. Everything else is a convention between")
print("  programmers that the hardware cannot enforce.")
PY
cat 04-no-types.txt

# --- 5. hex is a first-class skill: xxd and friends ---
{
  echo "=== tools for thinking in bytes ==="
  printf 'AEGIS\x00\x01\x02\xff' > /tmp/sample.bin
  echo "  --- xxd (the default) ---"
  xxd /tmp/sample.bin | sed 's/^/  /'
  echo "  --- xxd with offsets in hex ---"
  xxd -g1 -c8 /tmp/sample.bin | sed 's/^/  /'
  echo "  --- a specific offset range ---"
  xxd -s 5 -l 4 /tmp/sample.bin | sed 's/^/  /'
  echo "  --- patch a byte in place ---"
  printf '\x41' | dd of=/tmp/sample.bin bs=1 seek=5 count=1 conv=notrunc 2>/dev/null
  xxd /tmp/sample.bin | sed 's/^/  after patching offset 5: /'
  echo
  echo "  xxd -r reverses it, so you can convert hex <-> binary reliably:"
  echo "    xxd -r -p 41 47 49 53  > /tmp/back.bin && xxd /tmp/back.bin"
  printf '41474953' | xxd -r -p | xxd | sed 's/^/  /'
  rm -f /tmp/sample.bin /tmp/back.bin
} 2>&1 | tee 05-hex-tools.txt

Step 4 is the load-bearing demonstration: the same 12 bytes read as (uint32, double) or
(double, uint32) give different answers, with no error from either. That is type confusion
reduced to its essence, and it is why a memory-corruption bug is an interpretation bug
before it is a control-flow bug.
