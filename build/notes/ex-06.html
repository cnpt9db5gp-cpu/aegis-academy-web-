Bypassing NX, PIE and Full RELRO

Summary

The final board. With NX on, PIE on, and Full RELRO, most of the classic routes are closed. What
remains is a set of specific, well-understood techniques — and the recognition that a hardened
binary often is not the right target.

Key ideas

  • NX: return to existing code (ROP, ret2libc), or place shellcode somewhere executable and jump
  • PIE: leak the binary base or a libc pointer from a format string or an uninitialised read
  • Full RELRO: GOT is read-only → target __malloc_hook/__free_hook (older glibc), the
    exit handlers, a .fini_array entry, or overwrite a live function pointer
  • Modern glibc (2.34+) removed __malloc_hook/__free_hook — use environ, TLS, or FSOP
  • Stack pivot: move RSP to a larger writable region to gain more overflow capacity
  • JOP / SROP: when you cannot find a usable chain in the binary
  • The honest answer: a properly hardened binary is not the way in. Look for a weaker service.

The hardened binary's attack surface

Mitigation Closed off What is still open
NX Stack shellcode ROP, ret2libc, writable+executable regions (JIT, ld.so)
PIE Fixed code addresses Info leaks, partial over-reads, uninitialised stack
Full RELRO GOT overwrite Function pointers, exit handlers, heap metadata, hooks
Canary Blind overflow Leaks first; then all of the above
seccomp Forbidden syscalls Allowed syscalls, and their side effects

Terminology

Term Meaning
__malloc_hook / __free_hook glibc function pointers (removed in 2.34)
FSOP File-stream-oriented programming: corrupt a FILE* for hijack
_IO_list_all Head of the glibc FILE chain; corrupting it is an FSOP primitive
SROP Sigreturn-oriented programming: fake a signal frame to get registers
JOP Jump-oriented programming: dispatch via a table
Stack pivot Move RSP into an attacker-controlled large buffer
one-gadget libc address where constraints are already satisfied
Tcache poisoning Overwrite a freed chunk's forward pointer
environ The process environment block, on the stack, always mapped

# --- writable+executable regions would defeat NX outright ---
python3 - <<'PY'
import os, re
found = []
for pid in [os.getpid()]:
    try:
        for line in open(f"/proc/{pid}/maps"):
            m = re.match(r"([0-9a-f]+)-([0-9a-f]+) (\S+) ", line)
            if m and m.group(3) == "rwxp":
                found.append(line.strip())
    except PermissionError:
        pass
print("  writable+executable mappings in this process:", found or "none")
print("  If any existed, NX would be bypassable without ROP.")

Field lab

Objective: audit a fully hardened binary, enumerate what remains open, and demonstrate the
stack pivot that beats a small buffer.

mkdir -p ~/aegis/labs/ex-06 && cd ~/aegis/labs/ex-06

cat > target.c <<'EOF'
#include <stdio.h>
#include <string.h>
#include <unistd.h>
void win(void) { write(1, "you win\n", 8); }
void vuln(void) { char buf[32]; read(0, buf, 200); }   /* small buf, big read */
int main(void) { vuln(); return 0; }
EOF

# --- build the fully hardened version ---
gcc -Wall -g -O0 -fstack-protector-strong -pie -fPIE -D_FORTIFY_SOURCE=2 \
    -Wformat -Werror=format-security -Wl,-z,relro,-z,now target.c -o target-hardened

{
  echo "=== protection report ==="
  checksec --file=./target-hardened
  echo
  echo "=== raw evidence ==="
  readelf -h ./target-hardened | grep Type
  readelf -lW ./target-hardened | grep -E "GNU_STACK|GNU_RELRO"
  readelf -d ./target-hardened | grep -E "BIND_NOW|FLAGS"
  objdump -R ./target-hardened 2>/dev/null | head -6
} 2>&1 | tee 01-audit.txt

cat 01-audit.txt

# --- 1. how much can we actually write? ---
echo
echo "=== how far does the overflow reach? ==="
python3 - <<'PY' | tee 02-reach.txt
import subprocess, struct
# 32-byte buffer + canary + saved rbp, then everything after is ours to write
for n in [40, 56, 72, 96, 128, 160, 200]:
    r = subprocess.run(["./target-hardened"], input=b"A"*n, capture_output=True, timeout=5)
    status = "clean" if r.returncode == 0 else ("canary abort (134)" if r.returncode == 134 else f"crash ({r.returncode})")
    print(f"  wrote {n:>4} bytes -> {status}")
print()
print("  The canary stops a naive overflow, but the WRITE still succeeded.")
print("  That is why leaks matter: the memory past the buffer is readable.")

# --- 2. THE STACK PIVOT: 32 bytes is too small, so move RSP ---
cat > 03-stack-pivot.md <<'EOF'
# Stack pivoting: getting a bigger overflow

## The problem
`buf[32]` plus canary plus saved RBP gives you about 40 usable bytes of chain.
A useful chain needs 40-80 bytes (three gadgets plus three arguments).

## The idea
You do not need the chain to live at the original stack pointer. You only
need `rsp` to point at it when the chain executes.

## Method A: leave; ret
    *   leave           ; rsp = rbp ; pop rbp
    *   ret             ; jumps to [rbp]

So if you overwrite **saved RBP** with the address of your buffer, then trigger
`leave; ret`, execution returns into your own buffer.

## Method B: pop rsp; ret
Find `pop rsp ; ret` (or `xchg rsp, rax ; ret`). Overwrite the saved return
address with it, then your next 8 bytes become the new stack pointer.

## Method C: xchg rax, rsp
Common in modern glibc startup code, and a classic CTF pivot target.

## What you need a *big* writable buffer for
Write your shellcode (or chain) to a known location first — `.bss`, the heap,
or a location you read() into — then pivot there.

## Lab-safe demonstration
`leave; ret` present in the binary, a 32-byte overflow, and a scratch buffer
on the heap you control.
EOF
cat 03-stack-pivot.md

raw = open("./target-hardened","rb").read()
base = 0
# find the load base for a PIE binary by reading /proc/self/maps style offsets;
# for scanning we report file offsets plus the usual base so you can add ASLR later
import subprocess
out = subprocess.run(["readelf","-h","./target-hardened"],capture_output=True,text=True).stdout
type_ = [l for l in out.splitlines() if "Type:" in l][0].split(":")[1].strip()

patterns = {
    "leave ; ret":            b"\xc9\xc3",
    "pop rsp ; ret":          b"\x5c\xc3",
    "xchg rsp, rax ; ret":    b"\x48\x94\xc3",
    "pop rbp ; ret":          b"\x5d\xc3",
}
for name, pat in patterns.items():
    hits = [i for i in range(len(raw)-len(pat)+1) if raw[i:i+len(pat)] == pat]
    locs = ", ".join(f"0x{x:x}(file)" for x in hits[:3]) or "none"
    print(f"  {name:<24} {locs}")

# --- 4. what is left after every mitigation ---
cat > 05-remaining-surface.md <<'EOF'
# What is still available against a fully hardened binary

## Closed
- stack shellcode (NX)
- hardcoded code addresses (PIE)
- GOT overwrites (Full RELRO)
- blind stack smashing (canary)

## Open
1. **Info leaks** — format strings, uninitialised reads, out-of-bounds reads,
   use-after-free. Every real exploit chain starts here.
2. **Heap exploitation** — tcache poisoning, fastbin dup, house of force.
   Independent of NX/PIE/RELRO entirely.
3. **Function pointers** — `__free_hook`/`__malloc_hook` (pre-2.34), C++ vtables,
   exit handlers, `.fini_array`, `atexit` chains.
4. **FSOP** — corrupt a glibc `FILE*` structure; `_IO_list_all` walks the chain
   on flush, so corrupting it hijacks control. Survives Full RELRO.
5. **environ / TLS** — both are mapped and writable-from-a-leak; TLS `dtv` is
   a per-thread gadget source on some glibc versions.
6. **SROP** — a single `syscall; ret` plus a forged `rt_sigframe` on the stack
   gives you every register at once. Needs no gadgets at all.
7. **Kernel bugs** — a kernel exploit sidesteps every userspace mitigation.
8. **The weakest service** — usually the answer.

## The strategic point
A hardened binary raises the cost of an exploit; it does not remove the bug.
If your only path is a hardened binary, you are probably on the wrong host,
or the wrong service. This is `vulnerability-risk-exploit` in practice: risk is
likelihood times impact, and a hard target is not a soft one.
EOF
cat 05-remaining-surface.md

# --- 6. the honest professional conclusion ---
cat > 06-strategy.md <<'EOF'
# When to stop trying to exploit the hardened binary

Escalate down this list rather than grinding on one target:

1. Re-read the protections — you may have missed a weaker service on the host.
2. Look for credentials on that host, then use them against something softer.
3. Look for a different service entirely.
4. Look for the network: is there a host that trusts this one?
5. Look at the application layer, where mitigations usually do not apply.
6. Only then consider heap exploitation, FSOP or SROP.
7. Kernel exploitation is genuinely the last resort.

Every hour spent on a hardened binary is an hour not spent on the other four
hosts you already have credentials for. Enumeration breadth beats depth.
EOF
