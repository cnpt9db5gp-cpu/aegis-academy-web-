Virtualisation, Snapshots and Network Isolation

Summary

Everything in Tier 8 runs on a lab you build. The lab's properties decide whether the exercises
teach anything: a lab with internet access teaches you to attack yourself, and a lab without
snapshots teaches you to rebuild everything after every mistake.

The framing: the lab is the instrument, and a badly built lab
teaches the wrong lesson. Three properties matter — isolation,
snapshots, and network topology — and each of them maps to a specific
mistake it prevents.

Companion to lab-02 (the targets) and lab-03 (the domain). This
note is the platform underneath all of them.

Network isolation: the topology

  THE TOPOLOGY, and each link has a purpose:

    ┌─────────────────────────────────────────────┐
    │ HOST (Kali)                                 │
    │   vboxnet0  192.168.56.1/24   (host-only)   │
    │   vboxnet1  10.10.10.1/24    (host-only)   │
    └────────┬────────────────────┬───────────────┘
             │                    │
        ┌────▼─────┐         ┌────▼────┐
        │  DC01    │         │  WKS01  │
        │ .56.10   │         │ .56.20  │
        │ +.10.10.5│         │         │
        └────┬─────┘         └─────────┘
             │
        ┌────▼──────────┐
        │  SRV01        │
        │ 10.10.10.20   │   INTERNAL ONLY. Reachable only via the DC.
        └───────────────┘

  WHY TWO HOST-ONLY RANGES:
    192.168.56.0/24 is "EXTERNAL" in the fiction - it is where your
    workstation and the initial victims sit.

    10.10.10.0/24 is "INTERNAL" - it is where the servers sit, and
    nothing in 192.168.56.0/24 can route to it without a pivot
    through a compromised host.

    THAT IS THE ENTIRE POINT. `ad-06` and `tcm-06` are about pivoting,
    and you cannot practise pivoting on a flat network. Two ranges
    with one dual-homed host is the minimum that makes a pivot real.

  WHY HOST-ONLY AND NOT BRIDGED:
    bridged puts the lab VMs on your real LAN, which means:
      - your neighbours' machines can reach your deliberately
        vulnerable targets
      - your deliberately vulnerable targets can reach the internet
      - and if you run a scan, it hits your real network

    HOST-ONLY means: the VMs can talk to the host and to each other,
    and nothing else. Not the internet, not your LAN, not the world.

cat > 02-network.sh <<'EOF'
#!/usr/bin/env bash
# Build the lab network. Host-only ranges only. No NAT, no bridging.
echo "=== 1. is VirtualBox managing them, or Linux? ==="
echo "  TWO WAYS, and both work:"
echo
echo "  A. VirtualBox managed (preferred - survives a reboot)"
echo "     GUI:  Tools > Host Network Manager > Create"
echo "     vboxnet0 -> 192.168.56.1/24, DHCP on, 192.168.56.100-200"
echo "     vboxnet1 -> 10.10.10.1/24,    DHCP on, 10.10.10.100-200"
echo "     CLI:   VBoxManage hostonlynet add --netmask 255.255.255.0"
echo "             VBoxManage hostonlynet ip add vboxnet0 192.168.56.1"
echo
echo "  B. Linux-managed bridge (simpler, does NOT survive a reboot)"
echo "     the commands below:"
echo
echo "=== 2. the Linux bridges (option B) ==="
if ip -br a | grep -q "192.168.56"; then
  echo "  vboxnet0 already present:"
  ip -br a | grep 192.168.56 | sed 's/^/    /'
else
  echo "  creating vboxnet0"
  sudo ip link add vboxnet0 type bridge 2>/dev/null \
    && sudo ip addr add 192.168.56.1/24 dev vboxnet0 \
    && sudo ip link set vboxnet0 up && echo "    done"
fi
if ip -br a | grep -q "10.10.10"; then
  echo "  vboxnet1 already present:"
  ip -br a | grep 10.10.10 | sed 's/^/    /'
else
  echo "  creating vboxnet1"
  sudo ip link add vboxnet1 type bridge 2>/dev/null \
    && sudo ip addr add 10.10.10.1/24 dev vboxnet1 \
    && sudo ip link set vboxnet1 up && echo "    done"
fi
echo
echo "=== 3. VERIFY THE ISOLATION - this is the critical check ==="
echo "  current routes:"
ip route | sed 's/^/    /'
echo
echo "  EXPECTED: no default route changes, no NAT, nothing pointing"
echo "  at your real LAN gateway except your real interface."
echo
echo "  THE TEST THAT MATTERS:"
printf "  can a lab VM reach the internet?  "
if ip -br a | grep -q vboxnet; then
  echo "check from inside a VM (see below)"
else
  echo "no bridges present yet"
fi
echo
echo "  From inside a lab VM:"
echo "    ping -c1 8.8.8.8          must FAIL"
echo "    ping -c1 192.168.1.1      must FAIL (that is your real router)"
echo "    ping -c1 192.168.56.1     must SUCCEED (the host)"
echo "    ping -c1 10.10.10.20      must FAIL unless routed via the DC"
echo
echo "  IF A VM CAN REACH THE INTERNET, STOP AND FIX IT BEFORE"
echo "  INSTALLING ANY TARGET. A lab with egress is a lab that can"
echo "  attack something that is not yours."
EOF
chmod +x 02-network.sh
./02-network.sh 2>&1 | tee 03-network.txt

Snapshots: the thing that makes a lab usable

  WHY SNAPSHOTS, and the alternative:

    WITHOUT SNAPSHOTS   you rebuild 40 VMs after every exercise.
                        So you do fewer exercises, and you avoid
                        the ones that break things - which are
                        exactly the ones that teach.

    WITH SNAPSHOTS      one click, ten seconds, back to the start.
                        So you run ad-07's GPO abuse against a
                        domain controller knowing that you cannot
                        permanently break your own lab.

  THE FOUR SNAPSHOTS TO TAKE, in order:

    01-BASE           the OS, installed and updated, before anything
    02-DOMAIN         promoted to DC, with the lab AD built
    03-TARGETS        the deliberately vulnerable applications deployed
    04-PRE-EXERCISE   clean, ready, with the tooling present

  AND THE ONE MOST PEOPLE FORGET:

    05-AFTER-AD-05    taken AFTER you have dumped NTDS and installed
                      tooling. If you dump the hashes and then restore
                      to 03, you have to dump them again - and if you
                      DON'T restore, your lab is full of artefacts
                      from your own experiment that you will later
                      mistake for evidence of a real attack.

    That is not hypothetical. It is the single most common way a
    student's lab produces a false positive in a report.

cat > 04-snapshots.sh <<'EOF'
#!/usr/bin/env bash
# Snapshot discipline.
SNAP="VBoxManage snapshot"
VM="${1:?usage: ./04-snapshots.sh <vm-name> [snapname]}"
NAME="${2:-manual}"
echo "=== snapshot $NAME for $VM ==="
echo "  take:"
echo "    $SNAP \"$VM\" take \"$NAME\" --description \"$(date -u +%FT%TZ) $NAME\""
echo
echo "  restore (this is destructive - everything since is gone):"
echo "    $SNAP \"$VM\" restore \"$NAME\""
echo
echo "  list:"
echo "    $SNAP \"$VM\" list"
echo
echo "=== the VM state machine, and why it matters ==="
cat <<'STATE'
  powered-off   the snapshot captures disk state cleanly
  saved         a suspend - NOT a good snapshot point. Resume it and
                it will restore a live filesystem with a live clock.
  running       taking a snapshot is fine (VirtualBox freezes it) but
                restoring while running reverts to the snapshot's
                disk AND the machine resumes at that point with a
                different clock

  RULE: take snapshots with the VM POWERED OFF, or accept that the
        restored machine has a wrong clock and a dirty journal.
STATE
echo
echo "=== a snapshot script that enforces it ==="
cat <<'SCRIPT'
  #!/usr/bin/env bash
  set -euo pipefail
  VM="${1:?vm name}"; NAME="${2:?snapshot name}"
  state=$(VBoxManage showvminfo "$VM" | grep -m1 "^VM State" | tr -s ' ' | cut -d' ' -f3)
  if [ "$state" != "powered off" ]; then
    echo "REFUSING: $VM is '$state'. Power it off first."
    echo "  A snapshot of a running VM restores to a live filesystem."
    exit 3
  fi
  VBoxManage snapshot "$VM" take "$NAME" --description "$(date -u +%FT%TZ) $NAME"
  echo "taken: $NAME"
SCRIPT
echo
echo "=== the TIME problem, which will bite you ==="
echo "  A restored VM often boots with the clock at the snapshot time"
echo "  or at 1970. That breaks:"
echo "    - Kerberos (5-minute clock skew tolerance)"
echo "    - event log timeline reconstruction"
echo "    - any 'was this file newer than X' analysis"
echo "  After restoring a DC snapshot, sync the clock BEFORE testing:"
echo "    sudo timedatectl set-ntp true"
echo "    # and point it at your host running chrony, or at the other DC"
EOF
chmod +x 04-snapshots.sh
./04-snapshots.sh "DC01" "example" 2>&1 | tee 05-snapshots.txt

Resource planning

  THE ARITHMETIC THAT DECIDES WHAT YOU CAN RUN

    RAM is the binding constraint. 30 GiB total.
    - Windows Server DC:      4 GiB (2 GiB works for a small forest,
                                       4 GiB for a forest with GPOs)
    - Windows workstation:    4 GiB
    - Linux web target:       2 GiB
    - Linux file/smb target:  2 GiB
    - Overhead for the host:  4 GiB (your Kali, your tools)
    ------------------------------------------
    Total:                   16 GiB, leaves 14 GiB headroom

    THE RULE: never run more than three VMs at once on this host.
    A fourth will start swapping, and a swapping VM makes Kerberos
    and timeouts behave strangely, which corrupts your lesson.

  DISK
    400 GiB free. Each Windows VM is 60 GiB provisioned, ~25 GiB
    actually used. Five VMs is 125 GiB. Fine.

  CPU
    12 cores / 16 threads. Windows VMs want 2 vCPU each. Five VMs
    wanting 10 vCPU on a 16-thread host is fine as long as they are
    not all running nmap -A simultaneously.

  THE PERFORMANCE WARNING
    Without /dev/kvm, VirtualBox runs guests in software emulation.
    A Windows VM takes 10-50x longer to boot and to install updates.
    An hour of "install Windows Server" becomes a day. Check /dev/kvm
    first, before you start.

{
  echo "=== the /dev/kvm check, which decides your whole evening ==="
  if [ -c /dev/kvm ]; then
    echo "  /dev/kvm EXISTS - guests will run at near-native speed"
    ls -la /dev/kvm | sed 's/^/    /'
    groups | grep -o "kvm" | head -1 | sed 's/^/    you are in the kvm group: /' \
      || echo "    you are NOT in the kvm group: sudo usermod -aG kvm \$USER"
  else
    echo "  /dev/kvm MISSING"
    echo
    echo "  Causes, in order of likelihood:"
    echo "    1. the kvm kernel module is not loaded:  sudo modprobe kvm"
    echo "    2. your CPU lacks VT-x/AMD-V (check /proc/cpuinfo flags)"
    echo "    3. you are in a VM yourself without nested virtualisation"
    echo
    echo "  IF YOU CANNOT GET KVM: the lab still works, but budget"
    echo "  5-10x the time for VM setup, and prefer Linux targets."
  fi
} 2>&1 | tee 06-kvm.txt
