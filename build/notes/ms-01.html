Course Overview & The Shell

Summary

MIT's The Missing Semester of Your CS Education exists because every computer science degree
assumes you already know how to use a command line, an editor, a version control system, and a
debugger — and almost nobody does. For a security student this is not a nice-to-have: the shell
is the primary interface of your entire profession. nmap, gdb, john, metasploit, and
every exploit script you will ever write are driven from a terminal.

Lecture 1 covers the mental model: what a shell actually is, what happens when you press Enter,
and why that matters.

What actually happens when you press Enter

you type:   nmap -sV 127.0.0.1
    ↓
1. LINE EDITING     the terminal (readline) handles arrows, history, tab completion
    ↓
2. PARSING          the shell splits the line into words: nmap | -sV | 127.0.0.1
    ↓
3. EXPANSION        ~ becomes /home/nwpcs;  * becomes filenames;  $VAR becomes a value
    ↓
4. PATH LOOKUP      find an executable named nmap in the directories in $PATH
    ↓
5. EXECUTION        fork() a copy, execve() the binary, the parent waits
    ↓
6. EXIT CODE        the shell records 0 (success) or non-zero (failure)

Why this matters: most "the shell is broken" moments are actually a failure at step 4 (not
found on PATH) or step 3 (an expansion you did not intend). Knowing the six steps turns a vague
frustration into a specific diagnosis.

The essential builtins

Most of what you type is a builtin — implemented inside the shell itself, not a program on
disk. This matters because builtins work when /usr/bin is broken, which is exactly the
situation after a partial compromise or a broken chroot.

# Which of these is the shell itself, and which is a file on disk?
# `type -t` answers precisely: builtin | file | alias | keyword | function
for b in cd pwd echo export type command source alias history jobs kill test \
         which ls cat; do
  printf '  %-9s %s\n' "$b" "$(type -t "$b")"
done

Every builtin above is implemented inside bash. which, ls and cat
are file — separate programs on disk. That distinction is the whole
reason builtins survive a broken /usr/bin, so it is worth being able
to ask rather than assume.

Job control

Symbol Meaning
& run in background
Ctrl+Z suspend (SIGTSTP) — pauses, does not kill
bg resume in background
fg resume in foreground
Ctrl+C interrupt (SIGINT)
Ctrl+\ quit (SIGQUIT) — produces a core dump
$! PID of the last background job
kill %1 signal job 1 
# --- PRE-FLIGHT: this lab needs root, so authenticate ONCE, HERE, first ---
# `sudo something &` backgrounds the password PROMPT along with the command.
# With no terminal attached to answer it, sudo fails - and `2>/dev/null`
# then throws away the only clue. The result is a capture file that was
# never written, followed by a screenful of "no such file".
#
# `sudo -v` validates the credential in the FOREGROUND, where you can see
# and answer the prompt. It caches for ~15 minutes, so every backgrounded
# `sudo` below is prompt-free and actually runs.
if ! sudo -v; then
  echo "  sudo is unavailable or the password was wrong - stop here." >&2
  echo "  Everything below needs root. Nothing will be captured." >&2
  exit 1
fi
sleep 1000 &
jobs
fg %1
kill %1

# run something long, multitask, and come back to it
sudo nmap -sV -p- 192.168.56.101 &
tail -f /var/log/syslog        # use the terminal meanwhile
jobs                          # see it still running
fg %1                          # come back

Multiple terminals

Ctrl+Shift+T opens a new tab; Ctrl+Shift+N a new window. Learn this now. Long scans belong
in one tab while you work in another. Beginners lose fifteen minutes of scan output by
forgetting Ctrl+C will not stop an nmap run gracefully.

Shell scripting preview

A script is a file of shell commands. The three lines that make it a script rather than a
command list:

#!/bin/bash          # which interpreter runs this
set -euo pipefail     # fail fast, fail on unset vars, fail on pipe errors
echo "hello ${USER}"

Those three safety lines are the difference between a script that tells you what went wrong and
one that silently continues with empty variables.

Terminology

Term Meaning
Shell The interpreter: reads a line, expands it, executes it
Builtin A command implemented inside the shell (cd, export)
External command A program on disk (ls, nmap, python3)
PATH Ordered directories searched for executables
Expansion Substitution before execution: ~, *, $VAR, $(cmd)
Quoting "…" allows expansion; '…' forbids it; \ escapes one character
Job control Background, foreground, suspend, kill
Signal A message to a process: SIGINT (2), SIGTERM (15), SIGKILL (9)
Exit code 0 = success; anything else = failure
Shebang #! line naming the interpreter

Kali commands

# --- what is my shell and where does it search? ---
# --- PRE-FLIGHT: this lab needs root, so authenticate ONCE, HERE, first ---
# `sudo something &` backgrounds the password PROMPT along with the command.
# With no terminal attached to answer it, sudo fails - and `2>/dev/null`
# then throws away the only clue. The result is a capture file that was
# never written, followed by a screenful of "no such file".
#
# `sudo -v` validates the credential in the FOREGROUND, where you can see
# and answer the prompt. It caches for ~15 minutes, so every backgrounded
# `sudo` below is prompt-free and actually runs.
if ! sudo -v; then
  echo "  sudo is unavailable or the password was wrong - stop here." >&2
  echo "  Everything below needs root. Nothing will be captured." >&2
  exit 1
fi
echo "$SHELL"
echo "$PATH" | tr ':' '\n'
type -a nmap          # is it builtin, alias, or a path?
command -v nmap

# --- expansion, the thing that surprises everyone ---
echo ~                  # home
echo *                  # every file in cwd
echo *.md
echo "quoted * stays literal"
echo 'single quoted $HOME stays literal'
echo \$HOME              # escaped
file=$(ls *.md | head -1) && echo "first file: $file"   # command substitution

# --- background and resume ---
sleep 300 &
sudo nmap -sV -p- 192.168.56.101 > scan.txt 2>&1 &
jobs -l
tail -f scan.txt       # watch it while you do something else
kill %1                # or let it finish

# --- a real recon loop in the background, then go get coffee ---
{
  for ip in $(seq 1 254); do
    ping -c1 -W1 192.168.56.$ip >/dev/null 2>&1 && echo "192.168.56.$ip"
  done
} > ~/aegis/labs/alive-hosts.txt 2>&1 &
echo "scan running as PID $!"

# --- signals: the difference that matters ---
kill -TERM  <pid>   # graceful, cleanup runs
kill -KILL  <pid>   # no cleanup, last resort
kill -0    <pid>   # does this process exist? (permission check too)

# --- your own shell's memory ---
declare -p PATH | head -1
set | grep -E '^(SHELL|HOME|USER|PATH)='

Field lab

Objective: internalise the six-step execution model, and produce your first multi-host
discovery run using only shell builtins and tools you already have.

mkdir -p ~/aegis/labs/ms-01 && cd ~/aegis/labs/ms-01

# --- STEP BY STEP: trace one command ---
{
  echo "1. the line as typed:"
  echo '   nmap -sV --version-light -p- 127.0.0.1'
  echo
  echo "2. what it expands to:"
  echo "   $(echo nmap -sV --version-light -p- 127.0.0.1)"
  echo
  echo "3. where is nmap:"
  echo "   $(command -v nmap)"
  echo
  echo "4. is it a builtin or external:"
  type -a nmap
  echo
  echo "5. what PATH search order looks like:"
  echo "$PATH" | tr ':' '\n' | nl
} | tee 01-execution-model.txt

# --- RUN IT: your first real scan, loopback only ---
nmap -sV --version-light -p- 127.0.0.1 -oN 02-loopback-scan.txt
cat 02-loopback-scan.txt

# --- background work, do something else, come back ---
nmap -sV -p- 192.168.56.0/24 > 03-range-scan.txt 2>&1 &
echo "started as PID $!"
sleep 5
jobs -l
echo "--- doing other work while that runs ---"
id > /tmp/unrelated.txt && cat /tmp/unrelated.txt
jobs                                   # still there?
wait                                   # block until it finishes
cat 03-range-scan.txt

# --- SIGNALS ---
sleep 600 &
BGPID=$!
kill -0 $BGPID && echo "process $BGPID exists"
kill -TERM $BGPID
sleep 1
kill -0 $BGPID 2>/dev/null || echo "terminated cleanly after SIGTERM"

# --- expansion, demonstrated ---
{
  echo "cwd:        $(pwd)"
  echo "home:       ~"
  echo "wildcard:   *.txt  ->  $(ls *.txt | tr '\n' ' ')"
  echo "quoted:     '*.txt' ->  '*.txt'"
  echo "var:        $USER on $HOSTNAME"
  echo "cmdsub:     today is $(date +%A)"
} | tee 04-expansion.txt

Record: the output of 01-execution-model.txt. It is the mental model you will use to
diagnose every "command not found" for the rest of your career.

Self-test

  1. List the six steps between pressing Enter and the process starting.
  2. cd is a builtin and ls is not. Why does that distinction matter to an attacker?
  3. What is the difference between Ctrl+Z/bg and Ctrl+C?
  4. Why do security scripts start with set -euo pipefail?
  5. foo: command not found — which of the six steps failed, and what do you check first?
