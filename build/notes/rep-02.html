Writing Reproducible Findings and Evidence

Summary

A finding is only as good as its reproducibility. If a reader cannot re-run your proof from what
you wrote, you have written an assertion, not a finding.

The framing: the test of a finding is whether a competent engineer
who has never met you could reproduce it from the report alone. That
single sentence drives every formatting decision.

Companion to rep-01 (structure) and rep-03 (severity). This note
is the finding body and the evidence chain.

Anatomy of a finding

  1. TITLE          what, where, and the consequence. Not a CVE id.
                    "Unauthenticated remote code execution on WEB-01"
                    not "Critical finding 1"

  2. RISK           what an attacker GAINS, in business terms.
                    Written so a non-technical reader understands it.

  3. PREREQUISITE   what must be true for this to work.
                    THIS IS THE LINE THAT DISTINGUISHES A FINDING
                    FROM A POSSIBILITY.

  4. EVIDENCE       the exact request, the exact response.
                    Verbatim. Copy-pasteable.

  5. STEPS TO       numbered, minimal, reproducible from step 1.
     REPRODUCE      A reader should not have to think.

  6. ROOT CAUSE     why the vulnerability exists, technically.
                    This is what makes the fix obvious.

  7. REMEDIATION    specific, owned, and scheduled.
                    "Remove the endpoint" not "improve security".

  8. RE-TEST       when it will be checked, and how.

The evidence standard

# what goes in an evidence block, and what does not
evidence:
  target: "192.168.56.20:8080 (WEB-01)"
  context: "Authenticated as LAB\alice, a standard user account with no
            administrative rights. Authenticated access was supplied under
            the engagement letter."

    GET /admin/records HTTP/1.1
    Host: 192.168.56.20:8080

    HTTP/1.0 200 OK
    Server: SimpleHTTP/0.6 Python/3.13.2
    Content-Length: 14238

    [REDACTED — record structure shown;
     one sample row redacted; 0 records retained]
  observable: "HTTP 200 with 14,238 bytes. No Cookie or Authorization

               fresh session with an empty cookie jar."
  NOT_claimed:
    - "That the endpoint was used in anger"
    - "Which records exist"
    - "How many records exist in total"

  captured_by: "nwpcs"

# Evidence rules

```text
  WHAT MAKES EVIDENCE EVIDENCE
    1. REPRODUCIBLE   a reader can re-run it, from your text, on a
                      clean system, and get the same result.
    2. TIMESTAMPED    when it was observed, in UTC, with the timezone.
    3. CONTEXTUAL     which account, which privilege level, which
                      network position.
    4. ATTRIBUTED     who collected it, from where.
    5. UNALTERED      the artefact is hashed, and the hash is in the
                      report.

  WHAT MUST NEVER APPEAR IN A REPORT
    - a live credential, session cookie, or API key, in ANY encoding
    - another person's personal data, even one row
    - a full database dump, even "for evidence"
    - a screenshot that has not been checked for credentials
    - an internal hostname the client has not already disclosed,
      if the client is sensitive about it - ask first
    - anything you did not actually observe

  THE REDACTION RULE
    Redact to the SHAPE, not the content. "3 rows, 4 columns, the
    fourth column is a partial card number, values [REDACTED]" tells
    the client everything they need. The values themselves tell the
    client nothing they did not already have.

  THE SCREENSHOT RULE
    Screenshots are for HUMANS. Raw output is for REPRODUCTION.
    Both, and the screenshot is a convenience, not the evidence.
    Crop for layout, blur for secrets - and blur rather than crop
    for secrets, because cropping hides the context that makes the
    screenshot legible.
```
EOF

## F-04 · Unauthenticated access to customer records on WEB-01 · **CRITICAL**

**Risk**
An unauthenticated attacker with network access to port 8080 can
read the production customer database in full, including names, email
addresses, and partial payment card data. No credentials are required,
and the endpoint is not referenced anywhere in the application's
documentation.

**Prerequisite for exploitation**
A TCP connection to 192.168.56.20:8080 from the internal network. No
user interaction, no credentials, no special tooling. The endpoint is
not linked from any page, so it requires a direct request.

**Evidence**

GET /admin/records HTTP/1.1
Host: 192.168.56.20:8080
Connection: close

```http
HTTP/1.0 200 OK
Server: SimpleHTTP/0.6 Python/3.13.2
Content-Length: 14238

[REDACTED — structure shown, 3 sample rows redacted,
 no records retained]

The request carried no Cookie and no Authorization header. The
identical response was returned from a separate session with an empty
cookie jar, at 2026-10-14T11:04:22Z, as LAB\alice (a standard user).

Steps to reproduce
1. From any host on 192.168.56.0/24: curl -i http://192.168.56.20:8080/admin/records
2. No credentials are requested or required.
3. The response is the customer records table.

Not claimed
We did not enumerate the records, retrieve a dataset, or determine the
total row count beyond the response length. We establish access, not
exfiltration.

Root cause
The endpoint was introduced during the 2024 migration and was never
placed behind authentication. It is served by a development HTTP server
(python -m http.server) rather than the production application server,
which indicates it bypassed the normal routing and middleware chain.
The firewall rule permitting 8080 from the internal range was written
for the application servers and was never narrowed.

Remediation
| # | Action | Owner | Effort | Priority |
|---|---|---|---|---|
| 1 | Remove the endpoint; no application feature uses it | Web Platform | Immediate | Immediate |
| 2 | Migrate remaining endpoints off the development server | Web Platform | 2 days | Immediate |
| 3 | Narrow the 8080 firewall rule to the application server range | Network Ops | Immediate | Immediate |
| 4 | Add a CI check that fails when an /admin/* route has no authentication | Web Platform | 1 sprint | High |

Re-test 30 days after remediation, included in this engagement. The re-test repeats the
request above and confirms a 401 or 403, and confirms the firewall rule scope.
EOF

!/usr/bin/env python3

"""Check a draft report for the things that make it unusable.

Catches the failure modes that get a report rejected by the client's
legal team or ignored by their engineers.
"""
import re, sys, pathlib

PATTERNS = [
# (regex, severity, what it means)
(r"\b(?:\d{1,3}.){3}\d{1,3}\b(?!.[REDACTED)", 0, "an IP address - check it is in the approved list"),
(r"\b[a-f0-9]{64}\b", 0, "a sha256 - good, but check it is a FILE hash and labelled"),
(r"\b[a-f0-9]{32}\b", 2, "a bare 32-hex string - possibly a password hash. Remove or label."),
(r"(?:password|passwd|pwd)\s[:=]\s\S+", 3,
"a credential in plaintext. REMOVE."),
(r"(?i)authorization:\s(?![REDACTED)\S+", 3,
"an Authorization header. Redact it."),
(r"(?i)cookie:\s(?![REDACTED)\S+", 3,
"a Cookie header. Redact it."),
(r"\bBearer\s+[A-Za-z0-9.-]{20,}", 3, "a bearer token. Redact it."),
(r"(?i)\b(api[-]?key|secret|token)\b\s[:=]\s*\S+", 3,
"a key or token. Redact it."),
(r"\bCVSS[^0-9]{0,4}\d.\d\b", 1,
"a CVSS score. Fine to include, but it must not BE the severity."),
(r"(?i)\bcritical\b", 0, "Critical used - check the prerequisite supports it."),
(r"(?i)\bwe recommend .{0,20}$", 0, "check this recommendation is specific"),
(r"(?i)\bimprove .{0,30}security\b", 2,
"a non-specific remediation. This is the most common rejection reason."),
(r"(?i)\bwe found no\b|\bno vulnerabilities\b", 2,
"a negative finding. Must be scoped ('no findings in the scope tested')."),
(r"\bTODO|\bTBD|\bXXX\b", 3, "a placeholder. The report was submitted with a blank."),
(r"(?i)\bshould\b", 1, "'should' - is it a recommendation or a description?"),
]

def check(path):
text = pathlib.Path(path).read_text(errors="ignore")
lines = text.splitlines()
issues = []
for rx, sev, why in PATTERNS:
for i, line in enumerate(lines, 1):
for m in re.finditer(rx, line):
snippet = line[max(0, m.start()-25):m.end()+25]
issues.append((sev, i, why, snippet.strip()[:90]))
if not issues:
print(" no issues found by the automated check.")
print(" (that is not the same as 'ready to send' - see below.)")
return 0
for sev, i, why, snip in sorted(issues):
tag = ["INFO ", "WARN ", "CHECK", "FIX "][sev]
print(f" [{tag}] line {i:<5} {why}")
print(f" {snip}")
n3 = sum(1 for s, _ in issues if s == 3)
n2 = sum(1 for s, in issues if s == 2)
print(f"\n {n3} must-fix, {n2} to check, "
f"{sum(1 for s, * in issues if s<2)} informational.")
if n3: print(" DO NOT SEND with must-fix items.")
return 1 if n3 else 0

if name == "main":
if len(sys.argv) < 2:
print(doc); sys.exit(0)
rc = 0
for p in sys.argv[1:]:
print(f"=== {p} ==="); rc |= check(p); print()
print("THE CHECKS AN AUTOMATED TOOL CANNOT DO:")
print(" - can a competent engineer reproduce each finding from this text alone?")
print(" - is every prerequisite stated, and is the severity consistent with it?")
print(" - is every recommendation specific enough to schedule?")
print(" - does the executive summary match what the findings actually say?")
print(" - would the client accept this being forwarded to their board?")
sys.exit(rc)
PY
echo "written: 03-check.py"
```

Step 3 is the deliverable: 03-check.py flags a plaintext credential in the draft, a bare
32-hex password hash, and TODO — and then prints the five checks an automated tool cannot
do: whether a competent engineer could reproduce each finding from the text alone, whether the
severity is consistent with the stated prerequisite, and whether the executive summary matches
what the findings say.

02-template.md is the worked example, and the section that makes it good is "Not claimed":
we did not enumerate the records, retrieve a dataset, or determine the total row count beyond the
response length. We establish access, not exfiltration. That paragraph is what keeps the report
defensible.
