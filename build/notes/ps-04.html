Access Control, IDOR and Privilege Escalation

Summary

This is the topic PortSwigger puts early and OWASP puts at number one in real bug bounty,
because it requires no exploit technique at all. You change a number in a request. That is
the whole attack.

CS161's web note called IDOR "the most common high-severity finding". This lecture is where
that claim becomes mechanical: the vulnerability is a missing check, and the check is
missing because authorisation was never separated from authentication.

The two questions, and how code confuses them

  AUTHENTICATION  who are you?        -> "prove it"
  AUTHORISATION    may you do this     -> "to THIS object?"
                   to THIS object,
                   right now?

  CONFUSION: the app checks that you are logged in (authentication)
             and assumes that therefore you may see it (authorisation).

  THE TEST: is the check about WHO, or about WHAT?
            If it never mentions the object, it is an access control bug.

Vertical vs horizontal escalation

  VERTICAL   user -> admin
             higher privilege in the same role hierarchy
             often via a mass-assignment bug (see below)

  HORIZONTAL user A -> user B
             same privilege, different user's data
             almost always via a parameter change (IDOR)
             higher volume, and usually higher impact because it is
             a bulk data exposure rather than a single account

The complete taxonomy of access control failures

  1. IDOR / BROKEN OBJECT REFERENCE
     GET /api/invoice?id=1234   ->  id=1235
     the object identifier is client-supplied and unchecked

  2. MISSING FUNCTION LEVEL ACCESS CONTROL
     /admin exists for everyone, or the check is client-side only
     (a hidden link is not an access control)

  3. MISSING SERVER-SIDE VALIDATION
     a hidden field, a disabled button, a JS check - all bypassable

  4. FORCE BROWSING / PRIVILEGE ESCALATION
     guess /admin, /internal, /actuator, /.git, /backup

  5. VERTICAL ESCALATION VIA MASS ASSIGNMENT
     the app binds every JSON field to a user object:
       {"email":"...", "admin":true}   -> you are admin now
     fix: an allowlist of bindable fields (DTO / strong parameters)

  6. PARAMETER MANIPULATION
     ?role=admin  ?isAdmin=1  ?userId=1  ?account_id=1

  7. INSECURE DIRECT OBJECT REFERENCES IN FILE PATHS
     /download?file=../../etc/passwd   -> overlaps with ps-06

Mass assignment, the one people miss

// VULNERABLE: bind everything the client sent
$user = new User();
$user->fill($_POST);          // is_admin, role, id, balance - all of it

// SAFE: bind only what is allowed
$user->is_admin = false;               // explicit
// or, in Rails: user_params.require(:name, :email)
// or in Laravel: $fillable / $guarded
// or in Spring: @ModelAttribute with an explicit DTO

POST /profile
{"name":"bob","email":"b@x.com","is_admin":true,"balance":99999}

The fix is always an allowlist of bindable fields, never a
denylist of dangerous ones. Denylists miss every field the developers
did not think of.

Authentication bypass, the other half

  WEAK CREDENTIALS
    default credentials (admin/admin) - still the single most common finding
    credential stuffing from breach corpora (see cry-d1)
    password == username == email

  IMPLEMENTATION FLAWS
    type juggling:   PHP  "0e12345" == "0e67890"  is TRUE
                     JSON {"admin":true}  vs  {"admin":"true"}
    loose comparison in any language with numeric strings
    truthy strings:  "false", "0", "null", ""   are truthy in PHP
    array injection: ?password[]=x  turns the comparison into an array
                     comparison, which is always "not equal"

  SESSION ISSUES
    no rotation on login -> session fixation (see ps-07)
    no invalidation on logout -> the token still works
    JWT flaws -> see ps-07 and cry-d3

  RECOVERY
    predictable reset tokens
    reset tokens with no expiry
    username enumeration via the reset flow
    host header injection in the reset link

PHP type juggling deserves its own demonstration because it is still
live everywhere PHP runs.

Testing procedure

  1. MAP EVERYTHING
     - log in as a normal user
     - record every URL, method, body and response
     - the application's own links are the map
     - repeat as a SECOND, differently-privileged user

  2. FOR EVERY REQUEST THAT REFERENCES AN OBJECT
     - request an object YOU own            -> expect 200
     - request an object the OTHER user owns -> expect 403/404
     - if 200 with their data, that is an IDOR

  3. FOR EVERY PRIVILEGED FUNCTION
     - call it directly as a normal user
     - is the check server-side?
     - a hidden menu item is not a check

  4. FOR EVERY FORM THAT UPDATES A USER
     - add privilege fields
     - is the binding allowlisted?

  5. FOR EVERY AUTHENTICATION PATH
     - wrong password vs unknown user: different status/length/time?
     - is the session rotated? is it invalidated on logout?

Terminology

Term Meaning
Access control Who may do what to which object
Authentication Proving identity
Authorization Granting permission per object
IDOR / BORF Accessing an object by changing its identifier
Vertical escalation Low privilege to high
Horizontal escalation One user's data to another's
Mass assignment Binding unlisted client fields to a model
Force browsing Directly requesting a privileged URL
Type juggling PHP loose comparison pitfalls
Allowlist binding Explicitly listing bindable fields
Forced browsing Bypassing UI-level hiding
Least privilege (app) A session should do only what it must
Vertical/horizontal slice Test the full permission matrix

# --- 2. prove the IDOR ---
{
  echo "=== baseline: bob fetches HIS OWN invoice ==="
  curl -s -c b.jar -X POST -d 'as=bob' http://127.0.0.1:8080/app.php | grep -E "you are" | sed 's/^/  /'
  curl -s -b b.jar 'http://127.0.0.1:8080/app.php/invoice?id=2' | grep "invoice" | sed 's/^/  /'
  echo
  echo "=== IDOR: bob fetches ALICE'S invoice by changing one number ==="
  curl -s -b b.jar 'http://127.0.0.1:8080/app.php/invoice?id=1' | grep "invoice" | sed 's/^/  /'
  echo "  ^ uid=2 requesting invoice 1 (owned by uid=1). Same request shape,"
  echo "    one changed digit, someone else's data. That is the whole bug."
  echo
  echo "=== and enumerate: how much is exposed? ==="
  for i in 1 2 3; do
    printf "  id=%s -> %s\n" "$i" \
      "$(curl -s -b b.jar "http://127.0.0.1:8080/app.php/invoice?id=$i" | grep -oE 'amount=[0-9]+ memo=[A-Za-z]+' | head -1)"
  done
  echo
  echo "=== THE FIX, for comparison: /my filters by owner in the query ==="
  curl -s -b b.jar 'http://127.0.0.1:8080/app.php/my' | grep -oE "\[0-9\][^]]*" | sed 's/^/  /'
  echo "  ^ only bob's rows. Same data, one clause of difference."
} 2>&1 | tee 01-idor.txt

# --- 5. the auth-bypass patterns, run ---
python3 - <<'PY' | tee 04-authbypass.txt
print("  === PHP type juggling: the comparison that lies ===")
print()
cases = [
    ("'0e12345' == '0e67890'",        True,  "both numeric-looking -> compared as 0 == 0"),
    ("'0e12345' === '0e67890'",       False, "strict === compares strings"),
    ("'abc'   == 0",                  True,  "PHP 7: leading-numeric cast. PHP 8: fixed"),
    ("'1abc'  == 1",                  True,  "same"),
    ("'true'  == true",               False, "'true' string vs bool true"),
    ("boolval('false')",              True,  "the string 'false' is truthy"),
    ("boolval('0')",                  False, "the string '0' is falsy"),
    ("isset(\$_POST['p']) && \$_POST['p']", "TRUE", "array param makes it truthy"),
]
print(f"  {'comparison':<44} {'result':<8} why")
print("  " + "-"*92)
for expr, res, why in cases:
    print(f"  {expr:<44} {str(res):<8} {why}")
print()
print("  THE FIX, and it is one character:")
print("    if (\$_POST['p'] === 'yes')          not  == 'yes'")
print("    if (hash_equals(\$a, \$b))            not  == for tokens/passwords")
print("    if ((int)\$_POST['n'] === 1)          not  == 1")
print()
print("  PHP 8 fixed the string-to-number juggling. The == on two numeric")
print("  strings ('0e...') still works, and array-injection tricks still")
print("  work. Never rely on the language version for a security property.")

# --- 6. the full matrix tester ---
cat > 05-matrix.sh <<'EOF'
#!/usr/bin/env bash
# Test the FULL permission matrix, not one account. Most real IDOR is
# found by the second user, not by reading the code.
B=http://127.0.0.1:8080/app.php
declare -A UID_FOR=( [alice]=1 [bob]=2 [admin]=3 )

login() { rm -f "/tmp/j_$1"; curl -s -c "/tmp/j_$1" -X POST -d "as=$1" "$B" >/dev/null; }

echo "=== does <user> get <object> it should not have? ==="
printf "  %-8s %-8s %-14s %s\n" "USER" "OBJECT" "STATUS" "VERDICT"
printf "  " ; printf -- "-%.0s" {1..58}; echo

login alice; login bob
for u in alice bob; do
  for id in 1 2 3; do
    owner=$([ "$id" = 1 ] && echo alice || ([ "$id" = 2 ] && echo bob || echo admin))
    body=$(curl -s -b "/tmp/j_$u" "$B/invoice?id=$id")
    got=$(echo "$body" | grep -c "invoice #$id")
    expect=$([ "$u" = "$owner" ] && echo 1 || echo 0)
    if [ "$got" -eq 1 ] && [ "$expect" -eq 0 ]; then
      printf "  %-8s %-8s %-14s %s\n" "$u" "inv#$id" "200 OK" "*** IDOR ***"
    elif [ "$got" -eq 1 ]; then
      printf "  %-8s %-8s %-14s %s\n" "$u" "inv#$id" "200 OK" "own (correct)"
    else
      printf "  %-8s %-8s %-14s %s\n" "$u" "inv#$id" "denied" "correct"
    fi
  done
done

echo
echo "=== and the privileged area ==="
for u in alice bob; do
  n=$(curl -s -b "/tmp/j_$u" "$B/admin" | grep -c "ADMIN AREA")
  printf "  %-8s /admin -> %s\n" "$u" "$([ "$n" -eq 1 ] && echo '*** REACHABLE, should not be ***' || echo 'blocked (correct)')"
done
rm -f /tmp/j_alice /tmp/j_bob
EOF
chmod +x 05-matrix.sh
./05-matrix.sh 2>&1 | tee 06-matrix.txt
rm -f b.jar app2.php

Step 6 is the deliverable: 05-matrix.sh tests the full permission matrix — three users ×
three objects — rather than one account. Every IDOR campaign needs a second account, and most
people skip that and miss the bug entirely. Run it and the IDORs light up in a table.

Step 5 is worth doing directly: php -r with "0e12345" == "0e67890" is the auth bypass
that will outlive every PHP version.
