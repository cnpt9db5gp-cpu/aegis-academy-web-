Security Architecture

Summary

Lecture 2 covers the structural question: where do you put the trust boundary, and how do you
make the trusted part small enough to audit?

The answer the lecture develops is privilege separation — splitting a large untrusted program
into a small trusted monitor plus a large unprivileged userland.

Key ideas

  • Minimize the trusted computing base: everything that must be correct for security to hold
  • Privilege separation: split into a small privileged monitor and untrusted userland
  • Application-level vs OS-level: Linux namespaces, chroot, VMs are different layers of the
    same idea
  • Security vs reliability: privileged code must be simple, because it cannot recover
  • Sandboxing: restrict a process without trusting it
  • Reference monitors: the component that mediates every privileged operation

The privilege separation pattern

   ┌──────────────────────────────┐
   │  unprivileged userland       │  large, complex, crashable
   │  parser, renderer, network   │  bugs here are survivable
   └───────────┬──────────────────┘
               │ narrow IPC (a few messages, validated)
   ┌───────────┴──────────────────┐
   │  trusted monitor (privileged)│  small, simple, auditable
   └──────────────────────────────┘

Why it works: a bug in the large component costs you the large component,
not the system. The small component is small enough to read in an afternoon.

Three layers of the same idea

Layer Mechanism Boundary strength
Process Unix user/uid, file permissions strong, but same kernel
Container namespaces, cgroups, seccomp weak: shares the kernel
VM / enclave hypervisor, hardware strong: different kernel

Each step up is stronger and more expensive. This is isolation-mechanisms
and the VM discussion in os-05.

The economics

  • A small trusted component can be reviewed — and reviews find bugs
  • A small trusted component has fewer dependencies
  • A small trusted component has fewer lines, so fewer opportunities
  • The cost: extra IPC, complexity, and performance overhead

Google's site isolation and Chrome's sandbox are the industry version of this.

Terminology

Term Meaning
Trusted computing base (TCB) Everything that must be correct
Privilege separation Trusted monitor + untrusted userland
Reference monitor The mediator between subjects and objects
Sandboxing Confining a process's capabilities
chroot / jail Filesystem-level confinement
seccomp Syscall allowlist
Namespace Isolated kernel view
VM isolation Separate kernel entirely
TCB minimisation Reducing what must be trusted
Interface validation Checking every message at the boundary

Kali commands

# --- measure your own TCB, roughly ---
{
  echo "=== what must be correct for this host to be secure? ==="
  echo "  kernel            : $(uname -r)"
  echo "  libc              : $(ldd --version | head -1)"
  echo "  init system       : $(ps -p 1 -o comm= 2>/dev/null)"
  echo "  sshd              : $(sshd -V 2>&1 | head -1)"
  echo "  package manager   : apt"
} 2>&1 | tee 01-tcb.txt

# --- how big is the kernel you trust? ---
ls -la /boot/vmlinuz-* 2>/dev/null | awk '{printf "  kernel image: %s bytes\n", $5}'

# --- what is running as root right now? ---
ps -eo user,pid,pcpu,comm --sort=user | awk 'NR==1 || $1=="root"' | head -12

# --- privileged helpers that should be small and boring ---
sudo -l 2>/dev/null || sudo -n -l
ls -la /usr/bin/sudo /usr/bin/pkexec /usr/lib/dbus-1.0/dbus-daemon 2>/dev/null

# --- sandboxing available on this kernel ---
cat /proc/sys/kernel/unprivileged_userns_clone 2>/dev/null || echo "  (sysctl absent)"
sysctl kernel.unprivileged_userns_clone 2>/dev/null
seccomp --help 2>/dev/null | head -2 || echo "  libseccomp tools not installed"

# --- what namespaces exist for a process ---
ls -l /proc/self/ns/

# --- demonstrate a real sandbox ---
unshare -Ur -n -m sh -c 'echo "  inside: uid=$(id -u) netns=$(readlink /proc/self/ns/net)"'
echo "  ^ user namespace + network namespace + mount namespace, no root required"

Field lab

Objective: measure your own trusted computing base and run a real sandbox, so the principle
is concrete.

mkdir -p ~/aegis/labs/mit858-02 && cd ~/aegis/labs/mit858-02

# --- 1. inventory the TCB ---
{
  echo "=== TRUSTED COMPUTING BASE INVENTORY ==="
  echo
  echo "kernel      : $(uname -r)   ($(ls -la /boot/vmlinuz-* 2>/dev/null | awk 'NR==1{print $5}') bytes)"
  echo "libc        : $(ldd --version | head -1)"
  echo "init        : $(ps -p 1 -o comm= 2>/dev/null)"
  echo "sudo        : $(ls -la /usr/bin/sudo 2>/dev/null | awk '{print $5}') bytes"
  echo "sshd        : $(sshd -V 2>&1 | head -1)"
  echo
  echo "=== ROOT-OWNED PROCESSES (all must be correct) ==="
  ps -eo user,pid,comm --sort=user | awk '$1=="root"' | head -15
  echo
  echo "=== HOW BIG IS THE TRUSTED PART, REALLY ==="
  printf "  root-owned setuid binaries : %s\n" "$(find / -perm -4000 -type f 2>/dev/null | wc -l)"
  printf "  root-owned listeners       : %s\n" "$(ss -tulpn 2>/dev/null | grep -c 'users:((\"root\"' || echo 0)"
} 2>&1 | tee 01-tcb.txt

# --- 2. the size argument, measured ---
echo
echo "=== the size argument, with numbers ==="
{
  echo "  --- unprivileged code (large, bugs are survivable) ---"
  printf "    files in /usr/bin        : %s\n" "$(ls /usr/bin | wc -l)"
  printf "    total size of /usr/lib   : %s\n" "$(du -sh /usr/lib 2>/dev/null | cut -f1)"
  echo
  echo "  --- privileged code (small, must be correct) ---"
  printf "    setuid binaries          : %s\n" "$(find / -perm -4000 -type f 2>/dev/null | wc -l)"
  find / -perm -4000 -type f 2>/dev/null | head -8 | sed 's/^/      /'
  printf "    size of the sudo binary  : %s\n" "$(stat -c %s /usr/bin/sudo 2>/dev/null)"
} 2>&1 | tee 02-size.txt

# --- 3. RUN A SANDBOX, and try to break out of it ---
echo
echo "=== unshare: a real privilege separation, no root needed ==="
unshare -Ur -n -m -p -f --mount-proc sh -c '
  echo "  inside the namespace:"
  echo "    uid        : $(id -u) (namespaced - not real root)"
  echo "    network    : $(ls /sys/class/net 2>/dev/null | tr "\n" " ")"
  echo "    hostname   : $(hostname 2>/dev/null)"
  echo "    pid        : $$"
  echo
  echo "  trying to reach the network from inside:"
  timeout 2 getent hosts example.com >/dev/null 2>&1 \
    && echo "    DNS worked" || echo "    no network (isolation held)"
  echo
  echo "  trying to see the host filesystem:"
  ls /home/*/Projects 2>/dev/null | head -2 || echo "    host paths are not visible"
' 2>&1 | tee 03-sandbox.txt

# --- 4. the boundary, drawn explicitly ---
cat > 04-boundary.md <<'EOF'
# Where the trust boundary sits, per layer

## Process boundary (cheapest)
- unix uid/gid, file permissions, capabilities
- one kernel shared
- escape requires a kernel bug

## Container boundary
- namespaces: pid, mnt, net, uts, ipc, user
- cgroups for resources; seccomp for syscalls
- overlayfs for the filesystem
- **same kernel**: a kernel bug is an escape, not a compromise

## VM boundary
- separate kernel entirely
- escape requires a hypervisor bug
- cost: memory, boot time, operational complexity

## Enclave boundary (strongest, smallest)
- hardware memory encryption and entry-point measurement
- side channels remain the weakness (6.858 L7, L18)

## Choosing
- untrusted input, same trust level -> language-level checks
- untrusted plugin, same user -> seccomp / namespace
- untrusted tenant, shared kernel -> container (accept the kernel risk)
- untrusted tenant, hostile kernel -> VM
- cryptographic isolation -> enclave, if you can live with side channels
EOF
cat 04-boundary.md

# --- 5. the TCB you cannot reduce, and what to do about it ---
cat > 05-what-to-do.md <<'EOF'
# When you cannot shrink the TCB

1. **Reduce what runs privileged.** Disable services you do not need.
2. **Make the privileged code boring.** Small, no parsers, no allocations.
3. **Move complexity to userland.** Every line you move out of the TCB is
   a line you do not have to trust.
4. **Validate every interface message.** The boundary is where bugs live.
5. **Monitor the TCB.** Integrity checking, IMA, code signing.
6. **Update it.** A large TCB is a large attack surface over time.

The practical version: the day-to-day work of architecture security is
deleting things, not adding them.
EOF
cat 05-what-to-do.md

Step 3 is the live demonstration — a real sandbox with no root, where DNS fails and host
paths vanish. That is privilege separation happening, not described.
