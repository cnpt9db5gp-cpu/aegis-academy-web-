Metadata, Documents and Verification Discipline

Summary

Public documents leak more than any other OSINT category, because documents are written for
humans and humans do not consider the audience. Exif data, tracked changes, revision histories,
hidden sheets, embedded objects and stale hyperlinks all survive into the published file.

The framing: a published document is not a document. It is a
document plus everything the author forgot to remove. And the
discipline is verification: every claim you make about a document has
to survive someone asking how you know.

Companion to osi-01's method. This note is the document analysis
and the verification habit.

What a document leaks

  METADATA
    EXIF (images)      camera, GPS, serial number, timestamp, software
    Office core props   author, last-modified-by, company, template
    PDF info            producer, creator, creation AND modification
                        date, and - critically - whether they differ
    ZIP container       the DOCX/XLSX/PPTX ZIP, and every entry's
                        timestamp. A DOCX is a ZIP. Every timestamp
                        in it can differ from the others.

  THE MOST USEFUL SIGNAL IN ALL OF IT
    AUTHOR != LAST-MODIFIED-BY. Two names means two people touched it.
    LastModifiedBy = a departed employee often means the document
    predates them being deprovisioned, which dates it.

  AND: creator tool != creator tool. If a PDF's producer is a
  different version of Word than the client's, it was made
  elsewhere.

  REVISION AND TRACKED CHANGES
    Word: settings.xml holds rsid data; the revisions are in the
          document.xml as <w:ins> and <w:del>. Deleted text is
          STILL THERE.
    Excel: sharedStrings.xml, calcChain.xml, and the recovery files
    PDF:  incremental updates. A "final" PDF has ten revisions in it.

  EMBEDDED OBJECTS
    DOCX: any file, including an EXE
    XLSX: an OLE object, a macro, a Power Query (which contains the
          API KEYS AND THE QUERY)
    PDF:  embedded files, attached files, JavaScript, launch actions

  WHAT SURVIVES INTO A PDF
    - a hyperlink whose visible text is example.com and whose target
      is an internal-sharepoint-hostname
    - a comment
    - a layer name
    - the document's internal structure (which pages were assembled
      from which source)
    - the ORDER of assembly. If page 7 is from a different template,
      that is visible in the file structure.

cat > 01-documents.sh <<'EOF'
#!/usr/bin/env bash
# Document analysis. NOTHING here executes the document's content.
# No macros run, no embedded object is opened, nothing is rendered
# with a tool that fetches remote resources.
D="${1:?usage: ./01-documents.sh <file-or-directory>}"
mkdir -p work

echo "=== 1. TYPE ==="
file -b "$D" 2>/dev/null | sed 's/^/  /'
find "$D" -type f 2>/dev/null | while read -r f; do
  printf "  %-50s %s\n" "$(basename "$f")" "$(file -b "$f" | cut -c1-40)"
done | head -20

echo
echo "=== 2. EXIFTOOL, EVERY FIELD ==="
exiftool -a -u -G1 "$D" 2>/dev/null | head -60 | sed 's/^/  /'

echo
echo "=== 3. THE TWO CHECKS THAT MATTER ==="
exiftool -s -Author -Creator -LastAuthor -ModifyDate -CreateDate \
         -Company -Producer -CreatorTool -Software "$D" 2>/dev/null | sed 's/^/  /'
echo "  ^ Author vs CreatorTool, and CreateDate vs ModifyDate."
echo "    Disagreement is a finding: it means the file was edited"
echo "    somewhere else, or by someone else."

echo
echo "=== 4. THE ZIP CONTAINER (DOCX/XLSX/PPTX are ZIPs) ==="
if file -b "$D" 2>/dev/null | grep -qi "zip\|microsoft"; then
  unzip -l "$D" 2>/dev/null | head -25 | sed 's/^/  /'
  echo "  ^ any .exe, .dll, .bin, or .js in there is a finding."
  echo "    Office files with macros have a vbaProject.bin."
  mkdir -p work/unz
  unzip -o -q "$D" -d work/unz 2>/dev/null
  echo
  echo "  --- the macro, as text, without running it ---"
  ls work/unz/word/vbaProject.bin 2>/dev/null \
    && strings -a -el work/unz/word/vbaProject.bin | head -20 | sed 's/^/    /'
  echo
  echo "  --- Power Query (contains the API keys) ---"
  find work/unz -iname "*query*" -o -iname "*connection*" 2>/dev/null | head -5 | sed 's/^/    /'
  echo
  echo "  --- the tracked changes (deleted text is still there) ---"
  if [ -f work/unz/word/document.xml ]; then
    echo "    insertions: $(grep -o '<w:ins ' work/unz/word/document.xml | wc -l)"
    echo "    deletions : $(grep -o '<w:del ' work/unz/word/document.xml | wc -l)"
    echo "    ^ the deleted text is recoverable:"
    grep -oP '(?<=<w:delText[^>]{0,60}>)[^<]+' work/unz/word/document.xml | head -10 | sed 's/^/      /'
  fi
fi

echo
echo "=== 5. PDF STRUCTURE AND THE HIDDEN LAYERS ==="
if file -b "$D" 2>/dev/null | grep -qi pdf; then
  echo "  --- what is embedded ---"
  strings -a "$D" | grep -iE "/EmbeddedFile|/JavaScript|/Launch|/OpenAction|/URI" | sort -u | head -15 | sed 's/^/    /'
  echo "  ^ /JavaScript and /Launch are findings. /EmbeddedFile means"
  echo "    there is a file inside the PDF. /OpenAction runs on open."
  echo
  echo "  --- the incremental revisions (a 'final' PDF has several) ---"
  grep -ac "%%EOF" "$D" 2>/dev/null | xargs echo "    %%EOF markers:"
  echo "    ^ each one is a save. Ten means it was edited ten times."
  echo
  echo "  --- the layer names, which describe the template ---"
  strings -a "$D" | grep -iE "/(OC|Contents) ?[0-9]* ?/[A-Za-z ]*(Layer|Group|Header|Footer|Background)[A-Za-z ]*" \
    | sort -u | head -10 | sed 's/^/    /'
  echo
  echo "  --- hyperlinks: visible text vs actual target ---"
  pdfinfo -url "$D" 2>/dev/null | head -20 | sed 's/^/    /'
  echo "    ^ a link whose visible text and target disagree is a"
  echo "      phishing indicator, and in an OSINT context it tells"
  echo "      you what the internal hostname was."
fi

echo
echo "=== 6. WHAT IS DELIBERATELY NOT DONE ==="
cat <<'NOTE'
  NOT RENDERED. Opening a document in a viewer or converting it with
  a tool that fetches remote resources or follows /OpenAction will
  TELL THE AUTHOR the document was opened, and will fetch whatever
  the document says to fetch. On a hostile or unknown document that
  is an outbound connection you did not authorise.

  NOT EXECUTED. No macros, no embedded objects, no OLE.

  THE TOOLS USED (file, exiftool, unzip, strings, pdfinfo) parse the
  container. They do not run its content.
NOTE
EOF
chmod +x 01-documents.sh

cat > 02-verification.md <<'MD'
# Verification discipline

```text
  THE PROBLEM
    OSINT findings are easy to get wrong in three specific ways:

      1. STALE       the data was true and is not now. Shodan shows
                     a port open from six months ago.
      2. NOT YOURS   the name resolves to a shared host, a CDN, or
                     somebody else's server.
      3. MISLEADING  a technique on an attacker forum that does not
                     work. Most public "OSINT method" content is
                     written by people who have not verified it.

  THE FOUR VERIFICATION HABITS

  1. STAMP EVERY OBSERVATION
     Every finding carries an observed_at. Not "recently" - a
     timestamp. Six months from now you will not know, and the client
     will not ask.

  2. VERIFY OWNERSHIP BEFORE EVERY CLAIM
     Before "their web server is vulnerable", confirm the host is
     theirs:
       - does the IP resolve to their announced range?
       - does the certificate match their name?
       - do the headers (server, powered-by) match their stack?
     A finding against a CDN edge node is a finding against the CDN.

  3. DISTINGUISH "THE TOOL SAYS" FROM "I OBSERVED"
     "Shodan reports an open RDP port" is a second-hand claim about
     a moment you were not present for.
     "A connection to this address on 3389 succeeded at 14:22, and
     the address is in their announced range" is your observation.
     The first is a lead. The second is a finding.

  4. TRY IT YOURSELF, IN A BOUNDED WAY
     Every technique you read should be tried once, against your own
     throwaway, before you rely on it.
     Set up a domain you control, point it at a host you control,
     and check that the technique produces what the author claimed.
     This takes 20 minutes and it is the difference between
     competence and quoting.
MD

# --- the verification helpers ---
cat > 03-verify.sh <<'EOF'
#!/usr/bin/env bash
# Confirm a host belongs to the domain before you claim anything about it.
DOM="${1:?usage: ./03-verify.sh <domain>}"
HOST="${2:?usage: ./03-verify.sh <domain> <ip-or-host>}"
IP=$(dig +short "$HOST" | tail -1)
[ -z "$IP" ] && IP="$HOST"
echo "[scope] verifying $HOST ($IP) against $DOM"

echo
echo "=== 1. Is the address in their announced range? ==="
dig +short "$DOM" | sed 's/^/  their domain resolves to: /'
echo "  their NS: $(dig +short NS "$DOM" | tr '\n' ' ')"
dig +short TXT "$DOM" | grep -iE "v=spf1|include|ip4" | sed 's/^/  SPF (their ranges): /'
echo "  ^ compare this list against the address. If it is not here,"
echo "    the host may still be theirs (a range they announce via BGP)"
echo "    but you have not proven it."

echo
echo "=== 2. Does the certificate match? (one connection, TLS only) ==="
timeout 8 openssl s_client -connect "$HOST:443" -servername "$DOM" </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName 2>/dev/null | sed 's/^/  /'
echo "  ^ a SAN containing $DOM is ownership evidence."

echo
echo "=== 3. Ownership verdict ==="
if timeout 8 openssl s_client -connect "$HOST:443" -servername "$DOM" </dev/null 2>/dev/null \
     | openssl x509 -noout -ext subjectAltName 2>/dev/null \
     | grep -qi "$DOM"; then
  echo "  CONFIRMED: the certificate on $HOST names $DOM."
  echo "  A claim about this host is a claim about this domain."
else
  echo "  UNCONFIRMED: no certificate naming $DOM on this host."
  echo "  It may be a CDN, a shared host, or a third party."
  echo "  Do NOT report findings against it until you resolve this."
fi
echo
echo "  recorded at $(date -u +%Y-%m-%dT%H:%M:%SZ)"
EOF
chmod +x 03-verify.sh

Step 3 is the deliverable: 03-verify.sh refuses to let you claim anything about a host
until a certificate on it names your domain — because a finding against a CDN edge node is a
finding against the CDN. That single check is the difference between an accurate report and an
embarrassing one.

02-verification.md names the three specific ways OSINT findings go wrong — stale,
not yours, and misleading (most public "OSINT method" content is written by people who
have never verified it) — and the fourth habit: try it once against your own throwaway before
relying on it.

01-documents.sh deliberately ends with what it does not do: doesn't render, doesn't
execute macros, doesn't fetch remote resources — because opening a hostile document can TELL THE
AUTHOR it was opened.

  5. What survives into a PDF that most people do not expect?
