Injection and Malicious Plugin Families

Summary

Malware families have patterns, and the patterns are in the memory. This note covers the injection
techniques Volatility detects, the family-specific plugins, and the discipline of attributing a
sample to a family from memory artefacts alone.

The framing: injection is a technique, not a family. DLL injection,
process hollowing, reflective loading and APC injection are the four
common ones; the families are what use them, and the plugin families
are what identify the user.

Companion to vol-02 (the process layer) and for-05 (static
analysis). This note is technique → artefact → family.

The four injection techniques

  TECHNIQUE            WHAT IT DOES              WHAT IT LOOKS LIKE
  ---------------------------------------------------------------------------
  DLL INJECTION        LoadLibrary into another
                       process's address space.
                       (the classic; Cobalt Strike's default is
                        reflective, see below)

  REFLECTIVE DLL       The DLL maps itself: allocates, copies
  INJECTION            sections, fixes relocations, resolves
                       imports, calls DllMain. It NEVER appears
                       in the module list, because it was never
                       registered with the loader.
                       -> malfind: several RWX regions, one per
                          section, each starting with MZ-ish bytes
                          but NOT at offset 0 of a real file

  PROCESS HOLLOWING    Start a real process SUSPENDED, unmap its
                       image, write a new one, resume.
                       (Cobalt Strike's spawnto; used where you
                        need the process to LOOK legitimate)

  APC INJECTION        Queue an APC to a thread and make it run.
                       Useful for AV evasion because APCs execute
                       when the thread next waits.

  EARLY BIRD           Inject BEFORE the entry point runs, so the
  INJECTION            main() has already been patched. Invisible
                       to any tool that runs inside the process.

  THE VOLATILITY SIGNAL, for all of them:
    windows.malfind -> a private RWX region
    windows.dlllist -> a module in the list that is not what the
                       process should have, or a missing module
    windows.cmdline -> often empty or the original's (hollowing)
    windows.malfind.Dump -> carve the region, hand to for-05

# Technique → artefact → family

```text
  INJECTION TECHNIQUE
    private RWX regions           -> malfind
    module list disagrees with    -> dlllist
      the process's known purpose
    command line is empty or     -> cmdline
      the original's
    entry point outside any      -> dlllist + malfind
      module's address range

  PROCESS HOLLOWING, specifically
    - a process with a normal name and a normal path
    - almost NO modules loaded (the real ones were unmapped)
    - a large RWX region
    - cmdline empty
    - THREADS pointing at the RWX region, not at a module
    -> vol.py windows.malfind --pid <pid>
    -> vol.py windows.dlllist --pid <pid>     (compare the count)
    -> a thread whose start address is not in any module

  REFLECTIVE LOADING, specifically
    - malfind shows MULTIPLE RWX regions (one per section)
    - the first bytes of a region look like MZ but the PE header
      offset is wrong, or 'This program cannot be run in DOS mode'
      appears at a non-zero offset
    - dlllist does NOT show it (it was never registered)
    -> carve with malfind.Dump and hand to for-05

  APC INJECTION
    - very few artefacts in memory; it is mostly a behavioural tell
    - a thread whose start address is in ntdll (QueueUserAPC's
      trampoline) rather than in the process's own code
    -> windows.dlllist: the thread's start is not in any module

  EARLY BIRD
    - the main() entry point has been patched
    - malfind finds a RWX region at the entry point
    - almost nothing else is visible; this is the stealthiest
MD

# --- 2. the plugin families, and why they exist ---
cat > 02-families.md <<'MD'
# Plugin families, and the discipline behind them

```text
  WHY VOLATILITY HAS FAMILY-SPECIFIC PLUGINS

    A generic plugin can tell you "there is an RWX region". A family
    plugin can tell you "this is Cobalt Strike's default reflective
    loader, and the config is at offset X in the region".

    The family plugins encode knowledge that took reverse
    engineering to acquire: the config structure, the marker, the
    key. That knowledge is per-family and goes stale, which is why
    there are far fewer of them than generic plugins.

  THE EXAMPLES

    windows.cobaltstrike.*       config extraction from an injected
                                beacon. The config has the
                                C2 servers, the sleep time, the
                                campaign ID, and the public key.
                                IT IS PLAINTEXT (often XOR 0x2e or
                                similar). This is the single most
                                useful family plugin in practice.

    windows.suspicious.*         generic scoring: processes with no
                                modules, unusual names, parentage
                                anomalies. A triage shortcut.

    windows.malware.*            ransomware-family markers.

  THE DISCIPLINE, and it is the important part

    A family plugin's output is a HYPOTHESIS, not a conclusion.
    It parses a structure at an offset that the malware author
    controls. If the author changes the offset, the plugin returns
    garbage that may look like a valid config with a nonsense C2.

    THE RULE: a family plugin's config extraction must be
    corroborated:
      - the extracted C2 domain appears in windows.netscan
      - the extracted beacon size matches the socket's packets
      - the extracted sleep time matches the interval between packets
      - the extracted key works against something in the image

    If none of those line up, the extraction is wrong. Report it as
    "a structure consistent with <family> was found at <offset>; the
    contents did not correlate with observed network traffic and are
    therefore not treated as the configuration."
MD

# --- 3. the triage script ---
cat > 03-injection-triage.sh <<'EOF'
#!/usr/bin/env bash
VOL="${VOL:-vol.py}"; IMG="${1:?usage: ./03-injection-triage.sh memory.raw}"
mkdir -p dumps

echo "=== 1. malfind: every private RWX region ==="
$VOL windows.malfind -f "$IMG" 2>/dev/null | sed 's/^/  /'
echo
echo "  READ THE COLUMNS:"
echo "    PID      which process owns the region"
echo "    Start    the address - compare to the module list below"
echo "    End      the size"
echo "    Tag      MZ... means it has a PE header (possibly fake)"
echo "             VEx  means executable and writable"
echo "             RWX  means private + executable  <- the finding"
echo

echo "=== 2. for each suspect PID, the module list ==="
for pid in $($VOL windows.malfind -f "$IMG" 2>/dev/null | awk 'NR>1 && $7!=""{print $1}' | sort -un); do
  echo "  --- pid $pid ---"
  $VOL windows.pslist -f "$IMG" 2>/dev/null | awk -v p="$pid" '$1==p{print "    process: "$3"  threads:"$6}' | head -1
  $VOL windows.dlllist -f "$IMG" --pid "$pid" 2>/dev/null | head -6 | sed 's/^/      /'
  n=$($VOL windows.dlllist -f "$IMG" --pid "$pid" 2>/dev/null | grep -c "/")
  echo "      total modules: $n"
  [ "$n" -lt 5 ] && echo "      ^ VERY FEW MODULES. Combined with an RWX region, this is"
  [ "$n" -lt 5 ] && echo "        either PROCESS HOLLOWING or a statically-linked binary."
  echo
done

echo "=== 3. the command line of each suspect ==="
$VOL windows.cmdline -f "$IMG" 2>/dev/null | grep -iE "powershell|cmd|rundll32|mshta|wscript|cscript|regsvr32" \
  | sed 's/^/  /'
echo "  ^ a PowerShell with a long base64 argument is an encoded command."
echo "    Decode it. It is not encrypted."
echo

echo "=== 4. carve the regions and hand them to static analysis ==="
$VOL windows.malfind.Dump --pid "$pid" -f "$IMG" --dump-dir ./dumps 2>/dev/null
ls -la dumps/ 2>/dev/null | sed 's/^/  /'
echo
echo "  THESE ARE MALWARE. Do not double-click them. Do not leave them"
echo "  where a file manager renders a preview. Run them through"
echo "  for-05's triage.sh, which never executes anything."
echo
echo "=== 5. the family plugins, for corroboration ==="
$VOL windows.cobaltstrike_scan -f "$IMG" 2>/dev/null | sed 's/^/  /'
echo
echo "  ^ a family plugin's output is a HYPOTHESIS. Corroborate it"
echo "    against netscan: does the extracted C2 appear as a live"
echo "    connection? Does the extracted sleep time match the packet"
echo "    interval? If not, the extraction is wrong. Say so."
EOF
chmod +x 03-injection-triage.sh

# --- 4. the decision tree, as code ---
python3 - <<'PY' 2>&1 | tee 04-decision-tree.txt
print("  === malfind said something. What now? ===\n")

def diagnose(pid, name, path, module_count, rw_regions,
             cmdline, threads_in_modules):
    f = []
    # 1. the path check, first, because it is the cheapest
    if path and not path.lower().startswith(
            (r"c:\windows", r"c:\program files", r"c:\program files (x86)")):
        if "\\temp\\" in path.lower() or "\\appdata\\" in path.lower():
            f.append(("HIGH", "Process binary lives in %TEMP% or %APPDATA%. "
                              "No legitimate system binary does."))
    if name and name.lower() in ("svchost.exe","lsass.exe","services.exe",
                                 "csrss.exe","winlogon.exe") and path \
       and "\\windows\\system32" not in path.lower():
        f.append(("CRITICAL", f"Process named {name} is NOT running from "
                              "System32. That is process impersonation."))
    # 2. the module count, which separates hollowing from injection
    if module_count < 5 and rw_regions:
        f.append(("HIGH", f"{module_count} modules and {len(rw_regions)} RWX "
                          "regions. This is PROCESS HOLLOWING, or a "
                          "statically-linked binary."))
    elif module_count > 0 and rw_regions:
        f.append(("HIGH", f"{len(rw_regions)} RWX region(s) alongside "
                          f"{module_count} normal modules. This is DLL "
                          "INJECTION (reflective or classic)."))
    # 3. the command line
    if cmdline:
        cl = cmdline.lower()
        if "-enc" in cl or "-encodedcommand" in cl:
            f.append(("HIGH", "Command line contains -EncodedCommand. "
                              "Decode it; it is base64 UTF-16LE, not "
                              "encryption."))
        if "bypass" in cl or "noprofile" in cl or "hidden" in cl \
           or "w hidden" in cl:
            f.append(("MEDIUM", "Command line has evasion flags. Individually "
                                "legitimate; combined, a finding."))
        if not cl.strip():
            f.append(("MEDIUM", "Empty command line. Hollowed processes "
                                "often have none."))
    # 4. threads outside modules
    if threads_in_modules is False:
        f.append(("HIGH", "A thread's start address is not inside any loaded "
                          "module. That is APC injection or shellcode."))
    return f

cases = [
    dict(pid=3412, name="svchost.exe",
         path=r"C:\Users\jdoe\AppData\Local\Temp\svchost.exe",
         module_count=4, rw_regions=1,
         cmdline="svchost.exe -k netsvcs -w",
         threads_in_modules=True),
    dict(pid=1204, name="notepad.exe",
         path=r"C:\Windows\System32\notepad.exe",
         module_count=1, rw_regions=2,
         cmdline="", threads_in_modules=False),
    dict(pid=2280, name="powershell.exe",
         path=r"C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe",
         module_count=42, rw_regions=0,
         cmdline="powershell.exe -nop -w hidden -enc SQBFAFgAIAAoAE4A",
         threads_in_modules=True),
    dict(pid=998, name="chrome.exe",
         path=r"C:\Program Files\Google\Chrome\Application\chrome.exe",
         module_count=310, rw_regions=3,
         cmdline=r'"C:\Program Files\Google\Chrome\Application\chrome.exe"',
         threads_in_modules=True),
]

for c in cases:
    pid, name = c["pid"], c["name"]
    print(f"  " + "="*66)
    print(f"  PID {pid}  {name}")
    print(f"    path        : {c['path']}")
    print(f"    modules     : {c['module_count']}")
    print(f"    RWX regions : {len(c['rw_regions'])}")
    print(f"    cmdline     : {c['cmdline'][:50]}")
    print()
    f = diagnose(**c)
    if not f:
        print("    (nothing stands out - probably benign)")
    for sev, reason in f:
        print(f"    [{sev:<8}] {reason}")
    if name.lower() == "chrome.exe" and c["module_count"] > 300:
        print()
        print("    NOTE: a browser with hundreds of modules and a few RWX")
        print("    regions is JIT COMPILATION. That is the caveat that")
        print("    stops you reporting a browser as malware. Chromium,")
        print("    .NET, WPF, Java, and Firefox all do this.")
PY

# Why a family plugin's output is a hypothesis

```text
  A family plugin parses a STRUCTURE at an OFFSET THAT THE MALWARE
  AUTHOR CONTROLS.

    The plugin knows: "Cobalt Strike's default config starts with a
    0x69 0x69 0x69 0x69 marker, and the C2 list is a length-prefixed
    array of null-terminated strings after it."

    The author controls: the marker, the length prefix, the field
    order, the offset.

  SO: if the author changes the marker, the plugin reads whatever
  bytes happen to be there and interprets them as a config.

  THE RESULT IS A VALID-LOOKING CONFIG WITH NONSENSE IN IT.

  THAT IS WHY THE CORROBORATION RULE EXISTS:

    A family plugin's output must be corroborated against independent
    evidence before it appears in a report:

    ┌─────────────────────────────────────────────────────────────┐
    │ plugin says       corroborate with                          │
    ├─────────────────────────────────────────────────────────────┤
    │ C2 domain X       does netscan show a connection to X?      │
    │ sleep time N      is the packet interval N?                 │
    │ beacon size S     does the socket's traffic match S?         │
    │ public key K      does K work against something in memory?  │
    │ campaign ID C     does C appear in strings elsewhere?       │
    └─────────────────────────────────────────────────────────────┘

  IF NONE OF THEM LINE UP, THE EXTRACTION IS WRONG. And the report
  says so, in those words:

    "A structure consistent with <family> was identified at offset
     <X> within the injected region. Its contents did not correlate
     with observed network traffic and are therefore not treated as
     the malware's configuration. This is recorded as an artefact of
     unknown origin rather than as a positive identification."

  THAT SENTENCE is longer than "Cobalt Strike confirmed". And it is
  the one that survives someone checking your work.

EOF

Step 4 is the deliverable: the decision tree in code, and the chrome.exe case at the bottom —
310 modules and 3 RWX regions is JIT compilation, and reporting a browser as malware is the
error that ends a memory-forensics engagement's credibility. The svchost.exe case is the other
extreme: named svchost.exe, not running from System32 — that is process impersonation, and
it's one line to spot.

05-family-discipline.md is the discipline note: a family plugin parses a structure at an
offset the malware author controls, so its output is a hypothesis. If the extracted C2 doesn't
appear in netscan and the extracted sleep time doesn't match the packet interval, the
extraction is wrong — and the note gives you the exact sentence to write instead.
