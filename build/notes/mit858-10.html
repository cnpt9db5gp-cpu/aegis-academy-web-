Symbolic Execution

Summary

Testing every input is impossible; reasoning about paths is not. Symbolic execution executes
a program with symbolic rather than concrete inputs, so each branch forks into both possibilities
and the tool tracks the set of states that could reach your target.

This is MIT 6.858 lecture 10, and the practical reading is on symbolic execution finding "inputs
of death" in real binaries.

Key ideas

  • Replace concrete values with symbolic ones; the program forks at each branch
  • Maintain a path condition: the constraints that must hold to reach this state
  • Goal-directed search: keep only states that can still reach the target
  • Concrete execution (run it for real) versus concrete symbolic execution (fork the
    uninteresting parts, run the interesting ones)
  • Fuzzers (AFL) do the opposite: random inputs with coverage feedback. Symbolic goes
    exhaustively; fuzzing goes broad and cheap. They are complements.
  • The limit is path explosion: 100 branches = 2^100 paths

Concolic execution, the practical middle

symbolic:  every path      -> complete, but explodes
fuzzing:   random paths    -> fast, but may miss the bug
concolic:   most concrete, fork at interesting branches -> the practical choice

When the engine hits a syscall or complex library, it stops branching and
actually runs the code, then records the inputs for replay. That is what
angr does by default and what makes it usable on real binaries.

Path conditions in practice

def is_admin(user, password):
    if not check_password(password):     # branch A
        return False
    if user != "admin":                 # branch B
        return False
    return True

Concolic reasoning: to reach the return True, you need branch A false
(password correct) and branch B false (user is admin). The engine derives
precisely those constraints and solves them.

Terminology

Term Meaning
Symbolic execution Execute with symbolic inputs, forking at branches
Path condition Constraints under which this path is feasible
Path explosion Branching causes 2^n paths
Concolic execution Concrete execution plus symbolic branching at interesting points
Z3 / SMT solver The constraint solver deciding feasibility
angr A CFG-based binary analysis framework
Fuzzing / AFL Coverage-guided random input generation
Coverage Which code paths the input reached
Hook Override a function during symbolic execution
JIT / stub Generated code emulating external calls
Input of death An input the analysis proves causes memory unsafety

# --- a manual concolic experiment, no framework needed ---
cat > concolic.py <<'PY'
#!/usr/bin/env python3
"""
A concolic demonstration without any framework: find the inputs that
reach each branch by solving the constraints directly.
"""
def check(user, pin):
    if len(pin) != 4:      return "A:wrong-length"
    if not pin.isdigit():  return "B:not-digits"
    if pin != "1337":      return "C:wrong-code"
    if user != "root":     return "D:wrong-user"
    return "E:authenticated"

# Instead of trying 10000 combinations, derive the requirements:
print("  path to E requires:")
print("    len(pin) == 4")
print("    pin.isdigit()")
print("    pin == '1337'")
print("    user == 'root'")
print()
print("  solution: user='root', pin='1337'  -> ", check("root","1337"))
print("  failure : user='guest', pin='1337' -> ", check("guest","1337"))
print()
print("  The engine never 'tried' the wrong inputs. It reasoned about them.")
PY

#include <stdio.h>
#include <string.h>
#include <stdlib.h>

/* Four branches. Reaching the final line requires satisfying all four. */
void check(const char *user, const char *pin) {
    if (strlen(pin) != 4)            { puts("length");  return; }
    if (!isdigit((unsigned char)pin[0])) { puts("digits"); return; }
    if (strcmp(pin, "1337") != 0)    { puts("code");    return; }
    if (strcmp(user, "root") != 0)   { puts("user");    return; }
    puts("AUTHENTICATED");
}

int main(int argc, char **argv) {
    if (argc < 3) { fprintf(stderr, "usage: %s <user> <pin>\n", argv[0]); return 1; }
    check(argv[1], argv[2]);
    return 0;
}
EOF

# --- 3. concolic reasoning by hand ---
cat > 03-concolic.md <<'EOF'
# Concolic execution by hand

`target` has four branches. To reach `AUTHENTICATED`, all four must go the
way that does not return:

    strlen(pin) == 4          AND
    isdigit(pin[0])           AND
    pin == "1337"             AND
    user == "root"

A concolic engine derives exactly that conjunction and hands it to a solver.
The solver returns `{pin: "1337", user: "root"}`.

**The key insight:** the engine never *executes* the wrong paths. It executes
one path concretely, and when it reaches a branch whose outcome depends on
input it forks and adds the constraint to each successor's path condition.
Where execution reaches something it cannot model (a syscall, a library), it
stops forking and runs concretely, recording inputs for replay.

## The three knobs in angr

- `angr.Project(path, auto_load_libs=False)` — skip libc, model only your code
- `state = proj.factory.entry_state(args=[...])`
- `simgr = proj.factory.simulation_manager(state)`
- `simgr.explore(find=ADDR_AUTH, avoid=ADDR_FAIL)` — goal-directed

That is the whole API for the common case.
EOF
cat 03-concolic.md

cat > solve.py <<'PY'
import angr, claripy
proj = angr.Project("./target", auto_load_libs=False)
state = proj.factory.entry_state(args=[angr.SimFile("/dev/stdin"), "root", "1337"])
sm = proj.factory.simulation_manager(state)
print("  exploring for the path that reaches AUTHENTICATED...")
sm.explore(find=lambda s: b"AUTHENTICATED" in s.posix.dumps(0),
           avoid=lambda s: b"length" in s.posix.dumps(0) or b"digits" in s.posix.dumps(0))
if sm.found:
    stdin = sm.found[0].posix.dumps(0)
    print(f"  found: {stdin!r}")
else:
    print("  no solution found within the step budget")

# --- 5. which analysis when? ---
cat > 05-choosing.md <<'EOF'
# Choosing an analysis technique

| Technique | Cost | Completeness | Use when |
|---|---|---|---|
| unit tests | minutes | none | you know the input |
| fuzzing | minutes-hours | none | the input space is large, crashes are detectable |
| concolic / symbolic | seconds-minutes | high on small inputs | you can express a goal |
| static analysis (SAST) | seconds | high on what it models | reviewing, before running |
| dynamic taint tracking | runtime | high on observed paths | you need "where did this input go" |
| manual review | hours | low | the logic is subtle, or the bug is in the design |

**They are complements.** Fuzz to find crashes cheaply, symbolic to explain
and to reach deep states, static to review, dynamic to confirm.

The important discipline: each technique's *blind spots* are different, so
combining them finds what any one misses. This is the same argument as
defence in depth, applied to analysis.
EOF
