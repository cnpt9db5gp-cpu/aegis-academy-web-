Devices, Cables, Switches and Bridges

Summary

Layer 1 physical and Layer 2 data link, from real cable to real switch. The goal is not to memorise
connector pinouts — it is to understand what a switch actually does with a frame, because every
Layer 2 attack depends on that behaviour.

Key ideas

  • Copper: twisted pair (UTP/STP), 100 m limit for a run, 4 pairs used for 1 GbE
  • Fibre: immune to EMI, far longer runs, two types (single-mode vs multi-mode)
  • Hubs vs switches: a hub repeats to every port; a switch forwards by MAC table
  • Bridge vs switch: a bridge connects LANs; a switch is a many-port bridge
  • Collision domains: a hub shares one; a switch gives one per port
  • Broadcast domain: a switch does not break it — only a router or VLAN does. This
    distinction causes most early mistakes.

Terminology

Term Meaning
UTP / STP Unshielded / shielded twisted pair
Patch panel Where runs terminate in a rack
Hub Layer 1 repeater; one collision domain
Switch Layer 2 device with a MAC table
Bridge Connects two LAN segments at Layer 2
Collision domain Where frames can collide
Broadcast domain Where a broadcast is flooded
Full duplex No collisions; send and receive simultaneously
Auto-MDIX Switch auto-detects cable polarity

Kali commands

# --- read the link, exactly like a switch does ---
ip -br link
cat /sys/class/net/*/speed 2>/dev/null
cat /sys/class/net/*/duplex 2>/dev/null
for i in /sys/class/net/*; do
  n=$(basename $i)
  echo "  $n: $(cat $i/operstate 2>/dev/null) $(cat $i/speed 2>/dev/null)s"
done

# --- the switch's CAM table, visible on Linux ---
bridge fdb show 2>/dev/null || echo "(needs a bridge; see ip link)"
ip neigh show                      # the ARP cache is a Layer 2-adjacent table
arp -n | head

# --- cabling facts from the kernel ---
ethtool eth0 2>/dev/null
ethtool -i eth0 2>/dev/null
cat /sys/class/net/eth0/supported_link_modes 2>/dev/null

# --- is anything bridging? ---
lsmod | grep -E "bridge|8021q"
ip link show type bridge 2>/dev/null
ip -d link show | grep -A2 bridge | head

Field lab

Objective: observe a switch's forwarding behaviour from a Linux host.

# --- PRE-FLIGHT: this lab needs root, so authenticate ONCE, HERE, first ---
# `sudo something &` backgrounds the password PROMPT along with the command.
# With no terminal attached to answer it, sudo fails - and `2>/dev/null`
# then throws away the only clue. The result is a capture file that was
# never written, followed by a screenful of "no such file".
#
# `sudo -v` validates the credential in the FOREGROUND, where you can see
# and answer the prompt. It caches for ~15 minutes, so every backgrounded
# `sudo` below is prompt-free and actually runs.
if ! sudo -v; then
  echo "  sudo is unavailable or the password was wrong - stop here." >&2
  echo "  Everything below needs root. Nothing will be captured." >&2
  exit 1
fi
mkdir -p ~/aegis/labs/ccna-01 && cd ~/aegis/labs/ccna-01

# --- 1. your interfaces and their state ---
{
  echo "=== links ==="
  ip -br link
  echo
  echo "=== per-interface detail ==="
  for i in /sys/class/net/*; do
    n=$(basename $i)
    [ "$n" = "lo" ] && continue
    printf "  %-8s state=%-3s mtu=%-6s mac=%s\n" "$n" \
      "$(cat $i/operstate 2>/dev/null)" "$(cat $i/mtu 2>/dev/null)" \
      "$(cat $i/address 2>/dev/null)"
  done
} 2>&1 | tee 01-links.txt

# --- 2. the ARP cache IS a Layer 2 concept leaking into Layer 3 ---
{
  echo "=== ip neigh (the ARP table) ==="
  ip neigh show
  echo
  echo "note: entries in FAILED or INCOMPLETE state = nobody answered the ARP"
} 2>&1 | tee -a 01-links.txt

# --- 3. PROVE the broadcast domain, and that a switch does not stop it ---
sudo timeout 8 tcpdump -i lo -n -c 20 "arp or (udp port 67)" 2>/dev/null | head -12 &
CAP=$!
sleep 1
# send an ARP request for a non-existent host - it must be visible to everything
arping -c 3 -I lo 192.168.56.200 2>/dev/null || ping -c1 -W1 192.168.56.200 >/dev/null 2>&1 &
sleep 3; kill $CAP 2>/dev/null; wait 2>/dev/null
echo "  (if tcpdump captured the ARP, the broadcast reached this host)"

# --- 4. count broadcasts per interface, then think about segmentation ---
{
  echo "=== how many broadcasts does this box see? (10s sample) ==="
  sudo timeout 10 tcpdump -i any -n "arp" 2>/dev/null | wc -l
} 2>&1 | tee 02-broadcast.txt

# --- 5. your VLAN picture ---
{
  echo "=== VLANs this host participates in ==="
  ip -d link show | grep -B2 -A2 vlan | head -20 || echo "  (no VLAN interfaces configured)"
  echo
  echo "=== 802.1Q support loaded? ==="
  lsmod | grep -E "^8021q" || modinfo 8021q 2>/dev/null | head -2
} 2>&1 | tee 03-vlan.txt

# --- 6. what this means for an assessment ---
cat > 04-notes.md <<'EOF'
# Layer 2 observations

- Broadcast domain on this host: ______ (fill in from 02-broadcast.txt)
- ARP is unauthenticated: anyone on the segment can answer for any address
- A switch isolates collisions but NOT broadcasts
- Implication: an ARP spoof to become a MITM needs only L2 adjacency, no credentials
EOF
cat 04-notes.md

Step 3 is the whole point. Seeing the broadcast arrive is the moment "the switch forwards
frames, not traffic selectively" becomes concrete — and it is the foundation of every MITM
technique in Tier 2.
