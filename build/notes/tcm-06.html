Pivoting and Internal Network Movement

Summary

Pivoting is using one compromised host to reach networks you could not otherwise reach. It is
where engagements either become very valuable or very dangerous, because a pivot is the point
at which the blast radius grows by an order of magnitude.

The lecture's core discipline: every pivot is a new authorisation question. "I have a shell"
was never permission to scan the internal network.

Companion to ccnad-01 (routing and segmentation) and atb-01
(Active Directory trust paths). This note is the network mechanics.

Why pivot at all

  - segmentation worked, and the only way past it is a foothold
  - internal-only services (AD, databases, management consoles)
  - trust relationships: compromising a web server may reach an app server
  - the objective is behind a different firewall

  But also:
  - the perimeter IS the security boundary, and a flat network means the
    perimeter is the only defence. Proving that is the whole finding.

That last point is the one that belongs in the report. Pivoting without
hitting an authorisation boundary is itself the critical finding — it
proves segmentation does not exist.

The three techniques

  1. PROXY CHAIN      route traffic through an existing SSH connection
                      proxychains is the client; SSH -D is the server
  2. TUNNEL           encapsulate one protocol inside another
                      chisel, ligolo; carries arbitrary TCP/UDP over HTTP
  3. PORT FORWARD     expose a remote port as a local one
                      ssh -L / -R; simplest and most reliable

Choose by need, in that order of preference: port forward if one service,
proxy chain if a tool suite, tunnel if you need arbitrary protocols or the
link is unreliable.

Port forwarding, precisely

# LOCAL forward: 127.0.0.1:8888 on MY machine becomes 10.0.0.5:8080 on the target
ssh -N -L 8888:10.0.0.5:8088 user@192.168.56.20
# now: curl http://127.0.0.1:8888

# REMOTE forward: a port on the TARGET listens and forwards back to me
ssh -N -R 9001:127.0.0.1:9001 user@192.168.56.20
# now: connect to 192.168.56.20:9001 and reach MY listener

# SOCKS PROXY: route anything that honours SOCKS through the SSH session
ssh -N -D 127.0.0.1:1080 user@192.168.56.20
proxychains nmap -sT -sV -p- 10.0.0.5

The three-line rule for any forward:
1. bind to 127.0.0.1, never 0.0.0.0 — a forward on 0.0.0.0 exposes the
internal service to your whole network, which is a worse finding than the one you are chasing
2. pick a high, unused port
3. record it in the diary, and kill it when you are done

ProxyChains, correctly

# /etc/proxychains4.conf
# strict_chain            <- fail if any hop is down (use this)
# proxy_dns               <- also proxy DNS, or you leak queries
socks4  127.0.0.1 1080

# Verify it routes where you think it does
proxychains4 curl -s --max-time 5 https://ifconfig.me

proxy_dns matters more than people realise: without it, DNS queries leak
outside the tunnel, which both breaks resolution on split-horizon internal
networks and tells the target's resolver exactly what you are looking for.

Tunnelling: chisel

# chisel is the workhorse: TCP/UDP over HTTP or SOCKS, single static binary

# server side, on the host you already own
./chisel server --port 8080 --reverse --host 127.0.0.1

# client side, from the compromised host
./chisel client 127.0.0.1:8080 R:1080:socks

# now proxychains through the compromised host's SOCKS
proxychains4 ssh -o ProxyCommand="nc -X 5 -x 127.0.0.1:1080 %h %p" \\
    user@10.0.0.5

The reason tunnels exist: deep internal networks have no route back, only
a forward path. HTTP is usually the one thing allowed out, so tunnelling
inside HTTP is what survives.

SMB relay: the pivot that needs no exploit

  SMB SIGNING:
    - signed   : the client signs the SMB session key; the server verifies.
                 Relay is PREVENTED.
    - unsigned : the client does not sign. A third party can:

      1. victim authenticates to you (a file share or a web page that
         triggers an outbound SMB connection)
      2. you forward that authentication to the real server
      3. you are now authenticated as the victim to the real server

  CONDITION: the attacker must be able to receive the victim's outbound
             connection. This is what makes it a LAN attack.

  FIX: require SMB signing on every host. Enforce it with a GPO, not a
       per-host checkbox.

# Is signing required? This is a one-line check per host and a finding per host.
nmap -p 445 --script smb2-security-mode 192.168.56.20
# output contains: "message signing: enabled" or "disabled"

AD trust paths: the pivot map

  DOMAINADMIN of domain A  ->  trusts domain B  ->  admin in B
  A machine account in forest A -> SQL escalation -> domain admin in A
  Any admin in the domain -> shadow credentials -> domain admin
  Web server run as a service account -> read that account's privileges ->
     reach internal services

  Every one of these is a graph edge. Enumerate the graph, then walk it.
  That is why BloodHound is the tool of the stage.

Pivot discipline

  BEFORE EVERY PIVOT:
    [ ] is the destination range in the WRITTEN scope?
    [ ] did the client explicitly authorise internal movement?
    [ ] does the ROE set a hop limit or a host limit?
    [ ] is this a scan (noisy) or a single connection (quiet)?
    [ ] what is your stop condition on the internal network?

  DEFAULTS TO USE:
    hop limit          : if not written, assume 1 hop. Ask.
    scan rate internal : low. Internal networks have monitoring too.
    scope              : assume internal is NOT in scope until told.
    evidence           : record every hop, or you cannot draw the finding.

Terminology

Term Meaning
Pivot Using one host to reach another network
Lateral movement Moving between hosts
Proxy chain Traffic routed through a chain of proxies
SOCKS proxy Generic TCP proxy protocol
Port forward Local port mapped to a remote service
Tunnel One protocol encapsulated inside another
chisel Fast TCP/UDP tunnel over HTTP
ligolo TUN/TAP tunnel for full network access
SMB relay Reflecting authenticated SMB to impersonate a victim
SMB signing The control that prevents relay
Trust path An authorisation edge between domains
BloodHound AD graph enumeration and path analysis
Blast radius Damage potential; grows with every hop

# --- 1. build the pivot lab: two networks, only the "jump host" reaches both ---
cat > 00-lab.md <<'EOF'
# Pivot lab

Two VirtualBox networks:
  NET-A  192.168.56.0/24  "external"   -- you sit here
  NET-B  10.10.10.0/24     "internal"   -- only reachable via the jump host

| Host | Networks | Role |
|---|---|---|
| 192.168.56.1 | NET-A only | your workstation |
| 192.168.56.20 | NET-A + NET-B | the JUMP HOST - the pivot |
| 10.10.10.5 | NET-B only | internal web server |
| 10.10.10.6 | NET-B only | internal database |

Setup on the jump host (two NICs, one in each range):
  sudo ip link set ens33 up && sudo ip addr add 192.168.56.20/24 dev ens33
  sudo ip link set ens34 up && sudo ip addr add 10.10.10.20/24  dev ens34
  sudo sysctl -w net.ipv4.ip_forward=1

Then verify you CANNOT reach NET-B from NET-A, which is the premise:
  ping -c1 10.10.10.5        # from your workstation: must fail
  ssh 192.168.56.20 'ping -c1 10.10.10.5'   # from the jump host: must succeed
EOF
echo "written: 00-lab.md"

# --- 2. the three techniques, side by side ---
cat > 01-techniques.md <<'EOF'
# Choosing a pivot technique

| Need | Technique | Command |
|---|---|---|
| one internal HTTP service | port forward | `ssh -N -L 8888:10.10.10.5:80 user@jumphost` |
| a whole tool suite | SOCKS + proxychains | `ssh -N -D 127.0.0.1:1080 user@jumphost` |
| arbitrary TCP/UDP, HTTP-carried | chisel | `chisel client jumphost:8080 R:socks` |
| a whole network, TUN/TAP | ligolo | `ligolo-proxy` + tun interface |

## Always
- bind forwards to 127.0.0.1, never 0.0.0.0
- enable `proxy_dns` when using SOCKS
- use `strict_chain` in proxychains
- record the hop in the engagement diary
- tear it down at the end and verify

## Never
- leave a forward running after the engagement
- bind a forward to a routable interface "just for convenience"
- assume internal is in scope because external was
EOF
echo "written: 01-techniques.md"

# --- 3. demonstrate the premise: NET-B is unreachable ---
{
  echo "=== from NET-A (this workstation) ==="
  in_scope 10.10.10.5 && echo "  10.10.10.5 IN SCOPE per the guard" \
                        || echo "  10.10.10.5 REFUSED by the scope guard"
  echo "  ^ this is the whole point. The guard does not know that NET-B is"
  echo "    'internal to the engagement'. It knows 10/8 is not in my scope."
  echo
  echo "=== the routes I actually have ==="
  ip route | sed 's/^/  /'
  echo
  echo "=== without a pivot, NET-B is unreachable. That is segmentation"
  echo "    working, and it is what the pivot is here to test. ==="
} | tee 02-premise.txt

# --- 4. SOCKS proxy + proxychains, configured correctly ---
cat > /etc/proxychains4.conf.d/aegis.conf 2>/dev/null <<'EOF'
# AEGIS pivot config
strict_chain          # fail if a hop is down rather than leaking traffic
proxy_dns             # route DNS through the tunnel too
remote_dns_subnet 224
tcp_read_time_out 15000
tcp_connect_time_out 8000
[ProxyList]
socks5  127.0.0.1 1080
EOF
mkdir -p /etc/proxychains4.conf.d
cat > /etc/proxychains4.conf.d/aegis.conf <<'EOF'
strict_chain
proxy_dns
tcp_read_time_out 15000
tcp_connect_time_out 8000
[ProxyList]
socks5  127.0.0.1 1080
EOF
echo "written: /etc/proxychains4.conf.d/aegis.conf"
echo "  activate with:  proxychains4 -f /etc/proxychains4.conf.d/aegis.conf <cmd>"

# --- 5. the verification that makes a pivot trustworthy ---
cat > 03-verify.md <<'EOF'
# Verifying a pivot before you trust it

```bash
# 1. is the tunnel alive?
ss -tnp | grep 1080          # a SOCKS listener, loopback only

# 2. does traffic actually leave from the jump host?
ssh user@192.168.56.20 'curl -s --max-time 5 http://10.10.10.5/ | head -1'

# 3. does it appear to, from your side? (compare the two)
curl -s --max-time 5 http://127.0.0.1:8888/ | head -1

# 4. confirm your source address is the jump host, not you
proxychains4 -f /etc/proxychains4.conf.d/aegis.conf curl -s https://ifconfig.me

# 5. THE IMPORTANT ONE: is it leaking without the proxy?
#    a strict_chain misconfiguration falls back to a DIRECT connection
curl -s --max-time 5 http://10.10.10.5/ | head -1   # must FAIL

Step 5 catches the single most common pivot failure: a broken tunnel that
looks like it works because proxychains fell back to direct. Every
"pivot attempt" you record without step 5 may have been you, not the pivot.

Log every hop

14:20  pivot 1: SSH local forward 127.0.0.1:8888 -> 10.10.10.5:80
       via 192.168.56.20. Verified source address 10.10.10.20.
14:35  removed forward.

EOF
echo "written: 03-verify.md"

--- 6. SMB signing: the check that finds a relay pivot ---

{
echo "=== SMB signing status ==="
echo " signing enabled -> relay is not possible against this host"
echo " signing disabled -> relay is possible; report it"
echo
echo " check: nmap -p 445 --script smb2-security-mode "
echo " or locally:"
echo
# local equivalent: what does this host require?
if command -v testparm >/dev/null 2>&1; then
testparm -sv 2>/dev/null | grep -iE "server signing|client signing" | sed 's/^/ /'
fi
echo
echo "=== relay defence, in order of strength ==="
echo " 1. SMB signing REQUIRED everywhere (GPO, not per-host)"
echo " 2. SMB encryption for sensitive shares"
echo " 3. Restrict inbound SMB 445 to management hosts only"
echo " 4. LDAP signing, channel binding, and LDAP protections"
echo " (this is the OTHER relay family, and it is how most relays"
echo " work in practice)"
} | tee 04-smb.txt

--- 7. the AD trust graph, offline ---

cat > 05-ad-graph.md <<'EOF'

The AD graph, modelled offline

Every privilege-escalation path in Active Directory is an edge in a graph.
Nodes: users, groups, computers, sessions, ACLs. Edges: who can read
whose credential, who can control which service, which sessions exist.

  svc_webapp (service account)
        |
        | HasSession/ReadGMSAPassword
        v
  SA-WEBAPP  --GenericAll-->  DOMAIN ADMINS
        |
        | member of
        v
  "Backup Operators"  --SeRestorePrivilege-->  domain root
        |
        v
   takeover

The graph makes the path visible. BloodHound automates its collection;
the reading of the graph is the skill.

The three AD paths that appear in every engagement

  1. Credential exposure — a readable share, a config file, a plaintext
    password in a script. Found by looking, not by exploiting.
  2. ACL abuse — a GenericAll/WriteDACL on a user, group, or computer.
    Found by enumerating ACLs, not by guessing passwords.
  3. Service accounts — a service account in a privileged group is a
    single misconfiguration away from domain admin.

How to report a path

  Source      : user jdoe (domain Users)
  Path        : jdoe -> member of "Helpdesk" -> GenericWrite on
                SA-BACKUP -> SeRestorePrivilege -> DC01$
  Impact      : domain compromise from any authenticated account
  Effort      : none; jdoe is a normal account with no special rights
  Fix         : remove jdoe from Helpdesk; remove GenericWrite on
                SA-BACKUP; separate backup operator rights from
                interactive login rights

That is a Critical finding written in five lines. The graph is the work.
EOF
echo "written: 05-ad-graph.md"

--- 8. tear it all down, and prove it ---

cat > 06-teardown.sh <<'EOF'

!/usr/bin/env bash

Every pivot must be gone when the engagement ends.

echo "=== SOCKS listeners (pivots) ==="
ss -tnp 2>/dev/null | grep -E "127.0.0.1:1080|:1080 " | sed 's/^/ /' || echo " none"
echo
echo "=== SSH forwards still running ==="
ps -ef | grep -E "ssh .*-[LRD] " | grep -v grep | sed 's/^/ /' || echo " none"
echo
echo "=== chisel / ligolo processes ==="
ps -ef | grep -E "chisel|ligolo" | grep -v grep | sed 's/^/ /' || echo " none"
echo
echo "=== tun interfaces ==="
ip -br link | grep tun | sed 's/^/ /' || echo " none"
echo
echo "=== proxychains config installed by this engagement ==="
ls -la /etc/proxychains4.conf.d/aegis.conf 2>/dev/null && \
echo " REMOVE before finishing" || echo " (not present)"
echo
echo " Kill the SSH master sessions last, or you lose your access to"
echo " clean up anything remote."
EOF
chmod +x 06-teardown.sh
./06-teardown.sh 2>&1 | tee 06-teardown.txt
```

Step 3 is the deliverable: the scope guard refusing 10.10.10.5 even though it is
internal to the engagement. The guard doesn't know about NET-B; it knows 10/8 is not in the
written scope. That is exactly right — the ROE is a document, not a heuristic, and an
internal range is out of scope until someone says otherwise.

Step 6 produces the artifact that ends an engagement cleanly: proof of teardown.
