Network Security

Summary

Lecture 12 is the bleak one. The preparation reading is Security Problems in TCP/IP (Bellovin,
1994), and the lecture's argument is that many of TCP/IP's design choices make secure
communication impossible without bolting on a layer above.

Key ideas

  • IP is unauthenticated and unauthenticable: source addresses are claimed, not proven
  • TCP's three-way handshake is stateful and predictable, which is the root of its weaknesses
  • Sequence prediction enables blind injection into an established connection
  • Spoofing, smurf, source routing, ICMP redirects are all structural, not bugs
  • The DoS surface is enormous: no state means no way to distinguish friend from attacker
  • TLS and IPsec are bolt-ons; the network below them was never designed for this

The structural problems

Problem Why the design caused it
Source spoofing IP headers carry no proof of origin
Blind data injection sequence numbers are guessable
Smurf amplification UDP echo servers amplify small requests
ICMP redirect attacks the host trusts routing messages from anyone
SYN flood half-open connections consume server state
Traffic analysis headers and sizes are observable even when encrypted

None of these are implementation bugs. They are consequences of a
performance-oriented design that never considered an active adversary.

TCP sequence numbers, concretely

A classic blind injection:

1. Attacker learns the current sequence number of a connection (guess + observe)
2. Attacker sends a forged packet with that sequence number
3. The receiver accepts it as legitimate
4. The attacker never sees the reply

Modern kernels randomise ISNs per connection (RFC 6528), which forces an
attacker to be on-path or to brute-force a 32-bit space. That is a mitigation,
not a fix.

What fixes what

Defence Addresses
RFC 6528 ISN randomisation blind injection
TCP MD5 signatures blind injection (removed, too costly)
SYN cookies SYN flood state exhaustion
ingress filtering (BCP 38) source spoofing on your network
egress filtering spoofing from your network
disabling ICMP redirects redirect attacks
rate limiting broad DoS
TLS / IPsec confidentiality, integrity, authentication
WireGuard / Wireguard-style Noise modern, simpler, audited design

The honest conclusion: the fix for the network layer's flaws is to stop
relying on the network layer for anything and use end-to-end authenticated
encryption instead.

Terminology

Term Meaning
Source spoofing Forging the IP source address
Sequence prediction Guessing the next TCP sequence number
Blind injection Injecting into a connection without seeing replies
Smurf amplification Small UDP request → large flood
ICMP redirect Message telling a host to route via another
SYN flood Half-open connections exhausting server state
SYN cookies Encode state in the ISN instead of a table
Ingress filtering Dropping packets with impossible sources
On-path attacker Someone who can see and modify your traffic
Off-path attacker Someone who only sees one direction, or neither

# --- the anti-spoofing controls, on this host ---
{
  echo "=== source address validation ==="
  # what the system considers valid sources for our traffic
  ip route get 8.8.8.8 | sed 's/^/  /'
  ip route get 127.0.0.1 | sed 's/^/  /'
  echo
  echo "=== ICMP redirects accepted? (should be 0 on a host) ==="
  cat /proc/sys/net/ipv4/conf/all/accept_redirects 2>/dev/null
  cat /proc/sys/net/ipv4/conf/all/secure_redirects 2>/dev/null
  cat /proc/sys/net/ipv4/conf/all/send_redirects 2>/dev/null
  echo "  (all/accept_redirects 0 = good)"
  echo
  echo "=== SYN cookie protection ==="
  echo "  tcp_syncookies: $(cat /proc/sys/net/ipv4/tcp_syncookies 2>/dev/null)"
  echo
  echo "=== rp_filter (reverse path filtering = ingress filter) ==="
  for f in /proc/sys/net/ipv4/conf/*/rp_filter; do
    printf "  %-44s %s\n" "$f" "$(cat $f 2>/dev/null)"
  done
} 2>&1 | tee 01-network-hardening.txt

# --- 1. the full audit ---
{
  echo "=== TCP/IP SECURITY POSTURE ==="
  echo
  echo "-- ICMP redirects (an on-path attacker can steer traffic) --"
  for f in all default; do
    printf "  accept_redirects  %-10s %s\n" "$f" "$(cat /proc/sys/net/ipv4/conf/$f/accept_redirects 2>/dev/null)"
    printf "  send_redirects    %-10s %s\n" "$f" "$(cat /proc/sys/net/ipv4/conf/$f/send_redirects 2>/dev/null)"
    printf "  rp_filter         %-10s %s\n" "$f" "$(cat /proc/sys/net/ipv4/conf/$f/rp_filter 2>/dev/null)"
  done
  echo
  echo "-- SYN flood --"
  echo "  tcp_syncookies: $(cat /proc/sys/net/ipv4/tcp_syncookies 2>/dev/null)  (1 = enabled)"
  echo "  tcp_max_syn_backlog: $(cat /proc/sys/net/ipv4/tcp_max_syn_backlog 2>/dev/null)"
  echo "  tcp_abort_on_overflow: $(cat /proc/sys/net/ipv4/tcp_abort_on_overflow 2>/dev/null)"
  echo
  echo "-- martians (packets with impossible addresses, i.e. spoofing attempts) --"
  echo "  log_martians: $(cat /proc/sys/net/ipv4/conf/all/log_martians 2>/dev/null)"

} 2>&1 | tee 01-posture.txt

# --- 2. demonstrate the redirect setting is exploitable in principle ---
cat > 02-redirects.md <<'EOF'
# Why ICMP redirects matter

An ICMP redirect (type 5) tells a host: "to reach network X, use router Y".
A host that accepts them will update its routing table.

An on-path attacker can therefore **reroute a victim's traffic through a
machine the attacker controls**, without touching the victim's configuration,
without credentials, and without breaking TLS (the connection still works —
the attacker just proxies it).

## Defence
    net.ipv4.conf.all.accept_redirects = 0
    net.ipv4.conf.all.secure_redirects = 0

Setting it to 0 means the host ignores redirects entirely, which is correct
for anything except a genuine router.

## Related: source routing
IP source route options were designed for diagnostics and were usable to
bypass path ACLs. `net.ipv4.conf.all.accept_source_route = 0` disables it.
Modern stacks drop these options; check yours rather than assume.
EOF
cat 02-redirects.md

# --- 3. what is observable on this network, even with TLS ---
{
  echo "=== METADATA an on-path observer sees, without decrypting anything ==="
  sudo timeout 12 tcpdump -i any -n -q 2>/dev/null | head -200 > /tmp/aegis-snap.txt
  echo
  echo "  -- destination ports (which service, therefore which site class) --"
  awk '{print $3}' /tmp/aegis-snap.txt | cut -d. -f5 | sort | uniq -c | sort -rn | head -6
  echo
  echo "  -- packet sizes and timing (traffic analysis works even on ciphertext) --"
  awk '{print "packet length: " $NF}' /tmp/aegis-snap.txt | sort | uniq -c | sort -rn | head -6
  echo
  echo "  Read that again: packet SIZE and TIMING leak content structure."
  echo "  This is why TLS is not traffic-analysis resistance."
} 2>&1 | tee 03-observable.txt

# --- 5. the design argument, written out ---
cat > 05-conclusion.md <<'EOF'
# The lecture's argument

TCP/IP was designed for a cooperative network of a few trusted hosts, with
performance as the primary goal. Security was not a requirement, and the
assumptions are now all false:

| Original assumption | Reality |
|---|---|
| hosts are cooperative | hosts are hostile |
| networks are reliable and benign | networks are actively attacked |
| small, homogeneous networks | the entire internet |
| performance matters most | confidentiality and integrity matter too |
| physical access is trusted | it is not |

Bellovin's 1994 paper enumerated these; the mitigations bolted on since
(SYN cookies, RFC 6528, ingress filtering, TLS) each address one symptom.

**The architectural conclusion is not "patch TCP/IP".** It is: *do not rely on
the network layer for security at all*. Use end-to-end authenticated
encryption (TLS 1.3, WireGuard, SSH), assume the network is hostile, and treat
any protocol whose security depends on network-layer properties as unsafe.
EOF
cat 05-conclusion.md

Step 3 is the uncomfortable one: you cannot decrypt it, but packet size and timing still leak
structure. That is why traffic analysis is a real attack and TLS is not a complete answer.
