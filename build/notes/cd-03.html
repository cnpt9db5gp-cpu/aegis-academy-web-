Memory Forensics Challenges

Summary

Memory challenges are faster to resolve than disk challenges and much harder to fake your way
through, because the ground truth is a running system's state. This note covers the artefact
classes, the four questions that appear in nearly every one, and the discipline of writing a
memory finding so it survives scrutiny.

The framing: a memory answer is a claim about a moment. "This
process was running, at this address, at this time" — and every part of
that claim has to be checkable from your output.

Companion to vol-01..vol-04 (the tooling) and cd-01 (the flow).
This note is the discipline against real memory dumps.

The artefact classes

  WHAT IS IN A MEMORY DUMP THAT IS NOT ON DISK

    THE RUNNING PROCESS LIST     including processes that unlinked
                                 themselves
    COMMAND LINES                including ones that were wiped
    LOADED MODULES               including reflective DLLs that were
                                 never registered
    INJECTED MEMORY              private RWX regions with no file
    OPEN SOCKETS                 with the owning PID - who was talking
                                 to whom, right now
    OPEN HANDLES                 to files, registry keys, and other
                                 processes. A handle to a deleted
                                 file is a handle to a file you cannot
                                 find on disk
    THE DNS CACHE                domains this host resolved, and when
    REGISTRY HIVES               as they were in memory, which may
                                 differ from what is on disk (a
                                 registry key deleted from disk can
                                 still be in the cached hive)
    THE TOKEN OF EVERY PROCESS   the user's group memberships, from
                                 the PEB - a live authorisation
                                 snapshot (see ad-02's PAC)
    CLIPBOARD                    what was copied, if it has not
                                 rotated out of the 5-buffer
    KEYSTROKES                   if a keylogger ran, or if the
                                 console buffer has them
    ENVIRONMENT VARIABLES        per process; often where a C2
                                 config or a key ends up
    CACHED CREDENTIALS           in LSASS. The most dangerous thing in
                                 the image.

  THE QUESTION THAT MEMORY ANSWERS THAT DISK CANNOT:
    "What was this machine DOING at 14:32, and what was it talking to?"
    Disk tells you what exists. Memory tells you what is happening.

The four questions

  1. IS THERE A MALICIOUS PROCESS?
     pslist + pstree + cmdline + dlllist + malfind
     The join, not any one. See vol-02's three-way cross-check.

  2. WHAT WAS IT COMMUNICATING WITH?
     netscan + netstat + the DNS cache
     An established outbound connection at the capture timestamp,
     joined to a process name and a path, is the answer.

  3. IS THERE INJECTED CODE?
     malfind, then malfind.Dump, then hand the dump to for-05.
     A family plugin's output must be corroborated (vol-04).

  4. WHAT CREDENTIALS WERE ON THE MACHINE?
     hashdump (demonstrable) vs credential_dump (plaintext).
     The ROE question. See vol-03.

# The memory challenge flow

```bash
VOL="vol.py"; IMG="challenge.raw"

# 0. VERIFY THE IMAGE
sha256sum "$IMG"          # the challenge gives you one
file "$IMG"               # 'data' is CORRECT for a raw memory image
du -h "$IMG"              # should be close to the source machine's RAM

# 1. THE REFERENCE POINT (and it is the first plugin, always)
$VOL windows.info -f "$IMG"
#   ^ SystemTime is your clock. Every other timestamp in every other
#     plugin is relative to it. Record it. Record the offset from
#     your own clock.

# 2. THE PROCESS LAYER
$VOL windows.pstree -f "$IMG"            # the shape
$VOL windows.cmdline -f "$IMG"           # what was run, with paths
$VOL windows.dlllist -f "$IMG"           # modules per process

# 3. THE DIFF (this is the technique, not a plugin)
$VOL windows.pslist  -f "$IMG" | awk '{print $2}' | sort -u > /tmp/a
$VOL windows.psxview -f "$IMG" | awk '{print $2}' | sort -u > /tmp/b
comm -13 /tmp/a /tmp/b
#   ^ a process that psxview sees and pslist does not: DKOM.
#     This is the single strongest memory finding there is.

# 4. INJECTION
$VOL windows.malfind -f "$IMG"
#   for each hit: --pid, then dlllist --pid, and compare

# 5. THE NETWORK
$VOL windows.netscan -f "$IMG"
$VOL windows.netstat -f "$IMG"
#   join the PIDs to pslist. "svchost.exe" at a Temp path with an
#   outbound connection is the answer to most challenges.

# 6. THE DNS CACHE (the domain behind the IP)
$VOL windows.registry.printkey -f "$IMG" \
  --key 'ROAMING\MACHINE\SOFTWARE\MICROSOFT\WINDOWS NT\CURRENTVERSION\DNS\CACHE'

# 7. THE FILES ONLY IN MEMORY
$VOL windows.filescan -f "$IMG" | head -40
$VOL windows.dumpfiles --pid <pid> -f "$IMG" --dump-dir work/carved
#   ^ this is the handoff to for-05's static triage. Handle the
#     output as malware.

# 8. CREDENTIALS (authorisation gate)
$VOL windows.hashdump -f "$IMG" > work/hashes.txt
#   hashdump is the demonstrable finding. credential_dump prints
#   plaintext and needs its own ROE clause.
```

# --- 3. writing the answer ---
cat > 03-answer.md <<'MD'
# Writing a memory answer so it survives scrutiny

A memory finding is a claim about a moment. Every part of it has
to be checkable from the output you provide.

BAD "There was a malicious process called svchost32.exe and it
connected to 1.2.3.4"

GOOD Claim: process impersonation used to host a C2 channel.

     Evidence, in the order a reviewer would check it:

     1. PROCESS IDENTITY
        windows.pslist: PID 3412, name "svchost.exe",
        command line "svchost.exe -k netsvcs -w"
        windows.cmdline confirms the FULL PATH:
          C:\Users\jdoe\AppData\Local\Temp\svchost.exe
        The genuine svchost runs from
          C:\Windows\System32\svchost.exe
        -> the name is real; the binary is not.

     2. INJECTED CODE
        windows.malfind: PID 3412, 0x1f0000-0x1f7000,
        Tag VEx, 28 KB, no MZ header
        windows.dlllist --pid 3412: 4 modules, none from a
        signed Microsoft path
        -> a private RWX region, with almost nothing loaded.

     3. NETWORK
        windows.netstat: PID 3412, ESTABLISHED,
        10.10.10.50:49876 -> 198.51.100.44:443
        Created 2026-06-11 14:33:02 UTC
        windows.info SystemTime: 2026-06-11 14:34:18 UTC
        -> the connection was live 76 seconds before acquisition.

     4. ATTRIBUTION OF THE DESTINATION
        windows.registry.printkey (DNS\CACHE): entry for
        cdn.example.com, cached 14:33:01, resolves to
        198.51.100.44
        -> the IP is attributable to a domain.

     CONCLUSION: an impersonated system binary hosting injected
     memory, communicating with an external host over TLS,
     established 76 seconds before the image was taken.

     NOT CLAIMED: which actor, what the payload does, or what
     data left the host. None of that is in the image.


```text
  THE LAST PARAGRAPH IS THE ONE THAT MATTERS.

  A memory image is a snapshot of one machine at one second. It
  cannot tell you what happened before, what happened after, what was
  exfiltrated, or who did it. Say that, in those words, and your
  report is trustworthy. Overstate and it is not.

MD
cat 03-answer.md

cat > 04-linux.md <<'MD'

Linux memory challenges

VOL="vol.py"; IMG="challenge.lime"

$VOL linux.pslist   -f "$IMG"
$VOL linux.pstree   -f "$IMG"
$VOL linux.bash     -f "$IMG"           # bash history from memory
$VOL linux.psaux    -f "$IMG"
$VOL linux.lsof     -f "$IMG"           # open files
$VOL linux.ifconfig -f "$IMG"
$VOL linux.proc.Maps -f "$IMG" -p <pid> # the memory map of one process
$VOL linux.proc.Mounts -f "$IMG"
$VOL linux.hidden_modules -f "$IMG"
$VOL linux.check_modules -f "$IMG"

  WHY SOME CHALLENGES USE LINUX IMAGES
    - a smaller, more verifiable plugin set (the analyst can check
      every plugin by hand)
    - no symbol server dependency in the same way (still needs symbols)
    - the artefacts are simpler: .bash_history, /var/log, the process
      environment, and the network state
    - and it trains the same discipline

  THE LiME FORMAT
    A kernel module that dumps physical memory. The image is LiME-
    formatted; Volatility detects it from the header. The advantage
    over a raw dd of a memory device is that it is consistent and
    small enough to transfer.

  THE ARTEFACT LIST is shorter:
    bash history in memory (the real one, including the commands that
    were typed but never made it to the on-disk .bash_history)
    the process environment (PATH, and anything else exported)
    /proc/PID/maps (what is mapped where - and a deleted file still
      mapped is a finding)
    open sockets (ss equivalent)
    the rootkit's own hiding: linux.hidden_modules finds a module
    present in the list but absent from sysfs

# the two classic Linux challenges and their answers
echo "  'Who deleted /var/log/auth.log?'"
echo "    linux.bash -> the rm command, with its timestamp"
echo
echo "  'What was the process hiding?'"
echo "    linux.proc.Maps vs /proc/PID/maps from a disk image:"
echo "    a mapped region with no file behind it is the hiding"
echo
echo "  'Was rootkit installed?'"
echo "    linux.hidden_modules: a module in the loaded list with no"
echo "    matching entry in sysfs"
EOF
cat 04-linux.md

Step 2 is the deliverable: a table of thirteen memory artefacts, eight of which have no

03-answer.md is the discipline: a memory finding is a claim about a moment, and every part
of it must be checkable from output you provide. The sample answer builds it in review order —
process identity, injected code, network, destination attribution — and then ends with the
paragraph that makes a report trustworthy: "Not claimed: which actor, what the payload does, or
what data left the host. None of that is in the image."
