Debugging and Profiling

Summary

Debugging is the skill that separates people who run tools from people who understand systems.
In security it is non-negotiable: exploiting a buffer overflow is debugging, malware analysis
is debugging, and explaining why a payload crashed is debugging.

The tooling on Linux is excellent and mostly free. This lecture covers the four you need first:
gdb, strace, ltrace, and the profiler family.

gdb: the tool that matters most

gdb ./program                 # run a local binary
gdb -p 1234                   # attach to a running process (ptrace)
gdb --args ./prog arg1 arg2   # pass arguments

# the core loop
(gdb) break main
(gdb) run
(gdb) next / n                # step over / step into
(gdb) step / s                # step into
(gdb) print x                 # inspect variable
(gdb) print/x $rsp            # hex
(gdb) info registers
(gdb) x/32xb $rsp             # 32 bytes at the stack pointer, hex
(gdb) x/s $rdi                # read a string from an address
(gdb) disassemble main
(gdb) backtrace / bt          # how did I get here
(gdb) finish                  # run to end of current function

A debugging session you will actually have (buffer overflow, the canonical one):

gdb --args ./vuln
(gdb) break *main
(gdb) run
(gdb) disassemble main
(gdb) break *0x4011a6          # the call instruction
(gdb) continue
(gdb) info registers rsp rbp
(gdb) x/16gx $rsp
(gdb) print $rip
(gdb) x/i $rip                # disassemble at the current instruction
(gdb) bt
(gdb) quit

strace: what does this program actually ask the kernel for?

strace ./program                       # trace everything
strace -f ./program                    # follow forks
strace -p 1234                         # attach to a process
strace -e trace=network ./prog         # only syscalls touching the network
strace -e trace=openat ./prog          # only file opens
strace -o trace.txt ./prog             # write to file

# the two best strace uses in security:
strace -f -e trace=network curl https://example.com    # see every DNS + TLS handshake
strace -e trace=execve -f ./suspicious-binary          # see what a binary executes

strace on an untrusted binary is one of the cheapest, safest dynamic analyses available: the
program's own logic cannot hide a syscall from it (though anti-debugging tricks can blind parts
of it).

ltrace: library calls

ltrace ./prog
ltrace -e 'malloc+free+strcpy' ./prog     # only these

Where strace shows write(1, ...) (a syscall), ltrace shows printf("...") (the library
function that caused it). Combined, they answer "what did this program really do".

Profiling: performance, and occasionally behaviour

time ./prog
/usr/bin/time -v ./prog                  # memory, page faults, context switches

perf record -g ./prog && perf report      # sampling profiler
valgrind --leak-check=full ./prog        # memory errors (slow but precise)

valgrind is a Tier 3 tool: it will tell you exactly which line of a program performs an invalid
memory access, which is often faster than reasoning about a crash by hand.

Debugging a process you do not own

# attach (Linux allows this if same uid, or CAP_SYS_PTRACE)
sudo gdb -p $(pgrep -f vulnerable) 

# core dumps
ulimit -c unlimited
cat /proc/sys/kernel/core_pattern
gdb ./prog /var/lib/systemd/coredump/...

Terminology

Term Meaning
Debugger Attaches to a program and lets you inspect its state
Breakpoint Pause execution at an instruction or function
Watchpoint Pause when a memory address or register changes
Register CPU storage: rip, rsp, rbp, rax…
Single-step Execute one instruction, then stop
Backtrace / bt The call stack at the current point
System call The kernel entry: what strace records
Core dump A snapshot of a crashed process's memory
ptrace The syscall that lets one process control another
ASLR Randomising load addresses, so addresses differ per run

Kali commands

# --- is the toolchain there? ---
command -v gdb gdb-multiarch strace ltrace valgrind objdump readelf nm
gdb --version | head -1

# --- gdb batch mode (scriptable, no TTY needed) ---
gdb -q --batch \
    -ex 'break main' -ex 'run' -ex 'info registers rip rsp' \
    -ex 'disassemble main' -ex 'bt' \
    ./myprogram

# --- symbols: is the binary debuggable? ---
file ./myprogram
readelf -h ./myprogram | head -20
readelf -s ./myprogram | grep -i main
nm -C ./myprogram | grep -i main
objdump -d -M intel ./myprogram | head -40

# --- hardening check (essential before any exploitation) ---
checksec --file=./myprogram 2>/dev/null || \
  readelf -l ./myprogram | grep -E 'GNU_STACK|GNU_RELRO'
readelf -d ./myprogram | grep -E 'BIND_NOW|FLAGS'

# --- strace the tools you already use ---
strace -e trace=network -f nmap -sn 127.0.0.1 2>&1 | tail -20
strace -e trace=openat curl -s https://example.com 2>&1 | grep -E 'resolv|connect' | head

That last command is the moment it clicks — you can see curl resolving DNS and connecting,
syscall by syscall. This is how you will explain "how does a reverse shell work" with authority.

Field lab

Objective: debug a crash, trace a network operation, and audit your toolchain's hardening.

mkdir -p ~/aegis/labs/ms-05 && cd ~/aegis/labs/ms-05

# --- 1. is your debugging toolchain installed? ---
{
  for t in gdb gdb-multiarch strace ltrace valgrind objdump readelf nm checksec; do
    printf "%-16s %s\n" "$t" "$(command -v $t || echo 'MISSING -> sudo apt install $t')"
  done
} | tee 01-toolchain.txt

# --- 2. write a program that will crash, and debug it ---
cat > crashy.c <<'EOF'
#include <stdio.h>
#include <string.h>
int main(int argc, char **argv) {
    char buf[16];
    printf("give me input: ");
    fflush(stdout);
    strcpy(buf, argv[1]);        // no bounds check - the vulnerability
    printf("you said: %s\n", buf);
    return 0;
}
EOF
gcc -g -O0 -fno-stack-protector -no-pie crashy.c -o crashy
file crashy
checksec --file=./crashy

# --- 3. crash it, then look at it ---
./crashy AAAAAAAAAAAAAAAA ; echo "exit: $?"
dmesg 2>/dev/null | tail -3

gdb -q --batch \
    -ex 'break main' -ex 'run AAAA' \
    -ex 'info registers rip rsp rbp' \
    -ex 'disassemble main' \
    -ex 'print $rsp' \
    -ex 'x/16xb $rbp-16' \
    -ex 'bt' \
    -ex 'continue' \
    ./crashy 2>&1 | tee 02-gdb-trace.txt

# --- 4. what syscalls does a tool make? ---
strace -e trace=network -f nmap -sn 127.0.0.1 2>&1 | tail -25 | tee 03-strace-nmap.txt
strace -e trace=network curl -s https://example.com 2>&1 | grep -E 'socket|connect|sendto' | head -15 \
  >> 03-strace-nmap.txt

# --- 5. what files does a tool read? ---
strace -e trace=openat nmap --version 2>&1 | grep -oE '"[^"]+"' | sort -u | head -30 \
  > 04-strace-files.txt
head -20 04-strace-files.txt

# --- 6. hardening audit of a real target binary ---
sudo apt install -y checksec >/dev/null 2>&1
cp /usr/bin/nmap /tmp/nmap-copy 2>/dev/null
checksec --file=/tmp/nmap-copy 2>&1 | head -20 | tee 05-hardening.txt
rm -f /tmp/nmap-copy

# --- 7. core dump behaviour on your own machine ---
ulimit -c
echo "core limit above (0 = disabled by default on most distros)"

Step 3 is the Tier 3 skill in miniature. rbp-16 is where your buffer lives; the bytes past
it are the saved frame pointer and return address. Everything in ex-03 and ex-04 builds on
exactly this picture.

Record: in your scratchpad, write down what checksec says about crashy versus about
/usr/bin/nmap. The difference is why one crashes and the other does not.

Self-test

  1. gdb, strace, ltrace — what does each one show you that the others cannot?
  2. What does x/16xb $rsp print, and what is x/i/s short for?
  3. Why is ulimit -c unlimited needed before a core dump can be written?
  4. Your program crashes at address 0x7fffffffe000. How do you tell whether that is a
    stack address or a code address, and why does it matter?
  5. Why is strace considered a relatively safe way to analyse an unknown binary?
