Isolation Mechanisms

Summary

Isolation is the OS's core security service: ensuring one entity cannot read, corrupt, or control
another. It comes in layers, and each layer can fail in its own way.

  • Address space isolation — separate virtual memory per process
  • Mode protection — kernel/user rings
  • Privilege separation — trusted monitor, untrusted userland
  • Sandboxing — restrict what a program may do
  • Objects and capabilities — make authority explicit and transferable

A single layer is not enough. The Linux design ("everything is a process") is what makes this
tractable: if a component must be trusted, it is a small, isolated process rather than a
privileged function in a big binary.

Address space isolation

Each process gets its own virtual address space. The MMU translates virtual to physical
addresses on demand, and the page table defines what is legal.

Process A  [0x400000..0x600000] -> its own pages
Process B  [0x400000..0x600000] -> completely different physical pages

The same virtual address in two processes means nothing to each other. This is why
ASLR and stack overflows coexist: if you know an address, you can write to it — ASLR only
raises the cost of guessing.

Mode protection

CPU privilege levels (rings) prevent user-mode code from executing privileged instructions or
touching kernel memory. A syscall is a controlled, audited transition.

Privilege separation

Split a trusted component into:

  • a monitor (privileged, small, simple, auditable)
  • userland (large, complex, untrusted)

The XML parser in Firefox runs in userland; the browser's GUI does too. Only the compositor and
kernel talk to the GPU. A parser RCE becomes a userland compromise rather than a system one.

This is the central theme of 6.858: small trusted computing base.

Sandboxing

Restrictions applied to a running program:

Mechanism Restriction
chroot Filesystem root changed
seccomp Allowed syscall list
namespaces Isolated pid/mnt/net/uts/ipc/user views
cgroups Resource limits
AppArmor / SELinux Mandatory access control paths
containers namespaces + cgroups + overlayfs

Containers are not a security boundary against a kernel bug. They share the host kernel, so a
kernel vulnerability is a container escape. This is why VMs (enclave/KVM) are a stronger boundary.

Objects and capabilities

In Unix, authority is implied by UID: if you're root, you can do anything to any file you can
reach. Capabilities make authority explicit and unforgeable — a bearer token naming exactly
what may be done to which object.

getcap /usr/bin/ping        # cap_net_raw=ep  -> raw sockets without being root
setcap cap_net_bind_service=+ep ./myserver     # bind port 80 as a normal user

Terminology

Term Meaning
Address space A process's private view of memory
MMU Hardware that translates addresses
Page table The mapping that defines a process's valid memory
Privilege separation Trusted monitor + untrusted userland
Trusted computing base Everything that must be correct for security
chroot Change the apparent filesystem root
seccomp Syscall allowlist
Namespace Isolated view of a kernel resource
cgroup Resource control group
Capability An unforgeable token of specific authority
Container escape Breaking out via shared-kernel weakness

Kali commands

# address space of a process
cat /proc/self/maps | head -10
cat /proc/$$/maps | wc -l
pmap -x $$ | head

# namespaces of this shell
ls -l /proc/self/ns/
readlink /proc/self/ns/mnt /proc/self/ns/pid

# capabilities
getcap -r /usr/bin 2>/dev/null | head -10
setcap cap_net_raw+ep /tmp/captest 2>/dev/null && getcap /tmp/captest

# chroot demonstration (harmless)
mkdir -p /tmp/jail/bin /tmp/jail/etc && cp /bin/bash /tmp/jail/bin/ 2>/dev/null
chroot /tmp/jail /bin/bash -c 'ls /' 2>&1 | head -3
rm -rf /tmp/jail

# containers
docker ps 2>/dev/null | head -3
ls -la /var/run/docker.sock 2>/dev/null && echo "docker.sock = root-equivalent"

Field lab

Objective: prove on your own machine that address spaces are separate and that capabilities
grant authority without root.

mkdir -p ~/aegis/labs/os-05 && cd ~/aegis/labs/os-05

# --- 1. two processes, same virtual address, different reality ---
python3 - <<'PY' | tee 01-addrspace.txt
import subprocess, sys
# write a known value to a fixed virtual address in a child
child = r'''
import ctypes
buf = ctypes.create_string_buffer(b"AEGIS-MARKER")
print(hex(ctypes.addressof(buf)), flush=True)
input()
'''
p = subprocess.Popen([sys.executable, "-c", child], stdin=subprocess.PIPE,
                     stdout=subprocess.PIPE, text=True)
addr = p.stdout.readline().strip()
print("child buffer at:", addr)
pid = p.pid
print(f"--- /proc/{pid}/maps entries containing that address ---")
for line in open(f"/proc/{pid}/maps"):
    lo, hi = line.split()[0].split("-")
    if int(lo, 16) <= int(addr, 16) < int(hi, 16):
        print("  ", line.strip())
print("--- same range in MY maps (should be different physical backing) ---")
for line in open("/proc/self/maps"):
    lo, hi = line.split()[0].split("-")
    if int(lo, 16) <= int(addr, 16) < int(hi, 16):
        print("  ", line.strip())
p.stdin.write("\n"); p.stdin.flush()
PY

# --- 2. namespaces are per-process ---
{
  echo "=== my namespaces ==="
  ls -l /proc/self/ns/
  echo
  echo "=== PID 1's namespaces (the init process, a different world) ==="
  ls -l /proc/1/ns/
} | tee 02-namespaces.txt
echo "Read: PID 1 has its own pid namespace. Containers work by giving you a new PID 1."

# --- 3. capability = authority without root ---
{
  echo "=== ping without being root ==="
  getcap /usr/bin/ping
  ls -l /usr/bin/ping
  echo
  echo "=== the same privilege in a normal shell (should fail) ==="
  python3 -c "
import socket
try:
    s = socket.socket(socket.AF_INET, socket.SOCK_RAW, socket.IPPROTO_ICMP); print('raw socket: OK')
except PermissionError as e: print('raw socket:', e)
"
} | tee 03-capabilities.txt

# --- 4. chroot: a jail that is not a security boundary ---
sudo mkdir -p /tmp/jail/bin /tmp/jail/lib/x86_64-linux-gnu /tmp/jail/lib64
sudo cp /bin/bash /tmp/jail/bin/
sudo cp /bin/ls /tmp/jail/bin/
for l in $(ldd /bin/bash | grep -oE '/lib[^ ]*'); do
  sudo cp "$l" /tmp/jail/lib/x86_64-linux-gnu/ 2>/dev/null
done
sudo cp /lib64/ld-linux-x86-64.so.2 /tmp/jail/lib64/ 2>/dev/null
sudo chroot /tmp/jail /bin/bash -c 'echo "inside chroot:"; ls /; echo "---"; id' 2>&1 | tee 04-chroot.txt
echo
echo "Note: id still shows your real UID. chroot is a namespace, NOT an auth boundary."
sudo rm -rf /tmp/jail

# --- 5. containers share the kernel ---
docker info 2>/dev/null | grep -E "Kernel|Server Version" | head -3
echo "Container security model: namespaced kernel + cgroups + overlayfs."
echo "A kernel bug = escape. A hypervisor bug = the same problem for VMs."

Step 4's punchline is the important one: chroot did not change your UID. Filesystem
isolation and privilege are different problems, and conflating them is a classic mistake.

Record: 01-addrspace.txt shows two processes with the same virtual address backed by
different pages. That is memory isolation in two lines of output.
