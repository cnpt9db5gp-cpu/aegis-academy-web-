Memory, the Stack and Calling Conventions

Summary

Once the CPU is fetching bytes, the next question is where those bytes live. Three regions
matter for security work: the stack (automatic, grows down, holds frames), the heap
(manual, attacker-influenced size), and code (read-only, ideally).

The calling convention is the contract that says which register holds what across a function
call. It is also the reason a stack overflow can hijack control flow.

Companion to lo-03 (registers and instructions) and cs161-03 (the bug
taxonomy). This note is the memory model.

The regions

  HIGH ADDRESS
  +-------------------------+
  |  stack       | grows DOWN (toward lower addresses)
  +-------------------------+
  |  heap        | grows UP (toward higher addresses)
  +-------------------------+
  |  BSS        | uninitialised globals
  +-------------------------+
  |  DATA       | initialised globals
  +-------------------------+
  |  TEXT/RODATA| code and constants
  +-------------------------+
  LOW ADDRESS
Region Managed by Lifetime Security relevance
stack the CPU, automatically per frame overflow target; canaries
heap the program, manually until freed UAF, double free, heap overflow
bss loader program zero-initialised globals; format strings
data loader program initialised globals; GOT is here
text loader, should be RO program ROP gadgets live here

The stack frame

Every call pushes a frame containing what the function needs to work and
what the caller needs afterwards:

  HIGHER ADDRESS (older frames)
  +--------------------------+
  | caller's saved rbp       |  <- return address is BELOW this
  | return address           |  <- the value on the stack at [rsp]
  | saved rbp                |
  | locals / spill slots     |
  | arguments (caller area)  |
  +--------------------------+
  LOWER ADDRESS (rsp, grows down)

  frame pointer rbp  -> fixed reference to this frame
  stack pointer  rsp -> top of stack; the thing that MOVES

void f(int a, int b) {
    char buf[16];     /* locals      */
    int  x = a + b;   /* spill slot  */
}

On entry to f, the stack holds [... return address ... saved rbp ... a ... b ...] and rsp points at the bottom. push rbp; mov rbp, rsp establishes
rbp as a fixed anchor; locals go at negative offsets from rbp.

Why the anchor matters: with rbp fixed, locals have stable addresses
even though rsp moves. A function pointer, a saved register, or a buffer
written past its end all have predictable addresses relative to rbp.

The overflow

  ASCIIART, 64-bit, little endian, buffer of 8 bytes at rbp-8:

  normal:      [  rbp  ] [ret addr][b b b b b b b b]   <- rsp
                            ^
  smash it:    [  rbp  ] [AAAAAAAA][X X X X X X X X]
                            ^        ^ overwritten
  chain it:    [  rbp  ] [AAAAAAAA][ADDR][R O P   ]
                            ^        ^        ^
                          saved     return    next gadgets
                          rbp       address

  Everything between the buffer and the return address is what you must
  fill EXACTLY. That is what an offset calculation is.

The offset is distance from the start of your buffer to the saved return address. Everything in this note exists to make that number computable.

The System V AMD64 calling convention

int f(int a, int b, int c, int d, int e, int f_) {
    return a + b + c + d + e + f_;
}

  INTEGER / POINTER arguments:  rdi, rsi, rdx, rcx, r8,  r9
  then:                        pushed onto the stack, right to left
  RETURN value:                rax
  Callee-saved:                rbx, rbp, r12-r15  (must save & restore)
  Caller-saved:                rax, rcx, rdx, rsi, rdi, r8-r11
                               (may be clobbered by any call)
  Frame pointer:               rbp
  Stack alignment:             16 bytes at the call instruction
  Red zone:                    128 bytes below rsp, no signal handlers
  Variadic:                    al = number of vector registers used

Memorise the first two lines. rdi holds the first argument. That one
fact answers most "what does this function do" questions in a disassembly
listing, because the argument determines which function it is.

Caller vs callee, and why it matters

  CALLER-SAVED: you may clobber rax/rcx/rdx/rsi/rdi/r8-r11 freely.
                If you need a value to survive a call, save it yourself.

  CALLEE-SAVED: the callee must save and restore rbx/rbp/r12-r15.
                A well-written function pushes and pops these.

  IN PRACTICE: if you see a function that uses rbx or r12-r15 and NEVER
  pushes/pops them, it is either a leaf function or a compiler bug.
  In hand-written shellcode, YOU are both caller and callee, and
  getting this wrong corrupts the program you came back into.

Windows x64, briefly

// Windows x64 differs:
//   rcx, rdx, r8, r9   are the first four arguments (not rdi, rsi)
//   shadow space:      32 bytes reserved by the caller before any call
//   rax:               return value
//   callee-saved:      rbx, rbp, rdi, rsi, r12-r15
//   (note rdi/rsi flip sides)

If you are reading Windows shellcode or a Windows binary, the register
assignments are reversed from Linux. Getting this wrong is the single
most common cause of "my payload runs but does nothing".

Terminology

Term Meaning
Stack Automatic storage, grows toward lower addresses
Stack frame One function's region of the stack
rsp Stack pointer; moves constantly
rbp Frame pointer; fixed within a frame
Prologue / epilogue push rbp; mov rbp,rsp / mov rsp,rbp; pop rbp; ret
Calling convention The contract for argument/return passing
Caller-saved Registers a call may destroy
Callee-saved Registers a callee must preserve
Stack alignment 16-byte boundary at the call
Red zone 128 bytes below rsp usable without adjusting it
Stack pivot Redirecting rsp to attacker-chosen memory
Return address The value ret pops and jumps to
Frame pointer omission rbp used as a general register (-fomit-frame-pointer)

Kali commands

# --- 1. see a real stack frame ---
mkdir -p ~/aegis/labs/lo-02 && cd ~/aegis/labs/lo-02

cat > frame.c <<'EOF'
#include <stdio.h>
#include <string.h>

int add(int a, int b, int c, int d, int e, int f) {
    volatile char buf[16];
    memset((void *)buf, 0, sizeof buf);
    return a + b + c + d + e + f;      /* arguments beyond 4 are on the stack */
}

int caller(void) {
    int x = add(1, 2, 3, 4, 5, 6);     /* 21 */
    printf("%d\n", x);
    return x;
}

int main(void) { return caller(); }
EOF

gcc -g -O0 -fno-omit-frame-pointer frame.c -o frame
gcc -g -O0 -fomit-frame-pointer frame.c -o frame-noFP

{
  echo "=== WITH a frame pointer: rbp anchors everything ==="
  objdump -d frame | sed -n '/<add>:/,/^$/p' | sed 's/^/  /'
  echo
  echo "=== read it:"
  echo "    push rbp; mov rbp,rsp   -> rbp is now a fixed anchor"
  echo "    [rbp+16],[rbp+24]      -> the 5th and 6th arguments, on the stack"
  echo "    [rbp-1] .. [rbp-16]    -> the 16-byte buffer"
  echo "    leave / ret             -> restore rsp from rbp, pop, jump"
} 2>&1 | tee 01-frame.txt

{
  echo "=== WITHOUT a frame pointer: rbp is free, offsets are rsp-relative ==="
  objdump -d frame-noFP | sed -n '/<add>:/,/^$/p' | sed 's/^/  /'
  echo
  echo "  Same function, no anchor. Every local is rsp-relative and rsp moves"
  echo "  on every push/pop. This is the default on x86-64 and it is why"
  echo "  offset calculation is harder without a frame pointer."
} 2>&1 | tee 02-noFP.txt

# --- 2. the calling convention, proven by a C caller and an asm callee ---
cat > conv.S <<'EOF'
    .text
    .globl asm_sum6
# uint64_t asm_sum6(uint64_t a, b, c, d, e, f)
# System V: a=rdi b=rsi c=rdx d=rcx e=r8 f=r9, return in rax
asm_sum6:
    mov     rax, rdi          # a
    add     rax, rsi          # + b
    add     rax, rdx          # + c
    add     rax, rcx          # + d
    add     rax, r8           # + e
    add     rax, r9           # + f
    ret
EOF
cat > conv.c <<'EOF'
#include <stdio.h>
#include <stdint.h>
uint64_t asm_sum6(uint64_t a, uint64_t b, uint64_t c,
                  uint64_t d, uint64_t e, uint64_t f);
int main(void) {
    printf("  asm_sum6(1,2,3,4,5,6) = %llu  (expected 21)\n",
           (unsigned long long)asm_sum6(1,2,3,4,5,6));
    printf("  asm_sum6(10,20,30,40,50,60) = %llu  (expected 210)\n",
           (unsigned long long)asm_sum6(10,20,30,40,50,60));
    printf("  if this is wrong, the register order is different from what\n"
           "  you assumed - check which convention you are actually under.\n");
    return 0;
}
EOF
gcc -O0 -no-pie conv.S conv.c -o conv 2>&1 && ./conv | tee 03-convention.txt

# --- 4. the stack grows DOWN: proven ---
python3 - <<'PY' | tee 06-direction.txt
print("  On x86-64 the stack grows DOWN: toward LOWER addresses.")
print("  A push writes to a smaller address than the last push.")
print()
print("    after push 1:  rsp = 0x7ffe_ffff_f000  [ 1 ] <- here")
print("    after push 2:  rsp = 0x7ffe_ffff_fef8  [ 2 ] <- here, LOWER")
print()
print("  A buffer overflow therefore writes UPWARD, from the buffer toward")
print("  the frame's own saved return address. The two directions are why")
print("  a stack buffer is the natural target: the padding is contiguous")
print("  and the prize is a fixed, predictable distance away.")
print()
print("  Contrast: the heap grows UP (toward higher addresses). Heap")
print("  overflows walk forward into other allocations, which is why they")
print("  need a grooming step and stack overflows do not.")
PY
cat 06-direction.txt

# --- 5. the offset, actually computed ---
cat > offset.asm <<'EOF'
    .text
    .globl _start
_start:
    sub     rsp, 32           ; make room
    lea     rdi, [rsp]        ; rdi = buffer at rsp
    xor     rax, rax
    mov     rdx, 64           ; copy 64 bytes into a 32-byte buffer
    mov     rsi, rsp
    lea     rdi, [rsp]
    ; simple memcpy-ish loop
    mov     rcx, 64
.copy:
    mov     al, [rsi]
    mov     [rdi], al
    inc     rsi
    inc     rdi
    dec     rcx
    jnz     .copy
    ; now write past the buffer deliberately, to the return address
    mov     qword [rsp+32], 0x4141414141414141
    mov     rax, 60
    xor     rdi, rdi
    syscall
EOF
{
  echo "=== the layout we are deliberately breaking ==="
  echo "    rsp+0   .. rsp+31  buffer (32 bytes)"
  echo "    rsp+32           <-- the return address"
  echo "    so the offset is 32 bytes, and it is CONSTANT, not a guess"
  echo
  echo "=== how you find the offset when you cannot control the layout ==="
  echo "    1. write a cyclic pattern of A-Z a-z 0-9 (unique bytes)"
  echo "    2. let it crash"
  echo "    3. read the saved return address from the core / crash dump"
  echo "    4. find the cycle position that matches -> that is the offset"
  echo
  echo "    This is 'cyclic pattern + crash + read', and it is the single"
  echo "    most useful automation in stack exploitation."
} 2>&1 | tee 07-offset.txt

# --- 6. the regions, as reported by the loader ---
{
  echo "=== where this binary's memory regions are ==="
  readelf -lW ./frame | grep -E "LOAD|GNU_STACK" | sed 's/^/  /'
  echo
  echo "=== section-level view ==="
  readelf -SW ./frame | grep -E "\.text|\.rodata|\.data|\.bss|\.got" | sed 's/^/  /'
  echo
  echo "=== stack limits in this process ==="
  ulimit -s | awk '{print "  stack soft limit: " $1 " KB (" $1/1024 " MB)"}'
  ulimit -Hs | awk '{print "  stack hard limit: " $1 " KB"}'
  echo
  echo "=== the red zone: 128 bytes below rsp usable without touching rsp ==="
  cat > 07-red-zone.md <<'MD'
# The red zone

System V AMD64 reserves 128 bytes below `rsp` that a leaf function may use
without adjusting `rsp`. It exists so a leaf function can spill registers
without a prologue.

Consequence for exploitation: a `sub rsp, N` before a `call` is a large
NOP sled on x86-64, because everything in the red zone is writable memory
you reach by changing `rsp`. That is why "the stack has a red zone" matters
when you are writing a SROP frame or pivoting the stack.
MD
  echo "  (see 07-red-zone.md)"
} 2>&1 | tee 08-regions.txt
rm -f frame.c frame frame-noFP conv.S conv.c conv offset.asm

Step 2 is the deliverable: a C function calling a hand-written assembly function. If
asm_sum6(1,2,3,4,5,6) prints 21, your register assignments are right. If it prints
something else, your argument order is wrong — and that one line catches the mistake that
otherwise wastes an afternoon in a shellcode payload.

Step 3 shows rsp moving and rbp staying fixed across the prologue. Those two registers
behaving differently is the entire reason the frame pointer exists.
