Process and DLL Listing Plugins

Summary

Processes are the first thing you look at and the easiest thing to lie about. Volatility gives you
three views — the process list, the process tree, and the command lines — and then the two
plugins that find what should not be there: malfind and the module lists.

The framing: a process list is a claim, not a fact. The process
list is a doubly-linked list in the kernel, and anything with kernel
access can unlink itself from it. The command line is in user memory
and can be edited independently.

Companion to for-03 (the methodology) and vol-04 (injection).
This note is the process layer in detail.

The three process plugins

VOL="vol.py"
IMG="memory.raw"

# 1. pslist - the process list, walking the EPROCESS doubly-linked list
$VOL windows.pslist -f "$IMG"
#   columns: PID, PPID, ImageFileName, Offset, Threads, Handles,
#            SessionId, Wow64, CreateTime, ExitTime, File output

# 2. pstree - the same list, drawn as a tree
$VOL windows.pstree -f "$IMG"
#   ^ THIS IS THE ONE. A tree makes the parentage obvious, and the
#     parentage is what you ask questions about.

# 3. cmdline - every process's command line, with the full path
$VOL windows.cmdline -f "$IMG"
#   ^ "what was actually run". A PowerShell process with a base64
#     argument is the single most common thing you will find.

cat > 01-tree.md <<'MD'
# Reading a process tree

```text
  THE NORMAL SHAPES (Windows 10/11, PID 4 is System, PID 0 idle)

    System(4)
     +-- smss.exe(224)              <- session 0, first user-mode
     |    +-- csrss.exe(308)
     |    |    +-- wininit.exe(456) <- the USER-mode shell
     |    |    |    +-- explorer.exe(2100)
     |    |    |    |    +-- chrome.exe(3200)
     |    |    |    +-- userinit.exe(512)
     |    |    +-- services.exe(620)
     |    |         +-- svchost.exe(880)
     |    |         +-- wmiprvse.exe(4100)
     |    +-- winlogon.exe(388)
     +-- (System)                   <- session 0

  THE SHAPES THAT ARE WRONG

    explorer.exe
     +-- cmd.exe                    <- explorer spawning a shell
     |    +-- powershell.exe
         +-- notepad.exe

    svchost.exe (at a non-system path)
     +-- cmd.exe

    winword.exe
     +-- rundll32.exe               <- a macro or a DLL side-load

    explorer.exe
     +-- mshta.exe
         +-- powershell.exe

    System
     +-- explorer.exe               <- EXPLORER BELOW SYSTEM. This is
                                     wrong on every modern Windows and
                                     is the shape of a rootkit that
                                     failed to hide properly.

  WHAT TO LOOK AT, IN ORDER
    1. is the parent something that should NEVER spawn a child?
       (services.exe spawning cmd.exe, winlogon spawning a shell)
    2. is the executable at a path Windows does not use?
       (C:\Users\\...\AppData\Local\Temp\svchost.exe)
    3. is the name right but the PATH wrong?
    4. is there a process whose PPID does not exist? (an orphan is a
       sign the parent exited, which is normal, OR a sign of a fake)
    5. is anything running in session 0 that should not be?
       (a user process in session 0 means an interactive session
        created it - a service, a scheduled task, or an implant)
MD

# --- 2. the questions to ask the tree ---
cat > 02-questions.sh <<'EOF'
#!/usr/bin/env bash
VOL="${VOL:-vol.py}"; IMG="${1:?usage: ./02-questions.sh memory.raw}"
echo "=== 1. the tree ==="
$VOL windows.pstree -f "$IMG" 2>/dev/null | sed 's/^/  /'
echo
echo "=== 2. the paths (the names lie, the paths do not) ==="
$VOL windows.cmdline -f "$IMG" 2>/dev/null | sed 's/^/  /' | head -40
echo
echo "  LOOK AT: anything not in C:\\Windows\\, C:\\Program Files\\,"
echo "            or the user's AppData\\Roaming\\Microsoft\\Windows"
echo "            (which is where a legitimate app installs itself)."
echo "  Temp, Public, Downloads, and ProgramData are all findings."
echo
echo "=== 3. the counts, which is where rootkits show ==="
$VOL windows.pslist -f "$IMG" 2>/dev/null | grep -ci "explorer.exe" \
  | xargs echo "  explorer.exe instances:"
echo "  1 is normal for an interactive session. 2+ on a workstation"
echo "  is worth asking about (a remote session, or an extra shell)."
$VOL windows.pslist -f "$IMG" 2>/dev/null | grep -ci "winlogon.exe" \
  | xargs echo "  winlogon.exe instances:"
echo "  should be exactly 1 (or 2 with a fast-user-switching session)."
echo "  ZERO means no interactive session: a server, or a live"
echo "  capture of a machine nobody logged into."
echo
echo "=== 4. the ones that are almost never legitimate ==="
for p in mimikatz procdump rundll32 regsvr32 mshta wscript cscript \
         certutil bitsadmin nc ncat netcat plink; do
  n=$($VOL windows.pslist -f "$IMG" 2>/dev/null | grep -ci "$p")
  [ "$n" -gt 0 ] && echo "  $p x$n"
done
echo
echo "=== 5. the boot time, from windows.info ==="
$VOL windows.info -f "$IMG" 2>/dev/null | grep -iE "systemtime|kernel|physical" | sed 's/^/  /'
echo
echo "  ^ SystemTime is your reference for every other timestamp."
echo "    Record it and the offset from your own clock."
echo
echo "=== 6. the session mapping (who is at the keyboard) ==="
$VOL windows.getsids -f "$IMG" 2>/dev/null | sed 's/^/  /' | head -30
echo
echo "  ^ A process in session 0 that is NOT a service or a system"
echo "    binary is a finding: an implant that registered as a service,"
echo "    or a scheduled task that launched something interactive."
EOF
chmod +x 02-questions.sh

# --- 3. the modules ---
cat > 03-modules.md <<'MD'
# Module (DLL) listing

```bash
$VOL windows.dlllist -f "$IMG"
$VOL windows.dlllist -f "$IMG" --pid 2100        # one process
$VOL windows.dlllist.DllList --pid 2100 -f "$IMG"
$VOL windows.getsids -f "$IMG"                    # pid -> session
```

```text
  WHAT YOU ARE LOOKING FOR

  1. A DLL FROM A PATH THAT IS NOT WINDOWS.
       C:\Users\<user>\AppData\... in the module list of a SYSTEM
       process is the classic injection signature.

  2. A DLL WITH A NAME THAT DOES NOT MATCH ITS PATH.
       "explorer.dll" loaded from Temp. Name and path must agree.

  3. A KNOWN-INJECTION DLL NAME.
       There are public lists. The point is not the name; it is that
       the name is a string in the injected process's memory, and
       you should find it in the carved memory too.

  4. A SYSTEM PROCESS WITH MODULES IT SHOULD NOT HAVE.
       lsass.exe with a networking DLL. That is credential theft
       tooling (see for-05's imports list).

  5. THE ORDER. The injected module is usually loaded LAST, or has
       the most recent LoadTime. LoadTime is the field that tells you.

  6. NO MODULES AT ALL for a process that should have many.
       A hollowed process (see vol-04) has almost nothing.
```

```bash
# the module list is also a list of API availability
# a process with crypt32.dll can decrypt. with winhttp.dll can
# talk to a C2. with dbghelp.dll is doing anti-debug.
```

print("     DETECTION: windows.malfind output flagged 'unlinked'")

print("     A legitimate process is started suspended, its memory is")

cat > 05-shorthands.md <<'MD'
# Shorthand plugins that take the diff for you

psxview: walks FOUR different kernel lists, not one.

Any process it finds that pslist does not is a DKOM victim.

$VOL windows.pslist -f "$IMG" | awk '{print $2}' | sort > /tmp/pslist.pids
$VOL windows.psxview -f "$IMG" | awk '{print $2}' | sort > /tmp/psxview.pids
comm -13 /tmp/pslist.pids /tmp/psxview.pids

^ the answer, if there is one, is on this line

handles: every handle in the system, grouped by type

$VOL windows.handles -f "$IMG" --pid 620

filescan: files that were open OR resident at acquisition time

$VOL windows.filescan -f "$IMG"
$VOL windows.filescan.FileScan --pid 2100 -f "$IMG"

dumpfiles: carve a file out of memory by name

$VOL windows.dumpfiles -f "$IMG"
$VOL windows.dumpfiles --pid 2100 -f "$IMG" --dump-dir ./dumps

^ this is the handoff to static analysis. A DLL that only ever

existed in memory, carved out, is for-05's material.

the ADS-in-memory question (does the process have a mapped zone?)

$VOL windows.netscan -f "$IMG" --pid 2100


```text
  THE SIDE EFFECT OF filescan/dumpfiles: they produce files. Those
  files are in your working directory and they are MALWARE. Do not
  double-click them, do not open them in a preview pane, and do not
  leave them where a file manager will render a thumbnail. Write
  them to a directory with no autoindexing and work on them with
  the triage script in for-05.

MD
cat 05-shorthand.sh 2>/dev/null; mv 05-shorthand.sh 05-shorthands.md 2>/dev/null

Step 4 is the deliverable: the four ways a process list diverges from reality — DKOM, PEB
unlinking, hollowing, reflective loading — and for each, exactly which plugin misses it and
which finds it. Then the punchline: run pslist and psxview and diff the PID sets. That
diff is the finding, and it takes two minutes.

05-shorthands.md includes the warning that matters practically: dumpfiles produces files
that are malware, and writing them into a directory with a preview pane means the preview pane
renders them.
