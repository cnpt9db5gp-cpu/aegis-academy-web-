Denial of Service

Summary

CS161 closes the technical blocks with DoS, and the lecture's argument is that DoS is not a
separate vulnerability class — it is the exploitation technique applied to availability, and
it has a distinct defence structure because availability cannot be protected
cryptographically.

Companion to ccnad-01/ccnad-03 and mit858-12. Those teach the
protocol-level detail; this note is about threat modelling and defence.

Why DoS is different

confidentiality  -> protected by cryptography
integrity       -> protected by cryptography
availability    -> NOT protected by cryptography

There is no way to prove a message was delivered, or that a service was
available at a moment in time, from cryptography alone. DoS therefore depends
entirely on resource management, and its defences are economic rather
than technical.

The taxonomy

Vector Mechanism Amplification
Volumetric Fill bandwidth Huge (bots, reflection)
Protocol exhaustion One request consumes many resources Moderate
Application Expensive computation per request Depends
Algorithmic Input triggers worst-case behaviour Extreme, low bandwidth
Single-packet UDP fragmentation, state exhaustion Extreme

The interesting ones are the last two. A volumetric attack is expensive
for the attacker and easy to filter. An algorithmic attack costs one packet.

Algorithmic complexity attacks

  Hash table:   insert N keys, each hash() result forced to 0  -> O(N^2)
  Regex:        input matching a backtracking pattern          -> exponential
  Parsers:      deeply nested XML/JSON, huge base64, zip bombs -> memory/CPU
  Sorting:      comparison sorts with adversarial input       -> O(n log n) -> worse

Requirements: usually authenticated. That is why DoS testing belongs in
scope explicitly and almost never is by default.

Amplification

  attacker sends  a 60-byte UDP DNS query with a spoofed source
  resolver       replies with a 3 KB answer
  amplification  ~50x, from a bandwidth-light attacker

Classic amplifiers: DNS, NTP, memcached, chargen, CLDAP, and anything that
replies more than it receives. This is why BCP 38 ingress filtering is a
routing requirement rather than a nicety.

The defence-in-depth stack

  1. edge          - rate limit, geo/ASN filters, scrubbing
  2. network       - BCP 38, drop invalid sources, QoS for critical traffic
  3. transport     - SYN cookies, SYNPROXY, connection limits
  4. host          - resource limits (cgroups), watchdog, restart on fail
  5. application   - request cost limits, timeouts, complexity limits
  6. design        - queue, cache, shed load deliberately, degrade gracefully

Note that layers 1-3 filter and 4-6 budget. You need both: filtering is
finite, budgeting is what keeps you alive when it is exhausted.

Being a good citizen

  get authorisation in writing, naming the vector and the rate
  know the provider's acceptable use policy and your contact
  start slow; escalate only with the target's agreement
  do not test reflection against third-party infrastructure
  use Cloudflare or equivalent for YOUR site rather than being a test subject

Most providers consider unauthorised DoS testing a serious offence, and most
attackers are caught by their own infected hosts rather than by attribution.

Terminology

Term Meaning
Denial of service Making a resource unavailable
Volumetric Exhausting bandwidth
Amplification Small request, large reply
Reflection Spoofed-source reply to the victim
BCP 38 / ingress filtering Dropping spoofed sources
SYN cookies Encode state in the ISN, no table needed
SYNPROXY Proxy the handshake, validate before the server
Scrubbing Third-party DDoS mitigation
Load shedding Deliberately refusing work to stay alive
Zip bomb Small archive, enormous expansion
ReDoS Catastrophic regex backtracking

# Amplification reflection: your own box as a reflector

**Lab only, and only against yourself.** A reflection test sends a small
spoofed request to an open service and checks whether a large reply arrives
at your own address.

```bash
# DNS, against your own resolver only
dig +noall +answer ANY example.com @127.0.0.1

# NTP monlist, if chrony is running (rarely now)
#   the classic 556x amplifier, mostly fixed

# what would answer on this host?
sudo ss -ulnp | awk 'NR>1{print "  "$5, $7}'
```

## Why this matters for your own security

1. **You may be a reflector.** If an open UDP service on your network replies
   to spoofed requests, your network is being used to attack someone else,
   and your address takes the blame.
2. **You may be a victim.** Someone else may already be using you.

## The fix
- BCP 38 ingress filtering on every edge router
- no unnecessary UDP services
- rate limits on resolvers and any UDP responder

## The measurement
`sudo nstat -az | grep -i refrag` and your provider's abuse desk both
surface reflected traffic.
EOF

# --- a rate limiter you can actually run ---
cat > 04-ratelimit.md <<'EOF'
# Rate limiting, the cheapest availability control

Effective rate limiting is per *source* and per *resource*, with an algorithm
that is hard to game.

nginx: a leaky bucket per source IP

limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
location /api/ {
limit_req zone=api burst=20 nodelay;
proxy_pass http://backend;
}


The parameters that matter:
- **rate**: sustained requests per second per source
- **burst**: how many may arrive at once (absorbs legitimate spikes)
- **nodelay**: reject immediately rather than queueing (protects the backend)

## Why a naive limiter fails
- by IP: one attacker behind a NAT, or a botnet, exhausts everyone's budget
- global: a single heavy user starves everyone
- per account: trivially bypassed with many accounts

Layer them: per IP (cheap), per account (meaningful), global (backstop).
EOF
cat 04-ratelimit.md

# --- ReDoS: a real, one-line DoS against a regex ---
python3 - <<'PY' | tee 05-redos.txt
import re, time
# The classic catastrophic backtracking pattern: (a+)+ against a failing input
bad = re.compile(r"^(a+)+$")
good = re.compile(r"^a+$")
tests = ["aaaaaaaaaaaaaaaaaaaaaaaaX", "a"*28 + "X"]

for name, pat in (("vulnerable (a+)+", bad), ("fixed a+", good)):
    for t in tests:
        start = time.perf_counter()
        pat.match(t)
        dt = time.perf_counter() - start
        print(f"  {name:<18} len={len(t):<3} {dt*1000:9.2f} ms")
    print()

print("  A single request, no bandwidth, complete CPU exhaustion.")
print("  The fix is a linear pattern, or a timeout, or a non-backtracking engine.")
print("  Any regex from untrusted input is a DoS surface - this is ReDoS,")
print("  and it is why 'validate input, then regex' is not a complete answer.")
PY
cat 05-redos.txt

# --- the defensive stack, written out ---
cat > 06-defence.md <<'EOF'
# Defending against DoS: the full stack

## 1. Before you are attacked
- know your baseline: normal rps, normal bandwidth, normal concurrency
- alert on deviation from baseline, not on absolute thresholds
- run a load test so you know where your knee is

## 2. At the edge
- CDN / anycast so a volumetric attack is absorbed somewhere else
- provider scrubbing, pre-arranged, with a contact
- rate limiting per IP, per account, and global

## 3. In the network
- BCP 38 ingress filtering (stop amplification using you)
- QoS so critical traffic survives congestion
- SYN cookies and SYNPROXY

## 4. On the host
- cgroup limits so one process cannot exhaust the machine
- connection limits and timeouts
- fd limits (this is why "too many open files" is a DoS symptom)

## 5. In the application
- per-request cost limits and deadlines
- bounded complexity: no regex backtracking on user input
- caching so the database is not the bottleneck
- **load shedding**: deliberately reject work to stay alive

## 6. In the design
- queues with backpressure instead of unbounded work
- graceful degradation: serve cached content when the backend is down
- redundancy, so failure of one node is not failure of the service

## The order of preference under attack
  absorb (CDN) > reject (rate limit) > shed (drop work) > degrade (serve stale)
Catching traffic you cannot absorb is the worst option and the most
expensive.
EOF
cat 06-defence.md

Step 5 is the punchline: one HTTP request, a 29-character string, and complete CPU exhaustion.
No bandwidth required. That's why DoS lives in the application layer far more often than the
network layer.
