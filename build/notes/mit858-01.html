Introduction and Threat Models

Summary

Lecture 1 of 6.858 sets the frame for everything else: what is being protected, from whom, and
why. The central move is separating assets, adversaries and security goals before
discussing a single mechanism.

Key ideas

  • A threat model answers: who are we defending against, what do they want, what can they do?
  • Assets are what matter; security effort is spent in proportion to their value
  • Adversaries differ in capability enormously — an end user, a malicious process, a
    compromised kernel, the vendor, a network attacker
  • Security goals: confidentiality, integrity, availability, plus correctness and
    accountability
  • Attacker-controlled input is the root of most vulnerabilities: untrusted data reaching a
    trusted computation
  • The lecture's running example: a web server that crashes on malformed input is a vulnerability
    even if you do not yet know how to exploit it

The frame: assets, adversaries, goals

Adversary Capability Realistic goal
Remote user Send crafted requests Code execution on the server
Malicious app Run code as the user Read other users' files, escalate
Compromised process Same privileges as the victim Escalate to more privilege
Network attacker Read/modify traffic MitM, inject, drop
Kernel/VM escape Full hypervisor control Escape to host
Insider Legitimate access Exfiltrate data, or sabotage

The same bug has very different risk depending on which row you are in. Severity is a function
of the threat model, not of the CWE number.

Untrusted input and trusted computation

  untrusted                          trusted
  --------                           -------
  HTTP request  ──►  server code  ──►  kernel / memory
                      ▲
                      └── this boundary is where bugs live

Buffer overflows, SQL injection, XSS and deserialisation are all the same shape: attacker data
reaching a computation that trusts it. Defences are mostly about narrowing that trust.

Why a crash is a finding

A server that segfaults on a malformed request has, at minimum:
- lost availability (and possibly a crash loop)
- demonstrated that input reaches an unsafe operation

You do not need code execution to have a vulnerability. That framing matters in a report:
"remote crash, unauthenticated, on the public interface" is already a serious finding.

Terminology

Term Meaning
Threat model Assets, adversaries, and security goals
Asset What you are protecting
Attack surface Where untrusted input can enter
Adversary Who you are defending against, and with what capability
Trust boundary Where privilege or assumption changes
Principal The identity on whose behalf something acts
Authentication Proving who you are
Authorisation Deciding what you may do
Vulnerability A flaw that can be triggered by some adversary
Exploit Code that reliably triggers it

# 1. What is this host for?
# 2. What data on it matters most?

# --- turn the paper model into observations ---
# what is the attack surface?
ss -tulpn | head -15
nmap -sV -p- 127.0.0.1 2>/dev/null | grep open | head

# --- what is running with privilege? ---
ps aux --sort=-%mem | head -8
cat /proc/1/status | grep -E "Uid|CapEff"

# --- what data is on this host that would matter? ---
ls -la /home/ 2>/dev/null
find / -maxdepth 2 -name "*.db" -o -maxdepth 2 -name "*.env" 2>/dev/null | head

# --- what does the service believe about its callers? ---
# a request header is untrusted input; see what the server echoes back
curl -s -H "X-Test: $(python3 -c 'print("A"*500)')" http://127.0.0.1:8080/ 2>/dev/null | head -5

Field lab

Objective: write a real threat model for a system you own, then test one assumption in it.

mkdir -p ~/aegis/labs/mit858-01 && cd ~/aegis/labs/mit858-01

cat > threat-model.md <<'EOF'
# Threat Model: <system name>

## 1. Assets
| Asset | Value if lost | Where it lives |
|---|---|---|
| account credentials | critical | /etc/shadow, browser profile |
| SSH private keys | critical | ~/.ssh/ |
| this repo (notes + progress) | high | ~/Projects/ |
| lab VMs | medium | ~/VirtualBox VMs/ |

## 2. Adversaries
| Who | Capability | Reachable? |
|---|---|---|
| someone on my LAN | can send traffic to my listeners | yes |
| a malicious web page I visit | can reach my loopback listeners | yes - see notes |
| a malicious package I install | arbitrary code as my user | yes |
| physical access | none assumed | no |

## 3. Security goals
- confidentiality: my keys, my notes
- integrity: my progress file and git history
- availability: nothing critical runs on this host

## 4. Trust boundaries
1. network boundary of my Wi-Fi
2. process boundary (each program)
3. user/root boundary (sudo)

## 5. Assumptions I am relying on
- [ ] everything on my loopback is mine
- [ ] nothing I run is listening on 0.0.0.0
- [ ] my SSH key has no passphrase but the machine is physical-only
- [ ] the git remote is private and my key is only on this box

## 6. Attack surface
- listening sockets:
- web pages I open (they can reach 127.0.0.1!)
- third-party packages I install

## 7. Mitigations already in place
- ...
EOF

{
  echo "=== OBSERVE: what is actually true? ==="
  echo
  echo "--- assumption: nothing listening on 0.0.0.0 ---"
  ss -tulpn | awk '$5 ~ /0\.0\.0\.0|\*/ {print "  VIOLATION: " $1, $5, $7}'
  ss -tulpn | awk '$5 ~ /0\.0\.0\.0|\*/' | wc -l | xargs echo "  violations:"
  echo
  echo "--- assumption: my key material is where I think ---"
  ls -la ~/.ssh/ 2>/dev/null | sed 's/^/  /'
  echo
  echo "--- assumption: my repo is private ---"
  git -C ~/Projects/aegis-academy remote -v | sed 's/^/  /'
  echo
  echo "--- attack surface: processes with unusual privileges ---"
  ps -eo user,pid,comm --sort=user | awk 'NR==1 || $1=="root"' | head -8
  echo
  echo "--- data that would matter if this host were compromised ---"
  ls -la ~/ 2>/dev/null | grep -E "\.ssh|\.gnupg|Projects|Dropbox" | sed 's/^/  /'
} 2>&1 | tee 01-observations.txt

# --- 6. test one assumption: the browser-to-loopback boundary ---
cat > 02-browser-attack-surface.md <<'EOF'
# The boundary people forget

A web page you visit runs code in your browser, and the browser can make
requests to **localhost** on your behalf. Modern browsers block some of this
with Private Network Access, but the general problem remains: your local
services are reachable from hostile JavaScript.

Practical consequences:
- a dev server on :3000 is reachable by any page you load
- anything listening on a wildcard interface is reachable from the LAN
- browser extensions add their own privilege to the mix

This is the concrete reason `docs/RULES-OF-ENGAGEMENT.md` says labs bind to
127.0.0.1 or a host-only adapter, never to 0.0.0.0.
EOF
cat 02-browser-attack-surface.md

# --- 7. the crash-as-finding demonstration ---
cat > 03-crash-is-a-finding.md <<'EOF'
# A crash is already a vulnerability

You do not need code execution to report a serious issue:

- "Unauthenticated remote crash of the public service by a malformed request"
  is a denial-of-service finding on its own.
- "Input reaches an unsafe operation" is evidence, even without an exploit.

The mistake is waiting until you have RCE before you write anything down. In a
report, a reproducible crash with a request that triggers it is valuable,
specific, and actionable.

MIT 6.858 Lab 1 is exactly this: find a crash, then take it further.
EOF
cat 03-crash-is-a-finding.md
