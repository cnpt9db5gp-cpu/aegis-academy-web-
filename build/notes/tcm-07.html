Report Writing

Summary

The report is the deliverable. Everything before it is preparation; everything after it is
remediation. A technically successful engagement with an unusable report has failed the client.

The lecture's argument is that most of the value of a pentest arrives in the writing: the
technical part is a prerequisite for a report that changes decisions, and nothing else.

This is the closing note of Tier 3, and it closes the loop with tcm-01:
the ROE said what you would do; the report proves you did exactly that
and nothing more.

What a reader actually needs

  WHO READS IT
  - an executive:      "what is the risk, what do we do, what does it cost?"
  - a manager:         "who owns this, when will it be fixed, do we accept risk?"
  - an engineer:       "exactly what, exactly where, exactly how do I fix it?"

  AND THEY DISAGREE ABOUT DETAIL.

  So: layer it. Executive summary first (one page, no jargon).
  Technical detail in the body. Evidence in the appendix.
  A reader who stops after page one must still be able to act.

Structure that works

  1. Executive summary      one page, risk-ranked, with the recommendation
  2. Scope and methodology  what was tested, how, what was excluded, limits
  3. Findings               risk-ranked, one per finding, consistent template
  4. Remediation            specific, owned, dated
  5. Appendices             evidence, tool output, command transcripts

The finding template

  ## F-01  Unauthenticated remote code execution on WEB-01          [CRITICAL]

  **Risk**        An unauthenticated attacker on the internal network can
                  execute arbitrary code as root on the customer-facing web
                  server, and read the production customer database.

  **Evidence**
    Target      192.168.56.20:8080
    Method      Unauthenticated HTTP GET to /admin/records (verbatim in
                Appendix A)
    Observed    HTTP 200, 14,238 bytes, no credentials sent
    Access      root (uid=0), confirmed with `id`
    Impact      Read access to 41,882 customer records (structure only;
                no records exfiltrated)

  **Steps to reproduce**
    1. From the internal range, `curl http://192.168.56.20:8080/admin/records`
    2. No authentication is requested or required
    3. The response contains customer records

  **Root cause**
    The administrative endpoint was added during a migration and has no
    authentication, and the host's firewall rule permitting 8080 from the
    internal range was never scoped to the app servers only.

  **Remediation**
    1. Remove the endpoint or place it behind authentication  [Owner: Web
       Platform, Priority: Immediate]
    2. Restrict 8080 at the firewall to the app server range only
    3. Add a CI check that fails on unauthenticated admin routes

  **Re-test**   included at +30 days

Severity: likelihood × impact, and being honest about both

Low impact Medium High
Likely Medium High Critical
Possible Low Medium High
Unlikely Informational Low Medium 
  TWO THINGS GO WRONG, IN OPPOSITE DIRECTIONS:

  1. INFLATED:  "Critical" for something with no reachable path.
     - Fix: ask "what must be true for this to be exploited?" and answer
       it in the finding. If the answer is "the attacker already has
       domain admin", downgrade it.

  2. DEFLATED:  "Informational" for something the client will not fix.
     - Fix: severity is about the business, not about you being able to
       demonstrate it. "The backup files contain the full user database
       and are world-readable" is Critical even if you did not read them.

The corrective for both is the same sentence: state the prerequisite
for exploitation explicitly, in the finding, and let the reader judge.

Writing for remediation, not for proof

  BAD  : "The server is running an outdated version of OpenSSH with a
          buffer overflow vulnerability."
  GOOD : "Upgrade OpenSSH to 9.6 or later on WEB-01 (current: 7.4).
          The package is in the standard repository; no custom build is
          required. Estimated effort: 15 minutes, no restart of the app
          if the SSH daemon is restarted in place."

  BAD  : "Improve the security of the passwords."
  GOOD : "Enforce a 14-character minimum via the domain password policy
          (currently 8), and require MFA for all accounts in the
          Privileged Access Groups. Estimated effort: policy change,
          staged rollout over two weeks."

The second version is actionable by someone who was not on the engagement.
That is the entire test.

Evidence handling

  - evidence must be reproducible by a third party from what you wrote
  - redact credentials, tokens, personal data - ALWAYS
  - screenshots: blur, do not crop (cropping hides context)
  - attach raw tool output as appendices, not screenshots of it
  - hash your evidence archive so it cannot be altered later
  - store encrypted, delete on the contractual date
  - a finding whose evidence contains live credentials is a breach of
    your own engagement terms

The two reviews before you send it

  REVIEW 1 - TECHNICAL ACCURACY (a peer, not the author)
    - does every finding reproduce from the stated steps alone?
    - is every version, port and path correct?
    - is any severity indefensible?
    - is anything claimed that was not actually observed?

  REVIEW 2 - USABILITY (someone who was not on the engagement)
    - read only the executive summary. Can they name the top three risks
      and the first action?
    - read only finding F-04. Can the owner fix it without asking you?
    - is every finding owned by a named team with a date?

Review 2 is the one nobody does and the one that determines whether the
report gets acted on.

Terminology

Term Meaning
Executive summary One page, no jargon, risk-ranked
Finding A demonstrated vulnerability with evidence
Risk rating Likelihood × impact
CVSS A scoring system; useful for consistency, not for priority
Remediation The specific fix
Mitigation A temporary reduction in impact, not a fix
Retest Verification that remediation worked
Evidence Reproducible proof
Appendix Raw output, kept out of the reader's path
Root cause Why the vulnerability exists
Risk acceptance A business decision to live with a risk
Executive risk language Impact on the business, not on the CVE

# --- 2. the honest severity calculator ---
cat > severity.py <<'PY'
#!/usr/bin/env python3
"""Severity = likelihood x impact, with the prerequisite written down.

The point of this script is not the number. It is the PROMISED column:
"this is only exploitable IF <prerequisite>". A finding without a stated
prerequisite is either inflated or deflated, and both destroy trust.
"""
import csv, sys

LIKELIHOOD = {"unlikely": 1, "possible": 2, "likely": 3}
IMPACT     = {"low": 1, "medium": 2, "high": 3}

MATRIX = {  # likelihood -> impact
    (1,1): ("informational", 0.0), (1,2): ("low", 2.0), (1,3): ("medium", 4.0),
    (2,1): ("low", 2.5),           (2,2): ("medium", 4.5), (2,3): ("high", 7.0),
    (3,1): ("medium", 5.0),        (3,2): ("high", 7.5),    (3,3): ("critical", 9.5),
}

rows = list(csv.DictReader(open("findings.csv")))
print(f"  {'ID':<5} {'SEVERITY':<14} {'PREREQUISITE (must be true to exploit)'}")
print("  " + "-"*78)
for r in rows:
    # likelihood is derived from the prerequisite's difficulty, decided by you
    prereq = r["prereq"]
    lik = "unlikely" if "domain admin" in prereq else \
          "possible" if prereq else "likely"
    imp = {"critical": "high", "high": "high", "medium": "medium",
           "low": "low", "informational": "low"}.get(r["severity"], "medium")
    sev, _ = MATRIX[(LIKELIHOOD[lik], IMPACT[imp])]
    # CVSS disagrees with the honest assessment? That is worth a sentence.
    flag = ""
    if r["cvss"] and float(r["cvss"]) >= 9 and sev in ("low", "informational"):
        flag = "  <-- CVSS and honest severity disagree; explain in the finding"
    print(f"  {r['id']:<5} {sev:<14} {prereq}{flag}")
print()
print("  When CVSS and the honest assessment disagree, the honest one wins,")
print("  and the finding explains why. CVSS measures technical severity;")
print("  the report measures business risk.")
PY
python3 severity.py | tee 01-severity.txt

# --- 3. evidence handling, as automation ---
cat > 02-evidence.sh <<'EOF'
#!/usr/bin/env bash
# Package evidence so it cannot be silently altered later.
set -euo pipefail
STAMP=$(date +%Y%m%d-%H%M%S)
OUT="evidence-${STAMP}"
mkdir -p "$OUT"

echo "  collecting"
cp -f findings.csv "$OUT"/ 2>/dev/null || true
cp -f 01-severity.txt "$OUT"/ 2>/dev/null || true
cp -f 0*-DIARY.txt "$OUT"/ 2>/dev/null || true
cp -f scan-*.txt "$OUT"/ 2>/dev/null || true

echo "  redacting (credentials, tokens, personal data) before packaging"
# A redaction pass is a process, not a one-liner. Grep for what must go.
grep -rniE "password[[:space:]]*[:=]|passwd=|secret=|token=|api[_-]?key=|BEGIN .*PRIVATE KEY" "$OUT" \
  && echo "  ^ REVIEW THESE before sending anything to the client" \
  || echo "  no obvious credentials found in the evidence package"

echo "  hashing"
(cd "$OUT" && sha256sum * | tee SHA256SUMS)
echo
echo "  the client can now verify the evidence has not been altered:"
echo "    sha256sum -c SHA256SUMS"
EOF
chmod +x 02-evidence.sh
./02-evidence.sh 2>&1 | tee 03-evidence.txt
rm -rf evidence-*

# --- 4. the executive summary, in its real form ---
cat > 04-executive-summary.md <<'EOF'
# Penetration Test — Executive Summary

**Engagement:** AEGIS-LAB-2026-001
**Client:** [organisation]
**Dates:** [start] – [end]
**Assessor:** [name]
**Overall risk:** **CRITICAL**

## What we did
We assessed [scope: N hosts, M web applications, the internal Active
Directory] from [external/internal] perspective, over [N] days, using
network scanning, service enumeration, authenticated and unauthenticated
testing, and post-exploitation to establish impact. No denial-of-service
testing was performed. No data was modified.

## What we found
| # | Finding | Severity | Business impact |
|---|---|---|---|
| F-01 | Unauthenticated remote code execution on the customer-facing web server | **Critical** | An attacker on the internal network can reach the production customer database |
| F-02 | Local privilege escalation on every Linux host | High | Any low-privilege account, including a compromised web account, becomes root |
| F-03 | SMB signing not enforced | Medium | A hostile host on the same network can impersonate any user |
| F-04 | Development server bound to a routable interface | Low | Information disclosure; increases the attack surface |

Full technical detail in section 3.

## The three things that matter
1. **One internet-facing weakness reaches your customer data.** F-01 is a
   single HTTP request. No authentication, no special tooling.
2. **Compromise of any one host means compromise of all of them.** There is
   no segmentation between the web tier and the database tier; this was
   demonstrated end to end.
3. **Nothing here required a sophisticated attacker.** Every finding used
   standard tooling and, in three cases, no tooling at all.

## What we recommend, in order
| Priority | Action | Owner | Effort |
|---|---|---|---|
| 1 | Remove or authenticate `/admin/records` on WEB-01 | Web Platform | Immediate |
| 2 | Segment the web tier from the data tier | Network Ops | 1 sprint |
| 3 | Remove NOPASSWD sudo on the deploy account | Linux Ops | Immediate |
| 4 | Enforce SMB signing domain-wide | Windows Ops | 1 sprint |

## Limitations
- No denial-of-service testing was performed or authorised
- UDP services were not scanned (not in scope)
- Physical and social engineering were out of scope
- Internal testing was limited to [N] hours on [date]
- Findings reflect the state of the systems on the dates above

## Confidentiality
This document contains information about vulnerabilities in
[organisation]'s systems. It is provided under the terms of the
engagement letter dated [date] and must not be distributed further.
EOF
echo "written: 04-executive-summary.md"

# Section 3 — Findings

> Every finding uses the same template. Consistency is what lets an
> engineer scan the document and act, and lets a manager compare items.

---

## F-01 · Unauthenticated remote code execution on WEB-01 · **CRITICAL**

**Asset**  192.168.56.20:8080 (customer-facing web server)

**Risk**
An attacker with access to the internal network can execute arbitrary
operating-system commands as root on the customer-facing web server, and
from there read the production customer database containing 41,882 records
(including names, email addresses, and partial payment data).

**Prerequisite for exploitation**
The attacker must be able to open a TCP connection to port 8080 from the
internal range. No credentials, no user interaction, no special tooling.

**Evidence**
```http
GET /admin/records HTTP/1.1
Host: 192.168.56.20:8080
Connection: close

HTTP/1.0 200 OK
Server: SimpleHTTP/0.6 Python/3.13.2
Content-Length: 14238

[REDACTED — structure shown; 1 sample row redacted; no data retained]

The request contained no Cookie and no Authorization header. The same
response was received from a fresh session with an empty cookie jar.

On the resulting session:

$ id
uid=0(root) gid=0(root) groups=0(root)
$ hostname
WEB-01
$ cat /etc/app/database.yml | head -3
database:
  host: 10.10.10.6          # <- the internal database
  user: app_ro

Impact demonstrated
Read access to the customer records endpoint was confirmed from the
database host. No records were retrieved beyond confirming the query
returned data; see the engagement diary at 11:16.

Root cause
The administrative endpoint was introduced during the 2024 migration and
never placed behind authentication. It is served by a development HTTP
server (python -m http.server) rather than the production application
server, which suggests it bypassed the normal routing and middleware.

Remediation
| # | Action | Owner | Effort |
|---|---|---|---|
| 1 | Remove the endpoint; it is not required by the application | Web Platform | Immediate |
| 2 | Migrate remaining endpoints from the dev server to the app server | Web Platform | 2 days |
| 3 | Restrict 8080 at the firewall to the app server range | Network Ops | Immediate |
| 4 | Add a CI check that fails when an admin route has no authentication | Web Platform | 1 sprint |

Re-test 30 days after remediation, included in this engagement.

F-02 · Local privilege escalation via NOPASSWD sudo · HIGH

(same template; abbreviated here for space — see findings.csv for the index)
EOF

Pre-send review

Review 1 — technical accuracy (a peer, not the author)

  • [ ] Every finding reproduces from its stated steps alone, on a clean system
  • [ ] Every version, port, path and hostname is correct and was observed
  • [ ] Every severity can be defended if challenged
  • [ ] Nothing is claimed that was not actually observed
  • [ ] The prerequisite is stated in every finding
  • [ ] No credentials, tokens or personal data appear anywhere in the document
  • [ ] The scope section matches the ROE exactly — including what was excluded
  • [ ] The engagement diary has no unexplained gaps

Review 2 — usability (someone who was not on the engagement)

  • [ ] Reading only the executive summary, can they name the top three risks?
  • [ ] Can they name the first action to take?
  • [ ] Reading only finding F-04, can its owner fix it without asking you?
  • [ ] Is every finding owned by a named team with a target date?
  • [ ] Are the remediations specific enough to estimate and schedule?
  • [ ] Is the report under [N] pages for the executive portion?

If both reviews pass, send it. If either fails, do not.

EOF
echo "written: 06-review.md"
```

Step 2 is the deliverable: severity.py forces every finding to state its prerequisite
explicitly, and flags the cases where CVSS disagrees with an honest assessment. That
disagreement is where most reports lose the reader's trust — and where the finding that
explains it earns it back.

Step 4 is the one-page executive summary that every finding in the tier has been
building toward. If someone reads only that page, they can still act.

Record: 01-severity.txt, 04-executive-summary.md and 06-review.md.
