Windows Privilege Escalation and GPO Abuse

Summary

Domain admin is rarely the goal — local admin on a useful host is. This note is the Windows
escalation catalogue: the misconfigurations that turn a user into an administrator, and the
Group Policy mechanism that turns one admin into domain admin without touching a single host.

GPO abuse is the part that surprises people: it is a domain-wide escalation executed
through an ordinary management tool, with no exploit and often no host access at all.

Companion to ex-01..ex-06 (the exploitation mechanics) and ad-03's
graph. This note is the Windows-specific escalation and the GPO abuse.

Local escalation: the catalogue

  SERVICE AND INSTALLER
    unquoted service path with a writable directory
    (C:\Program Files\My App\ - the space is the vulnerability)
    writable service binary
    service with a weak DACL on the binary or its directory
    DLL search order hijack on a service that loads from a writable path
    unquoted path + writable C:\ -> plant the exe

  FILE PERMISSIONS
    a user-writable directory on the PATH of a service
    a user-writable scheduled task file
    a user-writable log directory a service parses

  REGISTRY
    HKLM\...\Image File Execution Options\ debugger = your exe
      (requires SeDebugPrivilege or Debug programs privilege)
    AppInit_DLLs for an exe a user will run
    IFEO on an exe the user launches
    Unquoted service path written into the registry

  PRIVILEGES (check these first — many are one command away)
    SeDebugPrivilege   -> read/write any process, dump LSASS
    SeImpersonatePrivilege -> token impersonation
    SeAssignPrimaryTokenPrivilege -> same
    SeTcbPrivilege     -> act as part of the OS
    SeBackupPrivilege  -> read any file by bypassing ACLs
    SeRestorePrivilege -> write any file bypassing ACLs
    SeLoadDriverPrivilege -> load a kernel driver. Game over.
    These are assigned to a user or a GROUP. "Backup Admins" gets
    SeBackupPrivilege by definition.

  THE TRIVIAL ONE
    whoami /priv | findstr /i "SeDebug Privilege"
    If you have SeDebugPrivilege and SeImpersonate, you have SYSTEM.
    Nothing else in this list matters.

Token manipulation, the two that matter

  THE PRINCIPLE: your token is the union of your SIDs' privileges plus
  the group's, and token filtering is what removes the ones that would
  let you escalate (read-only domain controllers, etc.).

  THE TWO CLASSIC ESCALATIONS:

  1. SeDebugPrivilege + SeImpersonatePrivilege
     Open SYSTEM's token, duplicate it, impersonate it.
     SYSTEM on the machine. No exploit. Configuration.

  2. A privileged service token you can read
     (SYSTEM, or a service account with a token you can open)
     → duplicate that token → use it.

  AND THE VARIANT THAT WORKS ON DOMAIN CONTROLLERS:
  an account that is a member of Domain Admins but is in the
  "Account Operators", "Backup Operators", or "Print Operators" group
  is TOKEN-FILTERED on a DC: the DC's SID is removed from their token.
  So the "Domain Admin" who cannot administer the domain is a real
  thing, and its inverse (an account that CAN) is a real finding.

  MEANWHILE on MEMBER SERVERS there is no filtering. So:
    a filtered Domain Admin on a DC cannot escalate easily
    the SAME account on a member server is a straight local admin.
  Which is why "get a shell on a member server, not the DC" is
  correct AD tradecraft.

Group Policy: the domain-wide escalation

  HOW GPO WORKS:
    a GPO is a collection of registry settings and scripts.
    computers receive GPOs by LINK ORDER (not security group).
    the LAST policy in the link order wins for a conflicting setting.
    startup scripts run as SYSTEM.
    scheduled tasks in a GPO run as SYSTEM.

  WHY IT IS ESCALATION:
    an attacker who can CREATE OR EDIT a GPO linked to an OU that
    contains a domain controller, or to the Domain Controllers OU,
    gets SYSTEM on the domain controller, as a scheduled task,
    without ever executing anything on it by hand.

  THE ATTACK CHAIN (this is the whole technique):
    1. you have WRITE on a GPO, or CREATE on a GPO in a user-
       controlled OU
    2. edit it:
         - add a scheduled task that runs your payload as SYSTEM
         - or a startup script
         - or change a setting that causes code execution
    3. wait for the refresh interval (or gpupdate /force it)
    4. the payload runs as SYSTEM on every machine in that OU,
       including the DC if the OU contains one

  THE VARIANTS THAT REPLACE execve-style payloads:
    - the "Computer Configuration > Preferences > Windows Settings"
      task, which is a legitimate feature (used for software installs)
    - the updater service abuse (ad-06's local escalation, but written
      as a GPO so it applies everywhere at once)

  THE VARIANT THAT DEPLOYS A BACKDOOR:
    - the GPO defence-in-depth bypass: abuse Sysmon or the Windows
      firewall GPO to disable the client's EDR, then use a scheduled
      task to persist. This is not a memory-execution trick; it is
      "change the security policy and let the client's own tooling
      trust the change".

Finding GPO abuse in an assessment

  THE AUDIT (all LDAP, from ad-03):
    1. which OUs do I have CREATE or WRITE on?
       (the write path is the attack surface, not the OUs)
    2. which of those OUs contain a domain controller or a server?
    3. is the Domain Controllers OU writable by a non-admin?
       -> a Critical on its own
    4. which GPOs do I have WRITE on?
    5. do those GPOs link to anything containing a DC?

  THE DEFENDER'S VIEW:
    - alert on 5136 for GroupPolicy objects being modified
    - alert on 4742 for computer account changes (the "DC replacement" GPO abuse)
    - monitor who has "Create Group Policy Objects" in the
      delegation on OUs
    - restrict GPO edit rights with "Group Policy Creator Owners"
      being scoped, not domain-wide

Reporting GPO abuse

## F-xx · Standard user can create a Group Policy Object linked to the Domain Controllers OU

Risk
  An authenticated user in the "Helpdesk" group can create a Group Policy
  Object and link it to the Domain Controllers organizational unit. The
  policy's scheduled task runs as SYSTEM on every domain controller
  under normal GPO refresh. This is domain compromise with no exploit,
  no host access, and no privileged tooling.

Prerequisites
  Membership of Helpdesk. Nothing else. No user interaction.

Evidence
  (Destructive actions were NOT taken. This was established by reading
   the ACLs and the delegation model, not by creating a policy.)
  The Helpdesk group has "Create Group Policy Objects" on
  OU=Domain Controllers,DC=lab,DC=internal. The OU contains two domain
  controllers (DC01, DC02).

  We did not create a policy. The ROE does not permit GPO
  modification, and the ACL analysis is sufficient to demonstrate the
  finding.

Business impact
  Complete domain compromise by any Helpdesk user. The Helpdesk group
  exists so that non-administrators can help users with their
  accounts; it was never intended to include GPO creation rights.

Remediation
  1. Remove "Create Group Policy Objects" from the Helpdesk group;
     scope Group Policy Creator Owners to a dedicated group  [Domain Admins, Immediate]
  2. Audit every OU for delegated GPO creation rights          [Security, 1 sprint]
  3. Enable Advanced Group Policy auditing (event 5136 for GroupPolicy
     objects)                                            [Security, 1 sprint]
  4. Review the full GPO delegation model; the current one grants
     more than the helpdesk function requires       [IT Ops, 1 sprint]

Note
  No GPO was created or modified during this assessment.

Terminology

Term Meaning
Unquoted service path A path with a space, where Windows guesses the exe name
SeDebugPrivilege Open any process; combined with SeImpersonate, SYSTEM
SeImpersonatePrivilege Duplicate and use another token
SeBackupPrivilege Read/write any file by bypassing ACLs
SeLoadDriverPrivilege Load a kernel driver
Token filtering Removing the DC SID on member servers; on DCs, strips others
Account Operators A group that is token-filtered on member servers but not DCs
GPO Group Policy Object: registry settings + scripts applied by link order
Startup script A GPO script that runs as SYSTEM at boot
Scheduled task in a GPO The escalation primitive; runs as SYSTEM
GPO link order The last conflicting policy wins; order = priority
Delegate permission "Create GPOs" etc, on an OU or a GPO
Group Policy Creator Owners The group that can edit all GPOs by default
5136 Directory object changed; the GPO detection
4742 Computer account changed; the DC-replacement escalation

cat > 01-privs.md <<'MD'
# Privilege enumeration - the FIRST thing you do on a Windows host

```cmd
whoami /priv
```
Look for anything in the list below. If you have SeDebugPrivilege AND
SeImpersonatePrivilege, you have SYSTEM. Do not go further.

| Privilege | What it gets you | Needs another? |
|---|---|---|
| SeDebugPrivilege | Open any process; read/write its memory | SeImpersonate |
| SeImpersonatePrivilege | Duplicate and use a token | SeDebug (to open SYSTEM) |
| SeAssignPrimaryTokenPrivilege | Same as impersonate | SeImpersonate |
| SeTcbPrivilege | Act as part of the OS | - |
| SeBackupPrivilege | Read any file (bypasses ACLs) | - |
| SeRestorePrivilege | Write any file (bypasses ACLs) | SeBackup to read first |
| SeLoadDriverPrivilege | Load a signed kernel driver | - |
| SeTakeOwnershipPrivilege | Take ownership of anything | - |
| SeCreateTokenPrivilege | Create a token from scratch | usually a service |

```cmd
:: the two together, the whole escalation in two lines
whoami /priv | findstr /i "SeDebug SeImpersonate"
:: if both are present -> SYSTEM. See ntdsutil or the token impersonation
:: technique. Nothing else in this lecture matters.
```

```powershell
# PowerShell equivalent
whoami /priv | Select-String "SeDebug|SeImpersonate|SeBackup|SeTcb"
```

# --- 2. the local escalation checks, on a Windows lab host ---
cat > 02-local-esc.md <<'MD'
# Local escalation checks on a Windows host (run as your current user)

:: 1. unquoted service paths (a space in the path is the bug)
wmic service get name,pathname,startmode | findstr /i /v "C:\Windows\" | findstr /i " "
powershell -c "Get-WmiObject Win32_Service | ? {$.PathName -match ' ' -and $.PathName -notmatch '^\"'} | select Name,PathName"

:: 2. writable service binaries
accesschk.exe -uwcv * -s * * * * 2>nul | findstr /i "WARN"
icacls "C:\Program Files\MyApp\service.exe"

:: 3. the Installed Applications - a common writable-then-run path
powershell -c "Get-WmiObject Win32_Product | select Name,IdentifyingNumber"

:: 4. scheduled tasks
schtasks /query /fo LIST /v | findstr /i "TaskName Run As"

:: 5. DLL search order - what DLLs does this process load from where?
:: (Process Explorer: Image Path tab -> DLLs; anything writable is it)
handle.exe -p *.dll

:: 6. the registry - IFEO and AppInit_DLLs
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options" /s
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Windows" /v AppInit_DLLs
reg query "HKLM\SYSTEM\CurrentControlSet\Control\Session Manager" /v AppCertDlls

:: 7. token filtering - is this a domain controller?
:: a DC has the "Account Operators" group stripped; a member server
:: does not. Compare whoami /groups on both.
nltest /dsgetdc:%USERDOMAIN%


```powershell
# the sharpest version: everything at once, and it flags what's unusual
Get-WmiObject Win32_Service |
  Where-Object { $_.PathName -notmatch '^"' -and $_.PathName -match ' ' } |
  Select-Object Name, StartName, PathName

# the ones running as SYSTEM with a writable binary
Get-WmiObject Win32_Service |
  Where-Object { $_.StartName -eq 'LocalSystem' } |
  ForEach-Object {
    $p = ($_.PathName -replace '"','').Split(' ')[0]
    if (Test-Path $p) {
      $acl = Get-Acl $p
      if ($acl.Access | Where-Object {
            $_.IdentityReference -match 'BUILTIN\\\\Users|Authenticated Users' }) {
        "WRITABLE + SYSTEM: $($_.Name) -> $p"
      }
    }
  }

MD

--- 3. the GPO audit, from your Linux box ---

cat > 03-gpo-audit.sh <<'EOF'

!/usr/bin/env bash

GPO escalation audit. READ-ONLY LDAP against YOUR lab DC.

DC="${1:?usage: ./03-gpo-audit.sh 192.168.56.10}"
b=$(echo "$DC" | cut -d. -f1)
case "$b" in 192.168.56.|10.10.10.|127.) ;;
) echo "REFUSED: $DC outside the lab range." >&2; exit 3 ;; esac
NC=$(ldapsearch -x -H "ldap://$DC" -b "" -s base defaultNamingContext 2>/dev/null \
| grep -m1 "^defaultNamingContext:" | awk '{print $2}')
echo "[scope] $DC in range; anonymous, read-only"
echo "[naming context] ${NC:-unknown}"
echo
echo "=== 1. GROUP POLICY CREATOR OWNERS: who edits every GPO by default? ==="
ldapsearch -x -H "ldap://$DC" -b "${NC}" \
"(&(objectClass=group)(sAMAccountName=Group Policy Creator Owners))" \
member 2>/dev/null | grep "^member:" | sed 's/^/ /'
echo " ^ if a non-admin group is in here, every GPO is editable by it."
echo " This is the single most common GPO-abuse finding."
echo
echo "=== 2. DELEGATED rights on the Domain Controllers OU ==="
echo " (nTSACL is the byte array; decode it with the DSACLs tool on Windows"
echo " or with impacket. From Linux, read it and look at the DACL length.)"
DC_OU=$(ldapsearch -x -H "ldap://$DC" -b "${NC}" \
"(objectClass=organizationalUnit)" dn 2>/dev/null \
| grep -m1 "^dn:" | sed 's/^dn: //')
echo " first OU found: ${DC_OU:-none}"
echo
echo " To list which OUs contain DCs (the escalation targets):"
ldapsearch -x -H "ldap://$DC" -b "${NC}" \
"(objectCategory=computer)(userAccountControl:1.2.840.113556.1.4.803:=8192)" \
dn 2>/dev/null | grep "^dn:" | sed 's/^/ /'
echo " ^ userAccountControl bit 8192 = TRUSTED_FOR_DELEGATION (a DC)"
echo
echo "=== 3. GPOs linked to the whole domain ==="
ldapsearch -x -H "ldap://$DC" -b "${NC}" \
"(objectClass=GroupPolicyContainer)" cn gPCFileSysPath gPCUserSysPath 2>/dev/null \
| grep -E "^(cn|gPCFileSysPath):" | sed 's/^/ /' | head -30
echo
echo "=== 4. scheduled tasks inside GPOs (the escalation primitive) ==="
echo " (the gPCMachineExtensionNames attribute lists the extensions; the"
echo " scheduled-tasks extension GUID tells you a task is defined.)"
ldapsearch -x -H "ldap://$DC" -b "${NC}" \
"(objectClass=GroupPolicyContainer)" cn gPCMachineExtensionNames 2>/dev/null \
| grep -E "^(cn|gPCMachineExtensionNames):" | sed 's/^/ /' | head -20
echo
echo "=== 5. the thing that makes it exploitable: DELEGATION on the OU ==="
echo " Ask the DC for the OU's nTSACL and decode it:"
echo " nxc ldap -u user -p pass --bloodhound # (writes an edge)"
echo " or, on a Windows host with access:"
echo " dsacls \\\\OU=,DC=lab,DC=internal"
echo " Look for: 'Create Group Policy Objects' granted to a non-admin."
echo
echo "=== 6. the SYSPREP check (the loudest GPO abuse of all) ==="
echo " If the domain FQDN is present in the DNS suffix of this host and"
echo " DNS is not secure, an attacker can hijack the sysprep search and"
echo " get arbitrary code execution as SYSTEM on every host that boots."
echo " Check: ipconfig /all | findstr /i \"DNS suffix\""
echo " Defend: omit the domain FQDN from the DNS suffix (GPO: 'Configure DNS'"
echo " - not set to the primary domain's DNS domain name)."
EOF
chmod +x 03-gpo-audit.sh

--- 5. what the report says ---

cat > 05-report.md <<'EOF'

F-xx · Unquoted service path on 4 servers

Risk
Four servers run services whose binary path contains a space and is
not quoted. On each, any authenticated user can place an executable
at the truncation point and have it run as LocalSystem at next boot,
simply by restarting the service. This grants SYSTEM on those servers
without any exploit.

Prerequisites
An authenticated account on the target server, and permission to
restart a service (which most authenticated users have by default
through the "Change a service configuration" right, or via SCM).

Evidence
server1: C:\Program Files\Contoso Sync\agent.exe -> LocalSystem
(a user-writable directory 'C:\Program Files\Contoso Sync\' exists)
[three more hosts]
We did not restart the services or place a payload. The ACL analysis
and the unquoted path are sufficient and are documented above.

Remediation
1. Quote the service path and move it to a directory users cannot write
[Server Ops, Immediate]
2. Remove "Change a service configuration" (SeServiceLogonRight) from
the default Users group [Domain Admins, Immediate]
3. Audit all service paths for unquoted paths and writable
directories [Server Ops, 1 sprint]

F-xx · Domain Admins token-filtered on domain controllers

Risk
Four accounts are members of Domain Admins but are in the Account
Operators group. On member servers these accounts have unrestricted
local administrative rights including backup and restore. On domain
controllers, the same accounts cannot exercise most of the Account
Operators rights over the network. The result is that the
organisation's privileged access review, which is based on group
membership, overstates what an attacker with these accounts can do
against a domain controller and understates what they can do against
every member server.

This is a governance finding rather than a direct path to compromise.
It is included because it materially changes the blast radius of any
account compromise in this domain, and it is not visible without
understanding token filtering.

Remediation
1. Document which privileged accounts are filtered on DCs and which
are not [Security, 1 sprint]
2. Re-scope Account Operators and Backup Operators to the minimum
set of hosts [Domain Admins, 2 sprints]
3. Add a PAM/JIT process for the four accounts [IT Ops, 1 sprint]
EOF
cat 05-report.md
```

Step 4 is the non-obvious one: token filtering. An Account Operators member is filtered on a
domain controller and unrestricted on a member server — which means the same credential is worth
more against the wrong target. That's why "get a shell on a member server, not the DC" is
correct tradecraft, and it changes how you read any group membership report.

05-report.md demonstrates the discipline the whole note is about: both findings state
explicitly that nothing destructive was done, and the ACL analysis is presented as sufficient.
Creating a GPO or restarting a service to "prove" it would breach the ROE and risk an outage.
