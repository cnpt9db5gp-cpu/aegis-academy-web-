Detection Engineering with YARA and Sigma

Summary

Triage tells you about one file. Detection engineering tells you about
the next thousand. This note is the discipline of turning an
observation into a rule, a rule into a deployment, and a deployment
into a coverage map.

The framing: a detection that only fires on the sample you already
have is not a detection. It is a description. The difference is
measured by what it finds on data you did not write it against.

Companion to for-05 (where the indicators come from) and ad-08
(Windows event-based detection). This note is the file and log
side, and the coverage discipline that applies to both.

YARA: the shape of a good rule

  A YARA RULE IS FOUR THINGS:
    meta      who wrote it, when, what it detects, and a reference
    strings   the observable facts (not the conclusion)
    condition  the logic that says "these together mean this"

  THE DISCIPLINE:
    STRINGS are facts.     "Global\\xyz_Module" is a fact.
    META is provenance.    TLP:Amber, author, reference, date.
    CONDITION is judgement. This is where the rule lives or dies.

// A worked rule, from a triage finding
import "pe"
import "math"

rule AEGIS_Exercise_Credential_Dumper
{
    meta:
        description = "Detects the credential dumper discussed in AEGIS-2026-001"
        author      = "nwpcs"
        date        = "2026-10-14"
        reference   = "AEGIS lab, case AEGIS-2026-001"
        tlp         = "Amber"
        confidence  = "Medium"

    strings:
        // FACT 1: a mutex name recovered statically from the sample
        $mutex = "Global\\AegisExerciseMutex_7f3a" ascii wide nocase

        // FACT 2: the API combination that indicates credential access
        $api1 = "CredEnumerateW" ascii
        $api2 = "LsaRetrievePrivateData" ascii
        $api3 = "CryptUnprotectData" ascii   // DPAPI

        // FACT 3: a PDB string that leaked the build path
        $pdb = "\\Build\\CredHarvest\\release\\x64\\" ascii wide

        // FACT 4: a URL recovered from the configuration
        $c2  = "cdn.example.com" ascii wide

    condition:
        uint16(0) == 0x5A4D and           // it is a PE
        $mutex and
        1 of ($api*) and
        ($pdb or $c2)
}

The four ways a YARA rule fails

  1. TOO NARROW
     You wrote it against one sample. It fires on that sample and
     nothing else, ever. It is a description of one file.
     THE FIX: two or more independent strings, ANDed. A mutex alone
              is one family member; a mutex AND an API AND a PDB path
              is a family.

  2. TOO BROAD
     "Contains the string 'http'" matches everything. You will get
     a flood, the analyst will mute it, and the rule is dead while
     appearing enabled.
     THE FIX: require the specific combination. Require the string
              that only the malware uses, not the one everything uses.

  3. THE CONDITION IS A GUESS
     If you cannot explain why each string is in the rule, remove it.
     Every string should have a reason you can say out loud.
     THE QUESTION: "if an analyst asked why is this string here, what
                  would I say?" If the answer is "I saw it in the
                  sample", the answer is not good enough.

  4. NO TESTING AGAINST A CORPUS
     A rule that has only been tested against the sample it was
     written from has not been tested.
     THE FIX: run it against a corpus of GOOD files. If it fires on
              50 Windows binaries, it is too broad.

mkdir -p ~/aegis/labs/for-06 && cd ~/aegis/labs/for-06
mkdir -p rules corpus/{good,bad} output

cat > 01-rule.yar <<'YARA'
import "pe"

rule AEGIS_Exercise_Credential_Dumper
{
    meta:
        description = "Credential dumper from AEGIS-2026-001"
        author      = "nwpcs"
        date        = "2026-10-14"
        reference   = "AEGIS lab case AEGIS-2026-001"
        tlp         = "Amber"
        confidence  = "Medium"
        scope       = "One family. Will not generalise."

    strings:
        $mutex = "Global\\AegisExerciseMutex_7f3a" ascii wide nocase
        $api1  = "CredEnumerateW" ascii
        $api2  = "LsaRetrievePrivateData" ascii
        $pdb   = "\\Build\\CredHarvest\\release\\x64\\" ascii wide
        $c2    = "cdn.example.com" ascii wide

    condition:
        uint16(0) == 0x5A4D and
        $mutex and
        1 of ($api*) and
        ($pdb or $c2)
}
YARA
echo "written: 01-rule.yar"

# --- the corpus test, which is the part everybody skips ---
{
  echo "=== yara is installed, and the rule parses ==="
  yara --version | sed 's/^/  /'
  yara rules/ 01-rule.yar 2>&1 | head -5 | sed 's/^/  /' \
    || echo "  (no output = no match, which is correct on an empty corpus)"
  echo
  echo "=== BUILD A CORPUS, because a rule needs one ==="
  mkdir -p corpus/good corpus/bad
  # "good": files that must NOT match. Real binaries from this system.
  for f in /usr/bin/strings /usr/bin/xxd /usr/bin/file /usr/bin/tshark; do
    [ -f "$f" ] && cp "$f" corpus/good/ 2>/dev/null
  done
  ls corpus/good/ | sed 's/^/  good: /'
  echo "  ^ these are the files that MUST NOT match. A rule that"
  echo "    fires on any of these is too broad."
  echo
  echo "=== TEST: the false-positive rate, which is the number that matters ==="
  fp=0
  for f in corpus/good/*; do
    [ -f "$f" ] || continue
    if yara rules/ 01-rule.yar "$f" >/dev/null 2>&1; then
      echo "  FALSE POSITIVE: $(basename "$f")"
      fp=$((fp+1))
    fi
  done
  total=$(ls corpus/good/ 2>/dev/null | wc -l)
  echo "  false positives: $fp / $total good files"
  echo
  if [ "$fp" -gt 0 ]; then
    echo "  THE RULE IS TOO BROAD. An analyst will see this, and will"
    echo "  stop reading the alerts, and the rule is now worse than"
    echo "  nothing. Remove the offending string."
  else
    echo "  clean on this corpus. This is a MINIMUM bar, not a pass:"
    echo "  a real test uses thousands of good files, and a real test"
    echo "  includes VARIANTS of the malware you did not have."
  fi
} 2>&1 | tee 02-corpus-test.txt

Sigma: detection rules for logs, not files

  YARA is for FILES. Sigma is for LOGS.

  A sigma rule is YAML with a fixed shape, so it can be converted
  into a query for whatever SIEM you use. That portability is the
  whole reason it exists.

title: Domain Replication Request from a Non-DC Host
id: 8b1e6f2a-4c7d-4e91-9a3b-2f6d8e1c5b04
status: experimental
description: >
  Detects a directory replication request carrying the DCSync rights.
  A legitimate replication request comes from another domain controller.
  The same request from a workstation or a member server is either a
  backup application that has not been reviewed, or an attack.
references:
  - AEGIS case AEGIS-2026-001, finding F-xx
  - ad-08 in the AEGIS curriculum
author: nwpcs
date: 2026-10-14
tags:
  - attack.credential_access
  - attack.t1003.006
logsource:
  product: windows
  service: security
detection:
  selection_object:
    EventID: 4662
    ObjectType: domainDNS
  selection_rights:
    ObjectAccess:
      - 1131f6aa-9c07-11d1-f79f-00c04fc2dcd2
      - 1131f6ad-9c07-11d1-f79f-00c04fc2dcd2
      - 89e95b76-444d-4c62-991a-0facbeda640c
  filter_dc:
    SubjectDomainName|endswith: "DCs"
  condition: selection_object and selection_rights and not filter_dc
falsepositives:
  - A backup or monitoring application with correctly scoped rights
  - System Centre, or a product that replicates the directory
level: high

The maturity ladder

  LEVEL 0  NO DETECTION
    You learn about attacks from your users and from your engagement
    report. There is no detection capability.

  LEVEL 1  FILE-BASED
    YARA at the mail gateway and at the file server. Catches known
    families of known files.

  LEVEL 2  LOG-BASED
    Sigma-converted queries in the SIEM for the high-signal events
    (DCSync's 4662, 5136 for roast preparation, 4672 with SeDebug).

  LEVEL 3  BEHAVIOURAL
    Detections that describe a SEQUENCE: a new prefetch, followed by
    a write to a system directory, followed by an outbound connection
    to a new external address. This is where detection actually
    starts working, because it catches the unknown.

  LEVEL 4  HUNT-DRIVEN
    You run queries on a schedule for the anomalies rather than the
    signatures: new SPNs, new delegation flags, new local admins,
    new accounts with never-seen-before logon patterns.

  MOST ORGANISATIONS ARE AT LEVEL 1 AND BELIEVE THEY ARE AT LEVEL 3,
  because they have alerts. Having alerts is not the same as having
  coverage.

Coverage: the question that matters

  "ARE WE COVERED?" IS ANSWERED BY A TABLE, NOT A FEELING.

  for each technique in your framework (MITRE ATT&CK):
    - is there a detection?        (a rule exists)
    - is it deployed?              (the rule runs in production)
    - is it tested?                (it fired on a test, correctly)
    - is it trusted?               (analysts have not muted it)
    - what is the false-positive rate?
    - WHAT IS THE RESIDUAL RISK if it does not fire?

  THE LAST ROW IS THE ONE NOBODY FILLS IN, and it is the one that
  tells the client what they are actually exposed to. "We have no
  detection for Kerberoasting, and if it happens we will find out
  when someone escalates" is a finding.

  THE TABLE, AND IT IS THE DELIVERABLE OF ANY ASSESSMENT THAT INCLUDES
  A DETECTION SECTION:

  | technique | detection | deployed | tested | FP rate | residual risk |
  |---|---|---|---|---|---|
  | DCSync | 4662 + 3 GUIDs | yes | no | unknown | HIGH - not tested |
  | AS-REP roasting | none | - | - | - | HIGH - no detection exists |
  | Kerberoasting | none | - | - | - | HIGH - only detectable after |
  |   | | | | | credential use, not the roast |
  | LSASS dumping | 4688 + 7045 | yes | no | unknown | MEDIUM |
  | SMB relay | none | - | - | - | MEDIUM - config check only |
