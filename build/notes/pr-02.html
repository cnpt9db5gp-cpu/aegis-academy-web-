File Permissions, SUID and Writable Service Abuse

Summary

Unix permissions are the oldest and still the most exploited privilege boundary. This lecture
covers the misconfigurations that turn an unprivileged user into root: SUID binaries, writable
service files, world-writable directories in PATH, and unsafe interpreter invocations.

Key ideas

  • Mode bits: rwx for owner/group/others; special bits s (SUID/SGID), t (sticky)
  • SUID on a file means: run with the file owner's privileges. Any bug in a SUID binary is
    a privilege escalation path by definition
  • The directory matters, not just the file. A writable directory containing an executable
    lets you replace the executable
  • PATH hijacking: if any PATH directory is writable by your user, you control that command
  • Unsafe interpreter calls: system("sh -c 'input'") runs sh from PATH
  • Writable config files for privileged services

Terminology

Term Meaning
Mode bits The 9 permission bits plus special bits
SUID (4000) Run as the file's owner
SGID (2000) Run with the file's group; also directory inheritance
Sticky bit (1000) Only the owner can delete files in the directory
umask Bits removed when creating files
PATH hijack Placing a malicious binary earlier in PATH
Wildcard sudo sudo * or sudo /path/* — always a finding
Race window Time between a check and the action

Kali commands

# --- find every SUID/SGID on this machine ---
find / -perm -4000 -type f 2>/dev/null | tee /tmp/suid.txt
find / -perm -2000 -type f 2>/dev/null | head -20
find / -perm -6000 -type f 2>/dev/null          # both bits

# --- which of them are NOT part of the base system? ---
dpkg -S $(cat /tmp/suid.txt) 2>/dev/null | grep -v "^dpkg-query" | head
# an SUID binary with no owning package = dropped there by someone

# --- world-writable files, excluding virtual filesystems ---
find / -xdev -perm -o+w -type f 2>/dev/null | grep -vE '^/(proc|sys|dev|run|tmp)' | head -20

# --- world-writable DIRECTORIES are more dangerous ---
find / -xdev -perm -o+w -type d 2>/dev/null | grep -vE '^/(proc|sys|dev|run|tmp|var/tmp)' | head -20

# --- is any PATH directory writable by me? ---
IFS=: read -ra P <<< "$PATH"
for d in "${P[@]}"; do
  [ -d "$d" ] && [ -w "$d" ] && echo "  WRITABLE IN PATH: $d ($(stat -c %U "$d"))"
done

# --- the classic interpreter attack surface ---
grep -rn "system(\|popen(\|exec.*sh\|/bin/sh" /usr/local/bin /opt 2>/dev/null | head

# --- sudo rules, always ---
sudo -n -l 2>/dev/null || sudo -l

Field lab

Objective: demonstrate four real escalation classes locally and safely, then verify them.

mkdir -p ~/aegis/labs/pr-02 && cd ~/aegis/labs/pr-02
WORK=/tmp/privesc-lab
rm -rf $WORK && mkdir -p $WORK && cd $WORK

echo "=== CLASS 1: PATH HIJACKING (no privileges needed) ==="
mkdir -p evil
cat > evil/ls <<'EOF'
#!/bin/sh
echo "[HIJACK] this is not /bin/ls - you just ran a binary from a writable PATH dir"
exec /bin/ls "$@"
EOF
chmod +x evil/ls
echo "normal  : $(PATH=/usr/bin:/bin command -v ls)"
echo "hijacked: $(PATH=$PWD/evil:/usr/bin:/bin command -v ls)"
PATH=$PWD/evil:/usr/bin:/bin ls -d /tmp | sed 's/^/  /'

echo
echo "=== CLASS 2: SUID BINARY ABUSE ==="
# Copy a shell and make it setuid-root in a LAB-SAFE way using a user namespace.
# If userns is available, this is contained and reversible.
if command -v unshare >/dev/null; then
  unshare -r sh -c '
    id
    cp /bin/bash /tmp/privesc-lab/bash-suid
    chmod u+s /tmp/privesc-lab/bash-suid
    ls -l /tmp/privesc-lab/bash-suid
    echo "--- escalating inside the user namespace (contained to this shell) ---"
    /tmp/privesc-lab/bash-suid -c "id -u; whoami"
  ' 2>&1 | tee 01-suid.txt
  echo
  echo "Note: inside a user namespace you are 'root' for that namespace ONLY."
  echo "On a real target the same technique targets a genuinely SUID-root binary."
else
  echo "unshare not available - see the SUID list from pr-01 instead"
fi

echo
echo "=== CLASS 3: WRITABLE SERVICE / CRON FILE ==="
# Simulate the misconfiguration that root's cron job will read.
sudo mkdir -p /opt/aegis-backup 2>/dev/null
sudo cp /dev/null /opt/aegis-backup/status 2>/dev/null
sudo chmod 777 /opt/aegis-backup 2>/dev/null
ls -ld /opt/aegis-backup 2>/dev/null
echo "  A root cron job that runs /opt/aegis-backup/run.sh would be exploited by:"
cat > /opt/aegis-backup/run.sh 2>/dev/null <<'EOF'
#!/bin/sh
# the payload a world-writable service directory lets you install
id > /tmp/pwned-by-cron.txt
EOF
chmod +x /opt/aegis-backup/run.sh 2>/dev/null
echo "  -> wrote run.sh into a 777 directory. If root's cron runs it, you win."
sudo chmod 755 /opt/aegis-backup 2>/dev/null
sudo rm -rf /opt/aegis-backup 2>/dev/null

echo
echo "=== CLASS 4: PERMISSION AUDIT OF YOUR OWN MACHINE ==="
{
  echo "--- SUID binaries not owned by any package (planted?) ---"
  comm -23 <(sort /tmp/suid.txt) <(dpkg -S $(cat /tmp/suid.txt) 2>/dev/null | cut -d: -f1 | sort -u) | head
  echo
  echo "--- world-writable dirs outside /tmp ---"
  find / -xdev -perm -o+w -type d 2>/dev/null | grep -vE '^/(proc|sys|dev|run|tmp|var/tmp)' | head
  echo
  echo "--- world-writable files in /etc ---"
  find /etc -writable -type f 2>/dev/null | head
  echo
  echo "--- writable PATH directories ---"
  IFS=: read -ra P <<< "$PATH"
  for d in "${P[@]}"; do [ -d "$d" ] && [ -w "$d" ] && echo "  $d"; done
  echo
  echo "--- sudo rules ---"
  sudo -n -l 2>/dev/null | tail -8
} 2>&1 | tee 02-audit.txt

echo
echo "=== CLEANUP ==="
cd /tmp && rm -rf $WORK /tmp/pwned-by-cron.txt
echo "lab artefacts removed"

02-audit.txt is a genuine assessment of your own machine. An SUID binary with no owning
package, a world-writable directory outside /tmp, or a writable PATH entry are all real
findings you should be able to explain to a non-technical colleague.

Record: 02-audit.txt, and which of the four classes you found on your own box.
