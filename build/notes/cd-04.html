Network Forensics Challenges

Summary

Network challenges have the highest ground truth and the shortest path to an answer. A capture is
small, fast to load, and every question is answerable from specific fields.

The framing: a PCAP's questions are all "who, when, how much" —
and the only hard part is knowing which field holds each one.

Companion to for-07 (the methodology) and vol-03 (the memory-side
network analysis). This note is the discipline against real captures.

The protocol inventory

  PROTOCOL          WHERE THE ANSWER IS              PORT
  --------------------------------------------------------------------------
  DNS               the queries, in order; the cache
                    (a TXT query with a long payload)

  HTTP              the requests and responses, with
                    full URLs, headers and User-Agent

  TLS               the SNI (the hostname), the
                    certificate chain (subject, issuer, SAN,
                    validity, and the SELF-SIGNED one),
                    JA3 (the client fingerprint), ALPN

  SMB               the tree connect (which share), the
                    session setup (which account, NTLM hash,
                    signing negotiated), and the file names

  Kerberos          the AS-REQ (which user, which SPN),
                    the TGS-REQ (which service), the
                    encryption type, and the 4768-equivalent

  SMB2 NEGOTIATE    the dialects offered - and whether
                    signing is required is NEGOTIATED HERE

  ICMP              unusual payloads (a covert channel), or
                    a connectivity story

  FTP / TFTP        an EXFILTRATION CHANNEL, in the clear,
                    on a non-standard port

  DNS TUNNELLING    long, base64-ish subdomains, high
                    query volume, uniform lengths

  JA3S              the server's fingerprint; a JA3S that is
                    not a known stack is interesting

  EVERYTHING ELSE   a finding. Which ports are talking, and
                    why?

cat > 01-inventory.md <<'MD'
# The capture inventory

```bash
P="challenge.pcap"

# 0. THE CAPTURE ITSELF
capinfos "$P"
#   ^ number of packets, duration, average rate, and the ENCRYPTION
#     flag. If it says encrypted, TLS is in play. If it says no
#     packets, you have the wrong file.

# 1. THE CONVERSATIONS  (always first)
tshark -r "$P" -q -z conv,tcp
tshark -r "$P" -q -z conv,udp
#   ^ who, to whom, how much, how long. This is the shape of the
#     whole capture and it answers "what is going on here" before
#     any detail.

# 2. THE PROTOCOL HIERARCHY  (what's in it at all)
tshark -r "$P" -q -z io,phs
#   ^ bytes per protocol. A protocol you do not expect, or a
#     protocol carrying an unusual number of bytes, is the story.

# 3. THE PROTOCOL HIERARCHY TREE (which ports)
tshark -r "$P" -q -z io,phs -z endpoints,tcp
tshark -r "$P" -q -z endpoints,ip

# 4. THE EXPERT INFO  (tshark's own analysis)
tshark -r "$P" -q -z expert
#   ^ malformed packets, retransmissions, checksum errors,
#     and protocol anomalies. A capture with a lot of expert info
#     usually means something unusual is happening.

# 5. THE HIERARCHY AS A TREE, for finding the odd port
tshark -r "$P" -q -z tree,tcp
```

cat > 02-protocols.md <<'MD'
# Per-protocol questions and the filters that answer them

````bash
P="challenge.pcap"

# === DNS ===
# every query, in chronological order
tshark -r "$P" -Y "dns.flags.response==0" -T fields \
  -e frame.time -e ip.src -e dns.qry.name -e dns.qry.type \
  | sort
# the questions are: the first unfamiliar domain, the domain before
# it, the query volume per domain, any TXT, any very long name

# DNS TXT (exfiltration over DNS)
tshark -r "$P" -Y "dns.qry.type==16" -T fields \
  -e frame.time -e dns.qry.name
# a TXT query with base64 in the name is data leaving over DNS

# a long subdomain
tshark -r "$P" -Y "dns.qry.name" -T fields -e dns.qry.name \
  | awk '{print length($0), $0}' | sort -rn | head

# === HTTP ===
tshark -r "$P" -Y "http.request" -T fields \
  -e frame.time -e ip.src -e ip.dst -e http.host -e http.request.method \
  -e http.request.uri -e http.user_agent | sort
# the download, its URL, its time, and the User-Agent

# what came back
tshark -r "$P" -Y "http.response.code" -T fields \
  -e frame.time -e ip.src -e http.response.code -e http.content_type \
  -e http.content_length | sort
# 200 with application/x-dosexec from a new host is the delivery

# upload vs download (exfiltration)
tshark -r "$P" -Y "http.request.method==POST" -T fields \
  -e frame.time -e ip.dst -e http.content_length | sort

# === TLS ===
# the SNI: the hostname, even though the payload is encrypted
tshark -r "$P" -Y "tls.handshake.extensions_server_name" -T fields \
  -e frame.time -e ip.dst -e tls.handshake.extensions_server_name | sort | uniq -c

# the certificate (a self-signed one is a finding)
tshark -r "$P" -Y "tls.handshake.certificate" -T fields \
  -e x509sat.printableString -e x509ce.dNSName 2>/dev/null | head
tshark -r "$P" -Y "tls.handshake.type==11" -V | grep -A2 "Issuer"

# JA3: the client fingerprint. One destination, one JA3 = notable.
tshark -r "$P" -Y "tls.handshake.type==1" -T fields \
  -e ip.dst -e tls.handshake.ja3_full | sort | uniq -c | sort -rn

# === SMB ===
# the tree connect: which share
tshark -r "$P" -Y "smb2.cmd==3" -T fields \
  -e frame.time -e ip.src -e ip.dst -e smb2.share_name 2>/dev/null

# the session setup: which account, which hash, signing?
tshark -r "$P" -Y "smb2.cmd==1" -T fields \
  -e frame.time -e ip.src -e smb2.session_setup_echo 2>/dev/null
tshark -r "$P" -Y "smb2" -V | grep -iE "signing|NTLMSSP|negotiate" | head

# SMB signing is NEGOTIATED in SMB2 NEGOTIATE. That is where you check.
tshark -r "$P" -Y "smb2.cmd==0" -V | grep -iE "signing|dialect"

# the file operations: what was copied where
tshark -r "$P" -Y "smb2.cmd==8" -T fields \
  -e frame.time -e ip.src -e ip.dst -e smb2.filename 2>/dev/null

# === KERBEROS ===
# the AS-REQ: who is authenticating, to which service
tshark -r "$P" -Y "kerberos.msgType==10" -T fields \
  -e frame.time -e ip.src -e kerberos.CNameString -e kerberos.SNameString

# the TGS-REQ: a service ticket. High volume = enumeration (roasting)
tshark -r "$P" -Y "kerberos.msgType==12" -T fields \
  -e frame.time -e kerberos.SNameString | sort | uniq -c | sort -rn
# ^ ONE host requesting tickets for MANY service names, in a burst,
#   is Kerberoasting happening live. The SNameString column is the
#     list of SPNs it went for.

# the encryption type (RC4 = 23, AES = 17/18). RC4 in a modern
# domain is a finding about the domain's configuration.
tshark -r "$P" -Y "kerberos" -T fields -e kerberos.encProvider 2>/dev/null \
  | sort | uniq -c

# === THE ONES THAT ARE ALWAYS A FINDING ===
# a non-standard port carrying anything
tshark -r "$P" -T fields -e tcp.dstport -e tcp.len | sort -n | uniq -c | sort -rn
# DNS over a non-53 port, HTTP over 443 (without TLS), FTP on 21
# with a large transfer - all findings
EOF

cat > 03-kerberos-in-capture.md <<'MD'
# Finding an attack in a capture, not just a conversation

```text
  THE QUESTION: "did the attacker enumerate the domain from this host?"

  THE ANSWER IS NOT A SINGLE PACKET. It is a SHAPE.

  Shape 1: A BURST OF TGS-REQUESTS FROM ONE SOURCE
    tshark -r c.pcap -Y "kerberos.msgType==12" -T fields \
      -e frame.time -e ip.src -e kerberos.SNameString | sort
    Look at: one IP, many SNames, within a few seconds.
    A normal user requests 2-5 service tickets. An attacker requests
    one per SPN in the domain. That is the difference between 5 and
    400, and it is visible in the timestamps.

  Shape 2: RC4 ENCRYPTION TYPE, IN A DOMAIN THAT USES AES
    tshark -r c.pcap -Y "kerberos" -T fields -e kerberos.encProvider \
      | sort | uniq -c
    If the domain has msDS-SupportedEncryptionTypes = 0x18, the DC
    will not issue RC4 tickets except to accounts that still support
    RC4. So an RC4 ticket in the capture means the roasting is
    targeting a specific RC4-enabled account. The timestamp of that
    ticket, against the DC's own activity, is the finding.

  Shape 3: THE HOST IS A WORKSTATION, NOT A SERVER
    Combine with the conversation list: the source of the ticket
    burst also has an outbound HTTP POST. That is exfiltration of
    the tickets. Two findings from one capture.

  THE WRITE-UP, in the shape the grader wants:
    "At 2026-06-11 15:22:03 UTC, host 10.10.10.50 issued 412
     Kerberos TGS-REQ messages to the domain controller, requesting
     tickets for 412 distinct service principal names over 87 seconds.
     Every other host in the capture issued fewer than six. The
     encryption type on 388 of those requests was 0x17 (RC4),
     indicating the target accounts still support RC4. This is
     consistent with SPN enumeration and service ticket harvesting.
     Source: challenge.pcap, frames 88410-89222."
```

```bash
# the count, which is the number that makes the finding
tshark -r challenge.pcap -Y "kerberos.msgType==12" \
  -T fields -e ip.src 2>/dev/null | sort | uniq -c | sort -rn | head
echo "  ^ one source with three orders of magnitude more TGS-REQs"
echo "    than any other is the finding, and the count is the proof."
```

```text
  AND THE NETWORK-SIDE OF AN AD ENGAGEMENT, which is what makes
  captures valuable even when disk and memory answer nothing:

    DC01 --(AS-REQ, alice)--> KDC          normal login
    WORK1 --(TGS-REQ, SPN=cifs/dc01)       one service: normal
    WORK1 --(TGS-REQ, SPN=http/sql01)       two services: normal
    WORK1 --(TGS-REQ, SPN=cifs/dc01)       ...
    WORK1 --(TGS-REQ, SPN=mysql/x)         400 of these: roasting
    WORK1 --(HTTP POST, 2.4 MB)--> x.x.x.x  exfiltration

    The capture shows the whole chain, in order, from a device that
    was not compromised and cannot lie about it.
```

python3 - <<'PY' 2>&1 | tee 04-shape.txt
print("  === a conversation versus a shape ===\n")
print("  THE WEAKEST QUESTION AND WHY IT IS WEAK:\n")
print("    'Which IP talked to which IP?'")
print("    A conversation list answers it in one command. Every")
print("    challenge can be answered from a conversation list alone,")
print("    and a challenge answered that way means you have not")
print("    actually read the capture.\n")
print("  THE QUESTIONS THAT REQUIRE THE SHAPE:\n")
print("    'How many DISTINCT service names did one host request in")
print("     a burst?'          -> a distribution, not a conversation")
print()
print("    'What is the interval between beacons to one destination?'")
print("                           -> periodicity, not a conversation")
print()
print("    'Did the byte count in one direction exceed the other?'")
print("                           -> asymmetry, not a conversation")
print()
print("    'Which JA3 appears for exactly one destination?'")
print("                           -> uniqueness, not a conversation")
print()
print("  THE FOUR SHAPES, and every network challenge's answer is one:\n")
print(f"  {'SHAPE':<28} {'HOW TO SEE IT':<38} {'WHAT IT MEANS'}")
print("  " + "-"*90)
print(f"  {'BURST / FAN-OUT':<28} {'uniq -c on one field':<38} enumeration")
print(f"  {'PERIODICITY':<28} {'sort by time, diff the times':<38} C2 beaconing")
print(f"  {'ASYMMETRY':<28} {'bytes out vs bytes in':<38} exfiltration")
print(f"  {'UNIQUENESS':<28} {'a fingerprint seen once':<38} a new client/tool")
print()
print("  EACH IS ONE LINE OF awk. EACH IS WORTH MORE POINTS THAN THE")
print("  ENTIRE CONVERSATION LIST, because the conversation list is")
print("  what the capture SHOWS and the shape is what it MEANS.")
print()
print("  EXAMPLE, the periodicity, done properly:")
print()
base = 0
period = 60
print(f"    {'time':<16} {'delta':<10} destination")
print("    " + "-"*46)
prev = None
for i in range(12):
    t = base + i * period
    d = "-" if prev is None else f"{t-prev}s"
    prev = t
    print(f"    {t:<16} {d:<10} 198.51.100.44")
print()
print(f"    delta is exactly {period}s, twelve times, to the same address.")
print(f"    That is not a user. That is a beacon. And a beacon with a")
print(f"    constant interval is either a default configuration or a")
print(f"    test - either way it is not human behaviour.")

Step 4 is the deliverable: a conversation versus a shape. The conversation list answers
"which IP talked to which IP" in one command — and a challenge answered that way means you
haven't read the capture. The four shapes are burst/fan-out, periodicity, asymmetry, and
uniqueness, each with the one-line awk that finds it and what it means.

03-kerberos-in-capture.md shows the shape applied to the canonical AD finding: 412 TGS-REQ
messages from one host for 412 distinct SPNs in 87 seconds, when a normal user issues 2–5. The
count is the proof, and the RC4 encryption type on 388 of them tells you which accounts the
roasting targeted.
