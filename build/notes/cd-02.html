Disk Forensics Challenges

Summary

The disk is where most challenges' answers live. This note is the discipline for working a disk
image against ground truth: the artefact classes you will meet, the order to work them in, and
the questions that appear in every one.

The framing: disk forensics is a lookup problem with a time
component. Almost every question has an answer in a specific,
findable structure, and the skill is knowing which structure holds
which question.

Companion to cd-01 (the flow) and for-04 (carving). This note is
the discipline against real challenges.

The artefact classes, and what each answers

  ARTEFACT                     ANSWERS THESE QUESTIONS
  --------------------------------------------------------------------------
  FILE SYSTEM (MFT)            what existed, when it was created and
                               modified, where it was, its size,
                               whether it is deleted, its streams

  $UsnJrnl                     the file system's own record of
                               creates/renames/deletes. Survives
                               timestomping. Answers "was this
                               renamed, and from where"

  PREFETCH                     which executables ran, and when
                               (last run time). Answers "what ran"

  EVENT LOGS (.evtx)           logons, process creation, service and
                               task changes, the Security log, and
                               whether the log was cleared

  REGISTRY                     persistence, configuration, USB
                               devices, installed software, recent
                               documents, user activity (UserAssist),
                               and what the user typed

  NTUSER.DAT                   per-user: logon times, RunMRU
                               (typed Run commands), TypedPaths
                               (explorer paths typed or clicked),
                               RecentDocs, MountPoints2

  LNK FILES (jump lists)       what was opened FROM EXPLORER, with
                               timestamps. Survives the file being
                               deleted. Answers "what did the user do"

  $MFT's RESIDENT DATA         the content of small (<700 byte) files,
                               including deleted ones

  RECYCLE BIN ($I + $R)        the original path, size, and deletion
                               time of a deleted file

  BROWSER DATA                 downloads, history, cookies, saved
                               passwords (DPAPI-encrypted), and
                               the autofill history

  EMAIL CLIENT DB              whether it came by email, from whom,
                               with the header intact

  SLACK / BACKUP DATA          things the file system never saw

  PREFETCH vs $UsnJrnl         prefetch says "it ran"; $UsnJrnl says
                               "the file system's view". When they
                               disagree about EXISTENCE, you have a
                               timestomp.

The order that works

# cd-01's 03-triage.sh produces the file map. From there:

# 1. THE FILE MAP, and the four greps
grep -iE "\\\\(Downloads|Desktop|Temp|Startup|Recycle\.Bin)\\\\" mft.txt
grep -iE '\.(exe|bat|ps1|vbs|js|scr|hta|jar)$' mft.txt
grep '\*' mft.txt                    # deleted
grep -E '\*:' mft.txt                # alternate data streams

# 2. PREFETCH, and diff it against what is on disk
#    an executable that ran but no longer exists is the interesting one
fls -r -p part.dd | grep -i prefetch | grep -i '\.exe' \
  | sed -E 's/.*\\([A-Z0-9_-]+\.EXE)-[0-9A-F]{10}\.pdb/\1/' | sort -u > ran.txt
grep -iE '\.exe$' mft.txt | sed -E 's/.*\\//' | sort -u > present.txt
comm -23 ran.txt present.txt
#    ^ ran and is gone. THAT list is where the answer usually is.

# 3. THE REGISTRY: persistence first
icat part.dd <reg_hive_inode> > system.hive
python3 -c "
from Registry import Registry
r = Registry.Registry('system.hive')
for k in r.open('Microsoft\\\\Windows\\\\CurrentVersion\\\\Run'):
    print(k.path(), '=', k.value())
for k in r.open('Microsoft\\\\Windows NT\\\\CurrentVersion\\\\Winlogon'):
    print(k.path(), '=', k.value())
"
# python-registry: pipx install python-registry

# 4. THE EVENT LOGS, which is where the timeline is
icat part.dd <evtx_inode> > sec.evtx
python3 -c "
import Evtx.Evtx as evtx
import Evtx.Views as e_views
with evtx.Evtx('sec.evtx') as log:
    for r in log.records():
        print(r.timestamp(), r.xml().replace('\n',' ')[:200])
"
# python-evtx: pipx install python-evtx
# and: EvtxECmd (libevtx-utils), for export to XML

# 5. THE USER ACTIVITY (NTUSER + jump lists), which is the last thing
#    people look at and the first thing a report needs
icat part.dd <ntuser_inode> > ntuser.dat
python3 -c "
from Registry import Registry
r = Registry.Registry('ntuser.dat')
for k in r.open('Software\\\\Microsoft\\\\Windows\\\\CurrentVersion\\\\Explorer\\\\RunMRU'):
    print(k.path(), '=', k.value())
for k in r.open('Software\\\\Microsoft\\\\Windows\\\\CurrentVersion\\\\Explorer\\\\TypedPaths'):
    print(k.path(), '=', k.value())
"
# 8. THE BROWSER, if the scenario is about delivery
#    Chrome:   User Data/Default/History (SQLite), Cookies, Login Data
#    Firefox:  places.sqlite, cookies.sqlite, logins.json (encrypted)
#    the timestamps are WEBSOCKET (microseconds since 1601), not
#    FILETIME. That conversion is a per-challenge skill.

The conversions nobody teaches you

mkdir -p ~/aegis/labs/cd-02
cd ~/aegis/labs/cd-02

cat > 01-conversions.py <<'PY'
#!/usr/bin/env python3
"""The timestamp conversions every disk challenge needs.

These are the four formats you will meet, and getting them wrong is
the single most common reason a disk answer is marked incorrect even
though you found the right artefact.
"""
from datetime import datetime, timedelta, timezone
import struct

EPOCH_FILETIME = datetime(1601, 1, 1, tzinfo=timezone.utc)
EPOCH_UNIX     = datetime(1970, 1, 1, tzinfo=timezone.utc)
EPOCH_WEBKIT   = datetime(1601, 1, 1, tzinfo=timezone.utc)

def filetime_to_dt(v: int) -> datetime:
    """Windows FILETIME: 100-nanosecond intervals since 1601-01-01."""
    return EPOCH_FILETIME + timedelta(microseconds=v / 10)

def unix_to_dt(v: int) -> datetime:
    return EPOCH_UNIX + timedelta(seconds=v)

def webkit_to_dt(v: int) -> datetime:
    """Chrome uses microseconds since 1601-01-01, like FILETIME but
    scaled by 1000. Getting this wrong shifts dates by 100000x."""
    return EPOCH_WEBKIT + timedelta(microseconds=v)

def dos_to_dt(v: int) -> datetime:
    """MS-DOS date-time: 2 bytes date + 2 bytes time. Used in $I files
    (recycle bin) and in ZIP local headers."""
    date, time = struct.unpack("<HH", struct.pack("<I", v))
    y   = ((date >> 9) & 0x7f) + 1980
    mon = (date >> 5) & 0x0f
    d   = date & 0x1f
    hh  = (time >> 11) & 0x1f
    mm  = (time >> 5) & 0x3f
    ss  = (time & 0x1f) * 2
    return datetime(y, mon, d, hh, mm, ss)

def ft_to_dos(dt: datetime):
    y = max(dt.year, 1980) - 1980
    date = (y << 9) | (dt.month << 5) | dt.day
    time = (dt.hour << 11) | (dt.minute << 5) | (dt.second // 2)
    return (date | (time << 16))

def show(label, raw, conv):
    dt = conv(raw)
    print(f"  {label:<34} {raw:<24} {dt:%Y-%m-%d %H:%M:%S} UTC")

print("  === THE SAME INSTANT, IN FOUR FORMATS ===")
target = datetime(2026, 6, 11, 14, 32, 41, tzinfo=timezone.utc)
ft  = int((target - EPOCH_FILETIME).total_seconds() * 1e7)
uni = int((target - EPOCH_UNIX).total_seconds())
wk  = int((target - EPOCH_WEBKIT).total_seconds() * 1e6)
print()
show("FILETIME (MFT, $I, .evtx)",      ft,  filetime_to_dt)
show("UNIX epoch (logs, python)",      uni, unix_to_dt)
show("WebKit/Chrome microseconds",     wk,  webkit_to_dt)
print(f"  {'DOS date-time (recycle, zip)':<34} {ft_to_dos(target):<24} {target:%Y-%m-%d %H:%M:%S} UTC")
print()
print("  ^ ONE instant, four encodings, four scales. A FILETIME read as")
print("    a UNIX epoch is 369 years out. A Chrome timestamp read as a")
print("    FILETIME is 100000x out. Neither is obviously wrong.")
print()
print("  === THE COMMON CONVERSIONS, DO THIS ONCE ===")
print(f"    FILETIME -> ISO : {filetime_to_dt(ft).isoformat()}")
print(f"    UNIX     -> ISO : {unix_to_dt(uni).isoformat()}")
print(f"    WebKit   -> ISO : {webkit_to_dt(wk).isoformat()}")
print()
print("  === ONES TO RECOGNISE ON SIGHT ===")
for name, v, conv in [
    ("FILETIME zero (never)",            0, filetime_to_dt),
    ("MFT epoch when no timestamp",      0, filetime_to_dt),
    ("Chrome 'never visited'",           9223372036854775807, webkit_to_dt),
    ("DOS zip 1980 floor",               0x00210000, dos_to_dt),
]:
    try: show(name, v, conv)
    except Exception as e: print(f"  {name:<34} {'-':<24} {type(e).__name__}")
print()
print("  9223372036854775807 in Chrome's history means 'never'. Seeing")
print("  it as a date is how you report a 7-billion-year-old cookie.")
PY
python3 01-conversions.py 2>&1 | tee 02-conversions.txt
rm -f 01-conversions.py

Step 3 is the deliverable: the same instant in four formats — FILETIME, UNIX epoch, Chrome
WebKit microseconds, and DOS date-time — with the two failure modes called out explicitly. A
FILETIME read as a UNIX epoch is 369 years out; a Chrome timestamp read as a FILETIME is 100,000×
out. Neither produces an obviously wrong answer, which is why it's the most common reason a
correct artefact produces an incorrect submission.

02-conversions.txt also shows the sentinel values — 0 for a never-timestamped MFT entry,
9223372036854775807 for a Chrome "never visited" cookie (read as a date, it's a
seven-billion-year-old cookie).
