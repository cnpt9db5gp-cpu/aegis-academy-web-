Path Traversal, LFI and File Upload

Summary

All three of these are the same bug in different clothing: a string that names a resource
crosses from your input into a component that resolves names — a filesystem, a template
engine, an image decoder. ps-01's ambiguity table predicted every one of them.

Path traversal

  /download?file=report.pdf          -> /home/www/report.pdf
  /download?file=../../etc/passwd    -> /etc/passwd

Encoding, and why it is always the reason

  WHAT THE STRING CONTAINS     WHAT EACH LAYER DECODES IT TO
  --------------------------   -------------------------------
  ../../etc/passwd             itself
  ..%2f..%2fetc%2fpasswd       after 1 URL decode
  ..%252f..%252fetc%252fpasswd after 2 URL decodes
  ..%c0%af..%c0%af             overlong UTF-8 (legacy)
  ..%5c..%5c                   Windows backslash
  ....//....//etc/passwd       some filters collapse ../ once, leaving ../
  %2e%2e%2f                    the decoded form of ../
  \x2e\x2e\x2f                  after some legacy decoders

Every successful traversal payload is a filter that decoded fewer
times than the filesystem did. Count the decoders: browser → proxy →
framework → middleware → controller → file API. If your filter runs at
layer 2 and the file open at layer 5, there are three opportunities.

Filters and their bypasses

  strip "../"          -> ....//   (strip leaves ..)   ...//  (collapse one pass)
                        -> ..\/     (backslash on some systems)
                        -> %2e%2e/  (encoded, if not decoded after the strip)
  ban ".."             -> ....      (filtered once, not recursively)
                        -> strings.Trim(s, ".") on the wrong side
  whitelist extension  -> read /etc/passwd? no. read /var/www/.env:
                           dotfile bypasses extension checks
                        -> null byte: file.php%00.jpg  (old PHP)
  resolve then check   -> CORRECT: realpath() must be INSIDE the base dir
  blacklist traversal  -> fails; you do not know the filenames

The fix

// THE FIX: resolve, then verify containment. Never string-filter.
$base = realpath('/var/www/public');            // absolute, symlinks resolved
$want = realpath($base . '/' . $userfile);      // resolve the requested path too
if ($want === false || !str_starts_with($want, $base . DIRECTORY_SEPARATOR)) {
    http_response_code(400); exit('denied');     // note the false check FIRST
}
readfile($want);

The === false check matters: without it, str_starts_with(false, ...)
coerces to "" and can pass. This is a real bug in real code.

LFI and RFI

  LFI  include/require/read of a local file
       -> read source of included PHP files   (source disclosure)
       -> read /etc/passwd, config with secrets
       -> if the included file is executable PHP: RCE
       -> log poisoning: get a log file included, put PHP in a User-Agent

  RFI  include/require of a REMOTE url (usually needs allow_url_include)
       -> remote code execution directly

  WRAPPERS:
    php://filter/convert.base64-encode/resource=index.php  -> read source
       (a wrapper that still counts as traversal in most apps' WAFs)
    php://input          -> the request body
    data://text/plain,<?php ...?>   -> code
    expect://, zip://, phar://        -> archive and PHAR tricks

Log poisoning deserves naming because it is the standard LFI-to-RCE
path on a server with no obvious include of user-writable content:

  1. find the access log path (usually /var/log/apache2/access.log)
  2. send a request with a PHP payload in the User-Agent
  3. include the log file with ?file=/var/log/apache2/access.log
  4. the payload is now inside a .log file that gets included as PHP

The defence is the same as traversal's: an allowlist of includable
files, never a path.

File upload

  THE THREE CHECKS, and which one attackers bypass:

  1. EXTENSION CHECK          bypassed by: .phtml .php5 .pht, case,
                              null bytes, double extensions, .htaccess
  2. MIME / CONTENT-TYPE      bypassed by: renaming a .jpg to .php keeps
                              Content-Type: image/jpeg - the header is
                              attacker-supplied and meaningless
  3. MAGIC BYTES              the real check: read the first bytes and
                              detect the actual format. Even then, an
                              image library can have a parser bug.

  THE UNIVERSAL BYPASS:
    upload a .jpg whose first bytes are  \x89PNG\r\n\x1a\n
    immediately followed by:            <?php system($_GET['c']); ?>
    GIF89a<?php system($_GET['c']); ?>
    (for image formats that are rendered inline)

The other half: getting the file executed

  Even a perfect .php upload is inert unless the server executes it.
  So you need ONE of:
    - the upload directory is web-accessible
    - .htaccess:  AddType application/x-httpd-php .jpg
    - a PHP include that picks up the file
    - a file manager / image-processing pipeline
    - log poisoning (above)
    - overwriting a template

  If none of these exist, the upload is a stored file and the finding
  drops to "arbitrary file upload, low execution risk". Saying that
  honestly is better than overstating it.

The fix

  - store uploads OUTSIDE the web root, or in a directory with no handler
  - generate a random server-side filename; never trust the client's
  - allowlist extensions by content, and re-encode images (strip EXIF,
    re-save) rather than accepting them
  - serve uploads with Content-Disposition: attachment and a fixed
    Content-Type, from a separate origin if possible
  - never let the upload name influence the path
  - disable PHP execution in the upload directory (server config)

Terminology

Term Meaning
Path traversal / directory traversal ../ escaping the intended directory
LFI Local file inclusion
RFI Remote file inclusion
realpath() Resolves symlinks and .. to an absolute path
Containment check Verifying the resolved path is inside the base
Double decoding Two decode layers; defeats single-layer filters
Null byte %00; truncates the filename in old PHP
Log poisoning Injecting code into a log, then including the log
PHP wrappers php://, data://, expect://, phar://
Magic bytes The real file signature; not the extension
Double extension shell.php.jpg; server vs browser disagreement
.htaccess bypass Adding a handler for a non-PHP extension
Stored upload A file that is never executed; much lower severity

# --- 6. the audit ---
cat > 05-audit.sh <<'EOF'
#!/usr/bin/env bash
echo "=== 1. every filesystem operation with user input ==="
grep -rnE "(file_get_contents|include|require|fopen|readfile|file|fopen|unlink|copy|rename|move_uploaded_file)" \
     --include="*.php" . | grep -E '\$_' | sed 's/^/  /'

echo; echo "=== 2. path operations with string concatenation ==="
grep -rnE "\.\s*['\"]?\.?./|__DIR__.*\.\s*\\\$|realpath" --include="*.php" . | sed 's/^/  /'

echo; echo "=== 3. upload handling ==="
grep -rn "move_uploaded_file\|\$_FILES" --include="*.php" . | sed 's/^/  /'

echo; echo "=== 4. the WRONG mitigations, which are still common ==="
grep -rnE "str_replace\(['\"].*\.\.|preg_replace.*\.\.|basename\(" --include="*.php" . | sed 's/^/  /'
echo "  ^ string filters and even basename() are bypassable (basename strips"
echo "    the traversal but does not check the RESULT is inside the base)."

echo; echo "=== 5. php wrappers, if the app can reach them ==="
grep -rnE "php://|data://|expect://|include\b|require\b" --include="*.php" . | sed 's/^/  /'

echo; echo "=== 6. does the upload directory execute? ==="
echo "  check for a .htaccess or an nginx handler covering uploads/"
ls -la uploads/.htaccess 2>/dev/null || echo "  uploads/.htaccess ABSENT - files will execute"
EOF
chmod +x 05-audit.sh

Step 3 is the important one: eight traversal payloads against the naive filter, and every
single one still traverses. That is not a missing-bypass problem, it's a wrong-shape-of-defence
problem — and it's the single most persuasive demonstration in this note.

Step 5 also matters for accuracy: the last three uploads succeed (double extension,
.phtml, magic-bytes PHP). But the note's own caveat is the professional point — check whether
the upload directory executes anything before calling it Critical.
