Enclaves

Summary

Process isolation asks the kernel for help. Trust-based isolation asks the CPU instead. An
enclave (Intel SGX, ARM TrustZone) is a region of memory the CPU itself encrypts and
protects, with entry and exit measured by the hardware.

This is the lecture's answer to: what if the OS itself is the adversary?

Key ideas

  • Trusted Execution Environments (TEEs): hardware-isolated regions with measured entry
  • SGX: enclaves in unencrypted normal memory, encrypted while resident; keys derived from
    measured code
  • Launch / measurement: a trusted computing base hashes the code before launch; that hash is
    the identity
  • Remote attestation: prove to a third party what code is running inside the enclave
  • TrustZone: an ARM secure world, a whole OS, hardware isolated
  • The catch: the CPU has to decrypt into memory, so side channels become the attack

SGX in one page

1. you write code, sign it, publish the measurement (a hash)
2. a client wants to run your code on a remote host
3. your code asks the untrusted host to LAUNCH it as an enclave
4. the hardware hashes the enclave's pages -> measurement
5. the enclave sends that measurement to the client
6. the client compares it to the signed hash it trusts
7. only if they match does the client send secrets in

The OS can lie about whether it launched an enclave, but not about what code is in one. That
distinction is the whole security property.

TrustZone

An ARM feature that splits the processor into a secure world and a normal world. The
secure world has its own memory and its own OS (Trusted Firmware, or a secure monitor like OP-TEE).
Switching worlds is expensive and controlled by a bit in a coprocessor register.

Coarse-grained but real isolation: normal-world kernel code cannot read secure-world memory.

Side channels: the fundamental tension

Memory must be decrypted to be computed on. That decrypt creates patterns an attacker can observe:

  • Cache timing: accessed memory leaves cache lines resident
  • Page-table access: which page was accessed is observable
  • Interrupt/modulo timing: how long something took
  • Power and EM: a different power draw for different operations
  • Speculative execution: the CPU executes past a bounds check and leaks via cache

Isolation and side-channel resistance are opposite requirements. More isolation usually means
more microarchitectural state visible across the boundary.

Terminology

Term Meaning
TEE Trusted Execution Environment
Enclave A hardware-isolated region of memory
Measurement A cryptographic hash of the enclave's initial code
Launch Host asks the CPU to create and measure an enclave
Remote attestation Proving to a remote party what code runs
Sealing key Derived from the measurement; encrypts local data
Side channel Leaking secrets through observable side effects
Cache timing attack Inferring memory access from cache state
Rollback attack Re-running old, valid-but-stale code
TrustZone ARM secure world / normal world split

# --- does this CPU have enclave or virtualization support? ---
{
  echo "=== CPU flags of interest ==="
  grep -oE "vmx|svm" /proc/cpuinfo | sort -u | sed 's/^/  /'
  echo
  echo "=== Intel SGX (requires sgx flag; absent on most consumer parts) ==="
  grep -oE "\bsgx\b" /proc/cpuinfo | head -1 || echo "  no sgx flag on this CPU"
  echo
  echo "=== ARM TrustZone (check DT compatible) ==="
  [ -f /proc/device-tree/compatible ] && tr '\0' '\n' < /proc/device-tree/compatible | head -3 | sed 's/^/  /'
  echo
  echo "=== runtime enclave support ==="
  ls -la /dev/sgx* 2>/dev/null || echo "  /dev/isgx and /dev/sgx_enclave absent"

} 2>&1 | tee 01-enclave-support.txt

# --- flush+reload, the canonical cache timing attack, against yourself ---
cat > cachetiming.py <<'PY'
import ctypes, time, os

SIZE = 256 * 1024
buf = ctypes.create_string_buffer(SIZE)

def flush():
    """Evict our buffer from cache using clflush."""
    # clflush rdi
    ctypes.memset(buf, 0, SIZE)

def victim():
    """Touch the buffer - this puts it in cache."""
    ctypes.memset(buf, 1, 16)

def timed(fn):
    best = 1e9
    for _ in range(200):
        flush()
        fn()
        t0 = time.perf_counter_ns()
        fn()
        best = min(best, time.perf_counter_ns() - t0)
    return best

if __name__ == "__main__":
    # Compile an inline asm helper via ctypes is awkward; use a C helper instead.
    print("  run the compiled helper: gcc -O0 cachetime.c -o cachetime && ./cachetime")
PY
rm -f cachetiming.py

cat > cachetime.c <<'EOF'
/* Flush+Reload: the canonical cache side channel, demonstrated on our own process. */
#include <stdio.h>
#include <string.h>
#include <stdint.h>
#include <time.h>

#define SIZE (256 * 1024)
static char buf[SIZE];

static void clflush_range(void *start, size_t len) {
    char *p = start;
    for (size_t i = 0; i < len; i += 64)
        __asm__ volatile("clflush (%0)" :: "r"(p + i) : "memory");
}
static void victim(size_t offset) { volatile char c = buf[offset]; (void)c; }

static uint64_t rdtsc(void) {
    uint32_t lo, hi;
    __asm__ volatile("rdtsc" : "=a"(lo), "=d"(hi));
    return ((uint64_t)hi << 32) | lo;
}

int main(void) {
    memset(buf, 0, SIZE);
    printf("  measuring access time with and without a prior access\n");
    printf("  %-12s %-14s %-14s %s\n", "offset", "cold(ms)", "warm(ms)", "verdict");
    for (size_t off = 0; off < 4096; off += 512) {
        clflush_range(buf, SIZE);
        uint64_t c0 = rdtsc();
        victim(off);
        uint64_t c1 = rdtsc();

        clflush_range(buf, SIZE);
        victim(off);                      /* prime the cache */
        uint64_t w0 = rdtsc();
        victim(off);
        uint64_t w1 = rdtsc();

        double cold = (c1 - c0) / 1e6, warm = (w1 - w0) / 1e6;
        printf("  %-12zu %-14.4f %-14.4f %s\n", off, cold, warm,
               warm < cold * 3 ? "cache HIT (was primed)" : "cold");
    }
    printf("\n  A cache hit is measurably faster. That difference is the side channel.\n");
    printf("  Everything an enclave protects is protected against exactly this.\n");
    return 0;
}
EOF
gcc -O0 cachetime.c -o cachetime && ./cachetime | tee 02-cachetiming.txt

cat > 03-side-channels.md <<'EOF'
# Why enclaves are not enough

Isolation says: "this memory belongs to someone else, and the OS cannot read it."
Side channels say: "this CPU is shared, and computation leaves observable traces."

## The traces
- cache line residency (Flush+Reload, Prime+Probe)
- translation lookaside buffer and page-table access patterns
- interrupt and speculation behaviour (Spectre, Meltdown)
- power and electromagnetic emission
- timing of memory-dependent branches

## Why enclave code is especially vulnerable
The enclave must decrypt its pages to execute. The moment instructions touch
secret data, that data's address pattern enters the shared microarchitectural
state — and the untrusted OS is right there to measure it.

## The mitigations and their costs
- constant-time programming (hard, and only covers timing)
- cache partitioning (Intel CAT, performance cost)
- core isolation (Pinning an enclave to a core, availability cost)
- frequent context switching, randomised scheduling (performance cost)
- newer hardware mitigations (IBPB, retpolines, control-flow enforcement)

## The honest conclusion
TEEs raise the bar: an attacker must be the OS *and* win a statistical side
channel. That is a real improvement. It is not a guarantee, and it is not a
replacement for other defences. `mit858-18` covers this in detail.
EOF
