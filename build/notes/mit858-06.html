Software Fault Isolation

Summary

If a bug in one component must not compromise the whole system, isolate the component. This
lecture covers the range from language-level sandboxing to hypervisors and back down to
language-managed runtimes.

Key ideas

  • Isolation vs sandboxing: isolation is the mechanism; sandboxing is a policy applied with it
  • Language-level sandboxing: the runtime enforces memory safety, so a bug stays in-process
    (Java, .NET, Python's refcounting, Rust's ownership)
  • Native Client (NaCl/Sandboxing API): a restricted instruction subset with validation
  • Hypervisors: Type 1 (bare metal, e.g. Xen) and Type 2 (hosted, e.g. VirtualBox/KVM)
  • Static binary verification: measure the code at load time and refuse to run if changed
  • The trade: isolation costs performance and memory, and every new interface is new code

Native Client, the lecture's reading

NaCl restricts the instruction set to what it can validate statically:

  • no direct memory access; only via validated jump tables
  • a validator proves the code and its data are consistent before execution
  • the sandbox relies on the validator, so validator bugs are critical
  • shipped in Chrome as "Native Client" (now retired) and PNaCl for Firefox

The general lesson: a restricted instruction subset is verifiable, and a verifiable subset
can be made safe against whole classes of memory-corruption bugs.

Hypervisors

Type Runs on Examples Trust
Type 1 (bare metal) hardware directly Xen, ESXi, Hyper-V no host OS
Type 2 (hosted) an OS VirtualBox, VMware Workstation the host OS

Both are "trusted": the hypervisor controls all guest memory. A hypervisor bug is an escape.
Exposed hypervisor interfaces (management APIs, device emulation) are high-value targets.

Static binary verification

Before running an untrusted binary, hash every page and compare against a signed manifest.

  • If it matches, run it
  • If it does not, refuse

This is IMA/EVM in Linux and code signing on Windows. It closes the
"inject a page after the check" window, though it does not close in-kernel
rootkits.

# --- 4. the SFI idea, illustrated ---
echo
echo "=== 4. restricted instruction sets: the NaCl idea ==="
cat > 04-nacl-idea.md <<'EOF'
# What a restricted instruction set buys you

A general-purpose ISA lets a program do anything with any memory. A
sandboxed ISA narrows that:

| Capability | General ISA | Sandboxed ISA |
|---|---|---|
| arbitrary memory read | yes | no - only validated regions |
| arbitrary memory write | yes | no |
| indirect jumps | anywhere | only validated targets |
| syscall | any | an explicit allowlist |
| self-modifying code | yes | no |

Because every instruction is checkable, a validator can prove properties that
are otherwise unprovable. That is why NaCl, wasm, and Java bytecode all take
this shape: move the trust from "the program is correct" to "the validator and
the runtime are correct".

**The cost:** the instruction set is smaller, so some code cannot be compiled
to it, and there is a performance penalty for indirect-call dispatch.

**Where you meet it today:** WebAssembly (the validator + JIT is a TCB that
browsers take seriously), JavaScript engines, and every managed runtime.
EOF
cat 04-nacl-idea.md

# --- 5. measure the cost ---
echo
echo "=== 5. what isolation costs ==="
python3 - <<'PY'
import time, subprocess
def bench(cmd, n=20):
    t = time.perf_counter()
    for _ in range(n): subprocess.run(cmd, capture_output=True)
    return (time.perf_counter() - t) / n * 1000
base = bench(["/bin/true"])
userns = bench(["unshare","-Ur","--","/bin/true"])
print(f"  /bin/true direct          : {base:.2f} ms")
print(f"  /bin/true under unshare -Ur: {userns:.2f} ms  (+{userns-base:.2f} ms for isolation)")
print()
print("  Process/namespace isolation is cheap. VM isolation is not:")
print("  it costs hundreds of MB of RAM and tens of seconds of boot time.")
print("  Choose the weakest isolation that still contains your threat.")
PY
free -h | head -2

# --- 6. the decision, written out ---
cat > 05-choosing.md <<'EOF'
# Choosing an isolation mechanism

| Your threat | Use | Why |
|---|---|---|
| a bug in my own plugin | language bounds / sanitizers | it is the same process; cheap |
| a hostile library in my process | seccomp + namespace | syscall restriction |
| a hostile user on a shared host | container, or per-user namespace | kernel shared, risk accepted |
| a hostile tenant | VM | separate kernel |
| a hostile kernel | enclave | hardware boundary |
| a hostile hypervisor | you are already at the bottom | nothing left; use encryption instead |

**The rule:** use the weakest isolation that still contains the adversary you
actually have. Every layer up costs memory, latency and operational
complexity, and adds a new interface to get wrong.
EOF
cat 05-choosing.md
