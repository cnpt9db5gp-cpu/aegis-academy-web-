Debugging with gdb and Reading Disassembly

Summary

gdb is not a debugger that happens to show assembly. It is a control-flow instrument: you
stop the program wherever you want, look at every piece of state, and step one instruction at
a time. That is the difference between guessing at a binary and knowing.

The skill is not memorising commands. It is knowing how to answer four
questions about any function you have never seen.

Companion to lo-03 (instructions) and lo-04 (the format). This note
is the tool that makes the other two concrete.

The four questions

  For any function you have never seen, you need:

  1. WHAT DOES IT DO?       arguments, return value, observable effects
  2. WHAT DOES IT TRUST?    which inputs are validated, which are not
  3. WHERE DOES IT JUMP?    branches, calls, and especially indirect ones
  4. WHAT CAN I CORRUPT?    which of its inputs reach a dangerous sink

  gdb answers 1 and 4 directly. Static analysis answers 2 and 3.
  You need both, and the combination is much faster than either.

The gdb model

  RUNNING PROCESS              you attach to a live process
  BREAKPOINT                   stop when an address is reached
  REGISTER                     read/write CPU state
  MEMORY                       read/write bytes at an address
  STEP (s)                     one instruction, into calls
  NEXT (n)                     one instruction, over calls
  FINISH (fin)                 run until the current function returns
  CONTINUE (c)                 run to the next breakpoint
  DISASSEMBLE                  objdump-style, addressable
  WATCH                        break when a value changes

The three stepping commands are the whole debugging skill:
s goes into, n goes over, fin returns. Confusing them is the
single most common beginner stall.

Layout, set once

# ~/.gdbinit  -- the difference between usable and unusable
cat > ~/.gdbinit <<'EOF'
set disassembly-flavor intel
set pagination off
set confirm off
set print pretty on
set history save on
set history filename ~/.gdb_history

# stop at main by default
# break main

# show the stack frame
define hook-stop
  info registers rip rsp rbp
  x/i $pc
  bt 1
end
document hook-stop
print RIP, RSP, RBP, the current instruction, and one frame of backtrace
end
EOF
echo "  written ~/.gdbinit"

Intel syntax is the default choice here because the rest of these notes use
it. If you read a course that uses AT&T, change only this line — and be
consistent, because mixed syntax in your own head causes real errors.

A complete session, on a real binary

mkdir -p ~/aegis/labs/lo-05 && cd ~/aegis/labs/lo-05

# build something with an actual bug, so the session has a purpose
cat > vuln.c <<'EOF'
#include <stdio.h>
#include <string.h>
#include <unistd.h>

// A deliberately unsafe copy. The parameter is the buffer's true size;
// the caller's value is trusted and attacker-influenced.
size_t copy_in(char *dst, size_t dst_size) {
    char scratch[16];
    read(0, scratch, 64);          // reads up to 64 bytes, ALWAYS
    memcpy(dst, scratch, dst_size); // copies dst_size bytes - the bug
    return dst_size;
}

int main(int argc, char **argv) {
    char buf[16];
    size_t n = (size_t)atoi(argv[1]);
    printf("copying %zu bytes into a 16-byte buffer\n", n);
    copy_in(buf, n);
    printf("survived\n");
    return 0;
}
EOF
gcc -g -O0 -fno-omit-frame-pointer -no-pie -z execstack vuln.c -o vuln
echo "built ./vuln"

# --- the session, step by step, non-interactively so it is reproducible ---
cat > 01-session.sh <<'EOF'
#!/usr/bin/env bash
# Every command below is a real gdb command. Run them by hand too.
gdb -q -batch \
  -ex "set disassembly-flavor intel" \
  -ex "info file" \
  -ex "break main" \
  -ex "run 32" \
  -ex "info registers rip rsp rbp rdi rsi" \
  -ex "x/8i \$pc" \
  -ex "bt" \
  -ex "disconnect" ./vuln 2>&1 | grep -vE "^\[Thread|^Reading symbols|^Breakpoint 1"
EOF
chmod +x 01-session.sh
./01-session.sh 2>&1 | tee 02-first-session.txt

# --- the four questions, answered with gdb ---
cat > 03-four-questions.sh <<'EOF'
#!/usr/bin/env bash
gdb -q -batch \
  -ex "set disassembly-flavor intel" \
  -ex "break copy_in" \
  -ex "run 32" \
  -ex "printf \"\n=== Q1: what does it take, and what does it return?\n\"" \
  -ex "info args" \
  -ex "info frame" \
  -ex "printf \"\n--- argument registers at entry ---\n\"" \
  -ex "info registers rdi rsi rdx rcx r8 r9 rax" \
  -ex "printf \"\n--- the caller's frame, so you can see the buffer ---\n\"" \
  -ex "up" \
  -ex "info locals" \
  -ex "p &buf" \
  -ex "p buf" \
  -ex "printf \"\n--- what is on the stack where the frame will sit ---\n\"" \
  -ex "x/16gx \$rsp" \
  -ex "printf \"\n=== Q3: where does it jump?\n\"" \
  -ex "disassemble copy_in" \
  -ex "disconnect" ./vuln 2>&1 | grep -vE "^\[Thread|^Reading sym|^Breakpoint"
EOF
chmod +x 03-four-questions.sh
./03-four-questions.sh 2>&1 | tee 04-four-questions.txt

What that second script actually showed you, which is the whole note:

  Q1  info args told you the signature (char*, size_t) - inferred, but
      almost always right, because the calling convention puts a char*
      in rdi and a size_t in rsi.

  Q1  info frame told you where rbp is, so every local's address is
      computable: locals are at rbp-8, rbp-16, ...

  Q3  disassemble gave you every branch, including which ones are
      INDIRECT. An indirect jump or call is where control flow can be
      redirected, and it is usually where a function pointer lives.

  Q4  (not a gdb command - it is the conclusion) rdi holds a pointer to a
      16-byte buffer. rsi holds 32. The function memcpy's 32 bytes into
      16. That is the bug, proven by register state at entry rather than
      by reading the source.

That is the method. You now know the bug from the binary, which is the
only way it will ever be available to you in an engagement.

The commands worth memorising

info registers            # all of them
info registers rip rsp rbp rdi rsi    # just these
info args                 # arguments of the current frame
info locals               # locals of the current frame
info frame                # frame base, return address, saved registers
info breakpoints          # what you have set
info sharedlibrary        # loaded libraries and their base addresses

x/16gx $rsp               # 16 qwords from rsp
x/32bx $rsp               # 32 bytes
x/s $rdi                  # a string at rdi
x/i $pc                   # the instruction at pc
x/4i $pc                  # four instructions
x/3i $pc-8                # three instructions ending AT pc (prologues)

disassemble /r function   # with raw bytes, essential for shellcode work
disassemble function
disassemble /s 0x400000,0x400100     # a range
set disassembly-flavor intel|att
layout asm                # side-by-side source/disasm in a TUI

break function
break *0x4005a0           # an address
break file.c:42
tbreak function           # one-shot
break ... if rdi == 0     # conditional

stepi / nexti              # one instruction, no source line logic
finish
continue
until 42
advance main+30
until *0x4005a0

watch -l *0x404050         # hardware watchpoint on memory
rwatch *0x404050           # read watchpoint
catch syscall write        # stop at write() syscalls

start                     # run to main
starti                    # run to the first instruction
attach <pid>
gcore core.1234            # dump the process image

Reading disassembly like a sentence

  0x4005a0 <copy_in>:
    push   rbp                    ; PROLOGUE. You found the entry point.
    mov    rbp, rsp
    sub    rsp, 0x20
    ; --- arguments, now at known offsets from rbp ---
    ; rdi = dst, rsi = dst_size
    lea    rax, [rbp-0x10]
    mov    edi, 0x40              ; read(0, buf, 64)
    call   read@plt
    ; --- the interesting part ---
    mov    rdx, [rbp+0x10]        ; dst_size, the TRUSTED value
    mov    rsi, rbp
    sub    rsi, 0x10              ; scratch = rbp-0x10
    mov    rdi, [rbp+0x8]         ; dst = rbp+0x8
    call   memcpy@plt             ; <-- the sink
    ; --- epilogue ---
    mov    rax, [rbp+0x10]
    leave
    ret

  READING IT:
    - rbp+0x8 is the first argument, rbp+0x10 is the second. Always.
    - rbp-0x10 is scratch, a 16-byte local.
    - memcpy's length comes from [rbp+0x10], which came from the CALLER.
      Nothing validated it against the buffer size.
    - that is the bug, and you found it without source.

When you cannot run the binary

{
  echo "=== static triage, no execution required ==="
  echo
  echo "--- file and format ---"
  file ./vuln
  echo
  echo "--- security posture (decides your whole strategy) ---"
  checksec --file=./vuln
  echo
  echo "--- imports: a behaviour sketch in 30 seconds ---"
  readelf --dyn-syms -W ./vuln | awk '$4=="FUNC" && $7!="UND"{print "   defined:", $NF}'
  objdump -T ./vuln | awk '$4=="DF"{print "   imported:", $NF}'
  echo
  echo "--- strings: the programmer describing their own code ---"
  strings -a -t x ./vuln | grep -iE "survived|copying|error|fail|%s|/tmp|127\.|0\.0\.0" | sed 's/^/  /'
  echo
  echo "--- dangerous imports are the sinks to look for ---"
  objdump -T ./vuln | grep -oE "\b(strcpy|strcat|sprintf|gets|scanf|read|recv|memcpy|system|execve|popen)\b" \
    | sort -u | sed 's/^/  sink: /'
  echo
  echo "--- cross-references to those sinks (objdump -d, then search) ---"
  objdump -d -M intel ./vuln | grep -B4 -E "call.*memcpy|call.*read" | head -20 | sed 's/^/  /'
} 2>&1 | tee 05-static-triage.txt

# --- the disassembler-round-trip: prove objdump is faithful ---
cat > 06-roundtrip.sh <<'EOF'
#!/usr/bin/env bash
# Disassemble a known program, then reassemble it. If the bytes match,
# the disassembly is a faithful representation of the binary.
objdump -d -M intel ./vuln | sed -n '/<copy_in>:/,/^$/p' | sed 's/^/  /'
echo
echo "  Note the raw bytes column. Those ARE the instruction encodings,"
echo "  straight from the file. The mnemonic column is objdump's reading"
echo "  of them, and 'disassembly' means 'this reading'."
EOF
chmod +x 06-roundtrip.sh
./06-roundtrip.sh 2>&1 | tee 07-roundtrip.txt

Patching a binary

{
  echo "=== changing a byte in place ==="
  cp vuln vuln-patched
  echo "  before: $(xxd -s 0x1180 -l 4 -p vuln 2>/dev/null || echo '(offset unknown)')"
  echo
  echo "  Find the offset you want to change, then patch it. Three ways:"
  echo
  echo "  1. a hex editor"
  echo "     xxd -s OFFSET -l 4 vuln-patched"
  echo "     xxd -r vuln-patched"
  echo
  echo "  2. printf + dd (the workhorse)"
  echo "     printf '\\x90\\x90\\x90\\x90' | dd of=vuln-patched bs=1 seek=OFFSET conv=notrunc"
  echo
  echo "  3. a patch script you can re-run, which is what you actually want"
  cat > patch.py <<'PY'
#!/usr/bin/env python3
"""Patch a binary by finding a unique byte pattern and replacing it.
Never patch by raw offset in a real engagement: offsets change when
you rebuild. Patch by CONTENT."""
import sys

def patch(path, old, new, count=1, offset=0):
    data = open(path, "rb").read()
    blob = bytes.fromhex(old.replace(" ", ""))
    rep = bytes.fromhex(new.replace(" ", ""))
    if len(blob) != len(rep):
        sys.exit("ERROR: replacement must be the same length as the original")
    n = data.count(blob, offset)
    if n != count:
        sys.exit(f"ERROR: found {n} occurrences of the pattern, expected {count}. "
                 "Refusing to patch an ambiguous binary.")
    idx = data.index(blob, offset)
    data = data[:idx] + rep + data[idx+len(blob):]
    open(path, "wb").write(data)
    print(f"  patched {count} byte(s) at file offset 0x{idx:x}")
    print(f"    {old} -> {new}")

if __name__ == "__main__":
    # example: swap the argument to read() from 0x40 to 0x10
    # find the exact bytes first: objdump -d | grep -A2 'mov.*edi,0x40'
    patch("vuln-patched",
          old="bf40000000",     # mov edi, 0x40
          new="bf10000000")     # mov edi, 0x10
PY
  python3 patch.py
  echo
  echo "  The same-length check and the uniqueness check are the two rules"
  echo "  that stop you corrupting a binary you have not verified."
  rm -f patch.py vuln-patched
} 2>&1 | tee 08-patching.txt

Terminology

Term Meaning
gdb The GNU debugger; a control-flow instrument
Breakpoint Stop when an address is reached
step / next / finish Into / over / return
Intel vs AT&T syntax mov rax, [rbp-8] vs mov -8(%rbp), %rax
info args / info locals Frame contents
info frame Frame base, return address, saved registers
x/ Examine memory: x/16gx $rsp
info registers CPU state
Watchpoint Break when a value changes
Core dump / gcore Process image for offline analysis
catch syscall Stop at a specific syscall
Static triage Analysis without executing
Patch by content Replace a unique byte pattern, never an offset
Sink A function where untrusted data becomes dangerous
Disassembly round-trip Prove the disassembly matches the bytes

# gdb cheatsheet

## Startup
```
gdb ./binary              gdb -p PID              gdb --args ./b arg1
start                     starti                 run
b main                    run                    b *0x4005a0
```

## The four questions
```
info args       Q1: what does it take
info frame      Q1: where are its locals (rbp is the anchor)
x/16gx $rsp     Q1: what is actually on the stack right now
disassemble fn  Q3: where does it jump
info registers  Q1: what is in the registers
x/i $pc         where am I, literally
```

## Memory
```
x/16gx $rsp     16 quadwords      x/32bx $rsp   32 bytes
x/s $rdi        string at rdi     x/4i $pc       4 instructions
x/3i $pc-8      the 3 instructions ENDING at pc (prologues)
set var i = 1   write memory      set {char}$rsp = 'A'
```

## Control
```
s / n / fin / c / u 42 / adv main+30 / until *0x4005a0
dis / dis /r / dis /s 0x400000,0x400200
layout asm / layout src / layout split
info breakpoints / info registers / bt / bt full / up / down / frame N
watch -l *0x404050    rwatch *0x404050    catch syscall write
```

## Batch mode (what I actually use, because it is reproducible)
```
gdb -q -batch -ex "b main" -ex run -ex "info args" -ex "disconnect" ./binary
```
Everything in a TUI is a keystroke you have to remember. Batch mode is a
script you can re-run, diff, and paste into a report.

## When it goes wrong
```
"Cannot access memory at address 0x0"
    -> the program already crashed, or you are at an unmapped page
       bt may be incomplete. Re-run and break earlier.

"No symbol table info available"
    -> stripped, or dynamic-only. Use addresses and x/ instead of names.

Everything is 0x7f...
    -> you are inside libc, not the binary. The addresses are right;
       you just broke on a PLT/library function.

Program received SIGSEGV
    -> that may be the crash you were looking for. bt, x/i $pc,
       x/8gx $rsp, info registers - and if it's the faulting address,
       x/4gx <fault address> to see what was there.
EOF

Step 4 (03-four-questions.sh) is the deliverable. It answers three of the four
questions using only register state and disassembly of a binary with no source available: the
signature comes from info args, the locals' addresses from info frame, and every branch
including the indirect ones from disassemble. The fourth question — what can be corrupted —
is then a conclusion you reach from those facts, which is exactly how it works in an
engagement.

08-patching.txt ships patch.py, which refuses to patch an ambiguous pattern and
refuses a length-changing replacement. Those two checks are the difference between editing a
binary and destroying one.

Self-test

  1. Name the four questions you must answer about an unknown function.
  2. What is the difference between step, next and finish?
  3. Why does x/3i $pc-8 show a function's prologue when x/3i $pc does not?
  4. Given rbp+0x10, what is the value there and why?
  5. Why is objdump -d -M intel the fastest way to triage a binary you cannot run?
  6. Why must a patch preserve length, and why refuse an ambiguous match?
  7. Why is batch mode preferable to the TUI for reproducible work?
