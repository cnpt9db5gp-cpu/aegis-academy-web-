Compilers, Linking and the ELF Format

Summary

A binary you are asked to reverse is the output of a toolchain: source → preprocessor →
compiler → assembler → object file → linker → binary. Every stage leaves a trace, and every
trace is something you can read.

Understanding the toolchain is not academic. It tells you why a function is nop-padded, why
a PLT exists, why a string is in .rodata rather than .text, and what the difference
between a statically and dynamically linked binary actually buys an attacker.

Companion to lo-01 (the file format) and lo-05 (the debugger). This
note is the pipeline between source and bytes.

The pipeline

   foo.c
     |  cpp  -E    preprocessor: expand #include, #define, macros
     v
   foo.i           (text, still C)
     |  gcc  -S    compile to assembly
     v
   foo.s
     |  as         assemble to machine code + relocations
     v
   foo.o           OBJECT FILE: code + data + relocation records + symbols
     |  ld / cc    link: resolve symbols across objects and libraries
     v
   a.out           BINARY: sections + entry point + program headers

The object file is the key artefact. It is not an executable; it is a
bundle of sections and a list of undefined references, waiting to be
resolved. Reading one teaches you what a binary will contain, before it
exists.

What the compiler decides, and how it reads to you

  -O0  no optimisation      verbose, spills everything to the stack,
                            re-reads values.  THE OPTIMISATION FOR RE.
  -O1  basic                folds constants, keeps the structure
  -O2  full                 inlines, vectorises, unrolls, reorders.
                            Functionally identical, structurally unrecognisable.
  -O3  aggressive           more unrolling, more vectorisation
  -Os  size                 smaller code, often the same shape as -O2
  -flto  whole-program      the compiler sees across translation units
                            and deletes or reorders far more

  REAL-WORLD CONSEQUENCE: most distributed software is -O2 or better.
  Your reverse engineering of a -O2 binary looks nothing like your
  reverse engineering of the same source at -O0. Practise at -O0,
  then learn to cope at -O2.

# The clearest demonstration that this matters
cat > /tmp/opt.c <<'EOF'
int f(int a, int b) { int c = a + b; return c * 2; }
EOF
for O in 0 1 2 3 s; do
  gcc -O$O -c /tmp/opt.c -o /tmp/opt$O.o 2>/dev/null
  printf "  -O%s : %3s bytes of .text\n" "$O" \
    "$(size -A /tmp/opt$O.o 2>/dev/null | awk '/\.text/{print $2}')"
done
echo
echo "  The sizes differ; the semantics do not. Everything you learn"
echo "  reverse engineering at -O0 has to be relearned at -O2."
rm -f /tmp/opt.c /tmp/opt*.o

Static vs dynamic linking — the security difference

  STATICALLY LINKED
    all of libc is in the binary
    + no PLT, no GOT, no lazy binding to think about
    + everything you need is in one file: great for a RE exercise
    + the binary cannot be tampered with by swapping a shared library
    - much larger
    - loses the operating system's security updates

  DYNAMICALLY LINKED
    libc.so is loaded by the loader at runtime
    + small binary, shared library, patch once for all
    - introduces the PLT and the GOT, which are WRITABLE DATA
    - an attacker with a write to the GOT can redirect calls
      (this is what Full RELRO closes)

  IMPACT ON EXPLOITATION:
    static : ROP straight into a libc function; its address is in the
             binary and known
    dynamic: ROP into the PLT stub; the address is known; the GOT
             resolves it on first call

Lazy binding, and why it matters

  LAZY (default):
    the PLT entry for printf() is a stub that jumps through the GOT.
    On first call it pushes the relocation index and jumps to
    ld.so, which resolves the address and WRITES IT INTO THE GOT.
    After that, the GOT points straight at the real printf.

  CONSEQUENCE: an unused GOT entry points at the PLT resolver, not at
  a function. So you cannot simply read the GOT to learn libc's base.

  IMMEDIATE (-z now / -Wl,-z,now):
    all relocations are resolved at load time. The GOT contains real
  addresses from the moment the program starts.

  THE RELRO ESCALATION:
    Partial RELRO  : GOT is writable at runtime (needed for lazy binding)
    Full RELRO     : .got.plt is marked read-only after resolution
    -> with Full RELRO you canno overwrite the GOT, so ret2plt dies and
       you need a different technique

This is the mechanical reason behind cs161-04's "Full RELRO → function
pointers, hooks, FSOP" line.

The GOT and the PLT

  GOT (Global Offset Table)  : an array of addresses, one per symbol
  PLT (Procedure Linkage Table): stubs that jump through GOT entries
  .got.plt                    : the PLT's part of the GOT, writable
  .got                        : the data pointers, usually RELRO

  call printf -> pushes the relocation index
              -> jumps to printf@plt
              -> jmp [printf@GOT]   <- an INDIRECT JUMP
                                   <- and indirect jumps are the
                                      entire basis of control-flow hijack

Reading the ELF

{
  echo "=== the header ==="
  readelf -hW ./somebinary | sed 's/^/  /'
  echo
  echo "=== program headers: what the loader maps ==="
  readelf -lW ./somebinary | sed 's/^/  /'
  echo
  echo "=== section headers: the toolchain's organisation ==="
  readelf -SW ./somebinary | sed 's/^/  /'
  echo
  echo "=== dynamic section: what the loader must resolve ==="
  readelf -dW ./somebinary 2>/dev/null | sed 's/^/  /'
  echo
  echo "=== symbols: names survived, and that is most of what you need ==="
  readelf -sW ./somebinary | head -20 | sed 's/^/  /'
  echo
  echo "=== relocations: unresolved references the linker filled in ==="
  readelf -rW ./somebinary 2>/dev/null | head -15 | sed 's/^/  /'
} 2>&1 | tee 01-elf.txt

How to read the header fields that matter

  Class          ELF64 or ELF32
  Type           EXEC (fixed base) or DYN (PIE - needs ASLR)
  Machine        x86-64 (EM_X86_64 = 62)
  Entry          the entry point address - where execution starts
  Section        where .text, .rodata, .got.plt actually are

  IF YOU KNOW ONLY ONE THING: read `Type`.
    EXEC  -> no PIE, addresses are fixed, your offsets are absolute
    DYN   -> PIE, the base is randomised, you need a leak

Stripped binaries, and how much you lose

  STRIPPED:  .symtab removed; dynamic symbols (.dynsym) usually survive
             IF the binary is dynamically linked

  WHAT SURVIVES STRIPPING:
    - all code
    - all data
    - all string constants
    - .dynsym (dynamic symbols) in a dynamically linked binary
    - the ELF header, program headers, section headers

  WHAT DOES NOT:
    - local function names
    - local variable names
    - static function symbols
    - debug info (a separate file: foo.debug, or DWARF in .debug_info)

  CONSEQUENCE FOR RE:
    stripped + static = the hardest case. You must recover structure
    from code alone.
    stripped + dynamic = you still have the imports, which tell you
    what the program does at a high level.

# What a strip actually removes, demonstrated
cat > /tmp/s.c <<'EOF'
#include <stdio.h>
int exported_helper(int x) { return x * 3; }
static int static_helper(int x) { return x + 1; }
int main(void) { printf("%d\n", exported_helper(static_helper(4))); return 0; }
EOF
gcc -O0 -g /tmp/s.c -o /tmp/s
strip --strip-debug /tmp/s        # keep dynamic symbols, drop local ones
strip /tmp/s                      # remove everything possible
for b in /tmp/s; do
  echo "  after strip: dynamic symbols still present"
  readelf -sW /tmp/s 2>/dev/null | grep -cE "FUNC" | xargs echo "    FUNC symbols:"
done
echo
echo "  A dynamically linked stripped binary keeps printf@GLIBC as a"
echo "  dynamic symbol. That single name tells you the program links libc"
echo "  and can therefore be ROP'd into it. The name survived stripping"
echo "  for exactly this reason."
rm -f /tmp/s.c /tmp/s

Terminology

Term Meaning
Preprocessor cpp: expands macros and includes
Object file (.o) Sections plus relocations plus symbols, not runnable
Relocation A reference to be patched at link or load time
Linker (ld) Resolves symbols across objects and libraries
Static linking Library code copied into the binary
Dynamic linking Library loaded at runtime by ld.so
PLT Procedure Linkage Table; jump stubs
GOT Global Offset Table; resolved addresses
Lazy binding Resolve a symbol on first call
Full RELRO GOT made read-only after resolution
PIE / ET_DYN Position-independent executable; needs a leak
Strip Remove symbol tables
DWARF Debug info format, usually in .debug_*
-O0 Unoptimised: spill everything, ideal for RE

# --- 1. build the same program at every optimisation level ---
cat > pipeline.c <<'EOF'
#include <stdio.h>
#include <stdlib.h>
int classify(int n) {
    if (n < 0)   return -1;
    if (n == 0)  return 0;
    if (n < 10)  return 1;
    return 2;
}
int main(int argc, char **argv) {
    int n = argc > 1 ? atoi(argv[1]) : 0;
    printf("%d\n", classify(n));
    return 0;
}
EOF

for O in 0 1 2 3 s; do
  gcc -O$O -no-pie pipeline.c -o pipe-O$O 2>/dev/null
done

{
  echo "=== the same source, five binaries, five different shapes ==="
  printf "  %-6s %-10s %s\n" "LEVEL" "TEXT BYTES" "STRUCTURE"
  for O in 0 1 2 3 s; do
    bytes=$(size pipe-O$O | awk 'NR==2{print $1}')
    nfun=$(objdump -d pipe-O$O | grep -cE "^\s+[0-9a-f]+ <")
    printf "  %-6s %-10s %s function bodies\n" "-O$O" "$bytes" "$nfun"
  done
  echo
  echo "  Then classify() itself, at -O0:"
  objdump -d --no-show-raw-insn pipe-O0 | sed -n '/<classify>:/,/ret/p' | sed 's/^/    /'
  echo
  echo "  ...and at -Os, which is what most distro binaries ship as:"
  objdump -d --no-show-raw-insn pipe-Os | sed -n '/<classify>:/,/ret/p' | sed 's/^/    /'
  echo
  echo "  Same behaviour. Completely different instruction sequence."
  echo "  This is why you learn RE on -O0 and then have to relearn it."
} 2>&1 | tee 01-opt.txt

# --- 2. inspect an object file - the artefact before the binary ---
{
  echo "=== pipeline.o: code + relocations + symbols, nothing runnable ==="
  gcc -O0 -c pipeline.c -o pipeline.o
  file pipeline.o | sed 's/^/  /'
  echo
  echo "  --- sections (the object file's table of contents) ---"
  readelf -SW pipeline.o | sed 's/^/  /'
  echo
  echo "  --- undefined symbols: what this file still needs ---"
  readelf -sW pipeline.o | awk '$7=="UND"{print "  "$0}' | sed 's/^/  /'
  echo
  echo "  --- relocations: 'put printf's address HERE' ---"
  readelf -rW pipeline.o | sed 's/^/  /'
  echo
  echo "  The object file cannot run. It is a description of what to build."
} 2>&1 | tee 02-object.txt

# --- 3. the linker, observed ---
{
  echo "=== link step: object + libc -> binary ==="
  echo "  (gcc pipeline.o -o linked   is shorthand for cc1 + as + ld)"
  echo
  echo "  what the linker RESOLVED:"
  readelf -rW linked 2>/dev/null | head -10 | sed 's/^/  /'
  echo "  ^ mostly empty now: the linker filled in the addresses."
  echo
  echo "  what the linker DECIDED:"
  readelf -hW linked | grep -E "Type|Entry" | sed 's/^/  /'
  echo
  echo "  and the dynamic entries that describe lazy resolution:"
  readelf -dW linked | sed 's/^/  /'
} 2>&1 | tee 03-link.txt

# --- 4. the GOT/PLT mechanism, demonstrated ---
{
  echo "=== the PLT stub for a lazily-bound function ==="
  objdump -d -j .plt -j .plt.sec linked 2>/dev/null | head -25 | sed 's/^/  /'
  echo
  echo "  Note the pattern:  push index ; jmp [resolver] ; ... jmp [GOT entry]"
  echo "  The second jmp is an INDIRECT JUMP. That is the whole basis of"
  echo "  ret2plt: you overwrite a GOT entry, and the next call goes there."
  echo
  echo "=== the GOT addresses themselves ==="
  objdump -R linked | head -12 | sed 's/^/  /'
  echo
  echo "=== PLT is a section you can find by name ==="
  readelf -SW linked | grep -E "\.plt|\.got" | sed 's/^/  /'
  echo
  echo "=== how big is the attack surface? ==="
  objdump -R linked | wc -l | xargs echo "  writable dynamic relocations:"
} 2>&1 | tee 04-gotplt.txt

# --- 5. RELRO: the escalation, measured ---
{
  echo "=== three builds, three RELRO postures ==="
  gcc -O0 -no-pie pipeline.c -o relro-none  2>/dev/null
  gcc -O0 -no-pie -Wl,-z,norelro pipeline.c -o relro-none  2>/dev/null
  gcc -O0 -no-pie -Wl,-z,relro pipeline.c -o relro-partial 2>/dev/null
  gcc -O0 -no-pie -Wl,-z,relro,-z,now pipeline.c -o relro-full 2>/dev/null

  printf "  %-14s %s\n" "BINARY" "RELRO STATUS"
  for b in relro-none relro-partial relro-full; do
    st=$(readelf -lW $b 2>/dev/null | grep GNU_RELRO >/dev/null && echo "has GNU_RELRO" || echo "no GNU_RELRO")
    bind=$(readelf -dW $b 2>/dev/null | grep -q BIND_NOW && echo "BIND_NOW (immediate)" || echo "lazy")
    printf "  %-14s %s, %s\n" "$b" "$st" "$bind"
  done
  echo
  echo "  CONSEQUENCE FOR EXPLOITATION:"
  echo "    no RELRO      -> GOT writable, ret2plt works"
  echo "    partial RELRO  -> .got.plt still writable, ret2plt still works"
  echo "    full RELRO     -> GOT read-only, ret2plt dead; need vtable,"
  echo "                     function pointers, or FSOP instead"
  echo
  echo "  This is the same escalation table cs161-04 gives, seen from the"
  echo "  linker rather than from the exploitation side."
} 2>&1 | tee 05-relro.txt

# --- 6. strip, and see exactly what you lose ---
{
  echo "=== before strip ==="
  gcc -O0 -g -no-pie pipeline.c -o full
  printf "  symbols: %s   sections: %s\n" \
    "$(readelf -sW full 2>/dev/null | grep -c FUNC)" \
    "$(readelf -SW full | grep -cE '^\s+\[')"
  echo "  classify present in .symtab? $(readelf -sW full | grep -c 'classify')"
  echo
  cp full stripped && strip stripped
  echo "=== after strip ==="
  printf "  symbols: %s   sections: %s\n" \
    "$(readelf -sW stripped 2>/dev/null | grep -c FUNC)" \
    "$(readelf -SW stripped | grep -cE '^\s+\[')"
  echo "  classify in .symtab?       $(readelf -sW stripped | grep -c 'classify')"
  echo "  classify in .dynsym?       $(readelf -sW --dyn-syms stripped 2>/dev/null | grep -c 'classify')"
  echo "  printf still visible?      $(readelf -sW --dyn-syms stripped 2>/dev/null | grep -c 'printf')"
  echo
  echo "  The local symbol is gone. The dynamic one survives, because the"
  echo "  loader needs it. That is why stripped dynamic binaries remain"
  echo "  partially self-describing."
} 2>&1 | tee 06-strip.txt

# --- 7. the RE starting point: functions first, never main ---
cat > 07-starting-point.md <<'EOF'
# Where to start in an unknown binary

```bash
# 1. the header. If Type is DYN, you are looking at a PIE binary.
readelf -hW ./binary | grep -E "Class|Type|Entry"

# 2. is it stripped?
file ./binary
readelf -sW ./binary | grep -c FUNC

# 3. dynamic symbols = the program's declared dependencies.
#    This is a table of contents for behaviour.
readelf --dyn-syms -W ./binary | grep FUNC | awk '{print "   ", $NF}' | head -20

# 4. imported functions tell you what the program DOES.
#    printf + fopen + strcmp + malloc = a text-processing CLI.
#    socket + bind + listen + accept    = a server.
#    This is triage, and it takes 30 seconds.

# 5. strings: your entry points and your data, all at once.
strings -a -t x ./binary | head -40

# 6. security posture before you reverse a single instruction
checksec --file=./binary

The order that works

  1. Header — 32 or 64 bit? PIE or not?
  2. Dynamic symbols — what does it import? That is a behaviour sketch.
  3. Strings — error messages are function descriptions written by
    the programmer; URLs and paths are targets; format strings are sinks.
  4. Security posture — checksec decides your whole exploit strategy.
  5. Functions — start at main, follow calls, work down.

Why strings before code

An error message like "failed to open %s" is a developer telling you what
the function does, with its arguments named. There is no source. This is
closer to source than any disassembly.
EOF
cat 07-starting-point.md
rm -f pipeline.c pipeline.o pipe-O linked relro- full stripped
```

Step 1 is the deliverable: the same source at five optimisation levels, with the actual
byte counts and function counts. It makes the argument concrete — you are not reverse
engineering "a program", you are reverse engineering a specific compilation of it.

Step 4 shows the PLT stubs and the GOT, which is the mechanical reason ret2plt exists
and why Full RELRO kills it.
