Security Principles and Threat Modeling

Summary

CS161 opens by insisting on a precise definition of security, because "secure" without a definition
is not a property you can reason about. The lecture's structure — principles, then crypto, then
memory safety, then exploitation, then OS, network, web, DoS — is itself the argument that most
vulnerabilities come from a small number of recurring mistakes.

Companion to mit858-01, which covers the same ground from the architecture side.
This note is the formal framing; that one is the systems framing.

The definition problem

"Secure" is not a binary property of a system. It is a relationship between three things:

SECURITY = ( system, adversary, goal )

secure(S, A, G)  :=  for every adversary A, S achieves goal G against A

Change any one of the three and the answer changes. The same binary is secure
against a random passerby and insecure against a root attacker. This is why
"is it secure?" is not answerable, and why every serious claim needs all
three terms.

The principles

1. Reachability determines exploitability

ATTACKER-CONTROLLED DATA -> PRIVILEGED OPERATION
         (input)                    (effect)

Almost every bug is some path that lets untrusted data influence a privileged
computation. Find the path, and you have found the bug class — regardless of
whether it is a buffer overflow, a SQL query, or a browser's parser.

2. No privilege without a validated boundary

If A can influence B's computation, that influence must be validated at
the boundary. Validation must be complete: a check that covers most cases is
a check that will be bypassed.

3. Minimize privilege

Every component should hold the least authority it needs. A parser with no
privilege cannot be used to gain privilege. This is the whole argument for
privilege separation.

4. Check assumptions at trust boundaries

Identities, authority, provenance and integrity all decay as they cross a
boundary. Verify them, do not infer them.

5. Fail closed

On error, deny. An open-by-default check is a vulnerability waiting for an
edge case.

6. Defence in depth

Assume any one control will fail. Two independent controls means one bug
does not yield a compromise.

A threat model you can actually write

1. What is the system? (components, entry points, data flows)
2. Who are the adversaries? (capability, reachability, motivation)
3. What are the assets? (what hurts if taken or corrupted)
4. What are the goals? (confidentiality / integrity / availability, per asset)
5. What are the assumptions? (and what breaks if each is false)
6. What is NOT in scope? (explicit, because the omission is the risk)

CS161's emphasis is step 6. Writing what you are not protecting is what
converts a vague worry into an actionable statement.

Terminology

Term Meaning
Security definition A precise statement relating system, adversary, goal
Adversary A party with a capability and a motive against you
Capability What the adversary can read, write, execute, observe
Reachability Whether the adversary can supply input at all
Trust boundary Where assumptions stop holding
Validation Complete checking at a boundary
Least privilege Minimum authority sufficient
Fail closed Deny on error
Defence in depth Independent controls, so one failure is not fatal
Asset Something whose loss causes harm

Field lab

Objective: write a complete threat model with an explicit out-of-scope section, and verify
each assumption against the running system.

mkdir -p ~/aegis/labs/cs161-01 && cd ~/aegis/labs/cs161-01

cat > model.md <<'EOF'
# Security definition

secure(S, A, G) — state it precisely:

  System    : <one sentence>
  Adversary : <capability, reachability, motivation>
  Goal      : <confidentiality / integrity / availability, per asset>

Restated: "Given <A>, <S> provides <G>."

## Assets
| Asset | Property | Value if lost | Location |
|---|---|---|---|
| SSH private key | C | critical | ~/.ssh/id_ed25519 |
| AEGIS notes + progress | I | high | ~/Projects/aegis-academy |
| git remote credentials | C,I | high | ~/.ssh (registered on GitHub) |
| machine availability | A | medium | this host |

## Adversaries
| Who | Capability | Reachable? | Wants |
|---|---|---|---|
| other host on my LAN | send TCP to my 0.0.0.0 listeners | yes if any exist | access |
| a web page I open | JS fetching my loopback services | yes, partially blocked | my dev services |
| a malicious package | arbitrary code as me | yes if I install it | everything I can read |
| someone with physical access | full | no (assumed) | disk |

## Goals
- C: private key never leaves the machine unencrypted to a network peer
- I: progress file cannot be altered without detection (git history)
- A: no service I depend on is taken down by a third party

## Assumptions I am relying on
- [ ] A1 no listener is bound to a non-loopback address
- [ ] A2 the SSH key has no passphrase, so physical access = full access
- [ ] A3 the git remote is private and this key is the only one registered
- [ ] A4 every package I install comes from the configured repos
- [ ] A5 my wireless is WPA2/WPA3 and the password is not on a sticky note

## Explicitly OUT of scope
- physical access to the machine (A2 accepted as a limitation, not solved)
- malicious firmware or a compromised kernel
- attacks requiring me to deliberately run hostile code
- the public Wi-Fi operator (I accept their traffic can be observed)

The out-of-scope list is the deliverable. Anything NOT listed here is a
finding I owe myself a defence for.
EOF

{
  echo "=== VERIFYING EACH ASSUMPTION ==="
  echo
  echo "--- A1: no listener on a non-loopback address ---"
  n=$(ss -tulpn | awk '$5 ~ /0\.0\.0\.0|\*/' | wc -l)
  ss -tulpn | awk '$5 ~ /0\.0\.0\.0|\*/ {print "    VIOLATION: " $1, $5, $7}'
  echo "    violations: $n   $([ "$n" -eq 0 ] && echo '(assumption holds)' || echo '(ASSUMPTION FAILS)')"
  echo
  echo "--- A2: SSH key protection ---"
  ls -l ~/.ssh/id_ed25519 2>/dev/null | sed 's/^/    /'
  echo "    unencrypted at rest (no passphrase) - documented as accepted risk"
  echo
  echo "--- A3: what is registered on my GitHub account ---"
  eval "$(ssh-agent -s)" >/dev/null 2>&1
  ssh -T git@github.com 2>&1 | head -1 | sed 's/^/    /'
  echo "    (key works; check github.com/settings/keys for anything unrecognised)"
  echo
  echo "--- A4: where do packages come from ---"
  grep -rhvE '^\s*(#|$)' /etc/apt/sources.list /etc/apt/sources.list.d/ 2>/dev/null | sed 's/^/    /'
  echo
  echo "--- A5: nothing listening that a page could reach ---"
  ss -tuln state listening | tail -n +2 | awk '{print "    ", $4}' | head -6
} 2>&1 | tee 01-assumptions.txt

# --- 6. reachability, demonstrated ---
cat > 02-reachability.md <<'EOF'
# Reachability, demonstrated

Three questions, in order:

1. **Can they send input at all?** (network reachability, file format, argument)
2. **Does it reach a parser?** (is there untrusted-data handling in the path)
3. **Does the parser influence a privileged operation?** (is that output used)

Most "vulnerability reports" fail at step 1. Most real exploits are found by
answering all three in order.

## The consequence for testing
- If step 1 fails, stop. No amount of step-3 creativity helps.
- If step 1 succeeds and step 2 fails, you found a dead input path — still a
  finding (the parser may be added later).
- Steps 2 and 3 together are the actual attack.

## The consequence for architecture
Every control should be placed at the cheapest reachable point. Validating at
the boundary is cheaper than detecting downstream, and cheaper than relying on
the parser being correct.
EOF
cat 02-reachability.md

# --- 7. the principles, applied to your own machine ---
cat > 03-principles.md <<'EOF'
# The principles, applied to this host

| Principle | On this host |
|---|---|
| No privilege without a validated boundary | sudo rules are the boundary; `sudo -n -l` shows them |
| Minimize privilege | my daily account is non-root with sudo; nothing runs as root that need not |
| Check assumptions at trust boundaries | the scope guard in every AEGIS script is a validated boundary |
| Fail closed | aegis scripts exit 3 and refuse on an out-of-scope target |
| Defence in depth | loopback binding + scope guard + ROE document |
| Reachability determines exploitability | `ss -tulpn` decides what is even worth reviewing |

## Where this machine fails its own principles
- Nothing enforces the scope guard: a script that omits it will scan whatever
  it is given. The guard is convention, not a control.
- The SSH key is unencrypted at rest, so A2 is a real gap rather than a
  documented risk.
- There is no integrity checking, so a compromised package is undetectable
  after the fact (this is Tier 6's detection-engineering problem).

An honest threat model names its own failures. This one has three.
EOF
cat 03-principles.md
echo
echo "Fill in model.md, then record your three failures in 03-principles.md."

Step 3 is the honest part: writing down the three ways this machine fails its own threat
model. A threat model that identifies no weaknesses is a document, not an analysis.
