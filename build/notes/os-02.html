C and gdb

Summary

Exploit development happens in C, and understanding it happens in gdb. This lecture covers what
you need about the C language that matters for memory safety — not the whole language — and how
to drive a debugger well enough to watch a stack frame being built.

This is the most practically important lecture in 6.S081. If you skip it, lectures 4-7 become
memorisation instead of comprehension.

The C parts that cause vulnerabilities

Pointers and manual memory

int  x = 5;
int *p = &x;     // p holds the ADDRESS of x
*p = 10;         // x is now 10

char buf[32];
char *q = buf;   // q points at the START of the array
q + 5            // points 5 bytes in - still inside the array
q + 40           // still a valid POINTER, but now out of bounds

The single most important C fact for security: the language does not know your array's size.
q + 40 is a perfectly legal pointer expression. It is the programmer's job to check bounds, and
C will never check it for you.

The dangerous functions

Function Problem Safe-ish replacement
strcpy No destination size limit strncpy + explicit null termination
strcat No size limit on append strncat
gets Cannot be used safely, ever fgets
sprintf Can overflow the destination snprintf
scanf("%s") No width limit scanf("%10s", ...)
memcpy Length is the caller's problem check first

strcpy, strcat and gets are how buffer overflows are born. You will see them in lecture 4.

Undefined behaviour

Anything the C standard does not specify is "undefined behaviour", and the compiler may do
anything — including removing your bounds check.

int n = 32;
char buf[n];
// VLA (variable length array) is a GCC extension, not standard C

Practical consequence: -O2 can delete a check it decides is redundant. This is why exploit
code is compiled at -O0 and why "the check was there" is not a defence.

Arrays, structs and the stack

struct user {
    int  uid;
    char name[32];
};                 // 36 bytes: 4 + 32, no padding surprise here

void greet(char *input) {
    char buf[32];        // 32 bytes of stack
    strcpy(buf, input);  // if input is longer -> overwrites saved RBP and return address
}

That function is the entire lecture 4 exploit.

gdb: the workflow

gcc -g -O0 -fno-stack-protector -no-pie -z execstack vuln.c -o vuln
gdb ./vuln
Command Meaning
break main / b *0x401136 Breakpoint at a function / address
run / start Execute / run to main
next / n Step over
step / s Step into
finish Run until the current function returns
continue / c Run to next breakpoint
print x / p x Print a variable
p/x $rsp Print in hex
info registers All registers
x/16xb $rsp 16 bytes at an address, hex
x/4gx $rbp 4 quadwords at a frame pointer
backtrace / bt Call stack
disassemble main Assembly for a function
info functions All symbols
delete breakpoints Clear them all

The session you will actually have

(gdb) break *main
(gdb) run
(gdb) disassemble main
(gdb) break *0x4011a6          # the call instruction
(gdb) continue
(gdb) info registers rsp rbp rip
(gdb) x/16gx $rsp
(gdb) p/x $rbp
(gdb) x/s $rdi
(gdb) bt
(gdb) quit

Write down the rsp/rbp values. On x86-64 the stack grows downward, so higher addresses are
older frames. Your buffer sits at low addresses near rsp.

Terminology

Term Meaning
Pointer A variable holding an address
Dangling pointer Points at freed or out-of-scope memory
Buffer overflow Writing past the end of a buffer
Stack frame Per-function region: locals, saved RBP, return address
Return address Where execution resumes after ret
ret instruction Pops the saved address into RIP
Breakpoint Pause point; INT3 (0xCC) in software
Watchpoint Pause when an address changes
Undefined behaviour Anything the standard does not specify
PIE Position-independent executable; randomised base
NX Non-executable stack/heap
ASLR Randomised load addresses

# --- static analysis while you type ---
gcc -Wall -Wextra -Wformat-security -fsanitize=address -g vuln.c -o vuln-asan

gcc -fanalyzer -Wall vuln.c -o /dev/null

# --- valgrind: precise memory errors ---
valgrind --leak-check=full --track-origins=yes ./vuln

Field lab

Objective: write a vulnerable C function, compile it three ways, and watch the stack frame
under gdb.

mkdir -p ~/aegis/labs/os-02 && cd ~/aegis/labs/os-02

cat > vuln.c <<'EOF'
#include <stdio.h>
#include <string.h>

void vulnerable(const char *input) {
    char buffer[32];
    strcpy(buffer, input);          /* the bug */
    printf("copied: %s\n", buffer);
}

int safe(const char *input) {
    char buffer[32];
    strncpy(buffer, input, sizeof(buffer) - 1);
    buffer[sizeof(buffer) - 1] = '\0';   /* explicit termination */
    printf("copied safely: %s\n", buffer);
    return 0;
}

int main(int argc, char **argv) {
    if (argc < 2) { fprintf(stderr, "usage: %s <string> [safe]\n", argv[0]); return 1; }
    if (argc > 2 && argv[2][0] == 's') return safe(argv[1]);
    vulnerable(argv[1]);
    return 0;
}
EOF

# --- build: weak, default, hardened ---
gcc -Wall -Wextra -g -O0 -fno-stack-protector -no-pie -z execstack vuln.c -o vuln-weak
gcc -Wall -Wextra -g -O0 vuln.c -o vuln-default
gcc -Wall -Wextra -g -O0 -fstack-protector-strong -D_FORTIFY_SOURCE=2 -pie -fPIE vuln.c -o vuln-hard

{
  for b in vuln-hard vuln-default vuln-weak; do
    echo "=================================="
    echo "$b"
    echo "=================================="
    file ./$b; checksec --file=./$b 2>/dev/null; echo
  done
} | tee 01-hardening.txt

# --- the observable difference ---
SHORT=$(python3 -c 'print("A"*20)')
LONG=$(python3 -c 'print("A"*200)')
./vuln-hard   "$SHORT"; echo "hard/short:   $?"
./vuln-hard   "$LONG";  echo "hard/long:    $?"
./vuln-default "$LONG";  echo "default/long: $?"
./vuln-weak   "$LONG";  echo "weak/long:    $?"
./vuln-weak   "$SHORT" safe; echo "safe version: $?"

# --- the gdb session ---
gdb -q --batch \
  -ex 'break main' -ex 'run' \
  -ex 'info registers rsp rbp rip' \
  -ex 'disassemble main' \
  -ex 'break vulnerable' -ex 'run' \
  -ex 'info registers rsp rbp' \
  -ex 'x/48xb $rbp-32' \
  -ex 'print buffer' \
  -ex 'bt' \
  -ex 'finish' \
  ./vuln-weak "$LONG" 2>&1 | tee 02-gdb-trace.txt

echo "In 02-gdb-trace.txt, compare rsp vs rbp."
echo "buffer is at LOW addresses (near rsp). The return address sits just ABOVE rbp."

# --- let a tool find it for you ---
gcc -g -fsanitize=address vuln.c -o vuln-asan 2>/dev/null
./vuln-asan "$LONG" 2>&1 | head -15 | tee 03-asan.txt
echo "AddressSanitizer pinpointed the overflow in one line. That is the whole job."

# --- static analysis ---
cppcheck --enable=warning,style,security vuln.c 2>&1 | head -10 | tee 04-cppcheck.txt

Step 3 is the whole lecture in miniature. buffer occupies 32 bytes; immediately above it sit
the saved frame pointer and the return address. Overwriting those is the return address you already
saw in kr-*/ms-05, now under your control.

Record: in your scratchpad, write the exact byte offsets: where buffer starts, where the
saved RBP sits, where the return address sits. ex-03 depends on these numbers.

Self-test

  2. Name three functions that cannot be used safely and their replacements.
  3. Why can the compiler delete a bounds check?
  4. What does x/16xb $rsp print, and what are x, i, s short for?
  5. On x86-64, is the buffer at a higher or lower address than the return address?
