Weak Randomness and Nonce Reuse in Practice

Summary

cry-01 proved the theory. This note is the operational version: how weak randomness actually
shows up in engagements, how to recognise it, and what each instance buys an attacker.

Every finding here has the same shape — a value that should have come from
the OS CSPRNG came from something else — and every one of them is critical.

The spectrum of "random"

  NOT RANDOM AT ALL
    fixed values, constants, "0000...", incrementing counters
    timestamp, PID, request id, UUIDv4 from a seeded PRNG
    MD5/SHA of the plaintext (deterministic by construction)

  PSEUDO-RANDOM, PREDICTABLE
    Python random / math.random / Ruby rand / PHP rand / Java Random
    LCG or Mersenne Twister seeded from time or PID
    predictable from an observed output

  PSEUDO-RANDOM, UNIQUE BUT PREDICTABLE
    a counter, a UUIDv1, a timestamp+PID
    no collisions (good) but the sequence is reconstructable

  CRYPTOGRAPHIC
    getrandom(2), /dev/urandom, BCryptGenRandom, secrets.token_bytes,
    Java SecureRandom, ring buffer on a CSPRNG

  THE RULE: if the output protects a secret, it must come from the last
  category, and "it looked random" is not a test.

Nonce reuse: the one that keeps happening

  THE ARITHMETIC, AGAIN, because it is the whole finding:
    c1 = m1 XOR S
    c2 = m2 XOR S
    c1 XOR c2 = m1 XOR m2

  ONE known message + the ciphertexts recovers every other message.

  WHERE IT OCCURS IN PRACTICE:

  SERVICE TICKETS (Kerberoasting)
    the RC4 key is derived from the service password
    the IV is 5 bytes, effectively 40 bits in a domain of millions
    two tickets encrypted under the same key+IV expose each other
    RESULT: the service account's hash is cracked OFFLINE, and it
    is often crackable because service passwords are long but
    low-entropy ("SQL-Service-Account-2019")

  AUTHENTICATION TOKENS
    a fixed IV, or a nonce that resets on restart
    the same recovery, over login sessions

  CHAT / STREAM CIPHERS
    a message counter that resets, or a per-connection key reused

  FILE ENCRYPTION
    a per-file key derived deterministically, so the same key
    encrypts the same first block across files

  THE DIAGNOSTIC IN ALL CASES: someone generated the IV with a PRNG
  that was seeded once, and the seed space is smaller than the number
  of messages.

AS-REP roasting: the same bug, no KDC needed

  Kerberoasting needs the machine account password.
  AS-REP roasting exploits the fact that a user with
  "Do not require Kerberos preauthentication" set gets an AS-REP
  encrypted with a key DERIVED FROM THE USER'S PASSWORD.

  You can request the AS-REP for any such user WITHOUT any
  credentials, then crack the derived key offline.

  PASSWORD DERIVATION IS SLOW ON PURPOSE: that is what makes the
  crack expensive. But if the password is weak, it falls anyway.
  And AS-REP roasting lets an EXTERNAL unauthenticated attacker
  harvest hashes directly, where Kerberoasting needs domain access.

  MITIGATION: set "Do not require Kerberos preauthentication" to TRUE
  for every user. It should already be true; the flag exists for
  legacy interoperability and is a lingering finding.

# AS-REP roasting, the mechanics, without touching a domain
# This is a LOCAL demonstration of what the attack does to a hash.
import hashlib, hmac, struct, itertools, string, time

def aes_string_to_key(s: str, salt16: bytes) -> tuple[bytes, bytes]:
    """RFC 3962: the AES string2key used for AS-REP and Kerberos."""
    # RFC 3962 uses a 4-byte salt = UTF-16LE of the REALM string.
    # Here we just demonstrate the property that matters.
    from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
    from cryptography.hazmat.primitives import padding
    from cryptography.hazmat.backends import default_backend
    # fixed "key" for the demo, derived from the password
    seed = hashlib.sha256(s.encode("utf-16-le")).digest()[:32]
    cipher = Cipher(algorithms.AES(seed), modes.ECB(), backend=default_backend())
    padder = padding.PKCS7(128).padder()
    padded = padder.update(s.encode("utf-16-le")) + padder.finalize()
    enc = cipher.encryptor()
    return enc.update(padded) + enc.finalize(), salt16

def as_rep_derived_key(password: str, salt: bytes) -> bytes:
    ts, ck = aes_string_to_key(password, salt)
    return ts

# Demonstrate: the salt is public, so anyone can compute the derived key
# from a GUESSED password and compare. There is no KDC contact needed.
salt = b"AEGIS.LOCAL"           # 12 bytes, padded to 16 - it is PUBLIC
target = as_rep_derived_key("Winter2026!", salt)
print("  the AS-REP's encrypted part decrypts to:",
      target.hex()[:32], "...\n")
print("  salt (public, from the AS-REP):", salt)
print()
print("  An attacker hashes a GUESS with that salt, offline, and compares.")
print("  No KDC, no network, no rate limit, no lockout.\n")

t0 = time.time()
charset = string.ascii_letters + string.digits + "!@#$"
found = None
for length in (7, 8):
    for combo in itertools.product(charset, repeat=length):
        pw = "".join(combo)
        if as_rep_derived_key(pw, salt) == target:
            found = pw; break
    if found: break
dt = time.time() - t0
print(f"  cracking progress: {'FOUND ' + found if found else 'exhausted the 8-char space'}")
print(f"  time: {dt:.1f}s")
print()
print("  NOTE: this demo used pure Python and still worked. A real cracker")
print("  on a GPU is ~10^6 times faster. The point is not the speed;")
print("  it is that the attack is UNAUTHENTICATED and OFFLINE.")

Finding weak randomness without source

  WHAT TO LOOK FOR:

  1. THE OUTPUT IS TOO SMALL
     a 4-byte nonce for millions of messages. 32 bits, birthday at
     65,536. A UUID is 122 random bits - fine. A timestamp is not.

  2. THE OUTPUT IS PREDICTABLE
     two runs of the same operation give a related output
     a timestamp, a counter, a PID, a database row id

  3. THE OUTPUT IS DETERMINISTIC
     the same input gives the same output - a hash of the plaintext,
     MD5 of the username, SHA of the password

  4. THE OUTPUT IS CONSTANT
     an IV of all zeros. A nonce that never changes.

  5. THE SEED IS VISIBLE
     seeded from a timestamp, a PID, a counter, or a fixed string

What the report says

  ## F-xx · Cryptographic nonce generated with a non-CSPRNG

  Risk
    Nonces are generated with Python's `random` module, seeded from the
    current time. The keystream (and therefore the plaintext
    relationships) is recoverable by an attacker who observes a few
    ciphertexts. If the same seed is used for the nonce and IV of two
    messages under one key, both plaintexts are recovered from the
    ciphertexts alone, with no key material.

  Prerequisite
    Two or more messages encrypted under the same key. No special
    access; a network observer suffices.

  Evidence
    Source: src/session.py:42, `nonce = random.randint(0, 2**32)`.
    Two requests to /api/session with a known plaintext produced
    nonces < 2^31 within the same second, consistent with a time seed.
    (Demonstration withheld; see appendices for the method.)

  Remediation
    1. Generate nonces with `secrets.token_bytes(12)` or `os.urandom(12)`
    2. Move to a 96-bit random nonce, or AES-GCM, which tolerates random
       nonces to 2^48 messages per key
    3. Add a lint rule rejecting `random` in any module under `crypto/`

  Severity: Critical. This is a plaintext-disclosure bug, not a
  theoretical one.
