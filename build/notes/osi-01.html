OSINT Methodology and the Framework as a Checklist

Summary

OSINT frameworks are usually taught as diagrams. That is the wrong use of one. A framework's
actual value is as an exhaustive checklist — a way to guarantee you did not forget the
obscure source that holds the answer.

The framing: a framework tells you what to look at, not how to think
about what you find. The thinking is a separate discipline, and it
is the one that makes OSINT an investigation rather than a search
engine tour.

Companion to tcm-02 (the operational version) and osi-02 (the
highest-yield technique). This note is the method.

What OSINT is, and the line that matters

  OSINT = intelligence gathered from publicly available sources.

  THE TEST, and it is one question:
      did you LEARN it, or did you MAKE someone give it to you?

    LEARNED  -> OSINT. A DNS record, a leaked config, a job ad.
    GIVEN    -> social engineering. Persuading a person is a
                different activity with a different authorisation
                and often a different legal position.

  WHY THE LINE MATTERS OPERATIONALLY:
    - the ROE usually permits the first and not the second
    - consent is required for the second in most jurisdictions
    - the second creates a relationship and a record with the target
    - and the second is how engagements become incidents

The five-step methodology

  1. DEFINE THE QUESTION, precisely
     "What do we know about lab.internal?"
     is not a question. "What subdomains does it have, which of them
     resolve to a non-current IP range, and which of those hosts a
     service that was retired" is a question you can finish.

  2. SELECT SOURCES, deliberately
     not "everything in the framework". Pick the three or four
     sources that plausibly hold the answer, and say why each.

  3. COLLECT, with provenance
     every fact gets: what it is, when it was observed, and the
     exact URL or query that produced it.
     A fact you cannot re-derive is a rumour.

  4. PROCESS: correlate, deduplicate, verify
     the joins are the work. Two identical strings found in two
     places are one identity, not two findings.

  5. PRESENT, with confidence and with gaps
     "confirmed", "probable", "possible" and "unverified" are four
     different labels and they must appear on the output.

The confidence labels, which are the whole discipline

  CONFIRMED     you observed it directly, this session, and you can
                show the query or the URL

  PROBABLE      two or more independent sources agree, or one source
                is authoritative and the inference is direct

  POSSIBLE      one source, plausible, not corroborated. State which
                source and why you believe it.

  UNVERIFIED    a rumour, a breach corpus claim, an aggregator's
                unsourced assertion. Never in a deliverable body;
                at most in an appendix with the caveat.

  THE RULE: an OSINT deliverable where every fact is "confirmed" is
  usually wrong - real intelligence is rarely that clean. An
  assessment where everything is "possible" has not been verified.
  The distribution is the quality signal.

The framework as a checklist

  HOW TO USE ONE, which is not how most people use one:

  BAD   Read the framework. Note the categories. Feel organised.
        Test nothing. Miss the answer, which was in the category you
        skimmed because you thought you had covered it.

  GOOD  Print the categories. Go down them one at a time, in the
        order of likelihood. For each, write ONE LINE: "does this
        source apply here, and if so what would I learn?"
        Mark each: applicable / not applicable / already covered.

  THE PAYOFF IS SPECIFIC: the answer to a real OSINT question is
  almost never in the two categories you thought of first. It is in
  "Transport" or "Archives & Records" or "Social Media" - the
  categories that feel irrelevant and that you skipped.

  AND THE ARTIFACT IS THE POINT: the completed checklist goes in
  the deliverable's appendix. It is the proof of coverage, and it is
  what lets a client tell you were thorough from what you were
  lucky.

The categories that actually pay

mkdir -p ~/aegis/labs/osi-01 && cd ~/aegis/labs/osi-01
mkdir -p findings raw

cat > 01-checklist.md <<'EOF'
# OSINT coverage checklist

> Work down this. For each line, write "applies / n-a / covered" and
> one sentence of what you learned or expect. The completed version
> goes in the deliverable appendix as the coverage proof.

## 1. THE TARGET ITSELF
- [ ] Apex domain, WHOIS / RDAP, registration date, registrar
- [ ] DNS: A, AAAA, MX, NS, TXT (SPF, DMARC, CAA, verification)
- [ ] ASN and netblocks. WHO OWNS the IP range?
- [ ] Certificate Transparency: every hostname EVER issued
- [ ] Historical DNS: what pointed here before?
- [ ] Reverse DNS on every address

## 2. THE INFRASTRUCTURE (tcm-02's technique, expanded)
- [ ] Cloud/CDN/WAF provider, and what that implies
- [ ] Subdomains by certificate
- [ ] Subdomains by DNS brute force (wordlist, in scope)
- [ ] Subdomains by passive sources (crt.sh, RapidDNS, bufferover)
- [ ] Non-standard ports from a passive banner database
- [ ] Historical subdomains that no longer resolve - WHICH MAY STILL BE LIVE

## 3. THE PEOPLE AND IDENTITIES
- [ ] Email format, from a public source (not by guessing)
- [ ] Named employees, from public sources only
- [ ] Breach corpus presence for corporate addresses
-      ^ RECORD WHICH BREACH AND WHICH FIELDS. NEVER THE HASH.
- [ ] Public code for the domain name: configs, keys, endpoints
- [ ] Public documents: PDFs, spreadsheets, presentations
-      ^ these leak org structure, versions, and internal naming

## 4. THE ARCHITECTURE (from public error messages and documents)
- [ ] Stack disclosure: server banners, error pages, JS bundles
- [ ] Framework versions from /static/ paths in search results
- [ ] API endpoints in public JavaScript source maps
- [ ] Internal hostnames in error messages, headers, certificates

## 5. THE SOCIAL MEDIA AND PEOPLE SEARCH
- [ ] Company pages: hiring posts, product posts, incident posts
- [ ] Employee posts about internal tooling
- [ ] Past employees, and where they went
      ^ a former employee's public repo is a common find

## 6. THE ARCHIVES AND RECORDS
- [ ] Wayback Machine: retired pages, retired endpoints
- [ ] Search engine caches of old error pages
- [ ] Public pastebins, git repos, and issue trackers
- [ ] Job postings: the tech stack, and sometimes the versions

## 7. THE DARK WEB (only if in scope, only the index)
- [ ] Paste sites, breach aggregators
- [ ] ^ IF NOT IN SCOPE: do not go. The ROE decides.

## 8. THE ORGANISATION'S OWN DISCLOSURE
- [ ] Security policy, bug bounty scope and exclusions
      ^ THE BUG BOUNTY SCOPE IS AN AUTHORISATION DOCUMENT.
        Test what is in it and nothing else, if you act within it.
- [ ] Published incident reports and lessons learned
- [ ] Regulatory filings and breach notifications

## 9. THE SUPPLY CHAIN
- [ ] Third-party providers with network access
- [ ] Cloud storage buckets under their name
- [ ] Vendors named in job ads and documentation

## Completed?
- [ ] Every line marked
- [ ] Every finding has: a label (confirmed/probable/possible/unverified),
      an observation time, and the exact query or URL
- [ ] The joins are recorded: fact A (source 1) + fact B (source 2)
      = identity C
EOF
echo "written: 01-checklist.md"

cat > 02-labels.md <<'EOF'
# Labelling every fact

```yaml
# findings/example.yaml - the format, and it is deliberately annoying
- id: F-001
  fact: "The domain resolves to 203.0.113.10, which is in an AS
         announced by Example Hosting, not by the organisation."
  confidence: confirmed
  observed_at: 2026-10-14T09:14:22Z
  source: "dig A lab.internal"
  repeatable: yes            # anyone can re-run this exact command

- id: F-002
  fact: "The subdomain legacy.lab.internal is present in CT logs
         from 2021 and does not currently resolve."
  confidence: confirmed
  observed_at: 2026-10-14T09:16:03Z
  source: "https://crt.sh/?q=lab.internal"
  repeatable: yes

- id: F-003
  fact: "The host 203.0.113.10 answers on 8080 and returns a page
         titled 'Admin Console', which is not referenced by any
         known application."
  confidence: probable
  observed_at: 2026-10-14T09:41:10Z
  source: "curl -sI https://203.0.113.10:8080/"
  repeatable: yes
  caveat: "may be a honeypot; the fingerprint is unverified"

- id: F-004
  fact: "Three corporate email addresses appear in a public breach
         corpus, in a breach dated 2019."
  confidence: probable
  observed_at: 2026-10-14T10:02:55Z
  source: "<redacted> - breach corpus, presence only"
  repeatable: no            # you are NOT downloading the corpus
  handling: "Existence and breach date only. No hashes, no passwords,
             no data retained. Deleted from the working set after
             recording."

# the discipline, as a check
grep -c "observed_at:" findings/*.yaml | sed 's/^/  labelled facts: /'
grep -L "observed_at:" findings/*.yaml | sed 's/^/  MISSING A TIMESTAMP: /'
grep -L "source:" findings/*.yaml | sed 's/^/  MISSING A SOURCE: /'

  THE RULE THAT MAKES THIS WORK:

    a fact with no observed_at is not a finding, it is an impression
    a fact with no repeatable source is not reproducible, it is a
      claim
    and a deliverable with both is a document nobody can check.

EOF
cat 02-labels.md

--- the offline concept: the join ---

python3 - <<'PY' 2>&1 | tee 03-joins.txt
print(" === the join is the work, and it is where OSINT differs from searching ===\n")
print(" A SEARCH finds facts. AN INVESTIGATION finds RELATIONSHIPS.\n")
print(" THE THREE JOINS THAT ACTUALLY PAY:\n")
print(" 1. CT LOG + HISTORICAL DNS")
print(" CT says: 'legacy.lab.internal had a certificate in 2021'")
print(" HDNS says: 'legacy.lab.internal resolved to 203.0.113.10 in 2022")
print(" and stopped resolving in 2023'")
print(" THE JOIN: the host is forgotten but the IP range may still be")
print(" theirs, and a forgotten host is the unpatched one.")
print()
print(" 2. PUBLIC CODE + EMAIL FORMAT")
print(" GitHub says: 'a repo contains .env.example with DB_HOST='")
print(" A paste says: 'a config leaked the DB_PASSWORD'")
print(" THE JOIN: the naming convention, the internal hostname, and the")
print(" credential for a system you now know the name of.")
print()
print(" 3. JOB POST + ERROR MESSAGE + CERTIFICATE SAN")
print(" Job post says: 'we run Elasticsearch 8.x'")
print(" Error page says: 'elasticsearch cluster yellow health'")
print(" Cert says: '*.search.lab.internal'")
print(" THE JOIN: a named Elasticsearch instance on a named subdomain.")
print(" None of the three gives you that alone. All three together do.")
print()
print(" THE DISCIPLINE: a join is a HYPOTHESIS until every input is")
print(" confirmed. Record each input with its own label, and label the")
print(" join with the LOWEST-confidence input.")
print()
print(" (if any input is 'possible', the join is 'possible'. This is")
print(" boring and it prevents the deliverable from asserting things")
print(" that turn out to be wrong.)")
PY
cat 03-joins.txt
```

Step 3 is the deliverable: the three joins that actually pay — CT log × historical DNS,
public code × email format, and job post × error page × certificate SAN — with the rule that a
join inherits the lowest-confidence label of any of its inputs. Boring, and it stops the
deliverable asserting things that turn out to be wrong.

01-checklist.md is the framework-as-checklist done properly: every line gets
applies / n-a / covered plus one sentence, and the completed version goes in the appendix as
coverage proof. The note's claim is specific — the answer is almost never in the two categories
you thought of first.

02-labels.md gives the four confidence labels and the finding format, with a grep check that
flags any fact missing a timestamp or a source.
