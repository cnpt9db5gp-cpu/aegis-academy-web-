psexec, wmiexec and smbexec for Remote Execution

Summary

Remote execution is how an engagement moves. Impacket has five ways to do it and the choice
matters — each leaves a different artifact in the client's logs and touches a different part of
the host.

The framing: every remote execution method writes something somewhere. The question is not
"which is stealthy" but "which artifact, and does the ROE permit it."

AUTHORISATION. These run a command on a host you are engaged to
test. That requires explicit scope; "credential testing" alone is not
sufficient. All examples target the lab range.

The five, compared

  TOOL        MECHANISM            WRITES        SERVICE?  NEEDS
  ------------------------------------------------------------------------
  psexec      creates a service    a service     YES       admin or SYSTEM
                            (ADMIN$ to upload the binary)
  smbexec     runs a command       a .exe in     no        admin or SYSTEM
              via a service        ADMIN$ or C$
  wmiexec     WMI Win32_Process    nothing on   no        admin (remote WMI
              Create               disk          (no
                                       service)     9)
  dcomexec    DCOM Service Control nothing on   YES       admin
              Manager - to start   disk
              a temporary service
  atexec      a scheduled task     nothing on   no        admin
                                          disk          (a task)

  AND THE INTERACTIVE ONE:
  evil-winrm  WinRM (5985/5986)   nothing on   no        the right privilege
              - a real PowerShell  disk          (WinRM    and a shell
                                must be enabled)
              session

  THE RANKING, for an assessment:
    1. evil-winrm      - interactive, no artifact, no service. Best UX.
    2. wmiexec         - no file on disk, no service. Cleanest of the
                         SMB-based ones.
    3. atexec          - creates a task, but tasks are normal and
                         self-cleaning.
    4. psexec          - the standard. Creates a service (7045 in the
                         log) and uploads a binary to ADMIN$.
    5. smbexec         - worst. Writes an executable into ADMIN$ or C$
                         that is left behind.

```text
  REMOTE EXECUTION IS A WRITE TO A HOST. It requires:
    [ ] the host is in the written scope
    [ ] the ROE permits remote execution (it is not implied by
        "credential testing")
    [ ] you know whether it creates a service (7045 in the client's
        logs) and whether they will call about it
    [ ] you know whether it writes a file to ADMIN$ or C$ - that is a
        change to their disk that you must clean up
    [ ] if you run it as SYSTEM on a DC, you know what that does to
        their monitoring

  AND: it is the step most likely to BREAK something. A command that
  assumes a path, a tool, or a locale that is not there is an outage.
  Prefer commands that are read-only (whoami, hostname, systeminfo)
  until you are sure the host is in a known state.
```
EOF

cat > exec.sh <<'EOF'
#!/usr/bin/env bash
# Wraps the five remote-execution methods with the scope guard and
# prints the artifact each one leaves.
set -euo pipefail
H="${1:?usage: ./exec.sh <lab-ip> <domain/cred> [method] [command]}"
CRED="${2:?domain/cred, e.g. LAB/alice:LabPass123}"
METHOD="${3:-whoami}"
CMD="${4:-whoami}"
case "$H" in 192.168.56.*|10.10.10.*|127.*) ;;
  *) echo "REFUSED: $H not in the lab range." >&2; exit 3 ;; esac
case "$CRED" in LAB/*|lab.internal/*) ;;
  *) echo "REFUSED: $CRED is not a lab domain credential." >&2; exit 3 ;; esac

case "$METHOD" in
  psexec)  echo "[method] psexec   -> creates a SERVICE (event 7045), uploads a binary to ADMIN\$"
           echo "[method]            -> cleans up the service, leaves the upload briefly"
           impacket-psexec -no-passback -dc-ip "$H" "$CRED@$H" "$CMD" ;;
  smbexec) echo "[method] smbexec  -> writes an .exe to ADMIN\$/C\$ and LEAVES IT if it crashes"
           echo "[method]            -> least preferred"
           impacket-smbexec -no-passback -dc-ip "$H" "$CRED@$H" "$CMD" ;;
  wmiexec) echo "[method] wmiexec  -> no file on disk, no service. WMI Create only"
           echo "[method]            -> needs remote WMI (port 135/49664) enabled"
           impacket-wmiexec -no-passback -dc-ip "$H" "$CRED@$H" "$CMD" ;;
  dcomexec) echo "[method] dcomexec -> creates a service via DCOM, then deletes it"
           impacket-dcomexec -no-passback -dc-ip "$H" "$CRED@$H" "$CMD" ;;
  atexec)  echo "[method] atexec   -> creates a SCHEDULED TASK, runs, deletes"
           echo "[method]            -> tasks are normal and visible in Task Scheduler"
           impacket-atexec -no-passback -dc-ip "$H" "$CRED@$H" "$CMD" ;;
  winrm)   echo "[method] winrm    -> a real interactive PowerShell. No artifact."
           command -v evil-winrm >/dev/null 2>&1 || { echo "install evil-winrm"; exit 1; }
           evil-winrm -i "$H" -u "${CRED%%:*}" -p "${CRED##*:}" ;;
  *) echo "methods: psexec smbexec wmiexec dcomexec atexec winrm" >&2; exit 1 ;;
esac
EOF
chmod +x exec.sh

cat > 02-artifacts.md <<'EOF'
# What each method leaves, and where the client sees it

| Method | Disk | Service | Log events | Cleanup |
|---|---|---|---|---|
| psexec | binary in ADMIN$ (removed after) | yes, transient | 7045, 4698/4702 (psexesvc) | automatic |
| smbexec | .exe in ADMIN$ or C$ | yes | 7045 | **manual - may persist** |
| wmiexec | none | no | 4688 (WmiPrvSE), 1 (WinRM host) | automatic |
| dcomexec | none | yes, transient | 7045, 4698 | automatic |
| atexec | none | no | 4698/4702 (a task), 4699 | automatic |
| evil-winrm | none | no | 4624 type 3, 21 (WinRM) | automatic |

## The ones to check after

AFTER ANY REMOTE EXECUTION, ON EVERY HOST YOU TOUCHED:

Windows (on the host, as admin):
  Get-ChildItem \\ADMIN$\\ -Filter *.exe | Select Name, LastWriteTime
  Get-ChildItem \\C$\\Windows\\Temp\\ | Where LastWriteTime -gt (Get-Date).AddHours(-1)
  Get-ChildItem \\C$\\Windows\\Temp\\ -Filter *.bat -Recurse -EA 0
  Get-SmbOpenFile          # who has a handle open right now

The cleanup is the client's filesystem. Leaving an executable in
ADMIN$ is a change you must either remove or report.


## The commands to run first

```text
  Start with read-only. whoami /all, hostname, ipconfig /all.
  You are confirming:
    - who the command actually ran as (admin? SYSTEM? a service?)
    - that the host is the host you think it is
    - the network position, for pivoting (ad-06)
  Every one of these is non-destructive. A command that fails because
  of a missing path is an outage you caused.

What does NOT need remote execution

  If you only need to READ something, do not execute anything:

    psexec - just read a file
      smbclient '//LAB/alice%pass@HOST/C$' -c 'get ADMIN\web.config'
      impacket-secretsdump -sam SAM -security SECURITY -system SYSTEM ...

    psexec - list the local administrators
      netexec smb HOST -u alice -H <hash> --local-auth

    psexec - check for delegation
      netexec smb HOST -u alice -p pass --delegation

    psexec - enumerate sessions on the host
      netexec smb HOST -u alice -p pass --enum-sessions

  A command that creates a service to run `dir` is a service created
  to run `dir`. Every unnecessary remote execution is a finding you
  created.

EOF

cat > 03-matrix.sh <<'EOF'

!/usr/bin/env bash

Read-only across the lab range. NO remote execution.

Use this to decide WHERE execution is needed, not as a substitute for it.

H="${1:?usage: ./03-matrix.sh 192.168.56.20}"
U="${2:-alice}"; P="${3:-LabPass123}"
case "$H" in 192.168.56.|10.10.10.|127.) ;;
) echo "REFUSED: $H not in the lab range." >&2; exit 3 ;; esac
echo "[scope] $H in the lab range; read-only"
echo
echo "=== 1. who am I here, and what rights do I have? ==="
lookupsid.py "LAB/$U:$P@$H" 2>/dev/null | head -3 | sed 's/^/ /'
echo
echo "=== 2. is this host a DC? (lookupsid against a DC behaves differently) ==="
nxc smb "$H" -u "$U" -p "$P" --enum-domain-trusts 2>&1 | sed 's/^/ /'
echo
echo "=== 3. delegation - unconstrained means I can capture TGTs here ==="
nxc smb "$H" -u "$U" -p "$P" --delegation 2>&1 | sed 's/^/ /'
echo
echo "=== 4. sessions - who is logged in HERE right now (imp-03 material) ==="
nxc smb "$H" -u "$U" -p "$P" --enum-sessions 2>&1 | sed 's/^/ /'
echo
echo "=== 5. local admin - whose hash gets me SYSTEM here ==="
nxc smb "$H" -u "$U" -p "$P" --local-auth 2>&1 | sed 's/^/ /'
echo
echo "=== 6. what can I read without executing anything? ==="
nxc smb "$H" -u "$U" -p "$P" --shares 2>&1 | sed 's/^/ /'
echo
echo "=== THE ORDER OF USE ==="
echo " 1. run this matrix over the lab range (read-only, no services)"
echo " 2. look for: a DC, unconstrained delegation, sessions, writable"
echo " shares, local admin"
echo " 3. ONLY THEN execute, and only on the hosts where execution"
echo " buys you something this matrix did not"
echo " 4. evil-winrm first, smbexec last"
EOF
chmod +x 03-matrix.sh
```

03-matrix.sh is the deliverable. The entire point of this note is on that line: "A
command that creates a service to run dir is a service created to run dir." Six read-only
checks — delegation, sessions, local admin, shares, trust — and only then execution, and only
where it buys something the matrix didn't.

02-artifacts.md maps each method to the exact log event the client will see (7045 for the
service, 4698 for the task) and to its cleanup behaviour, including that smbexec may leave an
executable in ADMIN$ if it crashes — which is a change to their disk you either remove or
report.
