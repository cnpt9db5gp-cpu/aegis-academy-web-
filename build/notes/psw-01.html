Apprentice Track Walkthroughs: Core Vulnerability Classes

Summary

The PortSwigger Academy video walkthroughs are the same vulnerabilities as ps-01..ps-03, but
demonstrated end-to-end on the official labs. The value here is process: watching how a
practitioner moves from a URL in the sitemap to a confirmed finding, rather than learning the
payload from a list.

The thing to take from this note is not the payloads. You have those. It is
the sequence: enumerate, form a hypothesis, test with the minimum
request, capture evidence, write it up while you still remember.

Companion to ps-01, ps-02 and ps-03. Those are the theory; this is
the walkthrough discipline.

The walkthrough loop

  1. ENUMERATE          what is here? (sitemap, directory listing, JS files,
                        robots.txt, the app's own links)
  2. MAP THE INPUTS      every parameter, header, cookie, body field, path
                        segment, and where it is rendered
  3. FORM A HYPOTHESIS   "this value is reflected in HTML, unencoded"
  4. PROVE IT            the smallest request that shows the effect
  5. ESCALATE            from reflection to execution to impact
  6. CAPTURE             request, response, screenshot, redacted
  7. WRITE IT UP         before you forget what you actually sent
  8. RESET               clean up, and verify you cleaned up

Step 8 is the one apprentices forget and professionals never do.

SQL injection, the walkthrough

  OBSERVATION    the product page takes ?productId=1 and renders
                 "Welcome back!" for some values. Others 404.

  HYPOTHESIS     the value is being concatenated into a query.

  MINIMUM PROOF  productId=1            -> "Welcome back!"
                 productId=2            -> 404
                 productId=1'           -> SQL error / 500   <- injection confirmed
                 productId=1 OR 1=1--   -> every product     <- impact demonstrated

  THE ORDER MATTERS:
    1' first proves it. If it 404s cleanly, the input may be validated
    or may be numeric-only. You learn that from the FIRST test, not the last.

  CAPTURE
    - the exact URL
    - both responses (the error one and the OR one)
    - a note that no data was extracted, only the row count demonstrated

  REPORT
    "ProductId is concatenated into a SQL query. A single quote causes an
     error; ' OR 1=1-- returns all products, so the entire catalogue is
     readable without authentication. Root cause: string concatenation in
     the product handler. Fix: parameterised query."

XSS, the walkthrough

  OBSERVATION    the search page reflects your query.

  HYPOTHESIS     the reflection is unencoded, and the page sets a cookie.

  MINIMUM PROOF  search?q=<img src=x onerror=alert(document.domain)>
                 -> the alert fires. That is the proof.

  ESCALATE       1. can you reach a cookie?   document.cookie
                 2. is it HttpOnly?            if not, it is stealable
                 3. can you make the payload persistent?  (stored)
                 4. does a CSP block it?       check the header

  CHECK THE CONTEXT, not just the tag
    <script> not firing does not mean "not vulnerable".
    Try: <img src=x onerror=...>, <svg onload=...>, then "><img ...>,
    then javascript:alert(1) in an href.

  THE ESCALATION THAT MATTERS
    Reflected + HttpOnly cookie  -> Medium (phishing-grade)
    Reflected + no HttpOnly      -> High  (session theft)
    Stored    + no HttpOnly      -> Critical (anyone who visits)

  CAPTURE the raw request and response, with the payload visible.

Path traversal, the walkthrough

  OBSERVATION    /files?filename=report.pdf

  HYPOTHESIS     unsanitised path concatenation.

  MINIMUM PROOF  /files?filename=../../../etc/passwd   -> the file's contents

  THE PROBES, in order:
    ../                  -> does it work at all?
    ..%2f                -> encoding around a filter?
    ....//               -> a filter that collapses once
    ..%252f              -> double encoding
    /etc/passwd          -> absolute, sometimes unfiltered entirely
    ....\/               -> backslashes

  ESCALATE       can you read application source?  -> it may contain a secret
                 can you reach .env, .git/config, or a backup file?
                 can you read something the WEB SERVER can execute?
                   -> php://filter/convert.base64-encode/resource=index.php

  REPORT the highest-impact file you read, redacted, and stop there.

Access control, the walkthrough

  OBSERVATION    you are logged in as a normal user. Another account exists
                 (or you can register one).

  HYPOTHESIS     objects are addressed by a client-supplied id.

  MINIMUM PROOF  GET /download?id=1  -> your document
                 GET /download?id=2  -> THEIR document    <- confirmed

  THE METHODOLOGY THAT FINDS IT
    1. map every endpoint with an identifier
    2. request your own object
    3. request your SECOND ACCOUNT's object with the same request
    4. also try: a GUID you did not receive, a negative id,
       id=0, id=9999999

  CHECK ALSO
    - the UI hides /admin? request it directly
    - is the check client-side? (a disabled button is not a check)
    - can you reach the admin API directly?

  CAPTURE one redacted request and response. Never fetch their full data.

Common beginner mistakes, and their fixes

  MISTAKE                         FIX
  --------------------------------  ----------------------------------------
  trying payloads in order of     work the CONTEXT: attribute payloads in
  fame                           attributes, URL payloads in URLs
  stopping at "it reflects"      demonstrate the EFFECT: alert fires, row
                                 returns, file downloads
  extracting all the data        prove and stop. The client needs the proof,
                                 not the table
  no second account               register one. It is the whole method.
  no evidence captured            screenshot the request AND response
  reporting the tool's name       report the vulnerability; a scanner name
                                 is not a finding
  no cleanup                      delete what you created, verify it is gone
  rating everything Critical      state the prerequisite. A finding on an
                                 unreachable service is not Critical.

The evidence standard

  A finding with a reproducible request is worth 10x one that says
  "we were able to access another user's invoice."

  INCLUDE:
    the exact request (headers and body)
    the exact response (status, relevant headers, redacted body)
    the account context (which account, which role)
    the prerequisites, stated
    a redacted screenshot as a human-readable copy

  EXCLUDE:
    real credentials, tokens, session cookies
    other users' personal data, even one row
    anything you did not actually observe

Self-test

  1. Name the eight steps of the walkthrough loop.
  2. What is the minimum proof for SQL injection, and why does 1' come first?
  3. Why does an XSS payload failing in one context not mean it is safe?
  4. What turns a reflected XSS from Medium into Critical?
  5. Why is a second account essential to access-control testing?
  6. What does a reproducible request add that a screenshot does not?
  7. Why should you extract the minimum data and stop?
  8. What must never go in a report?
