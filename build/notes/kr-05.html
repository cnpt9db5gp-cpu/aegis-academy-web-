Keeping Kali Current Without Breaking It

Summary

Kali is a rolling release: there is no version to upgrade to, only a repository that is
always in motion. apt update && apt upgrade on Kali can change thousands of packages across a
few hundred megabytes and — because Kali tracks upstream quickly — can occasionally leave you with
a mismatched library that breaks one tool.

This is the most common way new Kali users lose their environment. This lecture is about doing it
safely.

How a rolling upgrade actually differs from Debian

Debian stable Kali rolling
Upgrade size Occasionally large, then quiet for months Potentially large any day
Library versions Frozen for the release lifetime Track upstream within days
apt upgrade Safe, predictable Usually safe; occasionally a tool breaks
Risk Very low Low, but non-zero and hard to predict
Recovery Install an older ISO Restore a snapshot or rollback

The safe routine

# 1. See what is actually going to happen, BEFORE it happens
sudo apt update
apt list --upgradable 2>/dev/null | wc -l       # how many packages
apt-get -s upgrade | tail -20                   # -s = SIMULATE. Read it.

# 2. If the simulated upgrade touches something alarming (a kernel, libc, metasploit
#    framework), stop and snapshot the VM first.

# 3. Upgrade
sudo apt upgrade

# 4. Reboot if a new kernel was installed
# (uname -r before and after will tell you)

# 5. VERIFY — this is the step everyone skips
python3 -c "import scapy; print('scapy ok')"
msfconsole -q -x "version; exit" 2>/dev/null | head -5
nmap --version | head -2
john --list=formats | head -3

Things that genuinely break on rolling Kali

  • Kernel upgrades — a new kernel plus an old out-of-tree driver (some VPN and Wi-Fi drivers)
    means no wireless. sudo apt install linux-headers-$(uname -r) is the usual fix.
  • Metasploit Framework and its database — msfdb init repairs a broken database; a major
    framework update occasionally wants a fresh database anyway.
  • Python packaging collisions — pip install as root fights apt for the same libraries.
    The fix is isolation, covered in py-* and linux-privesc-doctrine.
  • Removal of a tool you relied on — Kali tracks upstream renames and removals.

The correct way to install a Python tool on Kali

This matters so much it gets its own lecture (pipx), but the short version:

# WRONG - fights the system interpreter, breaks apt eventually
sudo pip install some-tool
pip install some-tool --break-system-packages

# RIGHT - isolated, uninstallable, cannot break the OS
pipx install some-tool
some-tool --version

# ALSO RIGHT - per-project isolation
python3 -m venv ~/aegis/venvs/some-tool
source ~/aegis/venvs/some-tool/bin/activate
pip install some-tool
deactivate

Kali commands

# --- dry run: the most important command on a rolling distro ---
sudo apt update
apt-get -s upgrade            # simulate, print, change nothing
apt-get -s full-upgrade       # simulate including removals
apt list --upgradable | head -20

# --- what is holding packages back? ---
apt-mark showhold
apt-get -s dist-upgrade | grep -E '^(Remv|The following)'

# --- clean up, safely ---
sudo apt autoremove
sudo apt clean                # clears the package cache, frees space

# --- kernel and reboot bookkeeping ---
uname -r
dpkg -l 'linux-image*' | grep ^ii | awk '{print $2}'
ls /boot

# --- after an upgrade, sanity-check the toolchain ---
for t in nmap nc curl wget python3 pipx git gdb objdump; do
  printf "%-10s %s\n" "$t" "$(command -v $t || echo MISSING)"
done

# --- repair common breakages ---
sudo apt install --reinstall python3-pip python3-venv
msfdb init          # if metasploit db is broken
sudo apt update --allow-releaseinfo-change

# --- is this repo even sane? ---
apt-cache policy | head -30
grep -rhv '^#' /etc/apt/sources.list /etc/apt/sources.list.d/ 2>/dev/null | grep -v '^$'

Field lab

Objective: practise a safe upgrade cycle, and produce a baseline fingerprint of your
toolchain so you can tell immediately what a bad update did.

mkdir -p ~/aegis/labs/kr-05 && cd ~/aegis/labs/kr-05

# --- BASELINE: fingerprint every tool before touching anything ---
{
  echo "=== BASELINE $(date -Iseconds) ==="
  echo "kernel: $(uname -r)"
  echo "python: $(python3 --version)"
  for t in nmap nc netcat socat curl wget git gdb objdump radare2 sqlmap hydra john hashcat john metasploit msfconsole gobuster ffuf nikto; do
    p=$(command -v "$t" 2>/dev/null)
    if [ -n "$p" ]; then
      v=$("$t" --version 2>&1 | head -1)
      printf "%-14s %-40s %s\n" "$t" "$p" "$v"
    else
      printf "%-14s %s\n" "$t" "NOT INSTALLED"
    fi
  done
} | tee 01-baseline.txt

# --- NOW SIMULATE (changes nothing) ---
sudo apt update
apt list --upgradable 2>/dev/null | tail -n +2 | wc -l | xargs echo "packages upgradable:"
apt-get -s upgrade 2>/dev/null | grep -E '^(Inst|Remv)' | head -40 | tee 02-simulated.txt
apt-get -s upgrade 2>/dev/null | grep -c '^Inst' | xargs echo "would upgrade:"
apt-get -s upgrade 2>/dev/null | grep -c '^Remv' | xargs echo "would REMOVE:"

# --- Safety check: is a kernel or libc in that list? ---
grep -E 'linux-image|libc6|python3 ' 02-simulated.txt && \
  echo ">>> KERNEL/LIBC IN PLAY: snapshot the VM before proceeding" || \
  echo "No kernel/libc in this batch - routine upgrade"

# --- Disk headroom before you start ---
df -h / | tail -1

# --- Hold list is usually empty; if not, this is why ---
apt-mark showhold

Then, if and only if you have a VM snapshot: run sudo apt upgrade, reboot, and re-run the
fingerprint loop, diffing against 01-baseline.txt:

# after the upgrade - rerun the exact same fingerprint loop above,
# redirecting to a second file. Do not retype it: the point of the
# comparison is that both files came from identical code.
#   { ...the loop from step 1, unchanged... } > 02-after.txt
# Uncomment and run the loop itself here; the shell cannot expand
# "...same loop..." and the block below is a diff, not a program.
diff 01-baseline.txt 02-after.txt

Record: keep 01-baseline.txt permanently. When a tool mysteriously stops working in three
months, this file is the first thing you will want.
