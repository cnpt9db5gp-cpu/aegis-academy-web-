Phishing Analysis and Awareness (Defensive)

Summary

This note is about detecting phishing, not about sending it. Phishing analysis is a defensive
skill with a clean authorisation line: analysing a suspicious message that arrived is always
permitted; sending one is social engineering and needs a separate, explicit authorisation.

The framing: a phishing email is a document with an embedded
executable attachment, and it leaves the same forensic traces any
other malicious document does. The analysis is the document
analysis from osi-03, plus headers.

Companion to osi-03 (documents) and osi-05 (the consent
boundary). This note is the defensive analysis.

The authorisation line

  ALWAYS PERMITTED, no authorisation needed
    - analysing a message that arrived in your own or your
      organisation's mailbox
    - reporting it internally
    - detonating it in a sandbox you control
    - blocking the indicators

  REQUIRES EXPLICIT WRITTEN AUTHORISATION
    - sending a test message to real people
    - a phishing simulation campaign
    - any pretexting, even to a "friendly" internal contact

  NEVER PERMITTED without written authorisation AND a named
  stakeholder who has decided
    - anything that reaches a real person who did not consent

  THE SIMULATION QUESTION, and it is asked in every organisation:
    a phishing simulation is a security awareness control. It is also
    a dataset of which employees clicked, which is sensitive personal
    data about individual performance, and in some jurisdictions it
    needs its own legal basis.

    IF YOU ARE RECOMMENDING ONE, the recommendation includes:
      - a legal opinion, not just a security one
      - a data-handling plan for the click data, including retention
      - a non-punitive framing, because a punitive one suppresses
        reporting of real phishing
      - a plan for what happens to someone who clicks

cat > 01-headers.sh <<'EOF'
#!/usr/bin/env bash
# Header analysis of a message you RECEIVED.
# This is analysis of an inbound artefact. It sends nothing to anyone.
M="${1:?usage: ./01-headers.sh <message.eml or header text>}"
echo "=== 1. THE AUTHENTICATION RESULTS (the summary) ==="
if command -v spamassassin >/dev/null 2>&1 && [[ "$M" == *.eml ]]; then
  spamassassin -t < "$M" 2>&1 | grep -E "^[0-9.]+ |points|described" | sed 's/^/  /'
fi
echo
echo "=== 2. THE HOP CHAIN ==="
echo "  Received: from X by Y with ESMTP id Z; <date>"
grep -i "^received:" "$M" 2>/dev/null | sed 's/^/  /'
echo
echo "  READ THIS ORDERING. The top header is the most recent hop and"
echo "  was added by the receiving server. The BOTTOM is the closest"
echo "  to the sender. A hop claiming to be internal, above a hop"
echo "  claiming to be external, in the wrong order, is the signature"
echo "  of a spoofed Received header added by the sender's server."
echo
echo "=== 3. RETURN-PATH vs FROM (the classic) ==="
grep -iE "^(return-path|from|sender|reply-to):" "$M" | sed 's/^/  /'
echo
echo "  ^ From: the display name and address the user sees."
echo "    Return-Path: where bounces go, set by the SENDER."
echo "    Reply-To: where a reply goes."
echo "    All three differing is not proof, but it is a question."
echo
echo "=== 4. AUTHENTICATION RESULTS, IN DETAIL ==="
grep -iE "^(authentication-results|received-spf|dkim-signature|arc-authentication-results|arc-seal|domainkey-signature)" "$M" \
  | cut -c1-160 | sed 's/^/  /'
echo
echo "  spf=pass       the sending IP is authorised for the domain"
echo "  spf=fail       it is NOT. Combined with a visible From: of"
echo "                 the client, that is spoofing."
echo "  dkim=pass      the message is signed and it verifies"
echo "  dkim=none      the domain does not sign. Perfectly normal."
echo "  dkim=fail      the signature broke in transit. Or was"
echo "                 stripped. Or was forged."
echo "  dmarc=pass     the sending domain's policy was satisfied"
echo "  dmarc=fail     it was not, and the receiving MTA applied"
echo "                 whatever policy the domain publishes"
echo
echo "  NOTE the spf/dkim/dmarc pattern. A real message from a"
echo "  domain that publishes all three passes all three. A spoofed"
echo "  one fails at least one, and commonly fails dmarc with"
echo "  spf=softfail."
echo
echo "=== 5. THE BODY, AS TEXT ONLY ==="
grep -iE "^(subject|from|date|reply-to|return-path|message-id|x-mailer|user-agent)" "$M" \
  | cut -c1-120 | sed 's/^/  /'
echo
echo "=== 6. THE LINK TEXT vs THE LINK TARGET ==="
echo "  (copy the href and the visible text out by hand; they are"
echo "   usually both visible in the raw source, and a mismatch is"
echo "   the whole trick)"
echo
echo "  Look for:"
echo "    - a visible URL that differs from the href"
echo "    - a href with a different registrable domain"
echo "    - a URL with an @ (user@evil.com), a lookalike character"
echo "      (rn for m, 0 for O), or an unexpected subdomain depth"
echo "    - a shortened URL that does not expand to the expected host"
echo
echo "=== 7. THE ATTACHMENT ==="
grep -iE "^(content-type|content-disposition|filename)" "$M" | sed 's/^/  /'
echo
echo "  A PDF with a zip filename, a .doc that is really a .exe, an"
echo "  archive with a password, or an .html attachment are all"
echo "  findings. Check the attachment's REAL type with 'file'."
EOF
chmod +x 01-headers.sh

cat > 02-analysis.md <<'MD'
# The indicator set, and how to report it

```text
  WHAT TO EXTRACT FROM A SUSPICIOUS MESSAGE

    HEADERS
      the authentication verdict (spf / dkim / dmarc)
      the reply-to, if different from the from
      the message-id, and the date

    LINKS
      every href, and the visible text
      every URL, resolved ONCE, and where it goes
      ^ resolve it yourself. A phishing domain's TLS certificate is
        free information and sometimes self-signed with the
        campaign name in it.

    ATTACHMENTS
      sha256 (never md5 alone)
      file type, and the type it CLAIMS
      size
      ^ do not open it. Analyse the container (osi-03's script).

    INFRASTRUCTURE
      the sending IP, its ASN, its reverse DNS, its geolocation
      the subject line's specificity (a generic subject is a
      campaign; a specific one is a spearphish)

    BEHAVIOURAL
      does it create urgency?
      does it ask for credentials?
      does it reference something you would know (a project name,
      a person's name, a recent event)?
      is the greeting generic ("Dear User") or specific?

  THE REPORT, which is short by design

    Subject: [Verdict] - [verdict in one word] - [date]

    VERDICT: phishing | suspicious | benign | inconclusive
      "inconclusive" is a real answer and it is better than a guess.

    WHAT MADE IT SUSPICIOUS
      the specific indicators, with evidence

    WHAT TO DO
      block the sender, the domain, the URL, the hash
      report it internally
      if anyone entered credentials, reset that account and revoke
      the sessions (this is the important line)

    WHAT NOT TO DO
      forward it to colleagues "so they know"
      ^ that spreads it. Block and report. If awareness training is
        needed, use a sanitised version with the indicators removed.
```
MD

Step 3 is the deliverable: the indicator weight table, including the last row — a phishing
email from the client's own domain is more likely a compromised mailbox than a typo-squat, and
that is an incident with a completely different response, not a phishing report.

And the asymmetry: a false "phishing" call destroys trust in the whole channel — and if the
report is wrong often enough, the true ones get ignored, which is exactly when someone clicks
one. But a false "benign" call is how a real credential theft succeeds quietly.
