Exploitation and Mitigations

Summary

CS161's exploitation lecture takes the bugs from the previous lecture and asks a precise
question: given a vulnerability and a set of mitigations, what can an attacker actually do?
The answer is a chain, and the chain's shape is determined by the mitigations present.

Companion to ex-01..ex-06 and mit858-04. This note is the reasoning
about chain construction; those are the mechanics.

The modern exploit chain

  1. FIND         a memory-corruption bug
  2. LEAK         defeat ASLR / PIE / canary
  3. CONTROL      choose what the corrupted pointer points at
  4. EXECUTE      achieve the primitive you need
  5. ESCALATE     turn it into privilege or data access

Every step after 1 exists because a mitigation blocked the previous shortcut.
Modern exploits are long because mitigations are layered.

Choosing the primitive

You control Primitive Achieves
A return address ROP chain Arbitrary code execution from existing gadgets
A function pointer Call to a chosen address Execution
format string Arbitrary read, then %n write Read/write primitives
An uninitialised buffer Information disclosure ASLR bypass
Heap metadata Write-what-where Arbitrary write

The primitive determines the technique. Mitigations do not change what you
control; they change how you use it.

Mitigations, restated as constraints

Mitigation Constraint it imposes Workaround
Canary You cannot write past the canary without corrupting it Leak it first
NX Stack/heap are not executable ROP, ret2libc, or jump to executable memory
PIE + ASLR Code addresses are unknown Leak a code or libc pointer
Full RELRO GOT is read-only Function pointers, hooks, FSOP
Safe functions No unbounded copies Find a different function
CET / shadow stack Return addresses are checked against a shadow copy Need a write to the shadow stack

Why shadow stacks are interesting

CET adds a shadow stack: a separate, hardware-protected copy of the return
addresses. ret must match it, so a corrupted rsp is caught.

Consequence: classic stack smashing stops working even with every other
mitigation bypassed. The attacker must instead find a way to write to the
shadow stack — which is where ROP's gadget requirements change and where
JOP/SROP become relevant.

This is the current state of the arms race, and it is why the "just spray
the stack" era is over.

What CS161 expects you to reason about

Given a binary and an attacker capability, produce:

  1. The bug class and its location
  2. What the attacker can corrupt
  3. Which mitigations must be defeated, and in what order
  4. The information leak needed
  5. The primitive that becomes available
  6. What is still not possible even after that

Step 6 is the one students skip. There is almost always a step 6.

Terminology

Term Meaning
Exploit chain The full sequence from bug to objective
Primitive A capability gained from corruption
Arbitrary read / write Read/write any address
ROP Chain of ret-terminated gadgets
ret2libc Call libc functions, no injected code
Shadow stack / CET Hardware-protected copy of return addresses
JOP Dispatch through a gadget table
SROP Forge a signal frame to control all registers
ASLR bypass Leaking a base address
Mitigation bypass Defeating one specific control
Exploitability Whether a bug is reliably exploitable, given mitigations

Kali commands

# --- the decision procedure, applied to a binary ---
cat > triage.sh <<'EOF'
#!/usr/bin/env bash
# Given a binary and a corruption primitive, what is the chain?
B="${1:?usage: ./triage.sh ./binary <primitive>}"
P="${2:-return address}"
echo "=== BUG CLASS AND PRIMITIVE ==="
printf "  binary   : %s\n" "$B"
printf "  primitive: %s\n" "$P"
echo
echo "=== PROTECTIONS PRESENT (these set the constraints) ==="
checksec --file="$B" 2>/dev/null | grep -E "canary|NX|PIE|RELRO|Fortify|Shadow" | sed 's/^/  /'
echo
echo "=== CHAIN THIS IMPLIES ==="
NXC=$(checksec --file="$B" 2>/dev/null | grep -c "NX disabled")
PIEC=$(checksec --file="$B" 2>/dev/null | grep -c "No PIE")
CANC=$(checksec --file="$B" 2>/dev/null | grep -ci "canary: found")
SHADOW=$(checksec --file="$B" 2>/dev/null | grep -ci "shadow")
[ "$CANC" -gt 0 ] && echo "  1. canary present  -> leak it (over-read or format string)"
[ "$PIEC" -eq 0 ] && echo "  2. PIE + ASLR      -> leak a code or libc address"
[ "$NXC" -eq 0 ] && echo "  3. NX enabled      -> ROP / ret2libc, no stack shellcode"
echo "  4. primitive        : $P"
if [ "$SHADOW" -gt 0 ]; then
  echo "  5. SHADOW STACK     -> classic ret2libc will abort; need a write to the shadow stack"
else
  echo "  5. execute          -> ROP chain into libc"
fi
echo "  6. STILL NOT POSSIBLE:"
echo "       - without a leak, no address is known"
echo "       - heap primitives are usually a separate leak-then-write chain"
echo "       - kernel privileges need a separate escalation entirely"
EOF
chmod +x triage.sh

cat > target.c <<'EOF'
#include <stdio.h>
#include <string.h>
#include <unistd.h>
void win(void) { write(1, "win\n", 4); }
void vuln(void) { char b[48]; read(0, b, 200); }
int main(void) { vuln(); return 0; }
EOF
gcc -g -O0 -fno-stack-protector -no-pie -z execstack target.c -o target-weak
gcc -g -O0 -fstack-protector-strong -pie -fPIE target.c -o target-hard

./triage.sh ./target-weak "return address" | tee 01-triage.txt
echo
./triage.sh ./target-hard "return address" | tee -a 01-triage.txt

# --- measure what each mitigation actually costs ---
echo
echo "=== the performance cost of hardening, measured ==="
{
  printf "  %-28s %s\n" "binary" "startup"
  for b in target-weak target-hard; do
    t=$( { /usr/bin/time -f "%e" ./$b </dev/null >/dev/null; } 2>&1 )
    printf "  %-28s %s s\n" "$b" "$t"
  done
  echo
  echo "  In practice: canaries ~1%, PIE ~0%, RELRO ~0%, shadow stacks 1-5%."
  echo "  The cost is low. The reason it is not universal is historical,"
  echo "  not economic - except for microsecond-critical code paths."
}

# --- shadow stack availability on this machine ---
echo
echo "=== CET / shadow stack support here ==="
grep -oE "shadow_stack|ibt|user_shstk" /proc/cpuinfo | sort -u | sed 's/^/  /' || echo "  no CET flags"
command -v gcc && gcc -Q --help=common 2>/dev/null | grep -E "cf-protection|mshstk" | head -3 | sed 's/^/  /'

# --- the four steps, each demonstrated ---
echo
echo "=== step 2: the leak, in isolation ==="
cat > leak.c <<'EOF'
#include <stdio.h>
#include <unistd.h>
int main(void) {
    char b[128];
    read(0, b, sizeof(b));       /* over-read, no write: no abort */
    write(1, b, sizeof(b));      /* print whatever follows, including the canary */
    return 0;
}
EOF
gcc -g -O0 -fstack-protector leak.c -o leak
python3 - <<'PY' | tee 02-leak.txt
import subprocess, struct
r = subprocess.run(["./leak"], input=b"A"*72, capture_output=True, timeout=5)
out = r.stdout
print(f"  sent 72 bytes, received {len(out)} bytes back")
if len(out) > 72:
    canary = out[72:80]
    print(f"  bytes 72-80 (the canary): {canary.hex()}")
    print(f"  as a qword            : {struct.unpack('<Q', canary)[0]:#018x}")
    print(f"  low byte              : {canary[0]:#04x}  (0x00 == a real canary)")
PY
rm -f leak.c leak

Step 1 is the deliverable: triage.sh turns a binary plus a primitive into the specific
chain required, including the step that is still not possible. That script is reusable on any
assessment.

Self-test

  3. What does Full RELRO prevent you from overwriting, and what are three alternatives?
  4. What is a shadow stack, and why does it break classic ret2libc?
  5. What is a technique you still cannot use after defeating everything?
