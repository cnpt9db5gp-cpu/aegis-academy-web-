Passive Reconnaissance and OSINT Collection

Summary

The first stage of an engagement is to build a picture of the target without touching it.
Passive recon is what you can learn from data that already exists — DNS records, certificate
transparency logs, public code, breach corpora, job ads, documents, and the archive of the web.

The discipline point: passive recon has no footprint on the target. Nothing logs it,
nothing alerts, nothing gets rate-limited. That is why it happens first and why it is free.

Companion to ccna-01/ccnad-01 for the protocol mechanics of what you
are reading. This note is about the sources and how to weigh them.

The sources, ranked by yield

Source What it tells you Cost
Certificate Transparency logs Every hostname the org has ever issued for free, no contact
DNS records A, AAAA, MX, NS, TXT, SPF, DMARC free, no contact
ASN / WHOIS Netblocks, hosting, ownership free
Historical DNS / Wayback Retired hosts, forgotten subdomains free
Search engines Docs, configs, credentials, error pages free
Public code search Credentials, keys, config files, endpoints free
Breach corpora Which usernames and passwords are already known varies
Job ads Technology, versions, culture, org structure free
Email / error formats Mail server, org name, internal hostnames free
ASN & CDN attribution Where is this actually hosted free
Shodan / Censys / FOFA Banner, service, and often version data free tier

The most valuable single source is almost always CT logs. It gives you
a complete, non-intrusive inventory of every hostname an organisation has ever
had a certificate for, including the ones they have since forgotten.

OSINT, defined honestly

  OSINT = intelligence gathered from publicly available sources

  It is NOT:
    - pretexting (lying to a person to get information)
    - social engineering (manipulating a person)
    - unauthorised access to anything

  The line: did you learn it, or did you make someone give it to you?
  Learning it = OSINT. Persuading someone = social engineering, which is a
  different engagement with a different authorisation.

The tradecraft

  1. START NARROW    one domain, one organisation, one identifier
  2. GO WIDE         expand outward: domains -> subdomains -> emails ->
                     usernames -> people -> more identities
  3. RECORD EVERYTHING in a structured format, immediately
  4. CORRELATE       an email address found in a breach corpus and a
                     username from an AD dump is one identity, not two
  5. VERIFY          stale data is common; confirm before acting
  6. STAY PASSIVE    do not touch the target's infrastructure

Step 4 is where beginners stop. A pile of unlinked strings is not
intelligence. The value is in the joins.

From domains to people: the identity chain

  domain          example.com
    -> CT logs    dev.example.com, vpn.example.com, legacy.example.com
    -> DNS        legacy -> 203.0.113.9 (still live, forgotten, unpatched)
    -> MX/TXT     mail handled by mtaservice.net, SPF includes _spf.google.com
    -> search     "example.com filetype:pdf" -> an internal org chart
    -> code       github search "example.com" -> a repo with a config file
    -> breaches   support@ found in a corpus, with a password hash
    -> usernames  jsmith, a.smith, j.smith - which convention?
    -> people     the org chart names roles; the convention gives accounts

The forgotten legacy host is the entire point. Assets nobody maintains are
the most likely thing in the estate to be exploitable, and you found it
without sending a single packet.

What to do with what you find

  FINDING                          TELL IT TO THE CLIENT, NOT THE WORLD
  -------------------------------- ----------------------------------
  Exposed credential in a public   as a critical finding, redacted. Never
    repo                            use it yourself, even to "verify".
  Credential in a breach corpus    same. Report that the account is
                                    breached, not the password.
  Stale DNS pointing at live host  a finding: unmaintained asset
  Employee names / org structure   normal OSINT; use it to size the
                                    social engineering surface, and note
                                    that in the report
  Personal information             do NOT include. Refer to the client's
                                    privacy/DPO process instead.

The last row is the one that gets people fired. Personal data discovered
during OSINT is the client's legal problem, not your report content.

Passive DNS and historical records

  DNS records are not private. Anyone can query any public resolver.

  a.gtld (Google)      passive DNS for many TLDs
  hackertarget hostsearch  quick free pass
  crt.sh               CT log search
  Wayback Machine      historical content, and therefore historical URLs
  SecurityTrails       free tier, historical DNS

  Why historical DNS matters: an IP that used to be theirs, in an ASN that
  is still theirs, is a range they probably did not intend to be publicly
  scannable - and a range their firewall rules may not cover.

Kali commands

# All passive. Nothing here sends a packet to the target's web services.
mkdir -p ~/aegis/labs/tcm-02 && cd ~/aegis/labs/tcm-02

TARGET="${AEGIS_TARGET:-lab.internal}"

# --- 1. DNS: the free inventory ---
{
  echo "=== A / AAAA ==="
  dig +short A    "$TARGET" 2>/dev/null
  dig +short AAAA "$TARGET" 2>/dev/null
  echo
  echo "=== MX (mail) ==="
  dig +short MX "$TARGET" 2>/dev/null
  echo
  echo "=== NS (authority) ==="
  dig +short NS "$TARGET" 2>/dev/null
  echo
  echo "=== TXT (SPF, DMARC, verification tokens, sometimes more) ==="
  dig +short TXT "$TARGET" 2>/dev/null | head -10
  echo
  echo "=== SOA (serial, refresh - tells you how often they change DNS) ==="
  dig +short SOA "$TARGET" 2>/dev/null
} | tee 01-dns.txt

# TXT records are chronically over-shared. Read them like an attacker would.
dig +short TXT "$TARGET" 2>/dev/null | grep -iE \
  "v=spf1|google-site-verification|MS=|token|key|secret" | sed 's/^/  LEAK? /'

# --- 2. Certificate Transparency: every hostname, ever ---
{
  echo "=== CT logs for the target domain ==="
  # The base64-encoded domain API on crt.sh
  q=$(python3 -c "import base64,sys;print(base64.b64encode(sys.argv[1].encode()).decode())" "$TARGET")
  curl -s --max-time 20 "https://crt.sh/?q=${q}&output=json" 2>/dev/null \
    | python3 -c "
import sys, json
try: rows = json.load(sys.stdin)
except Exception: sys.exit('  (crt.sh unreachable)')
names = set()
for r in rows:
    for n in (r.get('name_value') or '').split('\n'):
        n = n.strip().lstrip('*.')
        if n and '*' not in n: names.add(n)
for n in sorted(names): print('  ', n)
print(f'\n   {len(names)} distinct hostnames, no packets sent to the target')
" 2>/dev/null || echo "  (no network access in this environment)"
} | tee 02-ct.txt

# --- 3. Local mirror of the same idea, fully offline ---
cat > 03-ct-offline.py <<'PY'
"""The CT principle, demonstrated without any network at all.

A CT log is just a list of certificates, append-only and publicly auditable.
The privacy consequence: every TLS hostname you own is permanently public,
forever, including the ones you have deleted from DNS.
"""
issued = [
    ("example.com",      "2021-03-02", "still active"),
    ("mail.example.com", "2021-03-02", "still active"),
    ("vpn.example.com",  "2021-03-02", "still active"),
    ("legacy.example.com","2021-03-02","DNS DELETED 2023, host still up"),
    ("test-stage.example.com","2021-03-02","never in DNS, still resolvable?"),
    ("corp-vpn.example.com",  "2021-03-02","internal cert, published anyway"),
]
print("  hostname                     issued     note")
print("  " + "-"*72)
for host, date, note in issued:
    flag = "  <-- FINDING" if ("DELETED" in note or "never" in note) else ""
    print(f"  {host:<28} {date}  {note}{flag}")
print()
print("  Three findings, zero packets sent:")
print("    1. a deleted host that may still be running")
print("    2. a stage host nobody remembers")
print("    3. an internal VPN name published externally (org chart leak)")
PY
python3 03-ct-offline.py | tee 04-ct-demo.txt

# --- 4. Public code search: the highest-yield and highest-risk source ---
{
  echo "=== what a public repo leak looks like ==="
  echo "  Search: site:github.com \"$TARGET\"  or  github.com/search?q=\"$TARGET\""
  echo "  Look for:"
  echo "    - config files with credentials"
  echo "    - .env files committed by accident"
  echo "    - internal hostnames in code, logs, or comments"
  echo "    - API keys and their scope"
  echo
  echo "  RULE: if you find a live credential, you STOP."
  echo "  You do not test it. You report its existence, redacted."
  echo
  echo "  Offline demonstration of what matches look like:"
  grep -rniE "password|api[_-]?key|secret|token|BEGIN .*PRIVATE KEY" \
    ~/Projects/aegis-academy --include="*.md" --include="*.py" 2>/dev/null \
    | grep -viE "example|password hashing|sudo -l" | head -8 | sed 's/^/  /' \
    || echo "  (no matches in your own repo - keep it that way)"
} | tee 05-codesearch.txt

# --- 5. Breach corpora: presence, not content ---
cat > 06-breach.md <<'EOF'
# Breach corpora: presence, not content

## What they are
Databases of email/username + password hashes leaked by breaches, indexed by
email address. Available freely and on the dark web.

## How to use them ethically and usefully
1. Query for a corporate email address
2. Record ONLY: which breach, what date, what fields were exposed
3. Do NOT record or use the password hash
4. Never attempt to crack it
5. Never attempt to log in with it

## What you report
| Finding | Severity | Recommendation |
|---|---|---|
| Accounts exposed in a breach, not yet MFA'd | High | Force password reset, enforce MFA |
| Corporate addresses exposed, reused elsewhere | Medium | Credential-stuffing exposure; MFA |
| Breach of a third party holding their data | Informational | Notify DPO; they handle it |

## What you must not do
- attempt authentication with any credential from any corpus
- download a corpus containing the client's real hashes
- re-share a corpus
- report the passwords, even to the client, even encrypted
EOF
cat 06-breach.md

# --- 6. Record everything, in a structure you can query later ---
cat > assets.csv <<'EOF'
host,ip,source,status,ports,notes
mail.lab.internal,192.168.56.20,DNS+A,live,,MX for lab.internal
vpn.lab.internal,192.168.56.21,CT,DNS NXDOMAIN,,"cert still valid; host never existed?"
legacy.lab.internal,192.168.56.22,CT+Wayback,live,22/80/443,"not in current DNS - candidate"
EOF
cat assets.csv
echo
echo "  asset list schema:"
echo "    host,ip,source,status,ports,notes"
echo "    'source' is how you learned it - that column is what tells you"
echo "    whether an asset is in the client's own inventory"
python3 - <<'PY'
import csv
with open("assets.csv") as f:
    rows = list(csv.DictReader(f))
print(f"  parsed {len(rows)} assets")
for r in rows:
    if r["status"] != "live":
        print(f"    flag: {r['host']} - {r['notes']}")
PY

Step 3 is the lesson in miniature: three findings from an append-only public log, with
zero packets sent. The deleted-but-still-running host is the archetype — an asset nobody
maintains because nobody knows it exists.
