Web Security Model

Summary

The web's security model is the oldest and least designed part of the internet: the browser
trusts the origin, the origin trusts the network, and the user trusts both. Lecture 11's
preparation reading is The Tangled Web, and the whole lecture is about why that trust is
structurally misplaced.

Key ideas

  • The browser is the security principal. It is the only component that can be trusted about
    what the user intended
  • Same-origin policy: a page may not read another origin's data. The core browser control
  • Origin = scheme + host + port. http://x.com and https://x.com are different origins
  • CORS is the mechanism for relaxing SOP, and its misconfigurations are extremely common
  • Cookies are ambient authority — sent automatically, which is what makes CSRF possible
  • Mixed content and the long tail of parsing differentials between browser and server
  • The browser cannot protect against a server that is itself malicious

The same-origin policy, precisely

A document loaded from origin A may:
  - embed images/scripts/styles from any origin
  - send requests to any origin (cookies ride along)
  - READ responses ONLY from its own origin (and origins with CORS permission)

That asymmetry is the whole model. Requests are always possible — which is why CSRF works —
but reading the reply requires permission, which is why XSS is so damaging.

The principal failures

Failure Model assumption broken
XSS Attacker code runs in the origin, so it inherits its authority
CSRF Cookies are ambient; the browser attaches authority the page did not choose
CORS misconfiguration A trusted origin is induced to permit a hostile one
Clickjacking The user cannot tell what they are clicking
Injection The server confuses data with code
Request smuggling Two parsers disagree about message boundaries

What the browser will and will not do

WILL:
  - sandbox scripts (CSP sandbox, iframe sandbox)
  - isolate origins (SOP, storage partitioning)
  - verify TLS
  - prompt for install permission
  - block mixed active content

WILL NOT:
  - stop a malicious server from reading its own data
  - stop an injection bug in the server
  - stop the user from being socially engineered
  - fix a confused server-side implementation

That last list is where most of Tier 4 lives.

Terminology

Term Meaning
Same-origin policy Cross-origin reads are denied by default
Origin Scheme + host + port triple
CORS Cross-Origin Resource Sharing; relaxes SOP
CSRF Forging an authenticated request using the victim's cookies
XSS Running attacker script inside a trusted origin
Ambient authority Authority the browser attaches automatically
CSP Content Security Policy; restricts script sources
Sandboxing sandbox attribute on iframes; restricts capability
Mixed content HTTPS page loading HTTP subresources
Idempotent verb Safe to retry: GET, HEAD, PUT, DELETE

Field lab

Objective: prove the same-origin policy and CORS behaviour, then audit your own machine's
cookie and header posture.

mkdir -p ~/aegis/labs/mit858-11 && cd ~/aegis/labs/mit858-11

# --- 1. a target that can demonstrate CORS properly ---
cat > server.py <<'PY'
#!/usr/bin/env python3
"""A tiny server with deliberately different CORS policies, for the exercise."""
from http.server import BaseHTTPRequestHandler, HTTPServer
import sys

class H(BaseHTTPRequestHandler):
    def log_message(self, *a): pass
    def do_GET(self):
        origin = self.headers.get("Origin", "")
        # three policies: none, permissive origin, reflected origin
        if self.path.startswith("/none"):
            pass
        elif self.path.startswith("/allow-evil"):
            self.send_header("Access-Control-Allow-Origin", "https://evil.example")
        elif self.path.startswith("/reflect"):
            self.send_header("Access-Control-Allow-Origin", origin or "*")
        self.send_response(200)
        self.send_header("Content-Type", "text/html")
        self.send_header("Set-Cookie", "sess=demo; HttpOnly; SameSite=Lax")
        self.end_headers()
        self.wfile.write(b"<h1>aegis cors lab</h1><p>secret-ish data here</p>")
HTTPServer(("127.0.0.1", 8099), H).serve_forever()
PY

cat > 03-cors-analysis.md <<'EOF'
# Reading a CORS configuration

## Safe patterns
- No `Access-Control-Allow-Origin` -> browser blocks cross-origin reads. Correct.
- A fixed allowlist, and only for origins you own.
- `Access-Control-Allow-Credentials: true` **with** an exact allowlist. Never with `*`.

## Unsafe patterns
1. **Reflecting the Origin header while allowing credentials**
   ```python
   self.send_header("Access-Control-Allow-Origin", origin)
   self.send_header("Access-Control-Allow-Credentials", "true")
   ```
   This is equivalent to `Access-Control-Allow-Origin: *` with credentials
   enabled. Every site on the internet can now read your authenticated
   responses and ride your cookies. This is one of the most common real
   findings in bug bounty, and it is exactly `/reflect` above.

2. **Allowing `null` origin**
   Sandboxed iframes, `data:` URLs and some file:// contexts all send the
   origin `null`. Allowing it means any of those can read your responses.

3. **Overly broad allowlist**
   `*.example.com` in a naive string match accepts
   `evil-example.com`. Parse the origin properly; do not use `startswith`.

4. **Credentialed requests without a preflight check**
   `Access-Control-Allow-Headers: *` combined with credentials.

## The preflight
For anything beyond a simple GET/POST, the browser sends an `OPTIONS`
preflight first. The server must answer with `Allow-Methods`,
`Allow-Headers` and `Allow-Origin`. Misconfigured preflights are how CORS
bypasses work.

## The interaction with cookies
`SameSite` and CORS solve *different* problems:
- `SameSite` limits which sites may send your cookie (CSRF defence)
- CORS limits which sites may read the response (data disclosure defence)

Neither stops the request itself from being sent. That gap is why CSRF still
needs a token.
EOF

cat > 05-model.md <<'EOF'
# The web security model, in one page

## Trust assumptions
1. The browser correctly identifies the origin of what it is displaying.
2. The origin is the security principal: anything running in it is trusted.
3. The network is hostile, so everything is encrypted in transit.
4. The user can tell where they are.

## Where each assumption fails
1. **Parsing differentials** - browser and server disagree about the URL
   (smuggling, open redirects)
2. **XSS** - assumption 2 fails; attacker code now runs as the origin
3. **No TLS on legacy** - assumption 3 fails
4. **Homograph domains, missing HTTPS indicators** - assumption 4 fails

## The controls that fall out of the model
- SOP + CORS: keep assumption 2 meaningful by limiting cross-origin reads
- CSRF tokens + SameSite: stop ambient authority from being usable
- CSP: limit what script can run even after XSS
- frame-ancestors / X-Frame-Options: stop clickjacking
- HSTS: stop downgrade
- Subresource Integrity: stop a compromised CDN from changing your script

## What is NOT in the model
Injection, access control, deserialisation, business logic, and the entire
server's own bugs. The browser is not a defence against a server-side flaw.
That is why OWASP's top category is not "browser problems".
EOF
