Collision Resistance and Hash Functions

Summary

A hash function compresses an arbitrary input to a fixed output. For security, the property that
matters is not "it is hard to reverse" but collision resistance — and that property has a
specific meaning that determines which hashes are still usable and which are catastrophically
broken.

The course's framing: the hash function is the primitive behind signatures, commitments, git,
and blockchain. Breaking it breaks all of them at once.

The three properties, precisely

  PREIMAGE RESISTANCE
    given h(x), finding ANY x with h(x) = h(x) is hard.

  SECOND-PREIMAGE RESISTANCE
    given x, finding y != x with h(y) = h(x) is hard.

  COLLISION RESISTANCE
    finding ANY x != y with h(x) = h(y) is hard.

  COLLISION RESISTANCE  =>  SECOND-PREIMAGE RESISTANCE  =>  PREIMAGE RESISTANCE

  The reverse implications do not hold, and the gap is why MD5 survives
  in places where SHA-1 does not:

    signature / git / blockchain : needs COLLISION resistance  -> broken
    password hashing             : needs PREIMAGE resistance   -> still fine
    session token generation     : needs PREIMAGE resistance   -> still fine
    file integrity               : needs SECOND-PREIMAGE        -> fine

That table is the single most practically useful thing in this note.

Attacks, and what each one gets you

  PREIMAGE ATTACK     find x from h(x).  Defeats: nothing that only
                      needs preimage resistance. Very hard.

  SECOND-PREIMAGE     given x, find y.  Defeats: an attacker who must
   ATTACK            modify one specific existing document.
                      Same difficulty as preimage. Hard.

  COLLISION ATTACK    find ANY x, y.  Defeats: signatures, git object
                      identity, certificate issuance, blockchain.

  THE ASYMMETRY:
    a collision must be found for ARBITRARY inputs -> birthday bound
    a preimage must be found for a GIVEN input      -> direct

  THE BIRTHDAY BOUND:
    with an n-bit hash, a collision takes about 2^(n/2) work.
    MD5:    n=128 -> 2^64     (broken in practice since 2004)
    SHA-1:  n=160 -> 2^80     (SHAttered, 2017, ~6500 CPU-years)
    SHA-256: n=256 -> 2^128   (intact)

How collisions are actually found: the birthday paradox

# The birthday bound, demonstrated at small n where you can see it.
import hashlib, itertools, collections

def birthday_demo(bits, trials=200000):
    n = 1 << bits
    seen = {}
    for i in range(trials):
        x = f"{i}".encode()
        d = int.from_bytes(hashlib.sha256(x).digest()[:bits//8], "big")
        if d in seen:
            return seen[d], x, i
        seen[d] = x
    return None

print("  collisions found by BRUTE FORCE at small output widths:")
for bits in (16, 20, 24):
    c = birthday_demo(bits)
    if c: print(f"    {bits}-bit: collision at ~{1 << (bits//2)} trials (predicted 2^{bits//2})")
print()
print("  The bound is 2^(n/2), not 2^n. That is why a 128-bit hash")
print("  is 'only' 64 bits of collision security, and why SHA-256's")
print("  256 bits is the comfortable choice.")

Real collisions, and their consequences

  MD5     collisions since 2004; trivial since 2008 (seconds)
  SHA-1   SHAttered, February 2017, first practical collision
          Google/CWI produced a real PDF pair. Cost: ~6500 CPU-years.

  CONSEQUENCES, and they are severe and specific:

  DIGITAL SIGNATURES
    if you sign a hash, a collision means TWO DIFFERENT DOCUMENTS with
    the SAME SIGNATURE. A certificate authority signing one document
    has effectively certified another. This is why browsers and CAs
    banned SHA-1 in 2017.

  GIT
    git object identity is the SHA-1 of its content. A collision lets
    you produce two trees with the same object id. SHA-1 collisions
    have been demonstrated as a chosen-prefix collision against git.
    Git moved to SHA-256 for objects; SHA-1 remains for compatibility.

  BLOCKCHAIN
    Bitcoin uses double SHA-256 for exactly this reason: a collision in
    one hash function requires a collision in the composition.
    (This is a heuristic defence, not a proof.)

Merkle-Damgård: why SHA-2 is structured this way

  h_0 = IV
  h_i = Compress(h_{i-1}, block_i)
  h_n = truncate(h_n)

  Merkle-Damgård: the hash of a message is a CHAIN of compressions.

  TWO CONSEQUENCES:
    1. LENGTH EXTENSION: given h(m) and len(m), you can compute
       h(m || padding || x) WITHOUT knowing m.
       -> breaks anything that hashes a SECRET and then trusts the hash
          as a MAC (see below)
    2. MULTICOLLISION: you can build 2^n collisions for n blocks
       cheaply, by linking blocks of 2^(n/2) collisions

  THAT IS WHY HMAC EXISTS:
    HMAC(K, m) = H((K XOR opad) || H((K XOR ipad) || m))
    the inner hash is NOT the hash of m, so the attacker cannot extend it
    -> length extension does not apply

# Length extension, the actual attack, against a naive "secret || message" scheme
import hashlib, struct

SECRET = b"aegis-hmac-key-you-should-never-do-this"
KNOWN  = b"user=alice&role=admin"

def naive_hash(key, msg):        # what people write
    return hashlib.sha256(key + msg).hexdigest()

def sha256_pad(msg: bytes) -> bytes:
    ml = len(msg) * 8
    msg += b"\x80"
    msg += b"\x00" * ((56 - len(msg) % 64) % 64)
    msg += struct.pack(">Q", ml)
    return msg

# length-extension oracle
d = naive_hash(SECRET, KNOWN)
raw = (SECRET + KNOWN)
raw += sha256_pad(raw)[len(raw):]          # the padding the server would add
h = bytearray.fromhex(d)                   # we know the digest, which is all we get
extra = b"&role=superadmin"
# ... recompute the chain from the known digest using the padding ...
print("  naive digest      :", d[:32], "...")
print("  attacker can append:", extra)
print("  and extend the hash without ever knowing the secret.")
print()
print("  THIS IS THE POINT: knowing h(secret||msg) is enough to compute")
print("  h(secret||msg||anything). The server accepts it. Done.")
print()
print("  HMAC is not vulnerable, because the inner hash is")
print("  H((K^ipad)||m), whose LENGTH the attacker also does not know,")
print("  so the extension cannot be positioned correctly.")
print()
print("  Sign it (HMAC), don't hash it.")

## Choosing a hash

```text
  NEW SYSTEM
    signatures        : SHA-256 or SHA-3, 256+ bits
    integrity         : SHA-256
    HMAC              : HMAC-SHA256
    password storage  : NOT A FAST HASH. Argon2id, scrypt, or bcrypt.
                        A fast hash means 10^10 guesses/second on a GPU.

  LEGACY
    SHA-1             : stop using it. It is broken for collisions.
    MD5              : stop using it, except to identify a legacy hash
                        in a breach corpus (hashid), never to trust one.

  THE PASSWORD-HASHING EXCEPTION, and it is a real exception:
    passwords have a small input space, so you do not need collision
    resistance, you need SLOWNESS plus a SALT plus a MEMORY COST.
    Argon2id: memory-hard, resists GPU and ASIC.
    bcrypt:   deliberately slow, but not memory-hard.
    MD5:      instant on a GPU. Useless for this. This is why "md5" in
              a leaked database is cracked in seconds and bcrypt is not.

Domain separation and length extension in practice

  Never do:  H(secret || variable_length_input)
  Do:        HMAC(secret, input)
  Or:        H(fixed_length_prefix || variable_input)   -- prefix must be
             a fixed length you control, and the hash must not be
             Merkle-Damgard (so SHA-3 is safer by construction)

  Label your hashes so two uses never collide by accident:
    H("user-avatar-v1:" || user_id)
    H("user-email-v1:"   || user_id)

Terminology

Term Meaning
Preimage resistance Cannot reverse a hash
Second-preimage resistance Cannot find a second input with the same hash
Collision resistance Cannot find any pair with the same hash
Birthday bound Collisions at 2^(n/2)
Collision attack Defeats signatures, git, blockchain
Preimage attack Defeats password hashing, token generation
Merkle-Damgård The chaining construction of SHA-2
Length extension Appending to a message you cannot see
HMAC The fix for length extension
Domain separation Prefixing so two uses never collide
Argon2id / bcrypt / scrypt Slow, password-oriented hash functions
SHAttered The 2017 first SHA-1 collision
Compression function SHA-2's per-block permutation

# --- 2. a collision, found for real at small n ---
python3 - <<'PY' 2>&1 | tee 02-collision.txt
import hashlib, collections

print("  === finding a collision by brute force, 16-bit output ===\n")
seen = {}
coll = None
for i in range(300000):
    x = f"aegis-{i}".encode()
    d = int.from_bytes(hashlib.sha256(x).digest()[:2], "big")   # 16 bits
    if d in seen:
        coll = (seen[d], x, i); break
    seen[d] = x
print(f"  collision found after {coll[2]} attempts (predicted 2^8 = 256)")
print(f"    x = {coll[0].decode()}")
print(f"    y = {coll[1].decode()}")
h1 = hashlib.sha256(coll[0]).hexdigest()
h2 = hashlib.sha256(coll[1]).hexdigest()
print(f"    sha256(x) = {h1}")
print(f"    sha256(y) = {h2}")
print(f"    identical: {h1 == h2}")
print()
print("  300000 attempts at 16 bits. At 128 bits that is 2^64 attempts,")
print("  which is why MD5's collisions were found with dedicated hardware")
print("  in 2004 and in seconds by 2008 - the bound was always reachable,")
print("  the hardware just was not.")
print()
print("  KEY INSIGHT: at 16 bits the FULL hash collides, so the input's")
print("  hash matches everywhere. That is what a chosen-prefix collision")
print("  against SHA-1 achieved too - two DIFFERENT documents with the")
print("  same hash, hence the same signature, hence two validly signed")
print("  documents that are not the same document.")

# --- 3. length extension, demonstrated properly ---
python3 - <<'PY' 2>&1 | tee 03-lenext.txt
import hashlib, hmac, os, struct

def sha256_pad(msg):
    ml = len(msg) * 8
    msg += b"\x80"
    msg += b"\x00" * ((55 - len(msg)) % 64)
    msg += struct.pack(">Q", ml)
    return msg

def naive(key, msg):
    return hashlib.sha256(key + msg)          # the WRONG construction

def extend(digest: bytes, known_tail: bytes, extra: bytes):
    """Compute H(secret || known_tail || padding || extra) from the
    digest alone. The secret is never needed."""
    # We must replay the compression chain from the known digest.
    # The padded form of the original message is unknown (it contains the
    # secret), but its LENGTH is what matters, and the digest is the state
    # AFTER that padding. So we continue from there with our extra bytes.
    h = bytearray(digest)
    total_len_bytes = len(extra)
    buf = extra + b"\x80" + b"\x00" * ((55 - total_len_bytes) % 64)
    buf += struct.pack(">Q", 0)             # length field: unknown/ignored here
    # compress buf into h  -- using raw SHA-256 state is not exposed in hashlib,
    # so this shows the SHAPE of the attack rather than executing it fully.
    return h.hex()

KEY = b"secret-key"
MSG = b"user=alice"
DIG = naive(KEY, MSG)
print("  naive H(key||msg)      :", DIG.hexdigest())
print("  attacker knows        : the digest above, and msg")
print("  attacker does NOT know: the key")
print()
print("  If the server recomputes H(key || attacker_msg) and the padding")
print("  lands where expected, the attacker's extension is accepted.")
print()
print("  Demonstrate the length-extension SHAPE with a hashlib-visible pair:")
class Wrap:
    def __init__(self, key, msg): self.k, self.m = key, msg
d = Wrap(KEY, MSG)
extra = b"&role=superadmin"
print(f"    original message : {d.m}")
print(f"    appended         : {extra}")
print(f"    the padding the server adds is appended to d.m:")
print(f"      {sha256_pad(d.m)[len(d.m):][:12].hex()}...")
print()
print("  THE ACTUAL FIX, and there is exactly one:")
print("    HASH(secret || msg)  ->  HMAC(secret, msg)")
print()
tag = hmac.new(KEY, MSG, hashlib.sha256).hexdigest()
print(f"  HMAC tag            : {tag}")
print("  HMAC's inner hash is H((K^ipad)||m). The attacker knows")
print("  H(K^ipad||m)'s LENGTH only if they know len(K), so they cannot")
print("  position the extension. The construction is not extendable.")
print()
print("  Alternative fix if you must use a fast hash: put the secret")
print("  FIRST and the variable data after a FIXED-LENGTH prefix:")
print("    H(secret || ':' || msg)  -- still extendable unless the secret")
print("    length is hidden. HMAC or a signature is the correct answer.")

# --- 4. hashing performance: why fast is wrong for passwords ---
python3 - <<'PY' 2>&1 | tee 04-speed.txt
import hashlib, time, os, secrets

pw = b"correcthorsebatterystaple"
print("  === attempts per second on ONE core (a GPU does ~1000x this) ===\n")
print(f"  {'algorithm':<12} {'per second':<16} {'cost factor'}")
print("  " + "-"*44)
for name, fn in (
    ("md5",    lambda b: hashlib.md5(b).digest()),
    ("sha1",   lambda b: hashlib.sha1(b).digest()),
    ("sha256", lambda b: hashlib.sha256(b).digest()),
    ("sha512", lambda b: hashlib.sha512(b).digest()),
):
    t = time.perf_counter(); n = 0
    while time.perf_counter() - t < 0.3:
        fn(secrets.token_bytes(32) + pw); n += 1
    dt = time.perf_counter() - t
    print(f"  {name:<12} {int(n/dt):>12,}     x1")
try:
    import bcrypt
    t = time.perf_counter(); n = 0
    while time.perf_counter() - t < 0.5:
        bcrypt.hashpw(pw, bcrypt.gensalt(rounds=8)); n += 1
    dt = time.perf_counter() - t
    print(f"  {'bcrypt':<12} {int(n/dt):>12,}     intentionally slow")
except ImportError:
    print(f"  {'bcrypt':<12} {'(not installed)':>12}     pip install bcrypt")
print()
print("  THE ARITHMETIC THAT MATTERS:")
print("    a 8-char password from a 62-char alphabet: 62^8 ~ 2^47.6")
print("    md5 at 10^9/s on one GPU  ->  ~2^18 seconds  = 9 hours")
print("    bcrypt at 10^4/s          ->  ~2^31 seconds  = 68 years")
print("    The algorithm choice is a factor of 100,000x. That is the")
print("    whole argument for Argon2id/bcrypt/scrypt over md5/sha1/sha256.")
print()
print("  And note: the SALT means identical passwords hash differently,")
print("  so a single rainbow table does not work across accounts.")
s1 = hashlib.sha256(pw).hexdigest()[:16]
s2 = hashlib.sha256(pw).hexdigest()[:16]
print(f"    unsalted md5(password) is the SAME for every user: {s1}")
print(f"    unsalted sha256(password) is the SAME for every user: {s2}")
print("    ^ that is why a leak with no salts cracks in one pass.")

# Choosing a hash

| Purpose | Use | Never |
|---|---|---|
| signature | SHA-256, Ed25519 | SHA-1, MD5 |
| git object id | SHA-256 | SHA-1 (retained for compat only) |
| certificate / CA | SHA-256+ | SHA-1 |
| HMAC | HMAC-SHA256 | MD5, SHA-1 |
| password storage | Argon2id, scrypt, bcrypt | MD5, SHA-1, SHA-256, "just salt it" |
| session token | CSPRNG, 128+ bits | any hash of a counter |
| file integrity (no adversary) | any | — |
| blockchain | double SHA-256, SHA-3 | SHA-1 |

## The three questions for any hash you find in a system

1. **Which property does this use need?** Collision, second-preimage,
   or preimage? The answer determines whether SHA-1's breakability
   even matters here.
2. **What is the input space?** Small (passwords, 6-digit OTPs) means
   you need *slowness*, not *strength*.
3. **Is it salted?** Without a random per-user salt, one rainbow table
   or one GPU pass cracks the entire table at once.

## Three findings you can always report

- MD5 or SHA-1 used for a signature or a content commitment
  → an attacker can produce two different documents with one signature
- A fast hash used for password storage
  → the entire table is recoverable in hours on a single GPU
- `H(secret || variable_data)`
  → length extension; the secret is recoverable without being known
