Calling Convention and Stack Frames

Summary

This is the most important lecture in 6.S081 for offensive work. The calling convention defines
exactly where the stack pointer, frame pointer, and return address live at every instant — which
means you can compute how many bytes to write to take over execution.

Everything in lecture 4's lab follows directly from this. If you can draw the frame from
memory, you can exploit it.

The x86-64 System V ABI

HIGH ADDRESSES  (older frames)
┌──────────────────────────┐  ← caller's frame
│  caller's locals         │
│  caller's saved RBP      │
├──────────────────────────┤  ← RBP points here in the current frame
│  SAVED RBP        +8     │     (16-byte return address slot)
│  RETURN ADDRESS   +0     │  ← "return address" — the exploit target
├──────────────────────────┤
│  arg7, arg6              │
│  arg5, arg4              │
│  arg3, arg2              │
│  arg1, arg1              │  ← stack-passed args start here
├──────────────────────────┤  ← RSP points here, frame grows DOWN
│  local variables         │
│  ...padding for 16-byte  │
│  alignment               │
└──────────────────────────┘  ← lowest address
LOW ADDRESSES   (this frame)

void example(int a, int b) {
    char buf[16];      // local
    // saved RBP
    // return address
}

Prologue (what the compiler emits):

push rbp
mov  rbp, rsp
sub  rsp, N

Epilogue:

leave           ; rsp = rbp; pop rbp
ret             ; pop rip from [rsp]

The five facts that make exploitation predictable

  1. Stack grows downward on x86-64.
  2. call pushes the return address, 8 bytes.
  3. push rbp saves the caller's frame pointer, 8 bytes.
  4. Locals sit at lower addresses than the return address.
  5. Therefore: overflowing a local buffer walks upward toward the return address.

Argument passing

  • Integer/pointer args: rdi, rsi, rdx, rcx, r8, r9 (first six)
  • Floating point: xmm0–xmm7
  • Everything beyond six integers: pushed onto the stack, right-to-left
  • Return value: rax
  • Callee-saved: rbx, rbp, r12–r15
  • Caller must preserve rcx and r11 (the syscall instruction clobbers them)

Computing the offset

# what is the distance from my buffer to the return address?
gdb -q --batch \
  -ex 'break main' -ex 'run' \
  -ex 'info registers rsp rbp' \
  -ex 'print $rbp - $rsp' \
  -ex 'x/4gx $rbp' \
  -ex 'quit' ./vuln

If rbp - rsp is 32 and you have a 24-byte buffer, then 8 bytes of padding reach the saved RBP
and 16 more reach the return address.

The cycle is: measure → compute → write → verify. That is the entire exploit development loop.

Why the canary exists

Because offsets are predictable. The stack canary is a random value placed between your buffer
and the saved frame pointer. If it does not match at ret, the program aborts — the overflow
still happened, but control flow was never transferred.

checksec --file=./vuln | grep canary

Terminology

Term Meaning
Calling convention The ABI rules for passing args and returning
Stack frame Per-function stack region
rbp / frame pointer Points at the frame base; saved/restored
rsp / stack pointer Points at the current top of stack
Return address Saved RIP; where ret jumps to
Prologue / epilogue Frame setup and teardown code
Caller/callee-saved Who must preserve which registers
Alignment Stack kept 16-byte aligned for SSE
Stack canary Random guard between locals and return address
Offset Bytes from a buffer to the return address
leave; ret Restore frame, then jump

Kali commands

# --- read the ABI from real assembly ---
objdump -d -M intel /usr/bin/ls | head -40
gdb -q --batch -ex 'break main' -ex 'run' -ex 'disassemble main' ./prog 2>/dev/null

# --- what does checksec say? ---
checksec --file=./myprog
readelf -l ./myprog | grep GNU_STACK        # NX
readelf -d ./myprog | grep -E 'BIND_NOW|FLAGS'   # RELRO
file ./myprog                                  # PIE

# --- the alignment rule, in practice ---
python3 -c 'print(0x10, 0x10//2, (0x10//2)*2)'

# --- read a frame pointer chain from a core dump ---
sudo coredumpctl list 2>/dev/null | head
gdb ./prog core.* -ex 'bt' -ex 'info frame' 2>/dev/null

Field lab

Objective: measure your exact offset to the return address. This number is the foundation of
ex-03 and ex-04.

mkdir -p ~/aegis/labs/os-04 && cd ~/aegis/labs/os-04

cat > stack.c <<'EOF'
#include <stdio.h>
#include <string.h>

/* three functions so you can watch the frame chain grow */
void third(const char *in) { char b16[16];  strcpy(b16, in);   printf("b16 ok\n"); }
void second(const char *in) { char b24[24];  strcpy(b24, in);  third(in); }
void first (const char *in) { char b32[32];  strcpy(b32, in);  second(in); }

int main(int argc, char **argv) {
    if (argc < 2) { fprintf(stderr, "usage: %s <string>\n", argv[0]); return 1; }
    first(argv[1]);
    return 0;
}
EOF

gcc -g -O0 -fno-stack-protector -no-pie -z execstack stack.c -o stack
checksec --file=./stack | grep -E "NX|Stack|PIE|Canary"

# --- 1. where is each buffer? ---
for fn in first second third; do
  gdb -q --batch -ex "break $fn" -ex "run $(python3 -c 'print("A"*80)')" \
      -ex "info registers rsp rbp" -ex "print \$rbp - \$rsp" \
      -ex "x/2gx \$rbp" -ex quit ./stack 2>/dev/null \
    | sed "s/^/[$fn] /"
done | tee 01-frames.txt

echo
echo "Look for the return address: on the stack it looks like 0x0040.... (non-zero, non-ASCII)."

# --- 2. brute-force the offset, the reliable way ---
python3 - <<'PY' | tee 02-offset.txt
import subprocess
for n in range(1, 160):
    payload = b"A" * n + b"BBBBBBBB"          # 0x4242424242424242 marker
    r = subprocess.run(["./stack", payload], capture_output=True, timeout=5)
    err = (r.stderr + r.stdout).decode("utf8","replace")
    if "424242424242" in err or r.returncode != 0:
        print(f"offset {n:3d}  rc={r.returncode}  {err.strip().splitlines()[-1][:70] if err.strip() else ''}")
        break
PY

echo
echo "That number is your offset to the saved return address. Write it down."

# --- 3. see the frame chain by hand ---
gdb -q --batch \
  -ex 'break first' -ex 'run' \
  -ex 'info registers rsp rbp' \
  -ex 'p/x $rbp' -ex 'p/x $rsp' \
  -ex 'x/12gx $rbp-16' \
  -ex 'bt' -ex quit ./stack 2>&1 | tail -30 | tee 03-frame-dump.txt

# --- 4. prove the canary stops it ---
gcc -g -O0 -fstack-protector-strong -pie -fPIE stack.c -o stack-hard
checksec --file=./stack-hard | grep -i canary
python3 - <<'PY'
import subprocess
for n in range(1, 200, 4):
    r = subprocess.run(["./stack-hard", b"A"*n], capture_output=True, timeout=5)
    if b"stack smashing" in r.stderr or b"detected" in r.stderr:
        print(f"stack-hard detected corruption at n={n}: {r.stderr.decode().splitlines()[0][:70]}")
        break
else:
    print("no abort observed - the check may need a wider sweep")
PY

Step 2 is the deliverable. An empirically measured offset beats any calculation, because
compilers insert padding you will not have predicted. This exact loop is what ex-03 formalises.

Record: your offset number, and the rbp - rsp values for all three frames.

Self-test

  1. In what order are the saved RBP and return address on the stack relative to a local buffer?
  2. Why must the stack be 16-byte aligned?
  3. Which registers does the caller preserve versus the callee?
  4. Why did compilers add stack canaries, given offsets are predictable?
  5. Why is measuring the offset by brute force more reliable than computing it?
