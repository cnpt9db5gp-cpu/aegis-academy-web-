Active Directory Fundamentals, Forests, Domains and Trusts

Summary

Active Directory is the object store and trust substrate for almost every Windows network on
earth. Understanding it is not optional for internal work, because everything an attacker does
in AD is a graph traversal — and the graph is defined by objects, groups, sessions and ACLs.

The lecture's framing: AD is not a user database. It is a namespace, a trust boundary
system, and a delegation mechanism. Every misconception about it comes from treating it as a
flat user list.

Companion to mit858-05 (operating systems) and tcm-06's trust-path
section. This note is the substrate; ad-02 is the protocol on top.

The objects

  USER              a security principal: a login identity
  GROUP             a collection of principals, used for authorisation
  COMPUTER          a machine account; a USER with a $ in the name
  ORGANIZATIONAL UNIT (OU)  a container for delegation of administration
  DOMAIN            the security boundary; a database (NTDS.dit) + a set of servers
  FOREST            the top of the hierarchy; a security boundary of last resort
  GLOBAL CATALOG    a read-only, forest-wide index, replicated to every DC
  SYSVOL            the NETLOGON share; scripts and GPOs, world-readable
  GPO               a set of registry settings and scripts, applied by link order
  ACL / ACE          who can do what to an object. The graph's edges.

The hierarchy

  FOREST  (aegis.local)
    └── DOMAIN  (aegis.local)
          ├── DC01  (domain controller, holds NTDS.dit)
          ├── DC02
          ├── OU=Workstations
          ├── OU=Servers
          ├── OU=Users
          │      ├── alice
          │      ├── bob
          │      └── erin
          └── CN=Users (the default container)

  EVERY OBJECT HAS:
    a SID          SecurityIdentifier: domain-5-21-...-1104
    a DN           DistinguishedName: CN=alice,OU=Users,DC=aegis,DC=local
    an objectGUID  a GUID that NEVER CHANGES, unlike the SID
    a name        which CAN change, and often does

SIDs are what authorisation is written against, not names. When a
group is renamed, the SID does not change and every ACL keeps working.
That is why AD ACLs are so hard to reason about by hand: you cannot see
what a SID means without resolving it.

Groups: the three types, and why the distinction matters

  DOMAIN LOCAL     scope: THIS domain. Can contain foreign domain
                   principals. Used for file shares and local resources.
  GLOBAL           scope: THIS forest. The membership travels with the
                   account. Used for role-based access.
  UNIVERSAL        scope: ANY domain, any domain local group.
                   Membership is stored in the Global Catalog, which
                   makes them slow. Used for cross-domain needs.

  NESTING GROUPS are where the real complexity lives:
    Domain Admins > IT Staff > alice
    alice is a Domain Admin by TRANSITIVITY, three hops away, and
    "who is in Domain Admins" does not answer it.

Authentication: NTLM vs Kerberos

  NTLM   a challenge-response protocol. The client proves knowledge of
         the password hash, in three messages.
         + works everywhere, even without a DC
         + no clock dependency
         - sends a challenge that can be relayed
         - NTLMv1 is trivially broken; NTLMv2 is required
         - the hash is the credential (pass-the-hash)

  KERBEROS
         + tickets, mutual authentication, delegation, no password on the wire
         + replay-resistant, clock-bounded
         - requires a DC and clock synchronisation
         - introduces the whole ticket model (ad-02)
         - TGTs and service tickets are GOLD if stolen

The migration story in every environment is: NTLM is being retired,
and the tickets that replace it are more valuable to steal. That trade
is the entire reason AD attacks escalated in the 2010s.

Password hashes, and why there are two

  NT HASH   MD4(password). 21 bytes.
            Fast. STORED EVERYWHERE: NTDS.dit, SAM, the registry,
            DCSync output, any memory dump.
            Not salted - which is why a rainbow table works and why
            pass-the-hash works.

  LM HASH   DES-based, first 8 characters, uppercase. Dead since
            Windows 2000 but still present as the LMHASH field
            (empty if LMCompatibilityLevel >= 5). Finding a non-empty
            LMHASH on a modern domain is a finding.

  KERBEROS   If the account is configured with AES support, the
  TICKET     ticket is encrypted with a key derived from the PASSWORD
             and the REALM. Roast the ticket and you get the
             password offline - that is Kerberoasting (ad-04).

NTDS.dit holds all of it, and it is the single most valuable file in
a Windows domain. DCSync (ad-05) is the authenticated way to read it.

ACLs and how authorisation actually works

  EVERY OBJECT HAS AN ACL: an ordered list of Access Control Entries.
  Each ACE is:  (identity SID, permission bits, type, inherited?)

  PERMISSION TYPES:
    Generic All / Read / Write / Execute
    Object-specific: WriteProperty, WriteDACL, WriteOwner,
                     GenericWrite, GenericAll, ValidatedWrite
    Extended rights: UserForceChangePassword, UserChangePassword,
                     Self, AllValidatedWriteProperties

  THE ACE TYPES:
    ALLOW      grants
    DENY       overrides (evaluated first in a DACL)

  WHO IS EVALUATED, IN ORDER:
    the object's owner (implicit READ_CONTROL and WRITE_DAC)
    the object's DACL, top to bottom, deny before allow
    the inherited ACEs from the parent
    the user's token: their SID + every group SID they are in,
                     transitively

  THE ATTACK-SURFACE ACEs, the ones that matter:
    GenericWrite        -> can set almost anything, including a script
    WriteDACL           -> can grant themselves anything. GAME OVER.
    WriteOwner          -> can take ownership, then do the above
    GenericAll          -> done
    ValidatedWrite      -> conditional write, abused to force group membership
    UserForceChangePassword -> take over any account you can see
    WriteSPN            -> request a service ticket (Kerberoasting)
    ReadGMSAPassword    -> read the group's managed service account password
    DCSync (on the domain)
    Self on a group     -> add yourself to it

Trusts

  DIRECTIONAL       A trusts B: A's users can access B, not vice versa
  BIDIRECTIONAL     both
  FOREST           every domain in a forest trusts every other one
                    transitively, without a configured trust object
  TRANSITIVE (in)  auth flows onward into the forest
  TRANSITIVE (out) auth flows into your trusted domains
  EXTERNAL         a Windows domain trusting a non-Windows realm (MIT,
                    cross-forest to ADFS/Azure AD)

  THE DANGEROUS PATTERN:
    Forest trusts every domain in it. So one weak domain anywhere in
    the forest is an entry point to all of them. A forest is a trust
    boundary only if every domain in it is strong.

  EXTERNAL TRUSTS are the ones to audit:
    does the trusted domain have weak authentication?
    is the trust one-way?
    does SID filtering apply?

Replication, and why it matters

  Multi-Master Replication (since Windows Server 2003)
    any DC can write; changes replicate out on a schedule
    therefore: a DC can serve a replication request to a peer

  DCSync: ask a DC for the directory data it replicates, as a peer.
  Requires: Replicating Directory Changes (All) + Replicating Directory
  Changes In Filtered Set, or DS-Replication-Get-Changes (all).
  Without those three rights you should not be able to do it.
  WITH them, you can dump every hash in the domain.

  THAT IS THE ENTIRE POINT OF DCSync: it is a legitimate replication
  operation that bypasses every other control, gated behind three
  specific rights that are usually granted too broadly.

Building a lab

  YOU NEED A REAL DOMAIN CONTROLLER. Options, best first:

  1. WINDOWS SERVER EVALUATION VM (recommended)
     Two NICs: host-only (192.168.56.0/24) and an internal lab range.
     Promote to DC with Install-ADDSForest. Full fidelity: Group Policy,
     Kerberos, delegation, Sysinternals, the works.
     Snapshots are essential; AD changes are not always reversible.

  2. SAMBA AD DC ON A DEBIAN VM
     lighter, faster to rebuild, good for the PROTOCOL mechanics
     (Kerberos, LDAP, SMB, BloodHound collection). Limited: no Group
     Policy modelling worth trusting, no RSAT.

  3. A CLOUD EVAL (Azure AD Free / a Windows VM on a free tier)
     realistic but changes the threat model and the network position.
     Not useful for learning pivoting.

  HARDWARE: your host has 30 GiB RAM and an i5-13500H. A DC VM wants
  2 vCPU / 4 GiB; a workstation 2/4. Two VMs fit comfortably. Assign
  the host-only range to the DC and a second internal range between
  them so you can practise pivoting (ad-06).

  SNAPSHOT BEFORE EVERY LECTURE. ad-07's GPO abuse will lock you out
  of your own DC if you are not careful, and that is a real skill to
  learn rather than a mistake to make twice.

Terminology

Term Meaning
Domain Security boundary: a database plus a set of servers
Forest One or more domains with a shared schema and transitive trust
DC Domain controller; holds a writable copy of NTDS.dit
NTDS.dit The directory database. The most valuable file in the domain
SID Security identifier; the immutable identity authorisation uses
DN Distinguished name; the LDAP path. Changes when things are renamed
objectGUID A GUID that never changes
OU Container for administrative delegation
GPO Group Policy Object; registry settings and scripts
ACL / ACE Ordered permission list on an object
WriteDACL Can rewrite the ACL. Equivalent to full control
Transitive trust Authentication flows onward automatically
Global Catalog Forest-wide read-only index; holds universal group membership
Replication Multi-master; any DC can answer a replication request
DCSync Using replication rights to dump the whole directory

# NT hash, LM hash, Kerberos ticket — what each one is

## NT HASH

MD4(UNICODE(password)) -> 21 bytes, always starts with a4b1c7
"password" -> 8846f7eaee8fb117ad06bdd830b7586c
^ first 4 bytes are always a4b1c7 (MD4 magic)
Not salted. Ever. So:
- one rainbow table cracks every account in every domain ever
- the hash IS the credential: present it instead of the password
- it is in NTDS.dit, SAM, the registry, and every memory dump
Python, to prove it:
hashlib.new("md4", "password".encode("utf-16-le")).hexdigest()
(OpenSSL 3 removed MD4 from the default provider. On Kali:
openssl dgst -provider legacy -md4 -binary ... or use impacket)


## LM HASH

DES(password[:8].upper()) padded to 16 bytes, twice if needed
The first 8 characters, uppercased. Annihilating.
Still present as the LMHASH field unless LMCompatibilityLevel >= 5.
Finding a non-empty LMHASH on a modern domain is a FINDING,
because it means every password in that domain is at most 8
uppercase alphanumeric characters, regardless of policy.


## KERBEROS TICKET

Ticket is encrypted with a key derived from the PASSWORD and the REALM.
Domain Admins are in the same realm, so a DC decrypts any user's
ticket using that user's password-derived key.
Therefore: give me any user's TGS and I can decrypt it IF I know or
guess their password.
Roasting = take many tickets, guess passwords offline.
The ticket itself tells you the account's AES key-usage number,
which tells you whether it is roastable at all.


## What to check on a lab DC

LMCompatibilityLevel >= 5 (in Default Domain Controllers policy)
Netlogon\DisableLMCompatibility
Use AES instead of DES for Kerberos (msDS-SupportedEncryptionTypes)
msDS-AllowedToDelegateTo (unconstrained delegation -> ad-02)
All service accounts: are any of them Domain Admins?

EOF

cat > 05-acl-enum.md <<'EOF'
# Enumerating ACLs without touching the domain

BloodHound collects this (bh-01). Here is the reasoning, so you know
what the graph means when you read it.

```text
  For every security-relevant object, you want its DACL.
  For every ACE, you want:
      principal SID  ->  who
      right          ->  what
      type           ->  ALLOW or DENY

  The interesting principals, in order of how often they are the answer:

    -1              Everyone
    S-1-5-18         LOCAL SYSTEM
    S-1-5-32-544     Administrators
    S-1-5-21-...-512  Domain Admins
    <domain users>   the built-in Users group

  The interesting rights, and what each one means for an attacker:

    GenericAll            -> done. Full control of the object.
    GenericWrite          -> can set almost any attribute, INCLUDING
                             a script path on a computer object.
    WriteDACL             -> can rewrite the ACL. Equivalent to GenericAll
                             because you can just grant yourself GenericAll.
    WriteOwner            -> can take ownership, then the above.
    ValidatedWrite        -> write conditioned on a check. Famous because
                             'User is a member of <group>' was validated
                             against the WRONG attribute (see ad-04).
    WriteSPN              -> request a service ticket for that account.
                             Kerberoasting (ad-04).
    ReadGMSAPassword      -> read a group's managed service account password.
    UserForceChangePassword -> reset any account you can read.
    Self (on a group)     -> add yourself to that group.
    DCSync                -> replicate the whole directory.
    AllowedToDelegateTo   -> impersonate that account to any service.

  WHAT MAKES A PATH WORTH REPORTING:
    - it starts from a principal a normal user can BE
    - it ends at Domain Admins, or at DCSync
    - it is short. One hop is a bug. Five hops is a design smell.
    - it does not require an exploit

The local enumeration version

# On a machine you are already on, with whatever rights you have:
# who can this token impersonate?
whoami /priv 2>/dev/null | grep -i impersonate

# what SPNs exist on THIS host?
setspn -Q */* 2>/dev/null

# what is in the delegation configuration?
nltest /dsgetdc:lab.internal 2>/dev/null

# the ACLs on the local machine's objects
dsacls \\lab.internal 2>/dev/null | head -40

EOF

cat > 06-baseline.md <<'EOF'

The AD defensive baseline

Check these BEFORE attacking your own lab. A lab with a hardened
baseline is a better teaching tool than an open one, because you can
demonstrate both the attack and the fix.

Control Setting Where
SMB signing REQUIRED on all hosts GPO: Computer Config > Policies > Windows Settings > Security Settings > Microsoft Windows Defender > Credential Guard > Digitally sign client-server communications
LDAP signing REQUIRED GPO: Domain Controllers > Policies > Windows Settings > Security Settings > Microsoft Windows Defender > Credential Guard > Domain controller secure LDAP communications
LDAP channel binding ENFORCED KB5012122; blocks the most common LDAP relay
SMB encryption on sensitive shares optional; blocks relay entirely on those shares
LMCompatibilityLevel 5 or above GPO: Computer Config > Policies > Windows Settings > Security Settings > Local Policies > Security Options > Network security: LMCompatibilityLevel
AES for Kerberos enabled msDS-SupportedEncryptionTypes on the account
AS-REP roasting not vulnerable ADUC > Attribute Editor > msDS-UserDoesNotNeedPreAuth = FALSE
Unconstrained delegation none ADUC > Attribute Editor > msDS-AllowedToDelegateTo empty on all accounts
Admin/protected accounts msDS-ProtectedFromAccidentalDeletion sAMAccountName ends in an admin flag, or msDS-AdminGroupQuota
Service account in Domain Admins none the single most common real finding
Privileged groups tiered, monitored PAW (Privileged Access Workstations)
LAPS deployed random local admin passwords
Credential filters LSASS protection run as a non-admin user, not a domain admin
SMB share enumeration blocked block guest access, restrict null sessions
Anonymous LDAP bind denied good hygiene, kills recon
Kerberos armouring enabled protects tickets in memory
Constrained delegation instead of unconstrained bind to a service, not to any SPN

The audit questions

  1. Is SMB signing required everywhere, or "required except for X"?
    "Except" is where the exception lives.
  2. How many accounts have msDS-AllowedToDelegateTo set?
    Even one is a finding; it enables TGT forwarding to any service.
  3. How many accounts have preauth disabled?
  4. How many service accounts are in a privileged group?
  5. Can an authenticated non-admin change a group membership?
  6. Is LAPS deployed? (Uniqueness of local admin passwords.)
  7. Is LSASS protected by a credential filter? (MFA - creds available)
  8. Are there any enabled accounts with a blank password?

The uncomfortable answers, in real environments

  • SMB signing "required except for the filer" — a filer that does not
    support it is one relay target away from being a domain compromise
  • One service account in Domain Admins — because the script that runs
    as a service needs rights, and nobody made a second account
  • Preauth disabled on one legacy service account — nobody has retired
    the account
  • No LAPS — three workstations share the same local admin password, and
    it has been in a password file since 2019

Each of these is a five-minute fix that has survived for years.

EOF
