Getting Started: Accounts, Triage and the Download Flow

Summary

CyberDefenders provides free blue-team CTF challenges built from real disk images, memory dumps
and network captures — actual incident data, anonymised, that you download once and analyse
offline. This note covers the mechanics: getting an account, what is in a challenge, and the
triage flow that turns a downloaded artefact into a working hypothesis.

The framing: these are the labs with real answer keys. Everything
else in this tier teaches you the technique; these teach you the
judgement, because there is a specific right answer and it is not
the one you would have guessed.

Companion to for-01 through for-07. Those are the methodology;
this is where you practise it against ground truth.

Accounts and the download flow

  THE FLOW, and the order matters:

    1. CREATE AN ACCOUNT          cyberdefenders.com
                                 Free tier: unlimited challenges,
                                 the same images, and a score.

    2. DOWNLOAD THE CHALLENGE    a .zip or .7z containing
                                 - the artefact (disk image, memory
                                   dump, or PCAP)
                                 - a README with the scenario and
                                   the questions
                                 - sometimes a hash to verify

    3. VERIFY THE HASH           the challenge usually provides one.
                                 If it does not, hash it yourself the
                                 moment you download it, and record
                                 it. That hash is your evidence that
                                 the file you analysed is the file
                                 you downloaded.

    4. WORK ON A COPY            same rule as every other forensic
                                 exercise (for-01). The original
                                 stays read-only.

    5. HASH EVERY FILE YOU       the same rule again. Your carved
       EXTRACT                   artefacts are evidence too.

    6. KEEP NOTES AS YOU GO      the questions are graded. A wrong
                                 answer with no method loses the
                                 same points as a guess.

    7. SUBMIT AND LEARN          the answer key explains the METHOD,
                                 not just the answer. Read it either
                                 way; a challenge you solved by
                                 guessing teaches nothing.

# CyberDefenders setup, done properly

```bash
# 1. an account at cyberdefenders.com (free tier)
# 2. pick a challenge. The disk ones are labelled "Disk Forensics",
#    the memory ones "MemLabs" or "Blue Team", the network ones
#    "Network Forensics".
# 3. download. It arrives as a zip; it contains the artefact and a
#    README with the scenario and the questions.
# 4. store the original, read-only, forever:
      mkdir -p ~/aegis/labs/cd-01/challenges/originals
      cp <downloaded> ~/aegis/labs/cd-01/challenges/originals/
      sha256sum ~/aegis/labs/cd-01/challenges/originals/* \
        | tee ~/aegis/labs/cd-01/notes/<challenge>-hash.txt
      chmod 0444 ~/aegis/labs/cd-01/challenges/originals/*
# 5. work on a copy:
      cp ~/aegis/labs/cd-01/challenges/originals/<file> \
         ~/aegis/labs/cd-01/challenges/work/
# 6. keep notes as you go. The grader is checking method.
```

```text
  THE THREE HABITS THESE LABS BUILD, and they transfer to a real
  engagement more than any technique does:

  1. START BROAD, NARROW FAST
     Enumerate everything cheap, then pick the thread to pull.
     The mistake is going deep on the first thing you find.

  2. EVERY ANSWER NEEDS A METHOD
     "The malware was delivered as an attachment from
      evil.sender@bad-domain.tld on 2026-06-11" plus the evidence
     for each of those three claims. The grader is looking for the
     path, not the destination.

  3. WHEN STUCK, CHANGE ARTIFACT CLASS
     Disk is not answering -> go to memory. Memory is not answering
     -> go to the registry. You cannot force an answer from the
     wrong source; you have to move to the one that has it.
```
EOF

cat > 02-triage.md <<'MD'
# The triage flow, for a disk challenge

```
# --- the whole flow, in order, with the reasoning ---

# 1. WHAT IS IT?
file challenge.dd
#    disk image / raw / EWF / PCAP / memory dump
#    THIS DETERMINES EVERYTHING DOWNSTREAM.

# 2. LAYOUT
mmls challenge.dd
#    partitions. Note the offsets. Note the SIZES: a 200 MB partition
#    on a 500 GB disk means you have the wrong image or a sparse one.
blkls -o <offset> challenge.dd > part1.dd

# 3. FILE SYSTEM
fsstat part1.dd | head -30
#    NTFS or FAT or ext4. Cluster size. Sector size.
#    FAT has no $MFT, no ADS, no USN journal - your technique set is
#    different and you should know that before you start.

# 4. THE ROOTS
fls -r -p part1.dd > mft.txt
#    every file, recursively, with the full path and the inode.
#    READ THIS FILE. It is the map of everything. 5,000 lines of it,
#    and the answer is usually visible in the paths alone:
#      Users\Public\Desktop\readme.txt
#      Users\victim\Downloads\invoice.pdf.exe
#      Windows\Temp\svchost32.exe
#      ProgramData\some-task\some-task.exe
#    anything in Downloads, Temp, ProgramData, Public, or Startup
#    is worth reading.

# 5. THE QUESTIONS, IN THE ORDER THAT ANSWERS THEM
grep -iE "download|desktop|temp|programdata|startup|recycle" mft.txt
grep -iE "\.exe|\.dll|\.bat|\.ps1|\.vbs|\.js|\.scr|\.pif|\.hta" mft.txt
grep -iE "autorun|desktop\.ini|\.lnk" mft.txt

# 6. THE RECYCLE BIN (FAT32 and modern NTFS)
#    \$I files are metadata: original path, size, deletion time
#    \$R files are the content
fls -r -p part1.dd | grep -i recycle

# 7. PREFETCH (NTFS, Windows XP and later)
#    PREFETCH\FOO.EXE-ABCDEF01.pdb
#    ^ every executable that has ever run, with LastRunTime
fls -r -p part1.dd | grep -i prefetch
#    and extract them:
icat part1.dd <inode> > /tmp/pf/FOU.pdb

# 8. THE EVENT LOGS
fls -r -p part1.dd | grep -i "winevt.*\.evtx"

# 9. BROWSER AND APPLICATION HISTORY
fls -r -p part1.dd | grep -iE "history|places\.sqlite|cookies\.sqlite|web data|log\.txt"
```

```text
  THE QUESTIONS YOU WILL BE ASKED, and the artefact that answers each:

  "What is the file hash of the malware?"      -> the carved file,
                                                  then sha256sum
  "What is the file's creation time?"           -> mft, or the
                                                  forensic timeline
  "How was it delivered?"                      -> browser history,
                                                  Downloads mtime,
                                                  email client DB
  "What is the malware's C2 domain?"            -> strings, or the
                                                  config (cry-d4, for-05)
  "When was it first executed?"                -> prefetch LastRunTime
  "What did it persist as?"                    -> Run key, scheduled
                                                  task, service, Startup
  "What did the user do after?"                -> UserAssist,
                                                  RecentDocs (jump lists)
  "Was any data exfiltrated?"                  -> browser downloads,
                                                  %APPDATA%, recycle
                                                  bin contents
  "Are there other compromised hosts?"         -> the network or the
                                                  event logs (4624)
```
MD

# --- 3. the working script ---
cat > 03-triage.sh <<'EOF'
#!/usr/bin/env bash
# First-pass triage of a disk challenge. Read-only.
IMG="${1:?usage: ./03-triage.sh challenge.dd}"
[ -f "$IMG" ] || { echo "no such file"; exit 1; }
W="work/$(basename "$IMG" .dd)"
mkdir -p "$W"

echo "=============================================================="
echo " TRIAGE: $IMG"
echo "=============================================================="
echo "  sha256: $(sha256sum "$IMG" | awk '{print $1}')"
echo "  size  : $(du -h "$IMG" | cut -f1)"
echo "  type  : $(file -b "$IMG")"
echo

echo "=== 1. PARTITIONS ==="
mmls "$IMG" 2>/dev/null | sed 's/^/  /'
# pick the largest NTFS/exFAT partition automatically
OFF=$(mmls "$IMG" 2>/dev/null | awk '
  $2 ~ /^(Linux|win|ntfs|exfat)/ && $3 ~ /^[0-9]+$/ {
    split($3,a,"("); gsub(/[^0-9]/,"",$3);
    if ($3+0 > best) { best=$3+0; off=$1 }
  } END { print (off ? off : 0) }')
echo "  using offset: $OFF"
echo

echo "=== 2. FILE SYSTEM ==="
fsstat -o "$OFF" "$IMG" 2>/dev/null | head -25 | sed 's/^/  /'
echo

echo "=== 3. THE FILE MAP (this is the answer, usually) ==="
fls -o "$OFF" -r -p "$IMG" > "$W/mft.txt" 2>/dev/null
echo "  $(wc -l < "$W/mft.txt") entries -> $W/mft.txt"
echo
echo "  --- directories, so you know the layout ---"
grep -E "d/d" "$W/mft.txt" | head -25 | sed 's/^/    /'
echo
echo "  --- executables and scripts, by extension ---"
grep -iE '\.(exe|dll|bat|ps1|vbs|js|scr|pif|hta|cmd|jar|vbe)$' "$W/mft.txt" \
  | sed 's/^/    /' | head -40
echo
echo "  --- the paths that matter (READ THESE) ---"
grep -iE "\\\\(Downloads|Desktop|Temp|AppData|Startup|ProgramData|Recycle\.Bin)\\\\" \
  "$W/mft.txt" | sed 's/^/    /' | head -40
echo

echo "=== 4. THE PREFETCH (what actually RAN) ==="
grep -i "prefetch" "$W/mft.txt" | grep -iE '\.(exe|com|bat|ps1)' | sed 's/^/  /' | head -40
echo "  ^ filenames are truncated to 8.3. That is normal."
echo "    Compare against the executables above: something in the list"
echo "    with NO prefetch entry never ran."
echo

echo "=== 5. THE EVENT LOGS ==="
grep -iE "\.evtx|\.evt" "$W/mft.txt" | sed 's/^/  /'
echo

echo "=== 6. DELETED ENTRIES (a '*' means deleted) ==="
grep -c '\*' "$W/mft.txt" | xargs echo "  deleted entries:"
grep '\*' "$W/mft.txt" | head -15 | sed 's/^/    /'
echo "  ^ a deleted executable with a prefetch entry ran BEFORE it"
echo "    was deleted. That pair is a strong finding."
echo

echo "=== 7. ALTERNATE DATA STREAMS ==="
fls -o "$OFF" -r -p -l "$IMG" 2>/dev/null | grep -E '\*:' | sed 's/^/  /' | head -20
echo "  (empty is normal on a challenge; the Zone.Identifier ones"
echo "   are the ones that matter)"
EOF
chmod +x 03-triage.sh

# --- 4. the offline concept: the three-source join ---
python3 - <<'PY' 2>&1 | tee 04-join.txt
print("  === why real challenges have ground truth ===\n")
print("  A synthetic lab has a designed answer. A real challenge has an")
print("  INCIDENT that actually happened, and the questions were written")
print("  from the incident timeline.\n")
print("  WHICH MEANS: the answer is always a JOIN of two or more sources.\n")
print("  THE CLASSIC THREES:")
print()
print("    FILE            +  PREFETCH        -> 'it ran at 14:32'"
print("    FILE            +  EVENT LOG       -> 'the parent process'"
print("    FILE            +  MFT TIMES       -> 'created before the"
print("                                         log entry that mentions"
print("                                         it, which is impossible'"
print("    BROWSER HISTORY +  FILE            -> 'downloaded from X"
print("                                         at T, the file is on"
print("                                         disk, its hash is H'"
print()
print("  EXAMPLE, THE JOIN:")
print()
print("    Q: 'What is the SHA-256 of the malicious file?'")
print()
print("    fls shows:  /Users/victim/Downloads/invoice.pdf (inode 4821)")
print("    but the    the file was DELETED from Downloads")
print("    $Recycle   and is in \\$Recycle.Bin\\S-1-5-21-...\\$R0000123.TXT")
print("    fls shows:  \\$I0000123.TXT   (the metadata: original path,")
print("               size, deletion time, in BINARY)")
print()
print("    SO: you read the $I metadata to get the original path and the")
print("    deletion time, then extract the $R content, then hash it.")
print()
print("    A challenge will ask you for the deletion time as a SEPARATE")
print("    question, because that is a different artefact and a different")
print("    skill. The $I file is a small binary struct:")
print()
print("      offset 0   8 bytes  version (1 or 2)")
print("      offset 8   8 bytes  file size")
print("      offset 16  8 bytes  deletion time (FILETIME)")
print("      offset 24  520      original path, UTF-16LE")
print()
print("    THAT STRUCTURE IS THE WHOLE POINT of the question. Reading a")
print("    little-endian FILETIME out of a binary blob is a skill, and")
print("    it is worth practising on three challenges.")
print()
print("  THE OTHER JOIN, AND IT IS THE ONE THAT EARNS THE MOST POINTS:")
print()
print("    Q: 'How did the malware get onto the machine?'")
print()
print("    You need ALL of:")
print("      - browser history: the URL, and the time")
print("      - Downloads: the file, and its hash")
print("      - prefetch: that it ran, and when")
print("      - MFT: its creation time (which predates the run)")
print("      - and usually: the email client's DB, if it came by email")
print()
print("    Each of those is a separate question in most challenges.")
print("    The full narrative is what a report needs, and it is what")
print("    an engagement deliverable actually is.")

# Answering with a method, not a value

```text
  THE GRADER WANTS THE PATH. Write it.

  BAD   Answer: a3f5...9c21
        (correct value, no evidence, no points for method)

  GOOD  Answer: a3f5...9c21
        Source: \\Users\\victim\\Downloads\\invoice.pdf (inode 4821),
                carved from unallocated space, 284,672 bytes
        Chain: Chrome history shows a download from
               http://cdn.legit-cdn.tld/update/x64/invoice.pdf at
               2026-06-11 14:29:03; the file's MFT created time is
               14:29:05; PREFETCH\\INVOICE.EXE-1F2A3B4C.pdb shows
               last run 14:32:41; the file was deleted at 15:04:12
               per \\$I0000123.TXT.
        Method: download -> execution -> deletion.

  The chain is the answer. Each link is a separate claim you can be
  wrong about independently, and that is exactly why it is worth
  points.

Step 3 is the deliverable: 03-triage.sh, a first-pass disk triage that automatically picks
the largest Windows partition, then dumps the file map and greps for the paths that matter —
\Downloads\, \Temp\, \ProgramData\, \Startup\, \Recycle.Bin\ — plus the deleted-entry
count, because a deleted executable that still has a prefetch entry is a strong finding.

Step 4 is the conceptual centre: real challenges are built from real incidents, so the answer
is always a join of two or more sources. It works through the $Recycle.Bin $I file
structure byte by byte — version, size, deletion FILETIME at offset 16, original path at offset
24 — and explains why reading a little-endian FILETIME out of a binary blob is a skill worth
practising on three challenges.

05-method.md is the grading habit: the grader wants the chain, not the value.
