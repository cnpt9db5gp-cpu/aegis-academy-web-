Post-Exploitation and Privilege Escalation

Summary

Post-exploitation answers a single question: what does this access actually give me? A shell
is a capability. A finding is an impact. This lecture is the translation step, and it is where
most of the value in a pentest report is produced.

The discipline is restraint. The instinct after gaining access is to go
further; the professional behaviour is to go exactly far enough to name the
impact, and then stop.

Companion to cs161-05 (privilege separation, the design side). This note
is the offensive side, applied to a live Linux host you own.

The post-exploitation loop

  1. ORIENT        who am I, where am I, what is this box?
  2. LOCALISE      enumerate users, groups, sudo rights, services
  3. EXPLOIT       escalate from current to root, minimally
  4. IMPACT        what does root on this box mean for the business?
  5. RESET         note what you changed, and change it back

Step 5 is the one nobody teaches and the one that saves you a call.

Linux enumeration: the questions, in order

# --- 1. ORIENT ---
whoami; id; hostname; hostname -I
uname -a; cat /etc/os-release
pwd; echo $SHELL; echo $PATH
ps -ef --forest | head -30
ss -tulnp
last | head -5                 # who has been on this box

# --- 2. LOCALISE: what is this user's authority? ---
sudo -l                                     # THE most important command
cat /etc/sudoers /etc/sudoers.d/* 2>/dev/null
id; groups
ls -la ~ ; ls -la ~/                        # readable SSH keys
cat ~/.ssh/id_rsa ~/.ssh/authorized_keys 2>/dev/null   # do not exfiltrate

# --- 3. LOCALISE: what does the host itself expose? ---
ls -l /etc/passwd; awk -F: '$3==0{print "UID 0:", $1}' /etc/passwd   # root accounts
find / -perm -4000 -type f 2>/dev/null     # SUID binaries
find / -perm -2000 -type f 2>/dev/null     # SGID binaries
getcap -r / 2>/dev/null                     # file capabilities
mount | grep -E "nfs|cifs"                  # mounted remote filesystems
cat /etc/crontab; ls -la /etc/cron*        # scheduled tasks
systemctl list-timers --no-pager 2>/dev/null
docker ps 2>/dev/null; ls -la /.dockerenv   # am I in a container?

# --- 4. what would make this a FINDING, not a curiosity? ---
# A readable shadow file, an exposed key, a writable service file, a
# cron job running as root, an NFS mount with no_root_squash.

sudo -l, and why it is the whole game

  (ALL) NOPASSWD: ALL           -> instant root. Report it. Done.
  (root) NOPASSWD: /usr/bin/vi -> run `sudo vi /etc/shadow`, `!sh` from vi
  (ALL) NOPASSWD: /usr/bin/find-> `sudo find . -exec /bin/sh \; -quit`
  (ALL) NOPASSWD: /var/backups -> read/write as root; edit a backup
  (dev) NOPASSWD: /opt/...    -> writable path, escalate via the service

Interpretation matters more than the command. sudo -l showing a
NOPASSWD rule for vi is a Critical finding whose proof is a one-line
escalation, not a whole chain. Knowing which NOPASSWD binaries are
"escape hatches" is the entire skill.

# The classic GTFOBins pattern, demonstrated on a deliberately permissive rule
sudo -l 2>/dev/null | sed 's/^/  /'
# If output contains NOPASSWD for any of: vi vim less more nano awk perl
# python ruby tar find docker systemctl env, note it. Those are escapes.

SUID, correctly understood

  An SUID binary runs with the privileges of its OWNER.
  If it is owned by root, the caller becomes root for its duration.

  Therefore: any SUID binary that
    - executes another program (find, env, tar, awk), or
    - loads a library from a writable path, or
    - inherits an environment variable that changes behaviour
  is a privilege escalation primitive.

  The check that matters:
    1. find SUID files                       -> who owns it?
    2. is it owned by root?                  -> yes, so it is a candidate
    3. can it be made to execute my input?   -> yes, so it is a finding
    4. is there a modern patch?              -> if yes, report + fix path

Not every SUID binary is exploitable. Modern distro SUID sets are
deliberately minimal. But a custom SUID binary written by an application
team is almost always exploitable, and that is where you look.

Kernel exploitation: the last resort

  KERNEL EXPLOIT REQUIRES:
    1. a specific vulnerable kernel version
    2. matching exploit source for that version
    3. matching C compiler / headers / offset tools
    4. knowledge of protections in play (SMEP, SMAP, KASLR, hardened usercopy)
    5. frequently, offsets for that exact build

  ON A MODERN SYSTEM: expect this to fail. Most hardened kernels (Ubuntu,
  Debian, Kali's own) patch the local privesc chains continuously.

  THEREFORE the professional order is:
    1. sudo misconfiguration        -> almost always succeeds
    2. SUID / capability misconfig  -> usually succeeds
    3. writable service / cron file -> usually succeeds
    4. credential in a readable file-> common in real engagements
    5. kernel exploit               -> a report item, not a plan

  A pentest that escalates via kernel exploit when a sudo rule was
  available has wasted the client's time and yours.

Writing back your changes

  THINGS THAT PERSIST AFTER A SHELL:
    - files you wrote                       -> remove
    - history entries                       -> clear, and say so
    - cron jobs / at jobs you created       -> remove
    - SSH keys you added to authorized_keys -> remove
    - users you created                     -> remove
    - systemd units or services you added   -> stop, disable, remove
    - binaries you replaced                 -> restore from package

  THINGS THAT DO NOT PERSIST (but you must confirm):
    - running processes you started
    - open sockets you opened
    - kernel keyrings you touched

  RECORD IT IN THE DIARY:
    "14:02 created /tmp/poc, executed as root, removed at 14:09.
     14:02 added a key for testing, removed at 14:05."
  This is not optional. It is the difference between a clean engagement
  and a client having to reimage a server.

Terminology

Term Meaning
Post-exploitation Determining impact of obtained access
Privilege escalation Gaining higher authority
Vertical escalation Low user to root/Admin
Horizontal escalation User A to user B's resources
SUID Execute with the file owner's privileges
SGID Execute / inherit with the group
File capability Fine-grained privileges without SUID root
sudo -l Enumerate permitted sudo rights
GTFOBins A catalogue of binaries usable for privilege escalation
no_root_squash NFS option that maps root to root — critical
Container escape From a container to the host
Kernel exploit Privilege escalation via a kernel vulnerability
CVE Common Vulnerabilities and Exposures identifier
Shell history Persistent record of commands run

# --- 1. the orient script, written once and reused everywhere ---
cat > orient.sh <<'EOF'
#!/usr/bin/env bash
# Everything you should know about a box, in the first 30 seconds.
echo "=== IDENTITY ==="
id; whoami; hostname; hostname -I 2>/dev/null
echo; echo "=== SYSTEM ==="
uname -a; grep PRETTY /etc/os-release 2>/dev/null
uptime
echo; echo "=== NETWORK ==="
ip -br a; ip route | head -5
ss -tulnp 2>/dev/null | head -15
echo; echo "=== PROCESSES ==="
ps -ef --forest 2>/dev/null | head -20
echo; echo "=== CONTAINER? ==="
[ -f /.dockerenv ] && echo "  /.dockerenv present - INSIDE A CONTAINER" || echo "  not in a container"
cat /proc/1/cgroup 2>/dev/null | head -3
echo; echo "=== AUTHORITY ==="
sudo -n -l 2>/dev/null && echo "  ^ passwordless sudo available"
groups
echo; echo "=== WHAT IS READABLE HERE ==="
ls -la ~ 2>/dev/null | head -10
EOF
chmod +x orient.sh
./orient.sh 2>&1 | tee 01-orient.txt

# --- 2. local enumeration: the full set, explained ---
cat > 02-localise.md <<'EOF'
# Local enumeration, with reasoning

| Command | Question it answers | Finding if... |
|---|---|---|
| `sudo -l` | What can this user do as root? | any NOPASSWD rule on an escape-hatch binary |
| `find / -perm -4000` | Are there SUID binaries? | any custom/non-standard one |
| `getcap -r /` | Do any files carry capabilities? | `cap_sys_admin`, `cap_dac_read_search` |
| `mount` | Are remote filesystems mounted? | NFS with `no_root_squash` |
| `cat /etc/crontab` | What runs on a schedule? | a job you can write to |
| `systemctl list-timers` | What else is scheduled? | same, less visible |
| `ls -la ~/` | What did the user leave? | SSH private keys, passwords, .aws |
| `awk -F: '$3==0' /etc/passwd` | How many root accounts? | more than one |
| `ps -ef` | What runs, as whom? | anything you can influence |
| `docker ps` | Am I containerised? | mounted docker socket |
| `cat /proc/1/cgroup` | Which container am I in? | container id for the escape |

## Order matters
Work outside-in. The user directory first (cheap, usually decisive), then
sudo (cheap, usually decisive), then SUID (cheap), then services (expensive),
then the kernel (last, and usually a report item instead).
EOF
echo "written: 02-localise.md"

# --- 3. the SUID audit ---
{
  echo "=== SUID binaries on this host ==="
  echo "  A SUID-root binary executes with root privileges for its caller."
  echo "  If it can be made to run another program, that is an escalation."
  echo
  find / -perm -4000 -type f 2>/dev/null | while read -r f; do
    own=$(stat -c %U "$f" 2>/dev/null)
    if [ "$own" = "root" ]; then tag="ESCAPE-HATCH CANDIDATE"; else tag="owned by $own"; fi
    printf "  %-60s %s\n" "$f" "$tag"
  done
  echo
  echo "=== the canonical escape-hatch list ==="
  echo "  These execute other programs or load libraries:"
  for b in find env awk perl python ruby tar vi vim less more nano \
           docker systemctl nsenter busybox; do
    if command -v "$b" >/dev/null 2>&1; then
      printf "  %-12s present at %s\n" "$b" "$(command -v $b)"
    fi
  done
  echo
  echo "  If any of the above is granted NOPASSWD sudo, escalation is trivial."
} 2>&1 | tee 03-suid.txt

# --- 4. what an escalation actually looks like, in its minimal form ---
cat > 04-escalation.md <<'EOF'
# Minimal escalation proofs

Each of these is a *demonstration*, not a payload. The report contains the
command; the target contains the consequence.

## From a NOPASSWD sudo rule
```bash
sudo -l | grep NOPASSWD          # the finding
sudo -u root /bin/bash -c 'id'  # the proof (only if permitted)

From a writable service file

ls -l /etc/systemd/system/app.service   # writable by your user?
cat /etc/systemd/system/app.service     # what does it run as?
# finding: a user-writable unit that runs as root is immediate root

From a cron job you can write

cat /etc/cron.d/app                    # root-owned, writable?
ls -l /var/spool/cron/crontabs/$(whoami)
# finding: user crontab entries run as the user, but /etc/cron.d
# entries often run as root - check the file, not the name

From an NFS mount

mount | grep nfs
# if no_root_squash is set:
sudo -u#-1 id     # maps to uid -1, which many NFS stacks treat as root

From a container

ls -la /var/run/docker.sock           # mounted? -> host root
cat /proc/1/cgroup
# finding: docker socket mounted into the container is a full host escape

From a kernel CVE

uname -r
# check for a matching local privesc in your resources; if none, this is
# a REPORT ITEM, not a plan. Do not spend the day.

What goes in the report

  • the misconfiguration (the finding)
  • the minimal command that demonstrates it (the evidence)
  • the fix (remove the rule / drop the SUID bit / fix ownership)
    EOF
    echo "written: 04-escalation.md"

--- 5. impact: the translation from capability to finding ---

cat > 05-impact.md <<'EOF'

From capability to finding

What you did What you write
got a shell on the web server Medium — Unauthenticated remote code execution on WEB-01
escalated to root on it High — Local privilege escalation on WEB-01, any account becomes root
read the application config, found a DB password High — Database reachable with a credential in a web-readable file
read the customer table Critical — Full customer database exposed to an unauthenticated attacker
pivoted to 40 hosts Critical — Flat internal network; the web server foothold compromises everything

The rule

Severity is a function of what an attacker gains, not of what you did.
Report the end of the chain, not the middle of it.

What you stop at

Prove that you can read the table. Do not read the table.
Prove that you can pivot to the file server. Do not pivot.
The client does not need the data. They need to know it is there.
EOF
echo "written: 05-impact.md"

--- 6. clean up after yourself, and prove it ---

cat > 06-cleanup.sh <<'EOF'

!/usr/bin/env bash

Post-engagement cleanup verification. Run it, and put the output in the report.

echo "=== files modified in the last N hours outside package paths ==="
find / -xdev -mmin -180 -type f \
-not -path "/proc/" -not -path "/sys/" -not -path "/run/" \
-not -path "/tmp/" -not -path "/var/log/" \
-not -path "/home//.cache/*" 2>/dev/null | head -20

echo; echo "=== scheduled tasks you might have added ==="
systemctl list-timers --no-pager 2>/dev/null | tail -5
crontab -l 2>/dev/null | sed 's/^/ /'

echo; echo "=== processes not belonging to a package ==="
ps -eo pid,user,etimes,cmd --sort=-etimes | awk 'NR==1 || $3 < 600' | head -10

echo; echo "=== shell history ==="
for h in ~/.bash_history ~/.zsh_history; do
[ -f "$h" ] && echo " $h: $(wc -l < "$h") lines, $(stat -c %y "$h")"
done
echo " (state in the report whether history was cleared and who authorised it)"

echo; echo "=== SSH keys ==="
ls -la ~/.ssh/ 2>/dev/null
ssh-keygen -lf ~/.ssh/authorized_keys 2>/dev/null | sed 's/^/ /'

echo; echo "=== new users ==="
awk -F: '$3>=1000 && $3<65534 {print " " $1}' /etc/passwd
EOF
chmod +x 06-cleanup.sh
./06-cleanup.sh 2>&1 | tee 06-cleanup.txt

--- 7. LINPEAS: read it, don't just run it ---

cat > 07-linpeas.md <<'EOF'

Reading LinPEAS before you run it

LinPEAS (and PrivescSpawn, pspy, and every other enumeration framework)
runs hundreds of checks. That is a problem for two reasons:

  1. Noise. Several hundred commands against a production host can trip
    monitoring, and the client may call you. Confirm in the ROE that
    enumeration tooling is permitted.

  2. Interpretation. A green "YES" is not a finding. The script finds
    conditions; you must convert them to impact.

How to use one properly

# 1. read what it will do, before doing it
head -40 /usr/share/linpeas/linpeas.sh

# 2. run it once, capture everything, work OFFLINE afterwards
sudo bash /usr/share/linpeas/linpeas.sh -a > ~/aegis/labs/tcm-05/linpeas.txt 2>&1

# 3. grep the output for the conditions that mean something
grep -iE "sudo.*NOPASSWD|sgid|interesting|dirty|escalat|exploit" linpeas.txt | head -30

# 4. verify EVERY hit manually before it goes in a report
#    LinPEAS false positives are common and embarrassing

The manual checks LinPEAS automates — do these first by hand

  • sudo -l
  • find / -perm -4000
  • cat /etc/crontab
  • mount for NFS
  • ls -la ~ for credentials

If those five give you nothing, LinPEAS probably will too, and you have
learned five skills instead of one tool invocation.
EOF
echo "written: 07-linpeas.md"
```

Step 3 is the deliverable: an actual SUID audit of this machine, sorted into
escape-hatch candidates versus ordinary binaries. Every one of those candidates is a
prerequisite for a finding, and knowing which binaries matter is the difference between
running a tool and understanding escalation.

Step 6 produces the artifact that makes a client trust the report: proof that you left
nothing behind.
