Wireless, Security and Network Automation

Summary

Wireless changes the threat model entirely: the medium is shared, frames are radio, and "who is
on this network" becomes a physical-space question. Automation is the other half — modern
networks are defined in files, which means the configuration is code, and code has bugs.

Key ideas

  • WPA3 replaces WPA2's 4-way handshake weakness; enterprise mode (802.1X/RADIUS) is the real
    answer, not a shared passphrase
  • WPA2 personal uses a 4-way handshake whose MIC can be attacked offline; tools exist
  • Evil twin: a rogue AP with the same SSID. Works because SSIDs are not authenticated
  • WPA3-SAE (Simultaneous Authentication of Equals) resists offline dictionary attacks;
    dragonfly is the key derivation
  • 802.11 management frames are unauthenticated by design — required for discovery
  • Network as code: Ansible, Terraform, Jinja templates. Review the config, not the device

Terminology

Term Meaning
SSID The network's name; broadcast in plaintext
BSSID The access point's MAC
Beacon Periodic broadcast announcing an AP
WEP Broken; do not deploy
WPA/WPA2/WPA3 Successive security standards
PSK Pre-shared key (personal mode)
802.1X / RADIUS Enterprise authentication per-user
SAE (Dragonfly) WPA3's key agreement, resistant to offline attack
Evil twin Rogue AP impersonating a legitimate one
Deauth Management-frame attack forcing a client off an AP
Network automation Config as version-controlled code

# --- the wireless security posture of your OWN AP ---

# --- network as code ---
command -v ansible terraform cidr-merge

# --- config drift: compare what is running to what is written ---
diff <(ip -br addr) <(cat /etc/network/interfaces 2>/dev/null) | head -10
echo "  (differences here are unmanaged configuration = findings)"

# --- hardcoded credentials in config, the automation-era version ---
grep -rniE "(password|passwd|secret|api_key)[[:space:]]*[=:]" /etc/ansible /etc/netplan 2>/dev/null | head

Field lab

Objective: understand the wireless threat model, and audit your own network configuration
the way an assessor would.

mkdir -p ~/aegis/labs/ccnad-04 && cd ~/aegis/labs/ccnad-04

# --- 1. what your own wireless hardware supports ---
{
  echo "=== wireless interfaces ==="
  iw dev 2>/dev/null || echo "  (iw not installed or no wireless device)"
  echo
  echo "=== drivers ==="
  lsmod | grep -E "rtw|ath|iwlwifi|brcm|mt76" || echo "  (none loaded - possibly a wired-only machine)"
  echo
  echo "=== regulatory domain ==="
  iw reg get 2>/dev/null | head -5
} 2>&1 | tee 01-wireless.txt

echo
echo "NOTE: this lab deliberately does not teach scanning of any wireless network"
echo "other than your own. See docs/RULES-OF-ENGAGEMENT.md - Wi-Fi testing requires"
echo "written authorisation for the network owner."

# --- 2. how WPA2's handshake can be attacked, conceptually ---
cat > 02-wpa2.md <<'EOF'
# WPA2 and the 4-way handshake

Four messages establish a session key from the PSK:

  AP -> STA   Message 1
  STA -> AP   Message 2
  AP -> STA   Message 3   <- carries the MIC, the target of offline attacks
  STA -> AP   Message 4

The PSK is derived from the SSID and the shared passphrase, both of which are
broadcast in the clear in every beacon frame. Given a captured handshake, an
attacker verifies passphrase guesses locally, with no online rate limit.

WPA2-Enterprise removes this entirely: each user has a distinct credential
verified by RADIUS, so capturing one handshake reveals nothing about any other.

WPA3-Personal replaces the handshake with SAE (Dragonfly), which resists
offline dictionary attack by design.

**Security takeaway:** the weakness is not in the cipher, it is in the *key
agreement* and in everyone sharing one secret. That is a recurring pattern
throughout this course.
EOF
cat 02-wpa2.md

# --- 3. the config-drift audit, which applies to every network ---
cat > 03-audit.sh <<'EOF'
#!/usr/bin/env bash
# Configuration drift and hygiene audit for your own host.
set -uo pipefail
say(){ printf '\n=== %s ===\n' "$*"; }

say "listeners bound beyond loopback"
ss -tulpn | awk '$5 ~ /0\.0\.0\.0|\*/ {print "  " $1, $5, $7}'

say "world-reachable services on this LAN (the real risk on a laptop)"
ss -tulpn | awk '$5 ~ /0\.0\.0\.0|\*/' | wc -l | xargs echo "  count:"

say "firewall state"
sudo iptables -S 2>/dev/null | head -10 || echo "  (no iptables access)"
sudo nft list ruleset 2>/dev/null | head -10 || echo "  (no nft ruleset)"

say "credentials in configuration"
sudo grep -rniE "(password|secret|api[_-]?key)[[:space:]]*[=:]" \
     /etc/netplan /etc/NetworkManager /etc/systemd/system 2>/dev/null | head -5

say "listening services with their owning package"
ss -tulpn | grep -oE 'users:\(\("[^"]+"' | sort -u | sed 's/users:(//'

say "updates pending"
apt list --upgradable 2>/dev/null | tail -n +2 | wc -l | xargs echo "  packages:"
EOF
chmod +x 03-audit.sh && ./03-audit.sh 2>&1 | tee 04-audit.txt

# --- 4. the network-as-code lesson ---
cat > 05-automation.md <<'EOF'
# Configuration as code: what changes for a security reviewer

**Before**: you read a device's running configuration. What you see is what is applied.

**After**: you read a repository. Several files, possibly templated, several
people's commits, and the deployed state may or may not match.

New review questions:
1. Is the config in version control? (history = who changed what, when)
2. Is it templated? (Jinja variables can inject unexpected values)
3. Where do secrets come from? (vault, environment variable, committed plaintext?)
4. Is there a drift check in CI? (config that nobody reviews silently rots)
5. Does the automation run with sufficient privilege, from where, and as which identity?

The last point is the big one: an automation system is a **privileged
credential in a script**. Ansible, Terraform and CI runners are targets in
their own right, and their logs are evidence.
EOF
cat 05-automation.md

Step 3 is the deliverable and applies directly to your Kali laptop: anything listening on
0.0.0.0 is visible to your entire Wi-Fi network right now. Close those before continuing.
