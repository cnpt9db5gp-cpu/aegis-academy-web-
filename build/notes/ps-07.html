JWT Attacks and Session Management

Summary

Sessions are the ambient authority of the web: whatever the browser attaches automatically, your
application trusts. This lecture covers the two implementations of "ambient authority" —
opaque server-side session tokens and self-contained JWTs — and the specific attacks each
configuration allows.

The framing that matters: a session mechanism has exactly two trust
decisions to get right — is the token authentic, and is it valid for
this request. Everything here is one of those two being wrong.

Opaque tokens (server-side sessions)

  BROWSER                          SERVER
  session=8f2a...  ---------->   look up in the session store
                  <----------     {"uid": 2, "role": "user"}

  + the server decides everything: expiry, invalidation, role
  + logout can be real
  - the store is state (and a scaling problem)
  - a store compromise is a total account compromise

JWT: self-contained

  header  {"alg":"HS256","typ":"JWT"}
  payload {"sub":2,"role":"user","exp":1234}
  signing input = base64url(header) + "." + base64url(payload)
  signature   = HMAC(signing_input, secret)

  SERVER VERIFIES THE SIGNATURE AND READS THE CLAIMS. No database.

Everything follows from those two properties. Self-contained means
the server does not need state, and self-contained also means the server
trusts data it received from the client — signed or not, that data was
produced by the client. The signature only proves nobody edited it in
transit.

The attacks

1. alg: none

{"alg":"none","typ":"JWT"}

  A verifier that reads alg from the header and then, seeing "none",
  skips verification entirely will accept:
    base64url(header).base64url(payload).
  ...with NO signature at all.

  This was in a huge number of real libraries. It is the canonical JWT bug.

# forge one, live
import base64, json
def b64(d): return base64.urlsafe_b64encode(json.dumps(d,separators=(',',':')).encode()).rstrip(b'=')
token = b64({"alg":"none","typ":"JWT"}) + b'.' + b64({"sub":1,"role":"admin"}).replace(b'=',b'=')

2. Algorithm confusion (RS256 → HS256)

  Server has an RSA PUBLIC key. It expects RS256, so it has the public
  key, not the private key.

  Attack: send  {"alg":"HS256"} with the PUBLIC KEY as the HMAC secret.
  The server, seeing HS256, HMACs with a key it holds - the public key.
  You signed it with the public key too. Valid signature.

  THE ASYMMETRY LEAK: RS256 verification needs only the public key.
  HS256 signing needs the secret. If the same key material is accepted
  for both, the public key becomes a signing key.

3. Weak secrets (HS256)

  "secret", "changeme", the app name, an empty string, a JWKS URL.
  A JWT is self-contained and offline-verifiable, so the attacker can
  brute-force the secret LOCALLY with no rate limit and no lockout.

  THAT IS THE POINT: the signing key is a password, and it is being
  used as one. Give it 32+ bytes of real entropy.

4. No algorithm allowlist / verifier confusion

  The correct behaviour is: configure the expected algorithm, and
  reject anything else. Never "take the algorithm from the token".

  Also: validate the signature against the header AND payload as
  separate arrays with a constant-time comparison. Some libraries
  compared the header on one path and the payload on another.

5. Claims you do not check

  iss   - who issued it. Unchecked, another issuer's token is accepted.
  aud   - who it is for. Unchecked, a token for another app is accepted.
  exp   - expiry. Unchecked, tokens are valid forever.
  nbf   - not before. Unchecked, negative-time tokens are accepted.
  jti   - a unique id. Unchecked, no revocation is possible at all.
  sub   - the subject. Unchecked, impersonate anyone.
  ALGORITHM FROM THE TOKEN - see above.
  kid   - which key. Unchecked, path traversal or SQL injection in the
          key lookup is a classic JWT vulnerability.

  THE CLIENT MUST NOT DECIDE. If the client checks the signature and
  sends {sub, role} to the API, the API has to verify again. A client
  that "decrypts" a JWT and uses its claims has given the user a
  forged-claims ticket.

Session management, the parts that are not JWT

  FIXATION       the attacker sets the session id BEFORE you log in.
                 If you do not regenerate on privilege change, the
                 attacker already has the winning ticket.
  PRE-AUTH       issue no session to anonymous users; or at least a
                 different one, and rotate it at login.
  ROTATION       new id at login AND at every privilege change
  INVALIDATION   server-side deletion on logout; JWT needs a denylist
                 or a short expiry
  ENTROPY        128+ bits from a CSPRNG, not 32 bits of counter
  COOKIE FLAGS   HttpOnly (no JS), Secure (no plaintext), SameSite
  SCOPE          narrow Path, short max-age, no domain wildcard
  ERROR HANDLING identical response for unknown vs expired token

SameSite deserves its own emphasis: it is the control that stops
CSRF (ps-04's cousin) without needing tokens at all, and it is
under-implemented because SameSite=None requires Secure, which
people work around by dropping Secure.

Terminology

Term Meaning
Session Server-side state keyed by an opaque token
JWT JSON Web Token: base64url header.payload.signature
alg: none Signature verification skipped entirely
Algorithm confusion RS256 → HS256 using the public key as the secret
Claim A field in the payload
iss / aud / exp / nbf Issuer / audience / expiry / not-before
kid Which key to verify with; a classic injection vector
JWKS The endpoint publishing public keys
Session fixation Attacker plants the id before login
Session rotation New id on privilege change
HttpOnly JavaScript cannot read the cookie
Secure Only sent over HTTPS
SameSite Controls cross-site sending; Lax is the modern default
Stateless No server-side session store
Revocation Making a token invalid before its expiry

# --- 1. JWT forge/verify toolkit, written from scratch so the mechanics
#        are visible rather than hidden behind a library ---
cat > jwt.py <<'PY'
#!/usr/bin/env python3
"""JWT mechanics, no libraries.

Everything here is base64url and HMAC. Once you have written it once,
JWT attacks stop being mysterious: they are all about WHICH of these
three steps the server skips or gets wrong.
"""
import base64, json, hmac, hashlib, sys

def b64u_encode(b: bytes) -> bytes:
    return base64.urlsafe_b64encode(b).rstrip(b"=")

def b64u_decode(s: bytes) -> bytes:
    s += b"=" * (-len(s) % 4)
    return base64.urlsafe_b64decode(s)

def sign_hs256(header: dict, payload: dict, secret: str) -> str:
    h = b64u_encode(json.dumps(header, separators=(",", ":")).encode())
    p = b64u_encode(json.dumps(payload, separators=(",", ":")).encode())
    signing_input = h + b"." + p
    sig = hmac.new(secret.encode(), signing_input, hashlib.sha256).digest()
    return (signing_input + b"." + b64u_encode(sig)).decode()

def verify_hs256(token: str, secret: str, expected_alg="HS256") -> bool:
    parts = token.split(".")
    if len(parts) != 3: return False
    h, p, s = parts
    hdr = json.loads(b64u_decode(h.encode()))
    # THE CHECK THAT MATTERS: is the algorithm the one I configured?
    if hdr.get("alg") != expected_alg: return False
    expect = hmac.new(secret.encode(), (h + "." + p).encode(), hashlib.sha256).digest()
    return hmac.compare_digest(b64u_decode(s.encode()), expect)   # constant time

def forge_none(payload: dict) -> str:
    return (b64u_encode(b'{"alg":"none","typ":"JWT"}') + b"." +
            b64u_encode(json.dumps(payload, separators=(",", ":")).encode()) +
            b".").decode()

if __name__ == "__main__":
    print(__doc__)
PY

# --- 2. a vulnerable verifier, written exactly as it appears in the wild ---
cat > verify-bad.php <<'PHP'
<?php
// THREE bugs, all real, all still seen:
//   1. alg is taken from the token, not configured
//   2. "none" means skip verification
//   3. claims are used without checking exp / iss / aud
function b64u(string $s): string {
    return base64_encode(strtr($s, '-_', '+/'));
}
function verify_bad(string $t): ?array {
    $p = explode('.', $t);
    if (count($p) !== 3) return null;
    $hdr = json_decode(base64_decode(strtr($p[0], '-_', '+/')), true);
    $pl  = json_decode(base64_decode(strtr($p[1], '-_', '+/')), true);
    if (!$hdr || !$pl) return null;
    if (($hdr['alg'] ?? '') === 'none') return $pl;          // BUG 1 + 2
    if (!hash_equals($p[2], $p[2])) return null;
    if (($pl['exp'] ?? 0) < time()) return null;              // half of BUG 3
    return $pl;                                             // no iss, no aud
}
$tok = $_GET['t'] ?? '';
$c = verify_bad($tok);
header('Content-Type: text/html; charset=utf-8');
echo $c ? "ACCEPTED: " . json_encode($c) . "<br>" : "REJECTED<br>";
echo "<p>you are: " . htmlspecialchars($c['sub'] ?? '-') .
     " role=" . htmlspecialchars($c['role'] ?? '-') . "</p>";

cat > verify-good.php <<'PHP'
<?php
// THE FIX. Four changes, all of them necessary.
const EXPECTED_ALG = 'HS256';
const SECRET       = 'a-real-32-byte-secret-not-in-source-control';
const ISSUER       = 'https://aegis.local';
const AUDIENCE     = 'aegis-app';

function b64u(string $s): string { return base64_decode(strtr($s, '-_', '+/')); }

function verify_good(string $t): ?array {
    $p = explode('.', $t);
    if (count($p) !== 3) return null;

    $hdr = json_decode(b64u($p[0]), true);
    $pl  = json_decode(b64u($p[1]), true);
    if (!is_array($hdr) || !is_array($pl)) return null;

    // 1. ALGORITHM IS CONFIGURED, NOT CHOSEN BY THE TOKEN
    if (($hdr['alg'] ?? '') !== EXPECTED_ALG) return null;
    if ($hdr['typ'] ?? '' !== 'JWT') return null;

    // 2. SIGNATURE, constant time
    $expect = rtrim(strtr(base64_encode(
        hash_hmac('sha256', $p[0] . '.' . $p[1], SECRET, true)), '+/', '-_'), '=');
    if (!hash_equals($expect, $p[2])) return null;

    // 3. CLAIMS
    $now = time();
    if (($pl['iss'] ?? '') !== ISSUER)   return null;
    if (($pl['aud'] ?? '') !== AUDIENCE) return null;
    if (($pl['exp'] ?? 0) <= $now - 60)  return null;   // small clock skew
    if (($pl['nbf'] ?? 0) >  $now + 60)  return null;

    return $pl;
}
$t = $_GET['t'] ?? '';
$c = verify_good($t);
header('Content-Type: text/html; charset=utf-8');
echo $c ? "ACCEPTED: " . json_encode($c) . "<br>" : "REJECTED<br>";
if ($c) echo "<p>you are: " . htmlspecialchars($c['sub']) .
               " role=" . htmlspecialchars($c['role']) . "</p>";

# --- 8. the audit checklist ---
cat > 05-audit.md <<'EOF'
# JWT and session audit

## Token handling
- [ ] `alg` is CONFIGURED on the server, never read from the token
- [ ] `"none"` is explicitly rejected
- [ ] An algorithm allowlist exists; unknown algorithms are rejected
- [ ] Signature comparison is constant time (`hmac.compare_digest`)
- [ ] The whole token is verified as one signing input, not fields piecemeal
- [ ] Key rotation is supported (multiple valid keys, or `kid`)
- [ ] `kid` is not passed into a query or a file path unsanitised
- [ ] HS256 secrets are 32+ bytes of real entropy, from a secret manager

## Claims
- [ ] `iss` checked against a configured value
- [ ] `aud` checked against a configured value
- [ ] `exp` checked, with a small clock-skew allowance
- [ ] `nbf` checked
- [ ] `sub` is used to look the user up on EVERY request (not cached
      in a claim), so a deleted user cannot keep a valid token
- [ ] `jti` present, and a revocation path exists

## Sessions
- [ ] Session id has >= 128 bits of entropy from a CSPRNG
- [ ] Regenerated on login and on every privilege change
- [ ] No session issued to an anonymous visitor (or rotated at login)
- [ ] Logout invalidates server-side
- [ ] Idle and absolute expiry both set
- [ ] Cookie: HttpOnly, Secure, SameSite=Lax (or Strict), narrow Path,
      no Domain wildcard
- [ ] Session id never appears in a URL (it leaks via Referer and history)

## Client-side
- [ ] The CLIENT does not make authorisation decisions from token claims
- [ ] The API re-verifies every request
- [ ] "Decode" is not used where "verify" is required

## Reporting
- [ ] `alg:none` accepted      -> Critical
- [ ] HS256 with a guessable secret -> Critical
- [ ] `aud` unchecked           -> High (cross-service token reuse)
- [ ] no rotation on login       -> High (session fixation)
- [ ] token in a URL             -> Medium (leakage)
- [ ] cookie without HttpOnly    -> Medium (XSS chain, see ps-03)
EOF

Step 4 is the deliverable: the attack battery run for real, with each forgery's outcome
recorded. alg: none with garbage in the signature position is the result to look at —
verifiers that skip the check entirely accept anything there.

Step 5 is the part that separates a reader from a scanner: the same battery against the
fixed verifier, where every forgery is rejected and the legitimate token still works. You cannot
write a fix you have not watched defeat.
