Instructions, Registers and Flags

Summary

x86-64 has sixteen 64-bit general purpose registers, a flags register that every arithmetic
instruction updates, and an instruction set that is far more regular than it first appears.
Regularity is the reason it can be disassembled, and the reason it can be exploited: the
instruction set is the attack surface.

The registers

  64-bit  32-bit  16-bit  8-bit(h) 8-bit(l)
  rax    eax    ax      al       ah       <- accumulator, return value
  rbx    ebx    bx      bl       bh       <- callee-saved
  rcx    ecx    cx      cl       ch       <- shift/loop count
  rdx    edx    dx      dl       dh       <- 2nd arg, div
  rsi    esi    si      sil      --       <- 1st source
  rdi    edi    di      dil      --       <- 1st destination, 1st arg
  rbp    ebp    bp      bpl      --       <- frame pointer, callee-saved
  rsp    esp    sp      spl      --       <- stack pointer
  r8-r15 -> same sub-register names (r8d/r8w/r8b)
  rip                                      <- instruction pointer

  SPECIAL:
    rax/rdi  -> sys_write, sys_exit, first arg
    rax/rcx/rdx -> sys_open
    rax/rdi/rsi/rdx/r10/r8/r9 -> sys_execve (note: r10, not rcx)
    rsp      -> always points at the stack
    rip      -> points at the next instruction

The multi-name trick is why mov al, 0x41 followed by mov ah, 0x42 produces
0x4241 in ax. Writing a byte register does not zero-extend the
whole register; only 32-bit writes clear the top 32 bits (the
"zero-extension" behaviour that surprises everyone once).

cat > /tmp/zext.asm <<'ASM'
    .text
    .globl _start
_start:
    mov     rax, 0x1122334455667788
    mov     eax, 0x99             ; 32-bit write ZEROES the top 32 bits
    mov     rbx, 0x1122334455667788
    mov     bl,  0x99             ; 8-bit write changes ONE byte
    mov     rax, 60
    mov     rdi, 0x11223344556677
    mov     rdi, 0
    syscall
ASM
nasm -f elf64 /tmp/zext.asm -o /tmp/zext.o 2>/dev/null && ld -o /tmp/zext /tmp/zext.o
echo "  rbx = 0x1122334455667788; mov bl, 0x99  ->  rbx = 0x1122334455667799"
echo "  rax = 0x1122334455667788; mov eax, 0x99 ->  rax = 0x0000000000000099"
echo "  ^ the 32-bit write cleared everything. gdb on /tmp/zext confirms both."
rm -f /tmp/zext.asm /tmp/zext.o /tmp/zext

Flags

  CF  carry flag          unsigned overflow / borrow
  ZF  zero flag           result == 0
  SF  sign flag           result's top bit (negative as signed)
  OF  overflow flag       signed overflow
  PF  parity              low byte has even parity

  Set by almost every arithmetic and logic instruction.
  Read by jcc and setcc.

  THE CLASSIC PAIR:
    cmp a, b        -> does NOT modify a or b, only the flags
    je  target      -> jump if ZF  (equal)
    jne target      -> jump if !ZF (not equal)
    ja  target      -> jump if CF=0 and ZF=0  (above, unsigned)
    jb  target      -> jump if CF=1           (below, unsigned)
    jg  target      -> jump if ZF=0 and SF=OF (greater, signed)
    jl  target      -> jump if SF != OF       (less, signed)

  CMP is SUB without storing. That is the whole idea, and it is why
  `cmp` is the instruction you see before almost every branch.

The instruction patterns you actually read

  MOV     dst, src        copy
  LEA     dst, [expr]      compute an ADDRESS (no memory access!)
  ADD/SUB r, imm           arithmetic
  CMP     a, b             set flags, keep both operands
  TEST    a, b             AND without storing; sets ZF if (a&b)==0
  PUSH    r                rsp -= 8; [rsp] = r
  POP     r                r = [rsp]; rsp += 8
  CALL    target           push return address; jmp target
  RET                     pop into rip
  JMP/Jcc target           branch
  XOR     r, r            zero a register (NOT "toggle" when dst==src)
  NOP                     padding (multi-byte NOPs exist on x86-64)
  SYSCALL                 trap to the kernel

LEA is the one that confuses beginners. It computes an address and
stores it in a register, without reading memory. lea rax, [rbp-8] means
"put the address rbp-8 in rax", which is not "load the value at
rbp-8" — that is mov rax, [rbp-8]. Reading a disassembly and
misreading lea as a load is one of the most common early errors.

XOR r, r zeroing works because a XOR a == 0 for any a. It is the
idiomatic way to clear a register and, unlike mov r, 0, is two bytes
(31 c0).

Why the instruction set is the attack surface

  RET pops whatever is at rsp into rip.
  Therefore: whoever controls [rsp] controls where execution goes.

  CALL pushes a return address.
  Therefore: whatever is on the stack at the moment of a ret is a target.

  Consequences, in order of importance:
    1. a stack overflow controls rip -> ROP
    2. a function pointer you control controls rip -> call to chosen address
    3. a vtable entry you control controls rip -> same, in C++
    4. `jmp [rax]` / `call [rax]` -> "indirect", and everything above
  There is no instruction that jumps somewhere without something
  designating the destination. Corrupt the designation, corrupt control flow.

This is why cs161-04's exploit chain is really a chain of
register-designation problems.

Encoding, in the smallest useful amount

  Instruction bytes contain: opcode, ModR/M byte, SIB, displacement,
  immediate - in an order that varies.

  Two consequences:
    - the length of an instruction is NOT fixed (1 to 15 bytes)
    - you cannot decode starting from a misaligned offset

  That second point is why a disassembler given the wrong entry point
  produces total garbage, and why the first thing you do when reversing
  is find a known function entry (a prologue, or a string reference).

Terminology

Term Meaning
GPR General purpose register
Zero-extension A 32-bit write clears the upper 32 bits
Flags register Condition codes; rflags on x86-64
cmp Compare without storing; sets flags
test Bitwise AND without storing
lea Compute an address; does not read memory
Prologue push rbp; mov rbp,rsp
Epilogue leave (mov rsp,rbp; pop rbp) then ret
ModR/M The byte encoding operands
Instruction length Variable, 1–15 bytes
Indirect branch call [rax], jmp [rbp+8]
Gadget Any instruction sequence ending in a useful transfer
syscall The user-to-kernel transition
Redundant encoding Multiple byte sequences for one instruction

Kali commands

mkdir -p ~/aegis/labs/lo-03 && cd ~/aegis/labs/lo-03

# --- 1. read a real function and annotate it ---
cat > ops.c <<'EOF'
#include <stdio.h>
int classify(int n) {
    if (n < 0)   return -1;
    if (n == 0)  return 0;
    if (n < 10)  return 1;
    return 2;
}
int main(void) {
    for (int i = -3; i <= 12; i++) printf("%d -> %d\n", i, classify(i));
    return 0;
}
EOF
gcc -g -O0 -no-pie ops.c -o ops

{
  echo "=== classify() as the CPU will execute it ==="
  objdump -d --no-show-raw-insn ops | sed -n '/<classify>:/,/^$/p'
  echo
  echo "=== ANNOTATION ==="
  echo "  push rbp / mov rbp,rsp / sub \$0x10,rsp    <- prologue"
  echo "  mov -0x4(%rbp),%eax                        <- load n"
  echo "  cmp \$0x0,%eax / jl  ...                    <- n < 0    (SF != OF)"
  echo "  cmp \$0x0,%eax / je  ...                    <- n == 0   (ZF set)"
  echo "  cmp \$0x9,%eax / jg  ...                    <- n > 9    (signed)"
  echo "  mov \$0x2,%eax / jmp leave                  <- default"
  echo "  leave / ret                                 <- epilogue"
  echo
  echo "  Note there is no 'n' register: every branch re-loads from the"
  echo "  stack slot. That is -O0 behaviour and it is why -O0 output is"
  echo "  far easier to reverse than optimised output."
} 2>&1 | tee 01-classify.txt

{
  echo "=== the SAME logic in assembly, hand-written ==="
  echo "  the shape every beginner internalises:"
  cat <<'ASM'
    classify:                ; int classify(int n)   n is in edi
        cmp     edi, 0
        jl      .neg
        je      .zero
        cmp     edi, 9
        jg      .big
        mov     eax, 1
        ret
    .neg:  mov eax, -1 ; ret
    .zero: mov eax, 0  ; ret
    .big:  mov eax, 2  ; ret
ASM
  echo
  echo "  Same branches, same flags, same outcomes. Now you can read either"
  echo "  direction, which is the actual skill."
} 2>&1 | tee 02-asm.txt

# --- 2. LEA is not a load ---
python3 - <<'PY' | tee 03-lea.txt
import dis  # not x86, but the same idea: address vs value

# demonstrate the confusion concretely with a C pair that compiles to
# exactly this distinction
print("  C:   int x = arr[i];          -> MOV  eax, [rbp-4+rax*4]   (a LOAD)")
print("  C:   int *p = &arr[i];        -> LEA  rax, [rbp-4+rax*4]   (an ADDRESS)")
print()
print("  Assembly:")
print("    lea rax, [rbp-8]     ; rax = rbp-8          <- NO memory access")
print("    mov rax, [rbp-8]     ; rax = *(rbp-8)       <- reads memory")
print()
print("  Read a disassembly and swap these and you will conclude the")
print("  program reads a pointer from the stack when it does not. This is")
print("  the single most common misreading in early RE work.")
print()
print("  Rule of thumb: LEA's operand is an address expression, and LEA")
print("  never appears with a memory destination on x86-64.")
PY
cat 03-lea.txt

# --- 3. flags, observed directly ---
cat > 04-flags.sh <<'EOF'
#!/usr/bin/env bash
# Watch CF/ZF/SF/OF update, using gdb's flag display.
command -v gdb >/dev/null || { echo "  gdb not installed"; exit 0; }
cat > /tmp/fl.c <<'C'
#include <stdio.h>
int main(void) {
    int a = 2000000000, b = 2000000000;
    unsigned u = 4000000000u, v = 4000000000u;
    printf("%d\n", a + b);          /* signed overflow:  OF=1 */
    printf("%u\n", u + v);          /* unsigned:        CF=1 */
    return 0;
}
C
gcc -O0 -g /tmp/fl.c -o /tmp/fl
gdb -q -batch /tmp/fl \
  -ex "break *main+15" -ex run \
  -ex "printf \"  signed overflow (OF):\n\"" \
  -ex "stepi" -ex "info flags" \
  -ex "break *main+22" -ex continue \
  -ex "printf \"  unsigned overflow (CF):\n\"" \
  -ex "stepi" -ex "info flags" 2>&1 | grep -E "OF|CF|overflow|^  " | head -20
rm -f /tmp/fl.c /tmp/fl
EOF
chmod +x 04-flags.sh
./04-flags.sh 2>&1 | tee 05-flags.txt

# --- 4. the gadget inventory: why ret is everything ---
{
  echo "=== a gadget is any instruction ending in ret ==="
  echo "  ROP works because these exist in abundance in every binary."
  echo
  echo "=== search a real binary for usable sequences ==="
  ROPgadget --binary /usr/bin/id 2>/dev/null | head -20 \
    || { echo "  ROPgadget not installed (apt install ropper / pipx install ROPgadget)"
         echo "  falling back to objdump:"
         objdump -d /usr/bin/id | grep -B1 "ret" | grep -A1 -E "pop|leave" | head -20
         echo
         echo "  any 'pop rX ; ret' is a gadget: load rX from the stack, then"
         echo "  jump to the next address. Chain enough and you control rdi,"
         echo "  rsi, and where execution goes next."
       }
} 2>&1 | tee 06-gadgets.txt

# --- 5. instruction lengths: why disassembly needs an entry point ---
python3 - <<'PY' | tee 07-lengths.txt
print("  Instruction lengths on x86-64 are variable, 1-15 bytes.")
print("  Examples from real code:")
print("    90                 nop                      1 byte")
print("    48 89 e5           mov rbp, rsp             3 bytes")
print("    0f 85 xx xx xx xx  jne rel32                6 bytes")
print("    48 b8 <8 bytes>    movabs rax, imm64       10 bytes")
print()
print("  Consequence: you cannot disassemble from an arbitrary byte.")
print("  Start one byte early and every instruction after it is garbage,")
print("  with no error message.")
print()
print("  This is why RE starts by locating a FUNCTION ENTRY - a push rbp;")
print("  mov rbp,rsp prologue, or a call target, or a string xref - and")
print("  disassembling forward from there.")
PY
cat 07-lengths.txt

# --- 6. write shellcode the hard way, to see every piece ---
cat > 08-shellcode.S <<'EOF'
    .intel_syntax noprefix
    .text
    .globl _start
_start:
    # execve("/bin/sh", argv, envp) - no libc, no PLT, just the kernel
    # rax=59 (sys_execve), rdi=filename, rsi=argv, rdx=envp
    push    rbx              # preserve callee-saved rbx (we never return,
    push    r12              #   but this is the discipline)
    xor     rdx, rdx         # envp = NULL
    xor     rsi, rsi         # argv = NULL  (not strictly needed)
    mov     rdi, 0x68732f6e69622f   # "//bin/sh" little-endian
    push    rdi              # ...on the stack, NULL-terminated
    mov     rdi, rsp         # rdi = pointer to it
    mov     rax, 59          # SYS_execve
    syscall
    pop     r12
    pop     rbx
EOF
{
  echo "=== the classic execve shellcode, written instruction by instruction ==="
  cat 08-shellcode.S
  echo
  echo "=== assembled, and here are its bytes ==="
  nasm -f bin 08-shellcode.S -o shellcode.bin 2>/dev/null \
    && { wc -c < shellcode.bin | xargs echo "  size:"; xxd shellcode.bin | sed 's/^/  /' ; }
  echo
  echo "  Note what this is NOT: it does not call libc, does not need the"
  echo "  stack to be executable, and does not need any address to be"
  echo "  known. That is why it still works. NX does not stop this."
  echo "  NX only stops code ON the stack - and this code never was."
} 2>&1 | tee 09-shellcode.txt
rm -f ops.c ops 08-shellcode.S shellcode.bin 02-asm.txt

Step 4 is the deliverable: a gadget inventory from a real system binary. Every pop rX; ret you find is a rung on the ladder — and finding them is what turns "I can control the
return address" into "I can control rdi, rsi, and rdx."

Step 6 writes execve("/bin/sh") in raw assembly with no libc. It is 23 bytes, needs
no stack execution, and needs no leaked addresses. That's the baseline every later technique
is measured against, and the thing NX does not stop.
