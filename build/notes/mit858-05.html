Privilege Separation

Summary

If you cannot make the trusted code small, split it. Put a small privileged component in front
of a large unprivileged one, so that a bug in the large part costs you the large part rather than
the system.

The lecture's reading is OKWS (O'Keefe et al.), which is the canonical description of this
pattern.

Key ideas

  • Privilege separation: privileged monitor + unprivileged userland
  • The monitor owns the resources; userland does the work
  • The interface between them is a small message protocol — and every message must be validated
  • Goals: survive crashes in userland, limit the blast radius of a bug, enable review
  • The classic case: Postfix, and the split between a privileged master and unprivileged
    helper processes
  • Failure mode: a validation bug in the monitor, or a confused deputy where userland convinces
    the monitor to do something it should not

The shape

      network
         │
   ┌─────▼───────────────┐
   │  UNPRIVILEGED        │   parser, renderer, userland logic
   │  - can crash freely  │   bugs cost you userland, not the system
   └─────┬───────────────┘
         │  narrow, validated IPC
   ┌─────▼───────────────┐
   │  PRIVILEGED MONITOR  │   owns files, sockets, privileges
   │  - small, simple     │   must be correct
   └─────────────────────┘

The failure modes to design against

Failure Mechanism Mitigation
Validation bug monitor trusts a length or path from userland strict validation at the boundary; fuzz the protocol
Confused deputy userland asks the monitor to do something legitimate for the wrong reason bind requests to a specific operation, not a general capability
Resource exhaustion userland sends unbounded requests rate limits and quotas at the monitor
Protocol injection userland smuggles a second request into one length-prefixed framing, no ad-hoc concatenation
Over-privilege monitor has more authority than it needs least privilege; the monitor holds only what it must

OKWS, in one paragraph

The design separates the switch (privileged, owns the post office connection, filesystem
and process control) from the server (unprivileged, does the work). Every request from
userland to the monitor is a fixed-format message that the monitor validates before acting. The
bug you fear is in the message parser, so the parser is tiny and fuzzed.

The generalisable lesson: the interface between trusted and untrusted code is where the
security lives, and it should be as small as possible.

Terminology

Term Meaning
Privilege separation Trusted monitor + unprivileged userland
Reference monitor The mandatory mediation point
IPC protocol The narrow message format between them
Confused deputy A component induced to misuse its own authority
Length-prefixed framing A protocol structure that prevents message injection
Blast radius How much a bug costs you
Postfix The canonical real-world privilege-separated mail system
Request validation Checking every field at the boundary
Quotas / rate limits Bounding resource use by the untrusted side
Fuzzing Throwing malformed input at the parser

# --- the code is the lesson ---
mkdir -p /tmp/sep-demo && cd /tmp/sep-demo
cat > monitor.c <<'EOF'
/* Minimal monitor: owns the resource, validates every request. */
#include <stdio.h>
#include <string.h>
#include <unistd.h>

/* The ONLY operations userland may request. */
static int op_read_file(int client, const char *path, size_t len);
static int op_bad(const char *path, size_t len) { (void)client; (void)path; (void)len; return -1; }

/* Validation is the entire security of this component. */
static int valid_path(const char *p) {
    if (!p || !*p) return 0;
    if (strlen(p) != 0) {
        if (strstr(p, "..")) return 0;              /* traversal */
        if (p[0] != '/') return 0;                   /* must be absolute */
        if (strncmp(p, "/srv/allowed/", 13) != 0) return 0;  /* confined root */
    }
    return 1;
}

static int op_read_file(int client, const char *path, size_t len) {
    if (len > 255) return -1;                         /* bound the request */
    if (!valid_path(path)) return -2;
    char buf[256];
    int n = snprintf(buf, sizeof(buf), "allowed: %s", path);
    write(client, buf, n);
    return 0;
}
EOF
gcc -Wall -Wextra -g -O0 -c monitor.c -o monitor.o 2>&1 | head -3
echo "  monitor compiled: $([ -f monitor.o ] && echo yes || echo no)"
echo "  total trusted source lines: $(wc -l < monitor.c)"
cd /tmp && rm -rf sep-demo

Field lab

Objective: build the smallest possible trust boundary and measure how much it protects.

mkdir -p ~/aegis/labs/mit858-05 && cd ~/aegis/labs/mit858-05

# --- 1. the monitor: small, and the only privileged thing ---
cat > monitor.c <<'EOF'
#include <stdio.h>
#include <string.h>
#include <unistd.h>

#define MAXPATH 256

/* Everything below is the trusted computing base for this service. */
static int valid_path(const char *p) {
    if (!p || !*p)                  return 0;
    if (strstr(p, ".."))            return 0;     /* no traversal */
    if (p[0] != '/')                return 0;     /* must be absolute */
    if (strncmp(p, "/srv/allowed/", 13)) return 0; /* confined root */
    if (strlen(p) > MAXPATH - 1)    return 0;     /* bounded */
    return 1;
}

/* The whole privileged API: three operations, no more. */
static int op_stat(int fd, const char *path);
static int op_read(int fd, const char *path);

int main(void) {
    char path[MAXPATH];
    ssize_t n = read(STDIN_FILENO, path, sizeof(path) - 1);
    if (n <= 0) return 1;
    path[n] = '\0';
    if (!valid_path(path)) {
        write(STDOUT_FILENO, "DENIED: path failed validation\n", 34);
        return 2;
    }
    write(STDOUT_FILENO, "ALLOWED: ", 9);
    write(STDOUT_FILENO, path, strlen(path));
    write(STDOUT_FILENO, "\n", 1);
    return 0;
}
EOF
gcc -Wall -Wextra -g -O0 monitor.c -o monitor
echo "  trusted source: $(wc -l < monitor.c) lines"
echo "  compiled size : $(stat -c %s monitor) bytes"

# --- 2. test the boundary ---
{
  echo "=== path validation results ==="
  while IFS= read -r p; do
    out=$(printf '%s' "$p" | ./monitor 2>&1); rc=$?
    printf "  %-34s rc=%-3s %s\n" "$p" "$rc" "$(echo "$out" | head -1)"
  done <<'EOF'
/srv/allowed/report.txt
/srv/allowed/../../etc/passwd
/etc/passwd
/srv/other/secret
srv/allowed/report.txt
/srv/allowed/
/dev/null
EOF
} | tee 01-validation.txt

# --- 3. the ratio, measured ---
echo
echo "=== the size argument ==="
cat > userland.c <<'EOF'
/* Deliberately large: all the parsing, rendering and logic that is UNTRUSTED. */
#include <stdio.h>
/* ... imagine 1500 lines of format parsing, template rendering, unicode
   normalisation, timezone handling, and report generation here ... */
int main(void) { puts("userland: does everything, holds no privilege"); return 0; }
EOF
for i in $(seq 1 60); do cat >> userland.c <<'EOF'
static void step_i(void) { /* logic */ }
EOF
done
gcc -Wall -g -O0 userland.c -o userland
{
  printf "  trusted monitor  : %5s lines\n" "$(wc -l < monitor.c)"
  printf "  untrusted userland: %5s lines\n" "$(wc -l < userland.c)"
  echo
  echo "  The ratio is the point. Review the monitor; fuzz the userland."
} | tee 02-ratio.txt

# --- 5. the failure modes, and how to test them ---
cat > 04-failure-modes.md <<'EOF'
# Designing against the ways privilege separation fails

## 1. Validation bug in the monitor
The parser accepts something it should not.
**Test:** fuzz it. AFL/libFuzzer on the message parser is the single
highest-value test you can write. This is `fuzzing`.

## 2. Confused deputy
Userland legitimately asks for operation X, but in a context where X should
not be permitted - so the request is technically valid but should never have
been made.
**Test:** ask "who is allowed to make this request?" for every operation. If
the answer is "anyone", you have a confused deputy.

## 3. Protocol injection
Userland smuggles a second, different request inside the first by
concatenating, or by lying about a length field.
**Test:** send `GOOD\nEVIL\n` and verify only GOOD is acted on.
**Fix:** length-prefixed framing, never newline-terminated strings.

## 4. Resource exhaustion
Userland sends unlimited requests; the monitor allocates unboundedly.
**Test:** send 10,000 requests and watch memory.
**Fix:** quotas and rate limits in the monitor, not in userland.

## 5. Over-privilege
The monitor holds more authority than the operations require.
**Test:** for each operation, list exactly which privileges it needs. A
monitor that opens arbitrary files needs more than one that opens one.

## 6. The monitor is not actually smaller
The most common real-world failure: after three years of feature requests,
the "small" monitor has grown large. Measure it.
**This is why you re-run `wc -l` on the trusted component periodically.**
EOF
cat 04-failure-modes.md
echo
echo "  write 05-my-design.md: your own monitor design and its failure modes"

Step 1's six-line validator is the whole lecture. Everything userland sends is checked
against it, and the trusted component is small enough that you can read it.
