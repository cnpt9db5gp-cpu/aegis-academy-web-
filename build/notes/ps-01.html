The HTTP Request Lifecycle and How the Web Works

Summary

Every web vulnerability in this tier is a consequence of how HTTP works — or, more precisely, of
what a server must guess when a request is ambiguous. Before SQL injection or request
smuggling, you need the raw request in your head.

PortSwigger Academy's first topic is this foundation, and it is the note that makes
ps-08 (request smuggling) legible: smuggling exists because two HTTP implementations
disagree about where one request ends and the next begins.

The request, byte by byte

GET /search?q=cats&cat=dog HTTP/1.1
Host: lab.internal:8080
User-Agent: Mozilla/5.0
Accept: text/html
Cookie: session=abc123
Authorization: Basic dXNlcjpwYXNz
X-Forwarded-For: 192.168.1.5

  REQUEST LINE   METHOD SP TARGET SP VERSION
                 the one line that must come first

  HEADERS        KEY: VALUE, colon-space, CRLF each
                 Host is mandatory in HTTP/1.1
                 Header folding (obs-fold) was removed in RFC 7230
                 Order matters to nobody except a parser differential

  EMPTY LINE     CRLF CRLF - the separator

  BODY           optional; Content-Length or Transfer-Encoding defines it

The response

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 1256
Set-Cookie: session=xyz; HttpOnly; Secure; SameSite=Lax
Cache-Control: no-store

<html>...</html>

The URL is the most dangerous string in the application

  https://user:pass@lab.internal:8080/path/page?a=1&b=2#fragment

  ^scheme ^userinfo      ^host      ^port ^path     ^query   ^fragment

  WHAT AMBIGUOUS?
  - @ in a path can mean 'userinfo' or 'path' depending on parser
  - # ends the request in the browser but may be forwarded by a proxy
  - ../ can be collapsed by the client, the proxy, or the server
    (some collapse it twice -> path traversal across a boundary)
  - %2e%2e%2f is '..%2f' after one decode, '../' after two
    DOUBLE URL ENCODING is a traversal primitive.
  - ; in a path can separate a path parameter (old IIS/Java behaviour)
  - a tab or newline in a header enables CRLF / request splitting

Every one of those ambiguities becomes a vulnerability somewhere in this
course. Smuggling, traversal, host-header attacks and CRLF injection all
live in this list.

Headers that carry security meaning

Header Why it matters
Host selects the virtual host; also a cache poisoning vector
Cookie the ambient authority — CSRF and session fixation live here
Authorization carries credentials; basic auth is base64, not encryption
X-Forwarded-For / X-Real-IP / Forwarded client-supplied, and apps trust them for ACLs
Content-Type selects the parser; a mismatch is an XXE/CSRF primitive
Content-Length how much body — the other half of smuggling
Transfer-Encoding: chunked an alternative body framing — smuggling's other half
Origin / Referer CORS checks; null origin is a bypass
X-Forwarded-Host / X-Original-URL routing overrides; SSRF and access control bypass

The rule that explains an entire vulnerability class: if a header is
used for an access decision, and the client can set it, it is not a
security control.

The lifecycle

  BROWSER
    -> URL resolution (scheme, host, port, DNS)
    -> TCP connect (+ TLS handshake)
    -> HTTP request
    -> [PROXY / LOAD BALANCER / WAF]        <- where smuggling happens
    -> [CDN / CACHE]                         <- where poisoning happens
    -> APPLICATION SERVER
         parses URL, routes, authenticates session, authorises object,
         queries the database, renders, encodes output
    -> HTTP response (+ Set-Cookie)
    -> browser parses HTML, executes JS, applies CSP

Your proxy sits between you and the target and shows you every step. That
visibility is the single most valuable tool in web security, and it is why
ps-08 is possible at all.

Proxies, intercepting proxies, and what they change

  FORWARD PROXY      acts on your behalf; the target sees the proxy
  REVERSE PROXY      sits in front of the server; the client sees the proxy
  INTERCEPTING PROXY a forward proxy you point a browser at, so you can
                    read and modify every request

  WHAT IT BUYS:
    - you see raw bytes, not a rendered page
    - you can change one header and re-send
    - you can replay a request exactly
    - you can send a request no UI would produce

  WHAT IT COSTS:
    - HTTPS needs certificates (see below)
    - your browser is slower and slightly different
    - some protections assume a real client

TLS and intercepting, honestly

  If the target uses HTTP:                proxy reads everything. done.
  If the target uses HTTPS:
      the proxy presents its OWN certificate and decrypts, then
      re-encrypts to the real server. You need:
        - burp's CA certificate installed in your browser's trust store
        - or --unsafe (proxy CA not installed) for quick throwaway labs

  NOTE FOR ENGAGEMENTS: installing a CA in your own browser is fine.
  Installing one system-wide on a client machine is not, and many ROCs
  prohibit it. Ask before.

Encoding, and why it is the root of half these bugs

  '  < >  "  '         the HTML metacharacters
  %20 %3C %3E %22 %27  URL-encoded forms of the same
  \x3c &#60; \u003c     HTML entity / hex / unicode forms

  THE DECODING CHAIN:
    raw  ->  URL decode  ->  HTML entity decode  ->  SQL parse  ->  shell
     at every stage, the character means something DIFFERENT to the
     next component.

  AN ATTACK IS A STRING THAT IS INERT AT ONE STAGE AND LIVE AT ANOTHER.
  A %252e decodes once to %2e, and again to '.' - so a validator that
  checks after ONE decode sees %2e, and the filesystem sees '.'.

Terminology

Term Meaning
Request line METHOD SP TARGET SP VERSION
Header Key: Value, CRLF-terminated
Host header Virtual host selector; a security-relevant input
URL parsing Fragmenting a URL into components; non-unique by design
Intercepting proxy Your tool in the middle of the request
Forward / reverse proxy Acts for you / sits in front of the server
URL decode %XX → byte; may happen more than once
Double encoding Survives one decode; a traversal primitive
CRLF injection Newline in a header; splits the request
Content-Type Selects which parser handles the body
TLS interception Proxy with its own CA, decrypting in the middle
Virtual host Name-based routing; Host selects it
Status code 2xx ok, 3xx redirect, 4xx client error, 5xx server error

# --- 2. see the raw request, which is what a proxy shows you ---
{
  echo "=== the request line and headers, exactly as sent ==="
  curl -sv --max-time 5 "http://127.0.0.1:8080/index.php?q=cats&cat=dog" 2>&1 \
    | grep -E "^[*>]" | sed 's/^/  /'
  echo
  echo "=== and the response headers ==="
  curl -sI --max-time 5 "http://127.0.0.1:8080/index.php?q=cats" | sed 's/^/  /'
  echo
  echo "=== the body, byte count ==="
  curl -s --max-time 5 "http://127.0.0.1:8080/index.php?q=cats" | wc -c | xargs echo "  bytes:"
} 2>&1 | tee 01-raw.txt

# --- 3. URL parsing is non-unique: prove it ---
python3 - <<'PY' | tee 02-ambiguity.txt
from urllib.parse import urlsplit
cases = [
    "http://lab.internal/a/b",
    "http://lab.internal/a/../b",
    "http://lab.internal/a/b/..%2f..%2fetc/passwd",
    "http://lab.internal/%2e%2e/%2e%2e/etc/passwd",
    "http://lab.internal/a%252e%252e%252fb",      # double-encoded
    "http://lab.internal/a;b=c",
    "http://lab.internal/a%3b=c",
    "http://lab.internal\\..\\..\\etc\\passwd",     # backslashes
    "http://evil.internal#@lab.internal/",
    "http://lab.internal/\\@evil.internal/",
]
print("  URL                                            parsed path")
print("  " + "-"*78)
for u in cases:
    p = urlsplit(u)
    print(f"  {u:<46} {p.path!r}")
print()
print("  Six different encodings, four different parsers (browser, proxy,")
print("  framework, filesystem) will disagree about what the path is.")
print("  That disagreement is request smuggling (ps-08), path traversal")
print("  (ps-06), and cache poisoning (ps-08) - one root cause, three lessons.")
PY
cat 02-ambiguity.txt

# --- 4. the header set, and what each one is trusted for ---
cat > 03-headers.sh <<'EOF'
#!/usr/bin/env bash
H="X-Forwarded-For: 10.0.0.1"
curl -s --max-time 5 "http://127.0.0.1:8080/index.php" \
  -H "$H" \
  -H "X-Real-IP: 10.0.0.2" \
  -H "X-Forwarded-Host: evil.internal" \
  -H "X-Original-URL: /admin" \
  -H "X-Custom-IP-Authorization: 127.0.0.1" \
  -H "X-Forwarded-Proto: https" \
  | grep -E "X-Forwarded-For|Host" | sed 's/^/  /'
echo
echo "  Every one of these headers is CLIENT-SUPPLIED and many apps use"

# --- 5. encoding layers, demonstrated ---
python3 - <<'PY' | tee 05-encoding.txt
import urllib.parse
payloads = {
    "<script>alert(1)</script>":                     "raw HTML metacharacters",
    "%3Cscript%3Ealert(1)%3C%2Fscript%3E":           "URL-encoded",
    "%253Cscript%253E":                               "double URL-encoded",
    "&lt;script&gt;":                                 "HTML entity",
    "&#60;script&#62;":                               "decimal entity",
    "\\x3cscript\\x3e":                               "hex escape",
    "<ScRiPt>alert(1)</ScRiPt>":                      "case variation",
    "<script\n>alert(1)</script>":                    "whitespace variation",
    "java\tscript:alert(1)":                          "tab inside the scheme",
}
print("  payload                               what it is              inert where?")
print("  " + "-"*88)
for p, d in payloads.items():
    dec1 = urllib.parse.unquote(p)
    dec2 = urllib.parse.unquote(dec1)
    live = ["<" in dec2, "&#" in p, "\\\\x3c" in p]
    where = "never - live everywhere"
    if "&#" in p or "\\x3c" in p: where = "only after HTML entity decode"
    elif "%25" in p:               where = "only after TWO url decodes"
    elif "%3C" in p:               where = "after ONE url decode"
    print(f"  {p:<38} {d:<24} {where}")
print()
print("  The point: 'is this dangerous?' is the wrong question.")
print("  The right question is 'in which component's parser is it live,'")
print("  and that component is not the one you are holding.")
PY
cat 05-encoding.txt

# Setting up an intercepting proxy

## For the PortSwigger Academy labs (official targets)
1. Download Burp Suite Community from portswigger.net/burp
2. Start it; it listens on 127.0.0.1:8080 by default
3. Firefox -> Settings -> Network -> Manual proxy 127.0.0.1:8080
4. Visit `http://burp` in the browser
5. Download the CA certificate and install it into Firefox's Authorities
6. Visit the academy target; the request now appears in Burp

For an HTTPS target you also need the CA installed. `http://burp` gives it
to you.

## Doing it without a GUI proxy (for scripted, local work)
```bash

PY

What to do with the visibility

  • Read the RAW request, not the rendered page
  • Change one header at a time; a diff beats a guess
  • Replay a request that succeeded and change exactly one thing
  • Look at the response for information disclosure before attacking

--- 7. the mental model to carry into every later note ---

cat > 07-model.md <<'EOF'

The model to carry into Tier 4

  BROWSER --parse--> [PROXY] --parse--> [CACHE] --parse--> SERVER
     |                   |               |                 |
  parser A           parser B        parser C          parser D
     \                  |               |                 /
      \                 |               |                /
       \          ANY DISAGREEMENT BETWEEN THESE IS A BUG
        --------------------------------------------------

  ps-02  server's SQL parser   vs your input        -> SQL injection
  ps-03  browser's HTML parser vs server's output   -> XSS
  ps-05  the fetcher's URL parser vs the validator   -> SSRF
  ps-06  the filesystem's path parser vs the filter  -> traversal
  ps-08  two HTTP parsers, front and back            -> smuggling

One diagram explains the entire tier. Every vulnerability is a
disagreement between two components about what a string means. Finding
them means finding the places where a string crosses two components and
neither validates the crossing.
EOF
cat 07-model.md
```

Step 3 is the deliverable: nine encodings of the same idea, with the column that says
which component sees it as live. "Is this dangerous?" is the wrong question — "live in which
parser?" is the right one, and that reframing is what makes ps-03, ps-06 and ps-08
approachable rather than a list of tricks.

Step 7 is the single diagram the whole tier hangs on: every vulnerability in Tier 4 is two
components disagreeing about what a string means.
