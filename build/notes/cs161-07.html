Web Security

Summary

CS161's web-security lecture takes the browser's security model from mit858-11 and asks the
application-level question: given that the browser trusts your origin, what can you do wrong
that turns that trust into an attack?

Companion to mit858-11 (the model) and portswigger-academy (the labs).
This note is the taxonomy of application-level mistakes.

The model, restated as an attack surface

  browser trusts origin O
  O is compromised by: injection, so attacker code runs as O
  attacker code as O can: read O's data, act as the user, call any origin

Almost every web vulnerability is a way to make attacker-controlled data
execute inside a trusted origin, or to make the server act on behalf of
someone it should not.

The four families

Family The mistake Consequence
Injection Data treated as code Code execution in the app's context
Broken authentication Identity not proven correctly Account takeover
Broken access control Authorisation not checked per object Reading others' data
Misconfiguration Defaults, over-permission, verbose errors Everything above

CS161's framing: the second and third are more common and more severe
than injection, despite injection dominating the attention.

Injection, mechanised

SQL:     "SELECT * FROM u WHERE n='" + name + "'"
         -> name = ' OR 1=1 --     gives the whole table

shell:   system("convert " + filename)
         -> filename = "; rm -rf ~  #

template: render(user_input)         -> server-side template injection

LDAP:    filter = "(&(uid=" + user + ")"
         -> user = *)(uid=*          matches everyone

Every one is the same shape: string concatenation into a language. The
fix is always the same: use the language's parameterised form.

  parameterised query   -> the value can never alter the query structure
  argv-style exec       -> the value can never become a command
  context-aware escaping -> the fallback when parameters are unavailable

Access control, the one people under-test

  authentication: who are you?
  authorisation:  may you do this to THIS object?

  broken:  GET /api/invoice?id=1234   and you change it to 1235

IDOR (Insecure Direct Object Reference) is the most common high-severity
finding in real bug bounty, because it requires no exploit technique — just a
number in a URL.

The test: for every endpoint, fetch an object you own, then fetch one you
do not, with the same request.

CS161's security-relevant web properties

  • Authentication: must be unforgeable and must not leak why it failed
  • Sessions: unguessable, rotated on privilege change, invalidated server-side
  • Authorisation: checked per object, per request, server-side
  • Input handling: validated, and never used to build anything executable
  • Output encoding: context-appropriate, at the point of output
  • State: cookies flagged HttpOnly, Secure, SameSite
  • CSRF: token or SameSite, because the browser attaches authority automatically
  • Errors: generic, consistent, and never reflecting input

Terminology

Term Meaning
SQL injection Concatenating input into a query
CSRF Forging a request with the victim's ambient cookies
XSS Script running in a trusted origin
IDOR Accessing an object by changing its identifier
Access control Per-object authorisation
Parameterised query Separating code from data
Context-aware escaping Encoding for the output context
Cookie flags HttpOnly, Secure, SameSite
Error oracle Error differences that leak secret state
Least privilege (web) A session should only do what it must

Kali commands

# --- what does this site send back? ---
curl -sI --max-time 5 http://127.0.0.1:8080/ | head -12
echo
echo "=== security headers that should be present ==="
for h in content-security-policy x-frame-options strict-transport-security \
         referrer-policy x-content-type-options permissions-policy; do
  v=$(curl -sI --max-time 3 http://127.0.0.1:8080/ 2>/dev/null | grep -i "^$h" | head -1)
  printf "  %-30s %s\n" "$h" "${v:-ABSENT}"
done

# --- cookies, and whether they are usable by script ---
curl -sv --max-time 5 http://127.0.0.1:8080/ 2>&1 | grep -i "set-cookie" | sed 's/^/  /'
echo "  HttpOnly absent = readable by JavaScript"
echo "  Secure absent   = sent over plain HTTP too"
echo "  SameSite absent = usable cross-site (CSRF exposure)"

# --- the enumeration that finds IDOR, on your own lab only ---
cat > 04-idor.md <<'EOF'
# The IDOR test, written down

For every endpoint that takes an identifier:

1.  authenticate as user A
2.  request an object A owns        -> 200
3.  request an object B owns        -> ????

If step 3 returns 200, the endpoint has no authorisation check.

## What to record
- the exact request
- the identifier you changed, and whose object it is
- the response status and a redacted snippet proving it is B's data

## What NOT to do
- do not fetch data you do not need; stop at the status code and size
- do not enumerate broadly; test one or two identifiers
- never put another user's real data in a report
EOF
cat 04-idor.md

# --- what methods does this endpoint accept? ---
for m in GET HEAD POST PUT DELETE PATCH OPTIONS TRACE; do
  printf "  %-8s %s\n" "$m" \
    "$(curl -s -o /dev/null -w '%{http_code}' -X $m --max-time 3 http://127.0.0.1:8080/ 2>/dev/null || echo '-')"
done
echo "  405 on the wrong verb tells you the resource exists."
echo "  200 on TRACE-style methods would be a finding in itself."

# --- error handling, which is an oracle if it is inconsistent ---
python3 - <<'PY' | tee 05-oracle.txt
cases = [
    ("unknown user",     "admin"),
    ("wrong password",   "admin"),   # same username, bad password
    ("no such user",     "nosuchuser"),
]
print("  these three SHOULD return the identical response.")
print()
for label, user in cases:
    print(f"  {label:<16} -> (compare status, length and time, not just the message)")
print()
print("  Differences that leak which usernames exist are a real finding:")
print("    different status code")
print("    different response length")
print("    measurably different timing")
PY
cat 05-oracle.txt

# --- the fixes, as a checklist ---
cat > 06-checklist.md <<'EOF'
# Web security checklist

## Authentication
- [ ] credentials compared in constant time
- [ ] no user enumeration via message, status, length or timing
- [ ] rate limited per account AND per source, without lockout
- [ ] password hashing is slow and salted (Argon2id, scrypt, bcrypt)
- [ ] MFA available, and second factors that resist phishing

## Sessions
- [ ] 128+ bits of entropy, from a CSPRNG
- [ ] rotated on login and on every privilege change
- [ ] invalidated server-side on logout
- [ ] cookie: HttpOnly, Secure, SameSite, narrow Path
- [ ] absolute and idle expiry

## Authorisation
- [ ] checked server-side, per object, per request
- [ ] default deny
- [ ] IDOR tested with a second, unprivileged account
- [ ] privilege changes re-verify, not just the login

## Input and output
- [ ] parameterised queries, never string concatenation
- [ ] no shell built from user input
- [ ] output encoding per context (HTML, attribute, JS, URL)
- [ ] CSP set, and not `unsafe-inline` without a nonce/hash
- [ ] file uploads validated by content, not by name

## Transport
- [ ] TLS everywhere, HSTS set
- [ ] no mixed content
- [ ] CORS: fixed allowlist, never reflecting Origin with credentials

## Errors
- [ ] generic and identical to the client
- [ ] detailed and correlated internally, never returned
- [ ] no stack traces, no SQL, no paths
EOF
cat 06-checklist.md

Step 5 is the subtle one: consistent error responses are a security control, and measuring
timing as well as status is how you check it.

Record: 04-idor.md and 06-checklist.md — that checklist is the Tier 4 working document.
