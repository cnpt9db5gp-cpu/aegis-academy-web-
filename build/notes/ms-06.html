Metaprogramming and Build Systems

Summary

Software is built by programs, not people. Build systems turn source into artefacts in a
repeatable way, and dependency managers fetch and pin the libraries your build needs.

For a security student this is not busywork. Three concrete reasons:

  1. You will compile vulnerable programs (Tier 3) and need to know which flags disable which
    mitigations.
  2. You will need to install Python tooling correctly — pipx, venvs, and dependency
    conflicts are a daily annoyance on Kali (see kr-05).
  3. Reproducibility is a professional skill. "It worked on my machine" is not acceptable
    when you hand someone a tool.

Compiling C: the flags that decide whether an exploit works

gcc -g -O0 -fno-stack-protector -no-pie -z execstack vuln.c -o vuln
Flag Effect Why you care
-g debug symbols gdb can show you variable names
-O0 / -O2 no optimisation / optimise Optimisation removes patterns to match
-fno-stack-protector removes stack canaries An overflow no longer aborts
-fno-pie / -no-pie fixed load address Hardcoded addresses work
-z execstack executable stack Shellcode can run directly
-static link everything No GOT/PLT to overwrite, bigger binary
-m32 32-bit build x86 shellcode and classic exploit courses are 32-bit

Check what you got:

checksec --file=./vuln
readelf -l ./vuln | grep GNU_STACK
file ./vuln

This one command is the bridge to Tier 3. Every mitigation lecture exists because these flags
can turn it off.

make: the smallest useful build system

# Makefile
CC      = gcc
CFLAGS  = -g -O0 -Wall -fno-stack-protector -no-pie
TARGET  = vuln
SRC     = vuln.c

all: $(TARGET)

$(TARGET): $(SRC)
    $(CC) $(CFLAGS) -o $@ $<

clean:
    rm -f $(TARGET)

.PHONY: all clean

make            # build
make clean      # tidy

The rule target: dependencies followed by a tab-indented recipe is the entire concept. make is
older than most people's careers and still runs most C and C++ builds on earth.

Python dependency management (the Kali-relevant part)

# WRONG: system-wide install, fights apt, breaks the OS
sudo pip install requests

# RIGHT: single CLI tool, fully isolated
pipx install yt-dlp
pipx list
pipx upgrade-all

# RIGHT: project-scoped
python3 -m venv ~/aegis/venvs/project
source ~/aegis/venvs/project/bin/activate
pip install requests
pip freeze > requirements.txt      # pin versions = reproducibility
deactivate

# Reading requirements:
cat requirements.txt
# requests==2.31.0
# urllib3==2.0.7

pip freeze > requirements.txt is the single highest-value habit in Python work. A script that
worked on your machine will work on someone else's if you ship the freeze file.

Dependency risk — a security property, not a bookkeeping one

pip list                                   # what do I have?
pip show requests                          # what depends on what?
pipdeptree -g                              # the dependency graph
pip install --dry-run some-package         # what WOULD it change?
pip download some-package --no-deps        # inspect without installing
pip-audit                                  # known CVEs in installed packages (needs: pipx install pip-audit)
pip index versions some-package            # available versions

Threat model for supply chain: installing a package runs arbitrary code from the maintainer
(and transitively from everyone they depend on). A typosquatted package name is a real attack. In
a work context, pip install should be a deliberate, reviewable act — not something a script does
on its own.

Makefiles, shell and Python as metaprogramming

All three are "programs that write or drive programs":

  • a Makefile is a program that decides what to compile and in what order
  • a shell script that emits commands is metaprogramming
  • Python's decorators, metaclasses and generators are metaprogramming in the strict sense

You already use the first two every day. You will meet the third in angr (Tier 3), which
synthesises program paths rather than running them.

Field lab

Objective: compile a deliberately vulnerable binary with known mitigations off, and inspect
the result — the setup for every Tier 3 exploitation lecture.

mkdir -p ~/aegis/labs/ms-06 && cd ~/aegis/labs/ms-06

# --- 1. toolchain inventory ---
{
  echo "=== compilers and build tools ==="
  for t in gcc g++ cc make cmake clang rustc go javac; do
    printf "%-8s %s\n" "$t" "$(command -v $t || echo 'not installed')"
  done
  echo
  echo "=== gcc version ==="; gcc --version | head -1
  echo "=== glibc ==="; ldd --version | head -1
} | tee 01-toolchain.txt

# --- 2. write a deliberately vulnerable program ---
cat > vuln.c <<'EOF'
#include <stdio.h>
#include <string.h>
#include <stdlib.h>

void vulnerable(const char *input) {
    char buffer[32];
    strcpy(buffer, input);            /* unbounded copy - the bug */
    printf("copied: %s\n", buffer);
}

int safe(const char *input) {
    char buffer[32];
    strncpy(buffer, input, sizeof(buffer) - 1);
    buffer[sizeof(buffer) - 1] = '\0'; /* null terminate - still bounded */
    printf("copied safely: %s\n", buffer);
    return 0;
}

int main(int argc, char **argv) {
    if (argc < 2) { fprintf(stderr, "usage: %s <string>\n", argv[0]); return 1; }
    if (getenv("SAFE")) safe(argv[1]); else vulnerable(argv[1]);
    return 0;
}
EOF

# --- 3. build it THREE ways: hardened, default, and weaponised ---
gcc -Wall -Wextra -g -O0 -fno-stack-protector -no-pie -z execstack vuln.c -o vuln-weak
gcc -Wall -Wextra -g -O0 vuln.c -o vuln-default
gcc -Wall -Wextra -g -O0 -fstack-protector-strong -D_FORTIFY_SOURCE=2 -pie -fPIE vuln.c -o vuln-hard

# --- 4. audit all three ---
{
  for b in vuln-hard vuln-default vuln-weak; do
    echo "=========================================="
    echo "BINARY: $b"
    echo "=========================================="
    file ./$b
    checksec --file=./$b 2>/dev/null || echo "(install checksec: sudo apt install checksec)"
    echo
  done
} | tee 02-hardening-comparison.txt

# --- 5. the difference is observable ---
./vuln-hard "$(python3 -c 'print("A"*200)')" ; echo "hard exit:   $?"
./vuln-default "$(python3 -c 'print("A"*200)')" ; echo "default exit:$?"
./vuln-weak "$(python3 -c 'print("A"*200)')"   ; echo "weak exit:   $?"

# --- 6. write the Makefile ---
cat > Makefile <<'MAKE'
CC     := gcc
WARN   := -Wall -Wextra
DEBUG  := -g -O0
WEAK   := -fno-stack-protector -no-pie -z execstack
TARGETS := vuln-weak vuln-default vuln-hard

all: $(TARGETS)

vuln-weak: vuln.c
    $(CC) $(WARN) $(DEBUG) $(WEAK) -o $@ $<

vuln-default: vuln.c
    $(CC) $(WARN) $(DEBUG) -o $@ $<

vuln-hard: vuln.c
    $(CC) $(WARN) $(DEBUG) -fstack-protector-strong -D_FORTIFY_SOURCE=2 -pie -fPIE -o $@ $<

clean:
    rm -f $(TARGETS)

.PHONY: all clean
MAKE
make clean && make
ls -la vuln-*

# --- 7. reproducibility ---
{
  echo "=== versions this build depends on ==="
  gcc --version | head -1
  ldd --version | head -1
  echo
  echo "=== linked libraries (vuln-hard) ==="
  ldd ./vuln-hard
} | tee 03-reproducibility.txt

Read the 02-hardening-comparison.txt table carefully. You have now, with your own hands,
turned each mitigation off one at a time. Every Tier 3 lecture about canaries, NX, PIE and RELRO
refers to exactly this output.

Record: which protections did gcc enable by default on Kali, and which needed a flag?
