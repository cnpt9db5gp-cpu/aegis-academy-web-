Introduction and Examples

Summary

MIT 6.S081 builds a real operating system in xv6, a small Unix-like system in ~10,000 lines of C.
Lecture 1 sets up the model: what an OS actually is, what a kernel boundary is, and why you
cannot understand security until you understand what the kernel enforces.

This course is the Tier 1 backbone. Every later tier assumes you know what a system call is,
what a syscall table does, and why isolation exists.

What an operating system actually does

An OS is a program that runs on the CPU at a privileged level and manages everything shared:
CPU time, memory, devices, files, and identity. Everything else is just a program it launched.

   ┌─────────── user space ────────────┐   ┌──────── kernel ────────┐
   │  shell  editor  nmap  gcc  python │   │  scheduler  memory     │
   └──────────────┬────────────────────┘   │  filesystem  drivers   │
                  │  system calls         │  syscall dispatch      │
                  └──────────────────────►└────────────────────────┘

The security model in one sentence: the kernel is the only trusted code, and every boundary
you cross — user/kernel, process/process, process/memory — is enforced there or nowhere.

The kernel / userspace boundary

  • Kernel mode (ring 0): full CPU privileges. Can touch any memory, any device.
  • User mode (ring 3): restricted. Cannot execute privileged instructions or access kernel
    memory directly.

A user program cannot flip a hardware bit from 0 to 1. To do anything privileged, it must
ask the kernel via a system call, and the kernel decides whether to allow it.

// user space - this is what nmap's socket() call ultimately does
int fd = socket(AF_INET, SOCK_STREAM, 0);

// kernel space - what handles it
// validates the arguments, checks permissions, allocates, records the fd

Why this matters for security: every privilege boundary you will ever test or bypass is
expressed as "can untrusted input influence what the kernel does on the user's behalf?" That
single question generates buffer overflows, TOCTOU races, and container escapes.

Abstractions and the principle of least authority

Each OS abstraction hides complexity while restricting authority:

Abstraction Hides Restricts
Process CPU scheduling, memory layout Address space isolation
Virtual memory Physical RAM, paging One process cannot read another's memory
Filesystem Block devices, inodes Permissions per file
User/UID Who is running File access control
Signal Async events Permission to signal a process

Every abstraction you learn is a security control. There is no separation between "how
computers work" and "how computers are attacked" — they are the same material read from two
directions.

Kali commands

# --- observe the boundary on YOUR machine ---
uname -a
cat /proc/version
ls -la /proc/self/
cat /proc/self/status | grep -E "Uid|Gid|CapEff|Seccomp"

# --- capabilities: privilege without ring 0 ---
cat /proc/self/status | grep Cap
command -v capsh && capsh --print | head -5
getcap /usr/bin/ping 2>/dev/null
# ping uses CAP_NET_RAW instead of running as root - least authority in action

# --- how many system calls does a program make? ---
strace -c -f ls 2>&1 | tail -25
# the "calls" column is the user's view of the kernel boundary
strace -e trace=execve -f /usr/bin/ls

# --- the kernel's own view ---
dmesg | tail -20
lsmod | head
cat /proc/interrupts | head -5

Field lab

Objective: map the kernel boundary on your own Linux box, using the same concepts the course
will use for xv6.

mkdir -p ~/aegis/labs/os-01 && cd ~/aegis/labs/os-01

{
  echo "=== KERNEL / USER BOUNDARY ==="
  echo "kernel:  $(uname -r)"
  echo "arch:    $(uname -m)"
  echo
  echo "=== my identity and privileges ==="
  id
  grep -E "^(Uid|Gid|CapEff|CapBnd|Seccomp|NoNewPrivs)" /proc/self/status
  echo
  echo "=== what the kernel lets me do ==="
  capsh --print 2>/dev/null | grep -E "^Current|^Bounding" || \
    echo "(install libcap2-bin for capsh)"
  echo
  echo "=== root bypass in action: ping without root ==="
  getcap /usr/bin/ping 2>/dev/null && echo "  -> ping uses CAP_NET_RAW, not root"
  echo
  echo "=== kernel modules loaded ==="
  lsmod | head -10
  echo
  echo "=== interrupt sources (first few) ==="
  head -3 /proc/interrupts
} 2>&1 | tee 01-boundary.txt

# --- HOW MANY SYSCALLS DOES A PROGRAM MAKE? ---
strace -c /usr/bin/ls 2>&1 | tail -30 | tee 02-syscalls-ls.txt

echo
echo "Read 02-syscalls-ls.txt: which syscalls dominate? openat, fstat, close?"
echo "Those are the kernel boundary being crossed thousands of times per second."

# --- compare a heavy program ---
strace -c -f nmap -sn 127.0.0.1 2>/dev/null | tail -20 | tee 03-syscalls-nmap.txt
echo
echo "nmap crosses the boundary far harder than ls. That is why it needs root for -sS."

# --- a syscall you can read by hand ---
strace -e trace=execve -f /usr/bin/ls 2>&1 | head -5
echo
echo "execve is how a shell 'runs' a program. exec replaces the current image entirely."

# --- namespaces: the modern isolation primitive ---
ls -la /proc/self/ns/
readlink /proc/self/ns/user
readlink /proc/self/ns/mnt

Record: 01-boundary.txt. Compare your CapEff line against a root shell's. That
difference is the entire privilege model expressed as a hex number, and you will read it again in
pr-01 and Tier 5.
