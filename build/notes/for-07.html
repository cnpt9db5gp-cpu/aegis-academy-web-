Network Forensics from PCAP

Summary

A packet capture is the highest-fidelity record of what actually crossed a network boundary. It
answers questions no log answers — who initiated, what exactly was said, in what order — and it
does so without trusting the machine that was compromised.

The framing: the network does not lie about the order of events. A
compromised host can forge its own logs. It cannot forge the order of
packets that arrived.

Companion to for-02 (timeline) and ccnad-* (the protocols). This
note is tshark-driven analysis of your own captures.

The workflow

  1. KNOW YOUR CAPTURE
     what was the capture point, what was in and out of it?
     A capture taken on the wrong side of NAT cannot be correlated with
     the server's logs, because the addresses do not match.

  2. THE CONVERSATIONS
     tshark -q -z conv,tcp        who talked to whom, how much
     the first question is always "what is the shape of this?"

  3. THE PROTOCOL MIX
     tshark -q -z io,phs          what protocols, and how much
     a sudden DNS TXT, or a beacon to a new domain, shows up here.

  4. THE DNS
     every domain resolved, in order. The first unfamiliar one is
     usually where the story starts.

  5. THE HTTP
     the requests, in order, with the User-Agent. Downloads from a
     new domain, by a browser, at 03:00.

  6. THE TLS METADATA
     you cannot read the payload, but you CAN read the SNI, the
     certificate chain, the JA3 fingerprint, and the timing and size
     of every flow. That is enough.

  7. THE BEACONS
     periodic, small, to the same destination. C2 looks like nothing
     else in a capture.

  8. THE EXFILTRATION
     a large outbound transfer, or a lot of small ones, to a new
     destination, or to a port that does not belong there.

The two that catch exfiltration

# --- 1. the analysis script ---
cat > 01-analyse.sh <<'EOF'
#!/usr/bin/env bash
# PCAP analysis, in the order that finds things.
P="${1:?usage: ./01-analyse.sh capture.pcap}"
[ -f "$P" ] || { echo "no such capture"; exit 1; }
tshark -r "$P" -q 2>/dev/null >/dev/null || { echo "tshark cannot read $P"; exit 1; }

echo "=============================================================="
echo " $P"
echo "=============================================================="
echo "  packets: $(tshark -r "$P" 2>/dev/null | wc -l)"
echo "  span   : $(tshark -r "$P" -q -z io,phs 2>/dev/null | head -2 | tail -1)"

echo
echo "=== 1. THE CONVERSATIONS (the shape) ==="
tshark -r "$P" -q -z conv,tcp 2>/dev/null | sed 's/^/  /'
echo
echo "  READ THIS FIRST. It answers: who talked to whom, how much,"
echo "  and for how long. Every later step is a refinement of it."
echo
echo "  The things to look for:"
echo "    - a host talking to something new and external"
echo "    - a periodic pair with a small, constant byte count"
echo "    - a very large transfer OUT that has no IN counterpart"
echo "    - a DNS server being talked to by more hosts than usual"

echo
echo "=== 2. THE PROTOCOL MIX ==="
tshark -r "$P" -q -z io,phs 2>/dev/null | sed 's/^/  /'
echo
echo "  A sudden appearance of a protocol you do not normally see"
echo "  (DNS over HTTPS, a new TLS port, ICMP with payload) is a"
echo "  finding on its own."

echo
echo "=== 3. DNS, IN ORDER (usually where the story starts) ==="
tshark -r "$P" -Y "dns.flags.response==0" \
  -T fields -e frame.time -e ip.src -e dns.qry.name 2>/dev/null \
  | sort | uniq -c | sort -rn | head -25 | sed 's/^/  /'
echo
echo "  The FIRST query to an unfamiliar domain, and the query BEFORE"
echo "  it, are usually the delivery and the click. Print them in"
echo "  chronological order, not by count:"
tshark -r "$P" -Y "dns.flags.response==0" \
  -T fields -e frame.time -e ip.src -e dns.qry.name 2>/dev/null \
  | sort | sed 's/^/  /'

echo
echo "=== 4. DNS TXT (tunneling shows here first) ==="
tshark -r "$P" -Y "dns.qry.type==16" -T fields -e dns.qry.name 2>/dev/null \
  | head -20 | sed 's/^/  /'
echo "  A long, base64-ish subdomain is tunnelling. A TXT query with a"
echo "  long payload is data exfiltration over DNS."

echo
echo "=== 5. HTTP REQUESTS, in order ==="
tshark -r "$P" -Y "http.request" \
  -T fields -e frame.time -e ip.src -e http.host -e http.request.method \
             -e http.request.uri -e http.user_agent 2>/dev/null \
  | sed 's/^/  /' | head -30

echo
echo "=== 6. HTTP DOWNLOADS (what was fetched) ==="
tshark -r "$P" -Y "http.response.code==200 && http.content_type" \
  -T fields -e frame.time -e ip.dst -e http.content_type \
             -e http.content_length 2>/dev/null | sed 's/^/  /' | head -20
echo
echo "  content_type of application/x-dosexec or similar, from a domain"
echo "  you do not recognise, is the delivery."

echo
echo "=== 7. TLS: SNI, certificate, and JA3 ==="
tshark -r "$P" -Y "tls.handshake.extensions_server_name" \
  -T fields -e frame.time -e ip.dst -e tls.handshake.extensions_server_name \
  2>/dev/null | sort | uniq -c | sort -rn | sed 's/^/  /' | head -20
echo
echo "  JA3 fingerprint (the TLS client hello parameters):"
tshark -r "$P" -Y "tls.handshake.type==1" \
  -T fields -e tls.handshake.ja3_full 2>/dev/null | sort | uniq -c | sort -rn | sed 's/^/  /'
echo
echo "  A JA3 that appears for exactly one destination is a client that"
echo "  is different from everything else on the network. That is"
echo "  either the malware, or a legitimate client you did not know"
echo "  was there. Both are worth a question."
echo
echo "  NOTE: SNI is visible unless Encrypted Client Hello is in use."
echo "  It is the single most useful field in a capture and it is"
echo "  going away. Record the SNI now."

echo
echo "=== 8. BEACONS: periodic, small, same destination ==="
tshark -r "$P" -Y "tcp" -T fields -e ip.dst -e tcp.dstport -e frame.len \
  -e frame.time_epoch 2>/dev/null | sort | uniq -c | sort -rn | head -15 | sed 's/^/  /'
echo
echo "  C2 has a shape: a small, constant-sized request every N"
echo "  seconds, to one destination. Look for a count that divides"
echo "  evenly into the capture's duration."

echo
echo "=== 9. EXFILTRATION: bytes out vs bytes in ==="
tshark -r "$P" -q -z conv,ip 2>/dev/null | sed 's/^/  /' | head -20
echo
echo "  A host with 10 MB in and 10 MB OUT is normal. A host with"
echo "  200 KB in and 40 MB out is an incident."
EOF
chmod +x 01-analyse.sh

  echo "  Then, in another terminal, generate some traffic:"

# start a loopback listener and capture against it
nohup python3 -m http.server 8099 --bind 127.0.0.1 >/dev/null 2>&1 &
SRV=$!
timeout 12 tshark -i lo -c 500 -w lab.pcap >/dev/null 2>&1 &
CAP=$!
sleep 2
curl -s --max-time 3 http://127.0.0.1:8099/ >/dev/null 2>&1
curl -s --max-time 3 http://127.0.0.1:8099/ >/dev/null 2>&1
curl -s --max-time 3 "http://127.0.0.1:8099/?search=test" >/dev/null 2>&1
wait $CAP 2>/dev/null
kill $SRV 2>/dev/null
sleep 1
ls -la lab.pcap 2>/dev/null | sed 's/^/  /' | tee -a 02-capture.txt

# --- 3. run the analysis ---
if [ -s lab.pcap ]; then
  ./01-analyse.sh lab.pcap 2>&1 | head -70 | tee 03-analysis.txt
fi

# --- 4. the structure-reading skills ---
cat > 04-reading.md <<'EOF'
# Reading a capture structurally

```text
  THE FIVE-STEP READ, and it is the same every time.

  1. SHAPE         tshark -q -z conv,tcp
                    Who, to whom, how much, how long. Nothing else
                    comes before this.

  2. TIMELINE      tshark -T fields -e frame.time -e ip.src -e ip.dst
                    Sort by time. Now you can see the SEQUENCE, which
                    is where the story is. A capture has no order
                    until you impose one.

  3. THE FIRST NEW THING
                    What is the first packet in this capture that
                    does not belong to the routine? Not the largest
                    transfer - the FIRST unfamiliar thing. In
                    practice it is almost always a DNS query to a
                    domain nobody in the business has heard of.

  4. THE PAYLOAD   For that: DNS query content, HTTP request, TLS SNI
                    and certificate. tshark -Y "<filter>" -V for the
                    full detail.

  5. THE AMOUNT    bytes in vs out for the host involved. Delivery is
                    small. Exfiltration is large. The asymmetry is
                    the finding.

The filters worth memorising

# the conversation list
tshark -r c.pcap -q -z conv,tcp

# HTTP, all requests, in order
tshark -r c.pcap -Y "http.request" -T fields \
  -e frame.time -e ip.src -e ip.dst -e http.host -e http.request.method -e http.request.uri

# TLS SNI
tshark -r c.pcap -Y "tls.handshake.extensions_server_name" -T fields \
  -e frame.time -e ip.dst -e tls.handshake.extensions_server_name

# JA3 / JA3S
tshark -r c.pcap -Y "tls.handshake.type==1" -T fields -e tls.handshake.ja3_full
tshark -r c.pcap -Y "tls.handshake.type==2" -T fields -e tls.handshake.ja3s_full

# DNS queries, in order
tshark -r c.pcap -Y "dns.flags.response==0" -T fields \
  -e frame.time -e ip.src -e dns.qry.name

# SMB, and specifically the relay-relevant one
tshark -r c.pcap -Y "smb2.cmd==15" -T fields -e frame.time -e ip.src -e ip.dst

# Kerberos, and the TGT request that means a new session
tshark -r c.pcap -Y "kerberos.msgType==10" -T fields -e frame.time -e ip.src

# everything to or from one host
tshark -r c.pcap -Y "ip.addr==192.168.56.20" -T fields -e frame.time -e ip.dst -e _ws.col.Protocol

# only the failures (errors, resets, retransmits)
tshark -r c.pcap -Y "tcp.flags.reset==1 || tcp.analysis.retransmission || icmp.type==3"

# a full dissection of one packet
tshark -r c.pcap -Y "frame.number==1234" -V

What a capture proves, and what it does not

  PROVES
    the order of events on the wire
    what bytes were sent, in the clear
    which host initiated (the source address and port)
    timing, to microseconds
    TLS metadata (SNI, certificate, JA3) even without decryption

  DOES NOT PROVE
    what happened off the wire
    who was at the keyboard at that address
    intent (a request to a domain is not malicious by itself)
    anything about a capture point that was on the wrong side of NAT,
      a proxy, or a load balancer - the addresses will not match the
      server's logs and you will spend a day finding out why

  THE PRACTICAL CONSEQUENCE:
    a PCAP is the best single artefact for reconstructing a sequence
    and the worst single artefact for attributing intent. Use it for
    the sequence. Use disk, memory and logs for the attribution.

  THE HASH, ALWAYS:
    pcap files are large and they contain everything anybody on the
    wire said. Hash one and record it like any other evidence.

# hash a capture
sha256sum lab.pcap
md5sum    lab.pcap
tshark -r lab.pcap -T fields -e frame.comment 2>/dev/null | grep -i "^#"
# ^ pcapng can carry a COMMENT. Whoever made the capture may have
#   written why. Read it before you ask.

EOF
cat 04-reading.md
rm -f lab.pcap
```

Step 3 is the deliverable: an actual tshark capture of loopback traffic, analysed by the
script. It shows the workflow on real packets — conversations first, then DNS in order, then
SNI and JA3 — rather than describing it.

04-reading.md is the discipline note: the network doesn't lie about order, but it can't
attribute intent. Use PCAP for the sequence, disk and memory and logs for the attribution —
and read the pcapng comment before asking whoever made the capture why they made it.
