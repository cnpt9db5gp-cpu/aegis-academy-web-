SSRF, XXE and Deserialisation

Summary

These three share a single mechanism: the server fetches, parses, or resurrects something on
your behalf, and does not validate it properly before use. Each is a trust boundary
failure in a different direction — inward (the server reaching out), sideways (an external
entity defining behaviour), and backwards (data becoming code).

SSRF

The mechanism

  You supply a URL.
  The SERVER fetches it.
  The response comes back to you (or is used server-side).

  Now control the URL and you have:
    - a request proxy on the server's network position
    - access to everything the server can reach and you cannot

// the bug
$url = $_GET['url'];
echo file_get_contents($url);

Why filters fail

  FILTER: "must be http:// and must not contain 127.0.0.1"

  BYPASSES, all still working:
    http://127.0.0.1                  literal
    http://127.1                      alternate notation
    http://0x7f000001                 hex
    http://2130706433                 decimal
    http://0177.0.0.1                 octal
    http://[::1]                      IPv6 loopback
    http://localhost                   by name
    http://localtest.me               resolves to 127.0.0.1
    http://127.0.0.1.nip.io           DNS -> 127.0.0.1
    http://[::ffff:127.0.0.1]         IPv4-mapped IPv6
    http://metadata.google.internal    the cloud one you actually want
    redirect: http://allowed.com/ -> 302 -> http://169.254.169.254/

The correct fix is not a better string filter. It is: resolve the
hostname, check all resolved addresses against an allowlist, then
pin the connection to the address you validated so DNS rebinding
cannot change it between the check and the request. Also disable
redirect following, or re-validate every hop.

Why it is severe

  SSRF to cloud metadata -> IAM credentials for the whole account
  SSRF to an internal admin -> full control of the internal app
  SSRF to a network scanner  -> port-scan the internal network from inside
  SSRF with a gopher:// sink -> speak arbitrary protocols

  THE CLOUD CASE:
    http://169.254.169.254/latest/meta-data/iam/security-credentials/
    -> AWS credentials
    http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token
    -> GCP token
    http://169.254.169.254/metadata/instance?api-version=2021-02-01
    -> Azure metadata, reachable WITHOUT a header (IMDSv1)

XXE

  XML lets you define entities. If the parser resolves them, you get
  arbitrary file read, and sometimes SSRF and DoS.

  <!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
  <root>&xxe;</root>

  WHERE THE PARSER IS:
    XML parsers in Java, .NET, PHP, Python, C, and most frameworks
    DO resolve entities by default unless told not to.

  THE FIX, always:
    <!DOCTYPE ... [ disable external entities ]>
    - libxml: LIBXML_NOENT off, and DOCTYPE loading disabled
    - PHP:  libxml_disable_entity_loader(true); now deprecated but seen
    - Java: disallow-doctype-decl = true
    - Python: defusedxml, or lxml with resolve_entities=False
    - .NET: XmlReaderSettings with DtdProcessing.Prohibit

  A more modern fix: do not accept XML at all unless you must, and prefer
  JSON. XXE is overwhelmingly an XML-acceptance problem.

Deserialisation

  An object graph is restored from bytes. If the format encodes TYPE
  INFORMATION - as Java, Python pickle, PHP serialize, .NET BinaryFormatter
  and Ruby Marshal all do - then "restoring" can construct arbitrary objects.

  THE MECHANISM:
    the stream contains not just values but CLASS NAMES and FIELD NAMES.
    the deserialiser looks up each class and populates it, calling any
    __wakeup / __destruct / readObject that exists.

  THE IMPACT:
    a gadget chain - an existing, legitimate class whose methods, called
    in the order the deserialiser chooses, do something dangerous.
    command execution is the usual result.

  LANGUAGES AT RISK AND THEIR NAMES:
    Java      ObjectInputStream, readObject, gadget chains in commons-collections
    Python    pickle.loads, __reduce__
    PHP       unserialize(), __wakeup, __destruct, POP chain
    .NET      BinaryFormatter, SoapFormatter (both now disabled by default)
    Ruby      Marshal.load (not eval, but equivalent)
    Node      node-serialize, child_process

# Python pickle, the simplest possible demonstration
import pickle, base64
class RCE:
    def __reduce__(self): return (eval, ("print('deserialised into code execution')",))
print(base64.b64encode(pickle.dumps(RCE())).decode())
# running pickle.loads on that payload executes the string

// PHP, the most commonly exploited in the wild
class Gadget {
  public $cmd;
  public function __destruct() { if ($this->cmd) system($this->cmd); }
}
unserialize($userInput);   // -> system() on a controlled string

The fix

  1. DO NOT DESERIALISE UNTRUSTED DATA. Ever. This is the whole fix.
  2. If you must: use a data-only format (JSON), never a type-carrying one.
  3. Signed serialised data (HMAC) prevents *tampering*, not *execution*
     - but it does stop an attacker who cannot get the key, which is most
  4. Allowlist the classes that may be deserialised where the API allows it
  5. Run deserialisation in a sandboxed process with no network

A signed-but-wrong-format token is still code execution — this is the
mechanism behind several JWT and cookie attacks in the wild. Signature
proves who wrote it; it does not prove it is data.

Terminology

Term Meaning

Blind SSRF You cannot see the response; infer from timing/behaviour
OAST / out-of-band Your server receives the callback
Cloud metadata 169.254.169.254 credential service
DNS rebinding Name resolves to a validated IP then changes
XXE XML external entity injection
External entity A SYSTEM entity that loads a URI
Billion laughs XXE-based expansion DoS
Deserialisation Restoring an object graph from bytes
Type confusion in streams Serialised formats carry class names
Gadget chain Legitimate classes whose methods become harmful
__reduce__ / __wakeup Python / PHP deserialisation hooks
Allowlist of classes Restrict what may be deserialised

# --- 1. SSRF with a scope guard, because this class of bug is for
#        internal addresses and you must not point it anywhere else ---
cat > scope-guard.sh <<'EOF'
#!/usr/bin/env bash
# The SSRF probe refuses anything that is not loopback. SSRF testing
# against cloud metadata or a third party is not your engagement.
allow_loopback_only() {
  local host="$1"
  case "$host" in
    127.*|localhost|::1|0:0:0:0:0:0:0:1) return 0 ;;
    *) return 1 ;;
  esac
}
for h in "$@"; do
  if ! allow_loopback_only "$h"; then
    echo "REFUSED: $h is not loopback. SSRF testing here stays local." >&2
    exit 3
  fi
done
EOF
chmod +x scope-guard.sh

# --- 6. the correct fix, side by side ---
cat > fetch-safe.php <<'PHP'
<?php
// THE FIX. Resolve, validate EVERY address, pin the connection, refuse
// redirects. A blocklist is not a fix; this is.
$u = $_GET['url'] ?? '';
function ssrf_safe_fetch(string $url, array $allowed_hosts, array $allowed_ips) {
    $p = parse_url($url);
    if ($p === false || !in_array(strtolower($p['scheme'] ?? ''), ['http','https'], true))
        return "scheme not allowed";
    $host = strtolower($p['host'] ?? '');
    if (!in_array($host, $allowed_hosts, true)) return "host not allowed";
    if (($p['port'] ?? 80) !== 80 && ($p['port'] ?? 80) !== 443) return "port not allowed";
    $ips = gethostbynamel($host);
    if (!$ips) return "dns failure";
    foreach ($ips as $ip)                                  // validate ALL of them
        if (!in_array($ip, $allowed_ips, true)) return "resolved ip not allowed: $ip";
    $ch = curl_init();
    curl_setopt_array($ch, [
      CURLOPT_URL => $url,
      CURLOPT_FOLLOWLOCATION => false,          // NO redirect following
      CURLOPT_RESOLVE => ["$host:".($p['port']??80).":".$ips[0]],  // PIN the ip
      CURLOPT_TIMEOUT => 3,
      CURLOPT_RETURNTRANSFER => true,
    ]);
    $r = curl_exec($ch);
    curl_close($ch);
    return $r === false ? "fetch failed" : substr($r, 0, 500);
}
echo "<pre>" . htmlspecialchars(
  ssrf_safe_fetch($u, ['example.test'], ['93.184.216.34'])) . "</pre>";
PHP
{
  echo "=== what the fix does, step by step ==="
  sed -n '/^function ssrf_safe_fetch/,/^}/p' fetch-safe.php | sed 's/^/  /' | head -22
  echo
  echo "  1. scheme allowlist          - not 'does not contain javascript:'"
  echo "  2. host allowlist            - not 'does not contain 127.'"
  echo "  3. port allowlist            - blocks the service-scanning use case"
  echo "  4. resolve, check EVERY ip   - one good ip does not excuse a bad one"
  echo "  5. CURLOPT_RESOLVE pinning   - DNS cannot change under you (rebinding)"
  echo "  6. no redirects              - each hop would need re-validation"
} 2>&1 | tee 02-ssrf-fixed.txt

Step 5 is the deliverable: seven notations of 127.0.0.1, and a naive blocklist catching
exactly one. That table is the entire argument for resolve-then-pin over string filtering, and
fetch-safe.php is the fix written out with the reason for each line.

Step 9 is the cleanest deserialisation demonstration available — __reduce__ returns a
callable, and the unpickler calls it. Twelve lines, and the concept is complete.
