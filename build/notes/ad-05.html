Credential Dumping with Impacket and Mimikatz

Summary

Once you have a foothold, the highest-value action in a Windows engagement is getting the hashes.
NTDS.dit holds every account in the domain, and there are two ways to read it: DCSync (the
protocol-correct way, requiring three specific rights) and credential dumping (steal it from
memory or from the filesystem).

The lecture's framing: DCSync is the clean one. Credential dumping is the messy one, and
every variant of it is a specific defence that a defender can turn on.

Companion to ad-04 (roasting) and imp-01 (the tooling). This note is
the decision: which method, what it means for the client, and what you
do after.

The two methods

  DCSYNC                       CREDENTIAL DUMPING
  -----------                  ------------------
  the replication protocol      memory or filesystem theft

  requires:                    requires:
    Replicating Directory       an admin-level session (SYSTEM works)
      Changes (All)             OR SeDebugPrivilege + SeImpersonate
    Replicating Directory
      Changes In Filtered Set
    DS-Replication-Get-        (or SeBackupPrivilege to copy the file)
      Changes (All)

  leaves:                      leaves:
    4624 logon events           a distinctive access pattern (or none)
    4662 object access          a service creation (mimikatz)
    4663 GUID enumeration       possibly nothing, if it is a raw disk read
    5136 directory changes
    replication traffic         no domain controller involvement

  invisible if the three        hard to make invisible; that is the
    rights are absent           point of every defence below

DCSync

  WHAT IT IS:
    Replication is a normal DC-to-DC protocol. Any DC can serve a
    replication request to a peer. DCSync is simply using that
    protocol against yourself.

    Replicating Directory Changes (All)       -> get the secrets
    Replicating Directory Changes In Filtered Set -> enumerate the NC
    DS-Replication-Get-Changes (All)          -> the modern equivalent

    CRUCIALLY: none of these are "Domain Admin" membership rights.
    They are SEPARATE rights that can be (and usually are) delegated
    to a service account. And a forest with a single DC does not need
    replication at all - so a single-DC forest has no reason to grant
    it, and granting it is a pure finding.

  HOW TO CHECK WHETHER YOU CAN
    ask the DC, unauthenticated:
      "(&(objectClass=DomainDNS)(nCSCreationName=*)"
      "(nETInfoNamingContext=*))"
    the presence of the three attributes in the nTSGeneralInfo
    context indicates the rights are present on the object.

  WHAT IT RETURNS
    - every user's NT hash
    - every computer account's NT hash (this is the big one)
    - krbtgt's hash, if the request is not filtered (krbtgt can read
      itself, so an unfiltered request returns it -> golden tickets)
    - the domain SIDs, groups, and the whole directory

  WHY IT IS SO OFTEN A FINDING
    because it is delegated for legitimate reasons (backup software,
    some management tools) and never revoked when the reason goes away.

Credential dumping: the variants

  1. LSASS MEMORY (Windows: mimikatz sekurlsa::logonpasswords)
     the hashes of everyone logged on, and the cached ones.
     defended by: credential guard, protected process, running as a
     non-admin, PAWs, session isolation.

  2. SAM (windows\system32\config\SAM)
     the local machine accounts. Needs SeBackupPrivilege or SYSTEM.
     the NT hash of every local account, including the local admin.

  3. NTDS.DIT  (windows\ntds\ntds.dit)
     the whole domain. Needs SYSTEM + bootkey, or a volume shadow copy,
     or DCSync (which is cleaner and does not need SYSTEM).
     defended by: protected users, LAPS, tiering, the same things that
     stop DCSync (which is: not having the rights).

  4. DPAPI (dpapi::masterkeys)
     the keys that decrypt saved credentials, browser passwords,
     WiFi keys. Cracked with a wordlist - the master key file is the
     secret, and it is small enough to brute force if the user's
     password is weak.

  5. CREDENTIAL MANAGER (cmdkey /list)
     stored RDP and network credentials. Sometimes a plaintext
     password is right there.

  6. KERBEROS TICKETS (sekurlsa::tickets)
     all cached TGTs and service tickets. A stolen TGT needs no
     cracking (ad-02).

The DPAPI key, which is the underrated one

  WHAT IT IS:
    Every time Windows saves a password (browser, RDP, credential
    manager), it encrypts it with a key derived from the USER's
    password, stored in DPAPI. The master key is on disk.

  THE ATTACK:
    1. steal the user's masterkey file
    2. steal the encrypted blob (browser DB, credential manager export)
    3. derive the DPAPI key from a password guess - CHEAP, one hash per guess
    4. decrypt

  WHY IT IS GOOD FOR AN ASSESSMENT:
    it converts a memory-only compromise into a recoverable credential
    set, and it needs no admin rights on the host if you have the
    user's files.

  WHAT IT IS NOT:
    it does not work for a domain admin's credential if the user is a
    protected user, and it is not instant - the master key file has a
    cost parameter (default 4800, which is seconds on a GPU).

  DEFENCE:
    - strong passwords (that is the whole defence; DPAPI's cost is
      tied to the password)
    - the "roaming" case, where the master key follows the user
      across machines, is the dangerous one: the same blob decrypts
      on every machine in the domain. That is a well-known finding.

After the dump: the chain

  DUMP  ->  many accounts, all hashes
        ->  offline: crack the weak ones (cry-d4's methodology)
        ->  online: use them directly, pass-the-hash
        ->  find the privileged one
        ->  look for DCSync rights in the graph
        ->  if the domain admin's hash is in the dump: you are done,
            and so is the engagement's most valuable finding

  WHAT TO CRACK FIRST, in order of value per minute of GPU time:
    1. Domain Admins, Enterprise Admins          (the win condition)
    2. Service accounts with SPNs                 (roastable, ad-04)
    3. Accounts with delegation attributes        (the key to ad-02)
    4. Accounts with preauth disabled             (the key to ad-04)
    5. Everything else, sorted by name entropy
    6. krbtgt                                     (only if you want to
                                                    prove the impact)

  (Step 6 deserves care: if you have krbtgt's hash, you can forge
   tickets that survive a password reset. Demonstrating that in a
   production domain is a decision to make WITH the client, not
   unilaterally. In most engagements you note the implication and
   do not exercise it.)

Controls, and what each one actually stops

Control Stops Notes
Credential Guard / LSA protection LSASS dumping the single most effective control
Run as a non-admin most dumping requires no privilege to have
Protected Users group ticket theft, DPAPI roaming also forces NTLM down
LAPS local admin reuse unique per machine
Tiered administration + PAWs using an admin hash process, not a technical control

Restricted admin for RDP pass-the-hash over RDP

Reporting

  ## F-xx · Domain credential material readable by a standard user

  Risk
    An authenticated user in the "Helpdesk" group can obtain the NT hash
    of every account in the forest, including both domain controllers'
    machine accounts and the krbtgt account. From there, an attacker can
    authenticate as any account, including Domain Administrators, without
    a password, and (via krbtgt) can forge tickets that survive a
    password reset.

  Prerequisites
    Membership of Helpdesk only. No exploit, no privileged session, no
    elevated tooling. The read is performed with the replication protocol
    using three directory rights that are granted to Helpdesk for a
    backup application that was decommissioned in 2023.

  Evidence
    Three directory rights present on the Domain object:
      Replicating Directory Changes (All)
      Replicating Directory Changes In Filtered Set
      DS-Replication-Get-Changes (All)
    A replication request for the domain returns 214 account objects
    with their NT hashes. The krbtgt hash was obtained and is stored in
    the encrypted evidence archive; it was not used to forge tickets.
    (Full account data is not reproduced in this report.)

  Business impact
    Complete compromise of the forest from any Helpdesk account. This
    is a one-step path to domain administrator and is the highest-impact
    finding in the engagement.

  Remediation
    1. Remove all three rights from the Helpdesk group       [Domain Admins, Immediate]
    2. Identify what requires them; if the backup application is retired,
       decommission the group                          [IT Ops, Immediate]
    3. Enable "Audit Directory Service Access" and alert on the
       replication GUIDs                          [Security, 1 sprint]
    4. Credential Guard on all servers and workstations [Endpoint, 1 sprint]
    5. Add Protected Users to all privileged accounts   [Domain Admins, 1 sprint]
    6. Reset krbtgt twice, 24 hours apart               [Domain Admins, Immediate]

  Re-test
    Included at +30 days: confirm the rights are absent and that the
    alerting fires on a test replication request.

Terminology

Term Meaning
DCSync Using replication rights to read the whole directory
DS-Replication-Get-Changes The modern third right
NTDS.dit The directory database; every hash in the domain
SAM The local machine account database
LSASS The process holding credentials in memory
Credential Guard VBS-based LSASS protection; the strongest control
RunAsPPL Weaker, user-mode-only LSA protection
DPAPI Windows credential encryption, keyed off the user's password
Master key file The DPAPI key on disk; the crackable secret
Protected Users Group that blocks ticket theft and forces NTLM down
LAPS Unique local admin passwords
krbtgt The account that signs TGTs; its hash enables golden tickets
4662 The event log ID that shows DCSync
7045 Service installed; mimikatz's service-based extraction

cat > 02-dcsync-check.sh <<'EOF'
#!/usr/bin/env bash
# Do YOU have the DCSync rights? READ-ONLY, and often ANONYMOUS.
DC="${1:?usage: ./02-dcsync-check.sh 192.168.56.10}"
b=$(echo "$DC" | cut -d. -f1)
case "$b" in 192.168.56.*|10.10.10.*|127.*) ;;
  *) echo "REFUSED: $DC outside the lab range." >&2; exit 3 ;; esac
NC=$(ldapsearch -x -H "ldap://$DC" -b "" -s base defaultNamingContext 2>/dev/null \
     | grep -m1 "^defaultNamingContext:" | awk '{print $2}')
echo "[scope] $DC in range"
echo
echo "=== does the domain object expose the replication rights? ==="
echo "    (an ANONYMOUS query. if it answers, that is the finding.)"
ldapsearch -x -H "ldap://$DC" -b "${NC:-DC=lab,DC=internal}" \
  -s base "(objectClass=DomainDNS)" \
  nTSGeneralInfo nCSCreationName nETInfoNamingContext 2>/dev/null \
  | grep -E "nCS|nET|nTS" | sed 's/^/  /'
echo
echo "  nCSCreationName is present   -> the DC object is replicated normally"
echo "  nETInfoNamingContext present -> the rights are ON the object"
echo
echo "=== who is in the replication groups (as the DC sees them) ==="
ldapsearch -x -H "ldap://$DC" -b "${NC:-DC=lab,DC=internal}" \
  "(memberOf=CN=Domain Admins,${NC:-DC=lab,DC=internal})" sAMAccountName 2>/dev/null \
  | grep "^sAMAccountName:" | sed 's/^/  /'
echo
echo "=== the rights, checked against your OWN account (not anonymous) ==="
echo "  If you have a credential, ldapwhoami -vv shows the effective rights:"
echo "    ldapwhoami -x -D 'CN=me,OU=Users,$NC' -W -H ldap://$DC -vv | grep -i access"
echo
echo "  Look for: Replicating Directory Changes (All)"
echo "  If it is there, your session can do DCSync. Report it and STOP."
echo "  Do not exercise DCSync in production without written agreement:"
echo "  a full replication request is a domain-wide event and the client's"
echo "  monitoring will see it. A rights check is enough evidence."
EOF
chmod +x 02-dcsync-check.sh

# --- 3. the non-destructive version ---
cat > 03-safe-dcsync.sh <<'EOF'
#!/usr/bin/env bash
# The LEAST invasive way to prove DCSync rights. Do this, not a full
# secretsdump, unless the ROE explicitly permits domain-wide replication.
DOM="${1:?}"; CRED="${2:?dc-ip or dc/domain and user:pass}"
DC=$(echo "$DOM" | cut -d/ -f1); b=$(echo "$DC" | cut -d. -f1)
case "$b" in 192.168.56.*|10.10.10.*|127.*) ;;
  *) echo "REFUSED: $DOM outside the lab range." >&2; exit 3 ;; esac
echo "[scope] $DOM in range; [roe] DCSync is credential testing, confirm the ROE"
echo
echo "=== 1. are the rights present on the DC? (LDAP, not replication) ==="
ldapwhoami -x -D "$CRED" -H "ldap://$DC" -vv 2>/dev/null \
  | grep -iE "Replicating Directory|Get-Changes" | sed 's/^/  /'
echo "  (an empty result means the rights are not granted - which is correct)"
echo
echo "=== 2. what COULD be done with them (statement of impact, not execution) ==="
echo "  A full replication request would return:"
echo "    - every user NT hash"
echo "    - every computer account NT hash"
echo "    - the krbtgt hash (if unfiltered)"
echo "  Use the enumeration scripts instead (imp-01) and state the"
echo "  rights presence as the finding. Reproduce the dump only when"
echo "  the ROE says 'domain-wide credential extraction authorised'."
echo
echo "=== 3. the enumeration that proves the SAME thing, safely ==="
echo "    ldapsearch for sAMAccountName + userAccountControl (ad-03)"
echo "    bloodhound-python for the DCSync EDGE, without any hashes"
echo "  A graph edge 'X can DCSync' is the finding. The hashes are not"
echo "  needed to prove it and you should not collect them by default."
EOF
chmod +x 03-safe-dcsync.sh

# --- 4. what to do with the dump ---
cat > 04-triage.py <<'PY'
#!/usr/bin/env python3
"""Triage a hash dump by value, not by order.

The instinct is to feed a 200-account dump to hashcat and wait. That
wastes hours. The instinct that works: decide what you are looking for
FIRST, then run only the hashcats that answer that question.
"""
import sys, re

# the two questions worth GPU hours
GOAL = {
    "win":     ["krbtgt", "administrator", "admin"],
    "lateral": ["svc", "service", "backup", "sql", "web", "iis", "app", "monitor"],
    "roast":   ["svc", "service", "app", "sql", "iis", "web"],
}

def triage(path, goal="win", accounts_file=None):
    entries = []
    for line in open(path, errors="ignore"):
        line = line.strip()
        if not line: continue
        if ":" in line:
            user, h = line.split(":", 1)
        elif "\\" in line:
            user, h = line.rsplit("\\", 1)
        else:
            continue
        if re.fullmatch(r"[0-9a-fA-F]{32}", h):         entries.append((user, h, "NT"))
        elif re.fullmatch(r"[0-9a-fA-F]{40}", h):        entries.append((user, h, "LM/NT"))
        elif h.startswith("$"):                        entries.append((user, h, "cached/derived"))
    if accounts_file:
        groups = {}
        for g in open(accounts_file, errors="ignore"):
            parts = [p.strip() for p in g.strip().split(",")]
            if len(parts) >= 2: groups.setdefault(parts[0], []).append(parts[1])
        for user, h, kind in entries:
            gs = groups.get(user, [])
            for g in gs:
                if re.search(r"Domain Admins|Enterprise Admins|Schema Admins", g, re.I):
                    print(f"  *** WIN CONDITION: {user} is in {g}")
                    break
    print(f"\n  {len(entries)} accounts parsed\n")
    print("  ORDER TO CRACK (value per GPU-minute):")
    print("  1. Domain Admins / krbtgt      -> the win condition")
    print("  2. Service accounts with SPNs   -> roastable (ad-04)")
    print("  3. Delegation/preauth accounts -> the key to ad-02/ad-04")
    print("  4. Everything else, name-sorted by entropy")
    print()
    tiers = {k: [] for k in GOAL}
    for user, h, kind in entries:
        for k, pats in GOAL.items():
            if any(p in user.lower() for p in pats):
                tiers[k].append(user)
    for k, users in tiers.items():
        if users:
            print(f"  [{k}] {len(users)} candidates: {', '.join(users[:8])}"
                  f"{' ...' if len(users)>8 else ''}")
    return entries

if __name__ == "__main__":
    path = sys.argv[1] if len(sys.argv) > 1 else None
    if not path:
        print(__doc__); sys.exit(0)
    triage(path, accounts_file=sys.argv[2] if len(sys.argv) > 2 else None)
PY
