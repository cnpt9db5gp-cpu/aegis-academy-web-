Network Security and Firewalls

Summary

CS161 treats the network as hostile by assumption and asks what security is possible at each
layer. The lecture's conclusion is that almost nothing is possible below the transport layer
without cryptography, and firewalls are a policy control rather than a security control.

Companion to ccna-01..ccna-08 and mit858-12. Those teach the
protocols; this note is about what a filter can and cannot achieve.

What a firewall can do

A packet filter makes a decision per packet (or per flow) on a tuple:

  src IP, dst IP, src port, dst port, protocol, flags, interface, direction

Actions: allow, deny, reject, log, rate-limit, or reset the connection.

That is the entire expressive power of a stateless filter. It cannot
know who the user is, what the data contains, or whether the request is
authorised. It is an access control list over packets.

Stateless versus stateful

Stateless Stateful
Decisions on each packet independently connection state
Example ip6tables iptables -m conntrack, nftables
Knows "is this a reply?" no yes
Can permit replies no — you must write an inbound rule yes
Evaded by UDP any-any rules harder
Cost low high (memory per flow)

Stateful inspection was invented because UDP has no handshake. Without
state, permitting outbound UDP requires permitting inbound UDP, which means
an arbitrary UDP source can reach you. This is why "block all UDP" was the
default posture for twenty years.

Application-layer firewalls

An L7 filter understands HTTP, SMTP or DNS and can make decisions on method,
path, header, or protocol structure.

This is where the real security value is, because it is the only place you
can see the application's own semantics. It is also trivially defeated by
TLS, unless it terminates TLS itself — which then makes it a TLS-terminating
proxy and a high-value target itself.

Firewalls are not a security boundary

  what a firewall DOES prevent:
    - accidental exposure
    - wide scanning from outside
    - noisy services on the wrong interface
    - policy enforcement and auditability

  what a firewall does NOT prevent:
    - an attacker already inside the network
    - anything over an allowed port
    - attacks at the application layer on allowed ports
    - data exfiltration over an allowed channel
    - itself: it is a privileged, network-facing, complex device

The last point is the one people forget. A firewall is a high-value target
precisely because it decides what is reachable.

Where a filter actually belongs

  network edge        - coarse policy, direction separation
  host firewall       - protect a single host, default-deny inbound
  segment boundary    - limit lateral movement (this is the real value)
  egress filtering    - stop both malware and exfiltration
  ingress filtering   - BCP 38: drop spoofed sources at your edge

Egress filtering is the most underrated control. Most intrusions and most
exfiltration succeed because outbound traffic is unrestricted.

Filtering expressions, concretely

  default deny all, then allow what is needed  <- fail closed
  never allow any/any on the last rule         <- leaves the default open

  nftables:
    table inet filter {
      chain input { type filter hook input priority 0; policy drop;
        iif lo accept
        ct state established,related accept
        tcp dport 22 ip saddr 192.168.56.0/24 accept
      }
    }

Note the three properties: policy drop (fail closed), loopback first,
established connections before anything else.

Terminology

Term Meaning
Packet filter ACL over packets by tuple
Stateless No connection state tracked
Stateful Tracks flows; permits replies
Conntrack Linux connection tracking table
Default deny Drop everything not explicitly allowed
Egress filtering Restrict what leaves
Ingress filtering / BCP 38 Drop traffic with impossible source addresses
L7 firewall Decides on application protocol content
Fail closed Deny on error
NAT Address translation; not a security control
Spoofed source Source address the sender does not own

# --- the stateful problem, demonstrated ---
python3 - <<'PY' | tee 03-stateful.txt
# Why stateful inspection exists: UDP has no handshake, so a stateless
# filter permitting outbound UDP must also permit inbound UDP.
print("  stateless filter for DNS (UDP 53), as most orgs wrote it:")
print("    ALLOW udp --dport 53 OUT")
print("    ALLOW udp --dport 53 IN      <- necessary! nothing tracks replies")
print()
print("  Consequence: ANY host may send UDP/53 to you, for ANY source port.")
print("  That is a UDP amplification reflector - see mit858-12.")
print()
print("  stateful equivalent:")
print("    ct state NEW,ESTABLISHED udp dport 53 OUT")
print("    ct state ESTABLISHED          IN   <- only replies to tracked flows")
print()
print("  Measured cost of state: conntrack needs memory per flow.")
import os
try:
    print("  conntrack max:",
          open("/sys/module/nf_conntrack/parameters/max").read().strip())
    with open("/proc/sys/net/netfilter/nf_conntrack_count") as f:
        print("  conntrack in use:", f.read().strip())
except Exception:
    print("  (conntrack not loaded)")
PY
cat 03-stateful.txt

# --- egress filtering, the underrated control ---
cat > 04-egress.md <<'EOF'
# Egress filtering

Most organisations filter inbound carefully and outbound not at all. That
asymmetry is why:
- command-and-control works: the malware needs to reach the internet
- exfiltration works: the data can leave on any port, any protocol
- lateral movement works: internal traffic is unrestricted

## What to allow outbound
- DNS, only to your internal resolvers (never directly from endpoints)
- HTTPS, to the destinations your users need
- NTP, only to your internal servers
- mail, only through your relay
- nothing else

## What this buys
1. DNS tunnelling stops working (no direct resolver access)
2. Most C2 stops working (beacon destinations are not on the allowlist)
3. Exfiltration is contained to approved channels
4. Compromised hosts are visibly talking to somewhere they should not

## The measurement to start with
    sudo ss -tunap | grep -v "127.0.0.1\|::1" | awk '{print $5}' | sort | uniq -c | sort -rn

What is this machine actually talking to? Most answers are surprising, and
every surprise is either a dependency you forgot or something you want to know
about. This is the single highest-value network finding in an assessment.
EOF
cat 04-egress.md

echo
echo "=== what is this host actually talking to? ==="
sudo timeout 10 ss -tunap 2>/dev/null | grep -v "127.0.0.1\|::1" | head -12 | sed 's/^/  /'

Step 5 is the practical finding: ask what the host is actually talking to. Most
assessments start here and skip the harder work.
